# A안

# 🍱 위치 및 환경 기반 점심 메뉴 추천 서비스 기획서

## 1. 프로젝트 개요
* **서비스명**: (가칭) 오늘 점심 뭐 먹지? (Lunch Recommendation App)
* **서비스 컨셉**: 위치 정보 동의 시 반경 5km 이내의 식당을 검색하여, 현재 날씨(비/눈) 및 상황(해장 등)에 최적화된 점심 메뉴를 **리스트 형태**로 추천해 주는 웹 서비스

---

## 2. 주요 기능 및 요구사항 (Functional Requirements)

### 2.1. 사용자 위치 정보 처리 (Privacy & Geolocation)
* **위치 정보 동의 필수**:
  * 사용자 브라우저의 `navigator.geolocation` API를 통해 현재 위도(Latitude) 및 경도(Longitude)를 수집.
  * 위치 동의를 거부하거나 지원하지 않는 환경에서는 서비스 이용 불가 처리 (안내 UI 노출 및 재시도 버튼 제공).
* **개인정보 보호 (Zero Storage)**:
  * 사용자의 위치 좌표는 **서버 DB에 절대 저장하지 않으며**, 세션/메모리 상에서 실시간 API 호출 용도로만 일회성 활용.

### 2.2. 식당 정보 노출 (UI & Data List)
* **지도 UI 미노출**:
  * 화면에 지도(Map SDK)를 렌더링하지 않고, **카드 형태의 리스트 View**로만 정보 제공.
* **노출 정보 구성**:
  * **기본 조건**: 현재 위치 기준 **반경 5km 이내**
  * **가게 이름**: 식당명
  * **음식 종류**: 한식, 중식, 일식, 양식, 분식, 아시안 등 (카테고리 태그)
  * **주요 메뉴**: 대표 메뉴 정보 (API 데이터에 따라 표출)
  * **평점/리뷰/거리**: 사용자 평점 및 현재 위치로부터의 거리 (m/km 단위)
  * **외부 지도 딥링크 버튼**:
    * 클릭 시 네이버 지도 또는 카카오맵 웹/앱으로 직접 연결 (PC: 새 탭 웹 브라우저, Mobile: 지도 앱 실행)

### 2.3. 상황별 룰 기반 추천 시스템 (Recommendation Logic)
1. **날씨 연동 자동 추천**:
   * 기상청 공공데이터 API 또는 OpenWeatherMap API 활용
   * **비/눈 오는 날**: 국물 요리(짬뽕, 칼국수, 부대찌개, 전골, 수제비 등) 태그 우선 필터링
2. **사용자 환경 선택 추천 (필터/태그)**:
   * **해장 특공대**: 콩나물국밥, 순대국, 뼈해장국, 쌀국수, 라면 등 해장 메뉴 중심 필터링
   * **선택형 카테고리**: 한식, 일식, 중식, 양식, 빠른 식사(분식/패스트푸드) 등
3. **결정 장애 해결 (추가 기능)**:
   * **랜덤 픽(룰렛) 기능**: 검색된 5km 내 결과 중 1개를 랜덤으로 뽑아주는 기능

## 3. 데이터 수집 및 API 활용 전략 (Data Architecture)

| 구분 | 활용 API / 데이터원 | 역할 및 목적 | 비고 |
| :--- | :--- | :--- | :--- |
| **식당 검색** | Kakao Local API (`/v2/local/search/keyword`) | 5km 이내 위치 기반 식당 검색, 거리, 카테고리, 딥링크 URL 수집 | 일일 10만건 무료 |
| **날씨 정보** | 기상청 단기예보 API / OpenWeatherMap | 현재 위/경도 기준 날씨 정보(비, 눈, 기온) 파악 | 무료 공공 API |
| **공공데이터** | 소상공인시장진흥공단_상가(업소)정보 API | 표준 업종 분류 및 위치 데이터 보조 활용 (선택사항) | 데이터 갱신 주기 고려 필요 |

## 4. 예외 처리 및 UX 고려사항 (Edge Cases & UI/UX)

1. **위치 권한 거부 시**:
   * "위치 정보 동의가 필요한 서비스입니다. 브라우저 설정에서 위치 권한을 허용해 주세요." 경고 문구 및 안내 버튼 노출.
2. **5km 이내 검색 결과 없음 / 부족할 경우**:
   * 검색 반경을 자동으로 넓히거나(예: 10km), "주변에 해당 조건의 식당이 없습니다. 다른 카테고리를 선택해 보세요." 안내 메시지 표시.
3. **날씨 API 오류 시**:
   * 날씨 정보를 가져오지 못하더라도 서비스 전체가 멈추지 않고 기본 추천(카테고리별 추천)으로 fallback 처리.

# B안
# 점심 추천 서비스 기획 및 요구사항 정리

## 1. 서비스 개요

### 1.1 목적

사용자의 현재 위치와 날씨, 식사 상황을 바탕으로 주변에서 실제로 방문할
수 있는 식당을 추천하는 서비스다.

단순히 음식 메뉴를 랜덤으로 뽑는 것이 아니라, **무엇을 먹을지 고민하는
사용자에게 주변의 실제 식당과 메뉴를 연결해 주는 것**을 핵심 가치로
한다.

### 1.2 핵심 방향

-   지도 화면 없이 식당 정보를 리스트 형태로 제공한다.
-   사용자 위치정보 사용에 동의한 경우에만 주변 식당을 검색한다.
-   위치정보는 주변 식당 검색 및 거리 계산에만 사용하고 서버나 DB에
    저장하지 않는다.
-   날씨와 사용자가 선택한 상황을 추천 조건에 반영한다.
-   공공데이터와 외부 장소 검색 API를 조합해 식당 정보를 확보한다.
-   길찾기는 별도의 지도 API를 구현하지 않고 외부 지도 서비스로
    연결한다.

------------------------------------------------------------------------

## 2. 주요 기능 및 요구사항

## 2.1 사용자 위치 기반 주변 식당 검색

### 기능 설명

브라우저의 위치정보 기능을 이용해 사용자의 현재 위치를 확인하고, 해당
좌표를 기준으로 반경 5km 이내 식당을 검색한다.

### 요구사항

-   위치정보 사용 전 사용자에게 명확한 동의를 요청한다.
-   사용자가 위치정보 제공을 거부하면 주변 식당 검색 기능은 제공하지
    않는다.
-   위치정보 동의 후 브라우저에서 위도·경도를 가져온다.
-   위치 좌표는 주변 식당 검색과 거리 계산에만 사용한다.
-   위도·경도 및 사용자의 정확한 위치는 서버 DB에 저장하지 않는다.
-   페이지 새로고침이나 재방문 시 위치정보가 필요하면 브라우저 권한
    상태에 따라 다시 확인한다.
-   위치정보를 가져오지 못하거나 권한이 거부된 경우에는 그 이유를
    안내한다.

### 검색 조건

-   기준 위치: 사용자의 현재 위치
-   검색 반경: 기본 5km
-   검색 대상: 음식점
-   거리 계산: 식당 좌표와 사용자 좌표 사이의 직선거리
-   정렬: 추천순, 가까운 순 등

> **정책 결정:** 현재 기획에서는 위치정보를 허용하지 않으면 주변 식당
> 검색을 제공하지 않는다. 추후 서비스 방향이 바뀌면 사용자가 직접 지역을
> 입력하는 대체 기능을 검토할 수 있다.

### 개인정보 및 보안 고려사항

-   브라우저 Geolocation API를 사용한다.
-   위치 좌표를 URL, 로그, 분석 도구 등에 불필요하게 남기지 않는다.
-   위치 좌표를 DB에 저장하지 않는다.
-   외부 식당 검색 API에 좌표를 전달하는 경우 해당 제공자의 처리방침과
    이용 조건을 확인한다.
-   위치정보 이용 목적과 저장하지 않는다는 점을 사용자에게 알기 쉽게
    고지한다.

## 2.2 주변 식당 리스트

### 기능 설명

현재 위치 기준 5km 이내 식당을 지도 대신 리스트 형태로 보여준다.

### 기본 노출 정보

  항목        설명                              비고
  ----------- --------------------------------- ----------------------------
  식당명      가게 이름                         필수
  거리        현재 위치에서 식당까지의 거리     예: 1.2km
  주소        식당 주소 또는 도로명 주소        길찾기 연결에 활용
  음식 종류   한식, 중식, 일식, 양식, 분식 등   카테고리
  대표 메뉴   식당에서 제공하는 메뉴            데이터 확보 가능 여부 확인
  평점        별점 또는 평점                    제공처가 허용하는 경우
  리뷰 수     사용자 리뷰 개수                  제공처가 허용하는 경우
  영업 상태   영업 중, 영업 종료 등             데이터 최신성 확인 필요
  길찾기      외부 지도 서비스 연결             지도 API 불필요

### 음식 종류 분류 예시

-   한식
-   중식
-   일식
-   양식
-   분식
-   아시안
-   패스트푸드
-   패밀리레스토랑
-   카페·디저트
-   기타

### 리스트 정렬 및 필터

초기 버전에서 고려할 기능:

-   추천순
-   가까운 순
-   음식 종류별 필터
-   평점순(평점 데이터가 확보된 경우)
-   영업 중인 식당만 보기(영업 상태 데이터가 확보된 경우)

### 데이터 관련 주의사항

식당명·주소·좌표·카테고리와 평점·리뷰·메뉴는 서로 다른 데이터 항목이다.
하나의 API가 모든 정보를 제공한다고 가정하지 않는다.

특히 외부 장소 검색 API가 평점, 리뷰 수, 상세 메뉴를 제공하지 않을 수
있다. 각 데이터 제공처의 공식 API 문서와 이용약관을 확인하고, 제공되지
않는 항목은 표시하지 않거나 별도 데이터 확보 방안을 검토한다.

## 2.3 날씨 기반 추천

### 기능 설명

현재 위치 주변의 날씨 또는 단기 예보를 확인해 날씨에 어울리는 음식과
식당을 추천한다.

### 추천 상황

  날씨 조건    추천 메뉴 예시
  ------------ --------------------------
  비 오는 날   칼국수, 수제비, 짬뽕, 전
  눈 오는 날   국밥, 전골, 찌개, 우동
  추운 날      순대국, 감자탕, 샤브샤브
  더운 날      냉면, 밀면, 초밥
  무더운 날    콩국수, 냉모밀, 샐러드

### 요구사항

-   기상청 등 날씨 데이터 API 활용을 검토한다.
-   강수 형태, 강수 확률, 기온 등을 추천 조건으로 사용한다.
-   날씨 정보는 현재 위치를 기준으로 조회한다.
-   날씨 데이터가 없거나 API 오류가 발생하면 날씨 추천을 제외하고 일반
    추천을 제공한다.
-   날씨에 따른 추천은 실제 식당의 메뉴 정보와 연결할 수 있는 경우에만
    해당 식당을 노출한다.

### 초기 추천 방식

초기에는 AI보다 규칙 기반 추천을 사용한다.

예시:

1.  현재 날씨 또는 예보 확인
2.  날씨에 해당하는 추천 음식 목록 선택
3.  주변 식당 중 관련 카테고리·메뉴가 일치하는 식당 검색
4.  거리와 데이터 신뢰도 등을 고려해 정렬

## 2.4 사용자 선택 상황별 추천

### 기능 설명

사용자가 현재 원하는 식사 상황을 직접 선택하면, 해당 조건에 맞는 주변
식당을 추천한다.

### 초기 상황 분류

  상황          메뉴 예시
  ------------- ----------------------------------
  해장          콩나물국밥, 뼈해장국, 선지해장국
  든든한 식사   백반, 제육볶음, 돈까스
  가벼운 식사   샐러드, 포케, 샌드위치
  얼큰한 음식   짬뽕, 김치찌개, 부대찌개
  따뜻한 음식   국밥, 칼국수, 우동
  혼밥          국밥, 덮밥, 김밥, 돈까스
  매콤한 음식   떡볶이, 닭갈비, 제육볶음
  고기          삼겹살, 불고기, 갈비

### 확장 가능한 조건

-   음식 종류
-   예상 가격대
-   식사 시간
-   혼밥 또는 여럿이 식사
-   매운 음식 선호
-   가벼운 식사 또는 든든한 식사

초기에는 상황 선택 항목을 너무 많이 만들지 않고, 자주 사용할 만한
조건부터 제공한다.

## 2.5 외부 지도 서비스 연결

### 기능 설명

서비스 내부에는 지도를 표시하지 않는다. 사용자가 식당의 길찾기 또는
주소를 선택하면 외부 지도 서비스로 이동한다.

### 지원 후보

-   네이버 지도
-   카카오맵
-   구글 지도

### 연결 방식

-   식당명과 주소 또는 좌표를 이용해 지도 검색·장소 URL을 구성한다.
-   PC에서는 기본 브라우저에서 지도 웹페이지를 연다.
-   모바일에서는 운영체제와 앱 설치 상태에 따라 지도 앱 또는 모바일
    웹으로 연결되도록 한다.
-   앱이 설치되지 않았거나 앱 연결이 불가능하면 웹페이지를 이용할 수
    있도록 한다.
-   실제 앱 실행 여부와 fallback 동작은 기기·브라우저별로 테스트한다.

### 유의사항

외부 지도 서비스의 URL 스킴 및 딥링크 정책은 변경될 수 있으므로 공식
문서를 확인한다. 지도 화면을 직접 구현하지 않으므로 지도 SDK나 지도
렌더링 비용은 발생하지 않는 구조를 목표로 한다.

## 3. 데이터 확보 전략

식당 데이터는 공공데이터와 민간 장소 검색 API를 조합하는 방향을 우선
검토한다.

### 3.1 공공데이터

  데이터                       활용 목적
  ---------------------------- ---------------------------------------------
  전국 일반음식점 표준데이터   식당명, 주소, 업종 등 기본 정보
  지방행정 인허가 데이터       영업 인허가 및 영업 상태 확인
  기상청 단기예보              강수 형태, 강수 확률, 기온 등

공공데이터포털: https://www.data.go.kr/

### 공공데이터 활용 시 확인할 점

-   좌표가 제공되는지 확인한다.
-   좌표가 없다면 주소를 좌표로 변환할 방법이 필요하다.
-   데이터 갱신 주기를 확인한다.
-   폐업·휴업 정보가 최신인지 확인한다.
-   메뉴, 평점, 리뷰는 공공데이터만으로 충분히 확보하기 어려울 수 있다.
-   데이터별 이용 조건과 출처 표시 의무를 확인한다.

### 3.2 민간 장소 검색 API

검토 대상:

-   카카오 로컬 API
-   네이버 검색·지역 관련 API 등 현재 제공 범위가 적합한 서비스
-   그 외 이용 조건과 데이터 범위가 적합한 장소 검색 제공자

비교할 항목:

-   주변 장소 검색 지원 여부
-   검색 반경 및 결과 건수 제한
-   식당 카테고리 분류 품질
-   위도·경도 및 주소 제공 여부
-   평점·리뷰·메뉴 제공 여부
-   API 호출 한도 및 비용
-   데이터 저장·캐싱·재노출 허용 범위
-   상업적 서비스 이용 가능 여부

> 특정 API가 모든 식당 정보와 리뷰를 제공한다고 전제하지 않는다. 공식
> 문서와 약관을 확인한 후 실제 구현 범위를 확정한다.

### 3.3 데이터 역할 분리

  평점·리뷰 수       제공처가 허용하는 API 데이터

  날씨               기상청 API

## 4. 추천 알고리즘

### 4.1 초기 버전: 규칙 기반 추천

복잡한 AI 모델을 도입하기 전에 명확한 조건으로 추천한다.

추천 처리 흐름:

1.  사용자가 위치정보 제공에 동의한다.
2.  브라우저에서 현재 좌표를 가져온다.
3.  주변 식당 데이터를 검색한다.
4.  반경 5km를 벗어난 식당을 제외한다.
5.  사용자가 선택한 상황 또는 현재 날씨에 맞는 메뉴·카테고리를 찾는다.
6.  거리, 평점 등 확보 가능한 정보를 기준으로 정렬한다.
7.  식당 리스트를 노출한다.

### 4.2 추천 점수 예시

초기 실험용 점수이며 실제 데이터 품질을 확인한 뒤 조정한다.

  평가 요소                     예시 배점
  --------------------------- -----------
  선택한 상황·메뉴와의 일치          40점
  거리                               25점
  평점                               20점
  리뷰 수                            15점
  합계                              100점

평점이나 리뷰가 없는 식당에 임의의 점수를 부여하지 않는다. 정보가 없는
경우 해당 항목을 제외하고 나머지 점수를 정규화하거나, 정보가 부족하다는
표시를 제공한다.

### 4.3 향후 확장

-   사용자가 선택한 음식 종류 기록
-   즐겨찾기 식당
-   추천 결과에서 제외한 식당
-   이전에 추천한 식당의 반복 노출 방지
-   사용자 선호에 따른 추천 가중치 조정

사용자 행동 데이터는 필요한 범위에서만 수집하고, 수집 목적과 보관 기간을
명확히 한다.

### 지도 관련 기술

-   지도 SDK 및 지도 렌더링 기능은 사용하지 않는다.
-   지도는 외부 서비스로 이동하는 링크만 제공한다.
-   지도 API 키나 지도 SDK를 필수 의존성으로 두지 않는다.

### 서버 측 API 사용 원칙

-   외부 API 키는 서버 환경변수로 관리한다.
-   브라우저에 비밀 API 키를 노출하지 않는다.
-   외부 API 응답을 내부 `Restaurant` 타입으로 변환한다.
-   제공처별 데이터 구조가 화면과 추천 로직에 직접 퍼지지 않도록
    Provider 계층을 둔다.

6.  **API 비용과 운영**
    -   무료 호출 한도는 충분한가?

## 11. 개발 착수 전 우선순위

권장 순서:

1.  카카오 로컬 API 등 후보 API의 최신 제공 필드와 이용약관 확인
2.  테스트 좌표를 이용해 주변 식당 검색
3.  검색 결과의 이름, 주소, 좌표, 카테고리 확인
4.  5km 거리 필터링 구현
5.  메뉴·평점·리뷰 데이터 확보 가능성 별도 검증
6.  공공데이터와 민간 API의 중복 및 보완 관계 확인
7.  검증 결과를 바탕으로 MVP 범위 확정

**가장 중요한 원칙:** 식당명·주소·좌표를 안정적으로 확보하는 것을 1차
목표로 삼고, 메뉴·평점·리뷰는 실제로 이용 가능한 데이터 소스를 확인한 뒤
단계적으로 추가한다. 지도 화면이나 유료 지도 SDK는 도입하지 않는다.

# 공공데이터 활용 방안
# 전국 음식점 공공데이터 활용 검토

## 1. 목적

점심 추천 서비스에서 사용할 전국 음식점 데이터를 공공데이터로 확보할 수
있는지 검토한다.

서비스의 기본 방향: - 사용자 위치정보 동의 시 현재 위치 기준 주변 식당
검색 - 기본 검색 반경 5km - 지도 대신 리스트 형태로 식당 제공 - 날씨와
식사 상황(해장, 든든한 식사 등)을 추천 조건에 반영 - 사용자 위치 좌표는
검색과 거리 계산에만 사용하고 기본 설계에서는 DB에 저장하지 않음

## 2. 활용 후보 공공데이터

### 2.1 전국일반음식점표준데이터

전국 지자체에서 관리하는 일반음식점 등록 및 인허가 현황을 확인할 수 있는
공공데이터다.

**활용 가능한 정보 예시** - 식당명 - 영업 상태 - 인허가 정보 - 소재지
주소 - 업소 기본 정보

**활용 목적** - 전국 음식점 기본 목록 확보 - 영업 인허가 정보 확인 -
식당 주소 및 기본 정보 보완

**확인할 사항** - 실제 제공 컬럼과 데이터 형식 - 좌표 제공 여부 및 좌표
정확도 - 데이터 갱신 주기 - 폐업·휴업 정보의 최신성 - 상업적 이용 및
저장·재배포 조건

공공데이터 상세 페이지:\
https://www.data.go.kr/data/15096283/standard.do -> csv파일임

> 데이터 건수와 갱신 주기는 조회 시점에 따라 달라질 수 있으므로 실제
> 다운로드 페이지에서 다시 확인한다.

### 2.2 소상공인시장진흥공단 상가(상권)정보 API

전국 상가업소 정보를 API로 조회할 수 있는 데이터다.

**활용 가능한 정보 예시** - 상호명 - 주소 - 업종 분류 - 경도·위도 -
행정구역 정보 - 반경 내 업소 검색에 활용할 수 있는 위치 정보

**활용 목적** - 사용자 위치 주변 음식점 검색 - 식당의 좌표 및 업종 분류
확보 - 지역 또는 반경 기준 음식점 조회

공공데이터 API 상세 페이지:\
https://www.data.go.kr/data/15012005/openapi.do -> 이 안에 여러 end-point 존재함.

**확인할 사항** - 실제 API 응답 필드 - 음식점 업종 분류의 세분화 수준 -
반경 검색의 기준 및 제한 - 호출 한도와 갱신 주기 - 상업적 이용, 저장,
캐싱 및 재노출 조건

**핵심:** 공공데이터는 식당의 기본 정보와 위치를 확보하는 데 활용하고,
메뉴·평점·리뷰는 별도 데이터 소스를 검토한다. 실제 제공 여부를 확인하지
않은 정보는 화면에 임의로 표시하지 않는다.

## 4. 권장 데이터 구성

두 공공데이터를 상호 보완적으로 검토한다.

1.  전국일반음식점표준데이터에서 식당 기본 정보와 인허가 정보를
    확보한다.
2.  상가(상권)정보 API에서 상호명, 업종, 위치 정보를 보완한다.
3.  식당명·주소·좌표 등을 기준으로 중복 여부를 검토한다.
4.  서비스 내부의 표준 음식점 데이터 모델로 변환한다.
5.  사용자 위치를 기준으로 5km 이내 식당을 검색한다.
6.  음식 종류, 날씨, 상황별 조건에 따라 추천 결과를 구성한다.

### 데이터 처리 흐름

``` text
전국일반음식점표준데이터
  식당명 · 주소 · 인허가 정보
              \
               \\
                > 데이터 정합성 검토 및 중복 제거
               //               |
              //                v
상가(상권)정보 API       서비스 내부 음식점 데이터
  상호명 · 업종 · 좌표           |
                                v
                       사용자 위치 기준 5km 검색
                                |
                                v
                    날씨 · 상황 · 음식 종류별 추천
                                |
                                v
                         식당 리스트 노출
```

### 데이터 저장 방식 검토

전국 데이터를 내부 DB에 적재하고 주기적으로 갱신하는 방식을 검토할 수
있다. 다만 실제 도입 전 다음 사항을 확인해야 한다.

-   원본 데이터의 저장 및 가공 허용 여부
-   상업적 서비스 이용 가능 여부
-   캐싱 및 재배포 조건
-   출처 표시 의무
-   갱신 주기와 삭제·정정 처리 방식

사용자의 현재 위치 좌표는 앞서 정한 개인정보 정책에 따라 검색과 거리
계산에만 사용하고 기본적으로 DB에 저장하지 않는다. 전국 음식점 데이터의
저장과 사용자 위치정보 저장은 서로 다른 문제이므로 구분해서 설계한다.

-   [ ] 5km 이내 거리 계산 및 필터링

## 7. 최종 정리

점심 추천 서비스의 음식점 검색 기반은 공공데이터로 구축하는 방향을
검토할 수 있다.

-   전국일반음식점표준데이터: 전국 음식점의 기본 정보 및 인허가 정보
    확보
-   소상공인시장진흥공단 상가(상권)정보 API: 상호명, 업종, 위치 정보
    보완
-   별도 데이터 소스: 메뉴, 평점, 리뷰 등 보완

다만 공공데이터가 있다는 사실만으로 전국 모든 식당의 좌표와 최신 영업
상태가 정확히 확보된다고 볼 수는 없다. 실제 데이터 샘플과 이용 조건을
확인한 뒤 구현 범위를 확정해야 한다.

**가장 먼저 할 일은 두 데이터의 실제 파일/API 응답을 비교하고, 좌표
정확도·중복률·업종 분류 품질을 검증하는 것이다.** 화면 개발이나 추천
알고리즘보다 이 데이터 검증을 먼저 진행한다.
