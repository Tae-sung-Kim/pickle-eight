# 궁합 테스트 기획서

기준 문서: `docs/research/compatibility.md`(10장 추천 범위, 12장 열린 질문, 9장 법적 정책). 기존 운세와의 관계는 `docs/research/fortune.md`, `src/constants/menu.constant.ts`, 운세 연령·동의 코드(`src/features/fortune/`)와 약관·방침(`src/app/terms/page.tsx`, `src/app/privacy/page.tsx`)을 확인했다.
상태: 기획 초안. 아래 "열린 질문" 답변 전까지 문구와 메뉴 위치는 확정하지 않는다.

## 목표

두 사람의 띠 또는 별자리를 골라 두 사람 사이의 관계를 재미로 보여 준다. 결과는 오락용 콘텐츠이며 연애·결혼·이별을 판단하는 근거가 아니라는 점을 화면에 함께 알린다.

## 범위

확정 전제(사용자가 리서치 권장안을 승인, 2026-11-24. 추가 결정 포함)

- 1차 범위는 띠 궁합과 별자리 궁합만 한다.
- 입력은 최소로 받는 것을 원칙으로 한다. 띠는 출생 연도, 별자리는 출생 월·일이다. 단 만 14세 확인 방식 때문에 입력 항목이 늘어날 수 있다(열린 질문 13번).
- 입력값은 저장하지 않는다. 기존 운세와 같은 방식이다.
- 가족·연애 관계를 단정하는 표현은 쓰지 않는다.
- 결과는 점수 대신 등급과 설명으로 쓴다. 이 방식은 권장안이며 열린 질문 5번에서 최종 확정한다.
- 연령 확인은 기존 운세와 똑같이 처리한다(사용자 결정 2026-11-24). 새 연령 게이트는 설계하지 않는다.
- AdFit 광고는 위험을 수용한다(사용자 결정 2026-11-24). 아래 법적 항목 참고.

포함

- 띠 궁합 페이지: 두 사람의 출생 연도를 넣으면 두 띠의 관계, 등급, 설명을 보여 준다.
- 별자리 궁합 페이지: 두 사람의 월·일을 넣으면 두 별자리의 원소 관계, 등급, 설명을 보여 준다.
- 궁합 허브 페이지: 두 페이지로 가는 진입점.
- 메뉴와 사이트맵 등록.
- 결과 화면과 입력 화면의 고지 문구, 상대방 정보 동의 안내.

제외

- 이름 궁합: 보류. 리서치 6장 기준이다. 계산 방식이 작명소마다 달라 결과가 일치하지 않고, 학술 근거가 약하며, 아동 이름 입력·차별·작명 상품 연결 위험이 있다. 6.2의 조건을 승인하면 2차 이후 다시 본다.
- 혈액형 궁합: 제외. 과학적 근거가 없고, 혈액형으로 성격을 단정하는 차별 우려가 있다.
- MBTI 궁합: 제외. 검사 도구의 상표·저작권 문제가 있고 근거가 약하다.
- 사주 궁합: 2차. 기존 사주 계산 재사용 여부와 시간 미상 처리는 2차 기획에서 정한다.
- 결과 공유: 이 기획에서 다루지 않는다. `docs/TODO.md` 우선순위 2번이며 별도 기획한다.
- 로또 연결, 행운 요소(색·숫자): 제외 권장. 열린 질문 11번.
- 관계 유형(연인·친구·동료·가족) 선택: 1차 제외 권장. 열린 질문 10번.
- 양태(활동·고정·변통) 규칙: 출처를 확보하지 못했으므로 제외한다.

## 유저 스토리

- US-1: 친구와 띠 궁합이 궁금한 사용자로서, 두 사람의 정보만 넣고 바로 관계를 보고 싶다. 왜냐하면 회원가입 없이 가볍게 재미로 보고 싶기 때문이다.
- US-2: 별자리가 궁금한 사용자로서, 두 사람의 정보를 넣고 원소 관계를 보고 싶다. 왜냐하면 개인 운세와 다른 "두 사람" 관점이 궁금하기 때문이다.
- US-3: "띠 궁합"을 검색한 사용자로서, 검색 결과에서 바로 해당 궁합 설명에 닿고 싶다. 왜냐하면 두 띠의 관계 뜻이 궁금하기 때문이다.
- US-4: 띠별 운세나 별자리 운세를 보던 사용자로서, 같은 흐름에서 궁합 페이지로 넘어가고 싶다. 왜냐하면 내 띠와 별자리를 확인한 뒤 상대와의 관계를 보고 싶기 때문이다.

## 완료 조건 (AC)

열린 질문 답변 전에는 AC-8, AC-9의 문구 항목과 AC-1, AC-2, AC-12의 입력 항목을 확정하지 않는다. 나머지 AC는 답변과 무관하게 적용한다.

- AC-1 [E2E]: 띠 궁합 페이지에서 두 사람의 출생 정보(열린 질문 13번 결정에 따라 연도 또는 생년월일)를 넣으면 한 화면에 두 띠 이름, 관계 이름, 등급, 설명 문단, 오락 고지가 나온다. 같은 입력을 다시 하면 같은 결과가 나온다. 새로고침하면 입력값이 비어 있다.
- AC-2 [E2E]: 별자리 궁합 페이지에서 두 사람의 출생 정보를 넣으면 한 화면에 두 별자리 이름, 원소 관계, 등급, 설명 문단, 오락 고지가 나온다. 새로고침하면 입력값이 비어 있다. 경계일 안내는 열린 질문 4번 결정에 따라 추가한다.
- AC-3 [E2E]: 메뉴에서 궁합 항목을 누르면 허브 페이지가 열리고, 허브에서 띠 궁합과 별자리 궁합 페이지로 각각 이동할 수 있다.
- AC-4 [단위]: 존재하지 않는 날짜(예: 2월 30일), 허용 범위 밖 연도, 두 사람 중 한쪽만 입력한 경우에는 결과를 만들지 않고 오류 안내를 돌려준다. 안내 문구는 AC-9 기준이다.
- AC-5 [단위]: 12띠의 모든 쌍 78개(같은 띠 12개 포함, 서로 다른 띠 66개)가 승인된 우선순위 규칙에 따라 하나의 관계 결과를 가진다. 육합 6쌍, 삼합 4조, 방합 4조, 충 6쌍, 원진 6쌍은 승인된 출처 목록과 일치한다.
- AC-6 [단위]: 12별자리의 원소 분류가 승인된 표와 일치한다. 서로 다른 별자리 쌍 66개와 같은 별자리 12개, 합 78개 모두 원소 관계 하나로 정해진다.
- AC-7 [단위]: 궁합 계산에 쓰는 각 사람의 띠와 별자리가 기존 띠별 운세, 별자리 운세의 판정과 같다. 입춘 날짜와 절기 경계 날짜를 포함한다.
- AC-8 [단위]: 결과와 안내 문구 전체가 금지 표현 목록(기존 목록과 궁합 추가 목록)에 없다. 결혼, 임신, 이별, 이혼, 바람 등 관계를 단정하는 단어가 없다.
- AC-9 [정적]: 오락 고지, 입력 미저장 안내, 상대방 정보 동의 안내, 과학적 근거 없음 고지, 연령 안내가 승인된 원문과 같다. 승인되지 않은 문장은 화면에 올리지 않는다.
- AC-10 [정적]: 허브와 두 궁합 페이지 모두 승인된 키워드로 제목, 설명, 키워드, 정식 주소(canonical), OG 정보를 가진다. 한 페이지에 h1이 하나다. 메뉴 목록과 사이트맵에 등록되어 있다. 결과 설명 문장이 서버에서 그려져 검색 엔진이 읽는 HTML에 들어 있다.
- AC-11 [정적]: 입력한 출생 정보가 브라우저 저장소나 외부 서버에 저장되거나 전송되는 코드가 없다. 약관·방침에 궁합 조항이 승인 문구대로 들어 있다.
- AC-12 [E2E]: 띠 궁합에서 이용 전 확인 항목을 모두 체크하기 전에는 입력 칸과 결과가 보이지 않는다. 확인을 거부하면 이용 불가 안내가 보인다. 확인 후 만 14세 미만 생년월일을 넣으면 연령 안내 화면만 보이고 궁합 결과는 나오지 않는다. 판정 기준은 열린 질문 13번 A 선택 시 운세와 같다.

## 예외·빈 상태

- 연도 범위 밖이거나 존재하지 않는 날짜: 결과를 만들지 않고 오류 안내를 보여 준다(AC-4).
- 두 사람 중 한쪽만 입력: 결과를 보여 주지 않고 나머지 입력을 요청한다. 결과 버튼을 막을지 안내 문구를 쓸지는 설계 단계에서 정한다.
- 같은 띠 또는 같은 별자리 조합: 결과 형식은 같다. 문구는 F-6의 전용 문구를 쓴다(열린 질문 9번).
- 입춘 전후 출생(띠), 절기 경계일 출생(별자리): 기본 동작이 정해지지 않았다. 열린 질문 3번과 4번에서 정한다.
- 만 14세 미만 생년월일: 운세와 같이 연령 안내 화면만 보여 주고 결과를 보여 주지 않는다(AC-12). 상대방 정보에도 같은 판정을 적용한다.
- 연도만 입력된 경우 만 나이를 정확히 계산할 수 없다. 열린 질문 13번에서 처리 방식을 정한다.
- 새로고침하거나 다른 페이지를 다녀오면 입력값은 초기화된다. 입력값을 남기지 않는다.
- 스크립트를 끄고 접속한 경우: 검색에 노출되는 설명 문장은 그대로 보여야 한다. 입력 기능을 쓸 수 없다는 안내 문구가 필요한지 확인한다.

## 검색 노출

- 키워드 (페이지별, 검색량은 모두 확인 필요)
  - 허브 페이지: 궁합 테스트, 무료 궁합
  - 띠 궁합 페이지: 띠 궁합, 띠별 궁합
  - 별자리 궁합 페이지: 별자리 궁합
- 제외 키워드: 이름 궁합, 혈액형 궁합, MBTI 궁합. 사주 궁합은 2차에서 추가한다.
- "연애 궁합"은 연애 단정 표현 위험 때문에 제목과 메타 정보에 쓰지 않는다(열린 질문 17번).
- 페이지가 답해야 할 질문
  - 허브 페이지: 궁합은 무엇을 기준으로 보는가. 띠와 별자리 중 무엇으로 봐야 하는가. 이 결과를 어디까지 믿어도 되는가.
  - 띠 궁합 페이지: 우리 띠는 어떤 관계인가. 육합, 충, 원진은 각각 무슨 뜻인가. 띠 궁합에 과학적 근거가 있는가.
  - 별자리 궁합 페이지: 별자리 궁합은 원소로 어떻게 보는가. 같은 원소끼리는 어떤 관계인가.
- 메타와 구조: 기존 SEO 규칙(`docs/conventions/seo.md`)을 그대로 따른다. 메뉴 라벨과 검색 키워드가 어긋나지 않게 한다. 빵부스러기 구조화 데이터를 넣는다. FAQ 구조화 데이터는 승인된 질문과 답이 페이지에 실제로 있을 때만 넣는다.
- 차별 포인트(가설): 점수 대신 관계 유형 설명을 중심에 둔다. 시장 검증을 하지 않았으므로 사이트 문구에 우위를 주장하지 않는다.
- 경쟁 사이트의 궁합 문장과 궁합표는 복사하지 않는다(리서치 7.3).

## 법적·정책 요구사항

- 개인정보 수집
  - 상대방 정보(출생 연도, 또는 생년월일)를 입력받는다. 입력자와 정보주체가 다르다.
  - 이름을 받지 않으므로 본인 정보보다 식별성이 낮다. 그래도 다른 정보와 결합하면 개인정보가 될 수 있다.
  - 입력값을 저장하지 않고 서버로 보내지 않는 것을 전제로 한다(AC-11).
  - 화면 입력 자체가 개인정보 처리에 해당하는지는 법률 확인 필요(리서치 9.1).
  - 정보주체 동의 쟁점은 운세 리서치 8.4와 열린 질문 12번에 있다.
- 상대방 정보 동의 안내 (사용자 결정 2026-11-24: 넣는다. 문장은 승인 필요)
  - 입력 화면에 아래 초안을 보여 준다. 초안은 승인 대상이며, 승인 전에는 화면에 올리지 않는다.
  - 초안: "입력하는 정보는 상대방의 것입니다. 입력하기 전에 상대방에게 궁합 확인에 쓴다는 것을 알리고 동의를 받았는지 확인해 주세요. 입력한 정보는 서버로 전송되거나 저장되지 않습니다."
- 만 14세 미만 (사용자 결정 2026-11-24: 운세와 똑같이 처리. 새 연령 게이트를 설계하지 않는다)
  - 재사용할 기존 구성 요소(확인만 한다. 설계 담당이 최종 판단한다)
    - 이용 전 확인 게이트: `src/features/fortune/shared/components/consent-gate.component.tsx`. 확인 전에는 자식 화면을 그리지 않는다.
    - 확인 화면: `consent-form.component.tsx`. 세 항목 중 첫 항목이 "만 14세 이상입니다."이다.
    - 확인 거부 화면: `consent-declined.component.tsx`.
    - 연령 안내 화면: `shared/components/age-blocked.component.tsx`(`FORTUNE_AGE_BLOCKED_TEXTS`).
    - 만 나이 계산과 판정: `src/features/fortune/hooks/use-birth-flow.hook.ts`의 생년월일 기준 판정(`calculateFortuneManAge`, `FORTUNE_MIN_AGE`). 기존 운세는 생년월일 전체를 받아 판정한다.
  - 재사용 시 확인할 점
    - 동의 화면 문구는 운세용이다("운세는 오락과 참고를 위한 것이며..."). 궁합에 그대로 쓰면 문구가 맞지 않는다. 궁합용 문구를 승인받아야 한다(열린 질문 14번).
    - 동의 저장은 탭 세션 단위이며 키가 운세와 같은 이름 규칙을 쓴다. 한쪽에서 동의하면 다른 쪽도 통과할지 결정이 필요하다(열린 질문 14번).
    - 띠 궁합(연도만)과 별자리 궁합(월·일만)은 생년월일 전체가 없어서 기존 방식으로 만 14세 미만을 판정할 수 없다. 이 차이가 가장 큰 쟁점이다(열린 질문 13번).
  - 약관·방침: 운세 조항은 약관 `src/app/terms/page.tsx` 7번 절(159·166줄 부근)과 방침 `src/app/privacy/page.tsx` 어린이 관련 절(254줄 부근)에 있다. 궁합을 열면 두 문서에 궁합 문장을 추가해야 한다. 문구는 승인 대상이다.
  - 법률 확인 필요: 개인정보보호법 제22조의2(법정대리인 동의) 적용 여부. 상대방 나이를 확인할 방법이 없다는 점이 쟁점이다. 미성년 이용 여부 점검도 이 항목에 포함한다.
- 고지 문구 (모두 승인 필요)
  1. 오락 목적 고지: 기존 운세 면책 문구를 재사용하고, 궁합 전용 문장을 추가한다.
  2. 입력 미저장 안내: 기존 운세의 입력 안내 방식을 따르되, 궁합용 문장을 새로 쓴다.
  3. 과학적 근거 없음 고지: 띠와 별자리 모두 전통 이론 또는 대중 관례이므로 넣는다(리서치 9.5).
  4. 상대방 정보 동의 안내: 위 "상대방 정보 동의 안내" 항목.
  5. 과장 표현 금지: "천생연분", "100% 궁합" 같은 표시는 쓰지 않는다. 「표시·광고의 공정화에 관한 법률」 제3조 적용은 법률 확인 필요.
- 단정 금지: 결혼, 임신, 이별, 이혼, 바람 등 관계를 예측하는 표현과 "운명의 상대"처럼 확정하는 표현을 쓰지 않는다. 기존 금지 목록(`FORTUNE_FORBIDDEN_TERMS`)을 그대로 적용하고, 궁합 전용 추가 목록을 승인받는다.
- 상업적 이용 주의 (광고 수익을 낼 경우)
  - 카카오 AdFit 광고: 위험 수용(사용자 결정 2026-11-24). 사용자가 궁합 결과 페이지와 허브 페이지의 광고 게재에 문제가 없다고 판단했다. 리서치 9.6에 적힌 AdFit 확인 항목(사행성 항목 해당 여부, 오해를 줄 수 있는 제목 아래 배치, 미성년 대상 제한)은 확인하지 않고 이 위험 수용에 포함한다. 이 결정은 기록으로 남기고, 나중에 광고 심사에서 문제가 생기면 다시 검토한다.
  - Google AdSense: 이번 결정 범위 밖이다. 사용하기 전에 따로 확인한다.
  - 광고로 결과를 잠그는 구조는 쓰지 않는다. `COMPLIANCE.md` 4장과 충돌을 피하기 위해서다.
  - 저작권: 띠 지지 관계와 별자리 원소 분류는 사실 규칙이라 쓸 수 있다. 경쟁 사이트의 문장, 점수 설명, 궁합표 전체는 복사하지 않는다. 문구는 직접 쓴다. AI가 만든 문구를 쓰면 권리 귀속은 법률 확인 필요이며, 작성 기록을 남긴다.
  - 띠 그림과 별자리 그림은 자체 제작한다(`COMPLIANCE.md` 11장 선례). 외부 아이콘을 쓰면 라이선스 확인이 필요하다.
  - 새 라이브러리를 추가하면 `DEPENDENCY_LICENSES.md`, `THIRD_PARTY_NOTICES.md`를 갱신한다.
- 로또 연결 금지: 궁합 결과와 로또 번호를 연결하지 않는다(운세 리서치 9장 권장).
