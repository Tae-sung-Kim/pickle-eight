## 목표

점심 하나뿐인 메뉴 룰렛을 저녁과 그 밖의 끼니까지 넓혀, 사용자가 끼니를 고르고 그 끼니 메뉴를 룰렛으로 뽑을 수 있게 한다. 이름과 주소도 점심에 묶이지 않는 이름으로 바꾸고, 기존 점심 주소는 새 주소로 영구 이동시켜 검색 자산을 잃지 않는다. 술안주는 끼니에 넣지 않는다.

## 현재 상태 확인 (기존 기능과 충돌 확인)

- 점심 기능은 이미 공개되어 있다(`docs/lunch/status.md`, 2026-11-19 "공개 완료"). TODO 5번의 "점심 안정화 후 진행"은 안정화 기준이 정해지지 않았다. 열린 질문 M12.
- 메뉴 그룹 `lunch`의 주소는 `/lunch/today` 하나다. `/lunch` 자체 페이지는 없다. `menu.constant.ts`의 그룹 주소와 항목 주소가 같다.
- `src/app/sitemap.ts`는 `/lunch/today`를 하드코딩하지 않는다. `MENU_LIST`에서 `comingSoon`이 아닌 그룹만 골라 자동으로 넣는다. 따라서 메뉴 주소를 바꾸면 사이트맵은 자동으로 바뀐다. 옛 주소를 빼는 별도 코드는 필요 없다고 본다. 대신 "옛 주소가 사이트맵에 없음"을 검사 항목으로 둔다.
- `next.config.ts`의 기존 `redirects()`는 `permanent: true`를 쓴다(로또 3건). Next.js에서 `permanent: true`는 308로 응답한다. 요구 사항은 301이다. 옵션 차이는 설계 단계에서 맞춘다(M13). 검색 엔진은 308과 301을 같은 방식으로 본다는 것이 공식 설명(Vercel/Next 측)이지만, 요구대로 301 응답을 확인하는 검사를 둔다.
- 메뉴 목록(`src/features/lunch/constants/lunch-menu.constant.ts`)은 48개, 카테고리 6개다. 단위 테스트(`unit/lunch/lunch-menu.test.ts`)가 48개와 카테고리별 개수(10/8/8/8/6/8)를 고정한다. (이 항목은 2026-11-23 이후 점심 목록이 바뀌어 "끼니별 메뉴 데이터" 장의 최신 수치를 따른다.)
- 지도 링크는 카카오맵, 네이버지도, 구글 지도 3개다. 기획서(`docs/lunch/plan.md` AC-13)와 `docs/lunch/legal-draft.md`는 2개다. 구글 링크는 QA 단계(`docs/lunch/qa-report.md` 113~128행)에서 추가되었고, 기획·설계 승인 기록에는 없다. 약관, 방침, COMPLIANCE.md 1장과 11장에도 구글이 들어가 있다. 승인 여부를 확인해야 한다(M11). 이 기획서는 구글을 현재 상태 그대로 두고 판단을 열린 질문으로 남긴다.
- 메뉴 점심 항목 색은 `text-menu-lunch`(`--menu-lunch`, `#a5481f`)다. 끼니가 늘면 그룹 이름과 색 토큰을 어떻게 할지 정해야 한다. `docs/conventions/design-system.md`의 메뉴 색 표 변경이 필요할 수 있어 사용자 승인 대상이다(M4 연결).
- 기존 점심 기능 문서(`docs/lunch/`)는 과거 기록으로 둔다. 새 기능 문서는 `docs/menu-meals/`에 쓴다.

## 유저 스토리

- US-1: 저녁 메뉴를 고민하는 직장인으로서 저녁 메뉴를 룰렛으로 뽑고 싶다. 퇴근 뒤에도 같은 방식으로 빨리 고르기 위해서다.
- US-2: 점심 룰렛을 쓰던 사용자로서 기존 주소로 들어가도 새 주소로 자연스럽게 옮겨 가고 싶다. 즐겨 찾던 주소가 깨지지 않게 하기 위해서다.
- US-3: 아침 식사를 고민하는 사용자로서 그 밖의 끼니를 골라 아침 메뉴를 뽑고 싶다. 점심과 저녁 말고도 고민이 있기 때문이다.
- US-4: "저녁 뭐 먹지"를 검색한 방문자로서 페이지 첫 화면에서 이 서비스가 무엇인지 확인하고 싶다. 검색 의도와 맞는지 바로 알기 위해서다.
- US-5: 운영자로서 끼니를 늘려도 화면과 문구에 음주 관련 단어가 노출되지 않는다는 점을 확인하고 싶다. 미성년자와 음주 권유 문제를 피하기 위해서다.
  - 변경 이유: 저녁에 안주 연상 메뉴가 남으므로 "음주 관련 내용이 노출되지 않는다"를 "음주 관련 단어가 화면과 문구에 노출되지 않는다"로 좁혔다.
- US-6: 운영자로서 옛 주소가 검색 결과에서 새 주소로 넘어가는지 확인하고 싶다. 배포 뒤 검색 유입이 끊기지 않게 하기 위해서다.

## 끼니 선택 방식 (기획 방향)

비교
| 방식 | 장점 | 단점 |
|---|---|---|
| A. 한 화면에서 끼니 선택 (기본안) | 주소 1개로 관리. 페이지 내용이 겹치지 않음. 주소 변경과 301이 1건. 기존 룰렛 구조를 그대로 쓴다 | "저녁 뭐 먹지"처럼 끼니별 검색 키워드에 따로 맞춘 페이지가 없음. 화면 요소가 조금 늘어남 |
| B. 끼니별 페이지 (예: 끼니마다 주소 하나) | 끼니별 검색 키워드에 각각 맞출 수 있음 | 같은 기능을 여러 번 복제해 얇은 페이지가 될 위험. 끼니마다 설명, FAQ, 문구를 따로 써야 함. 주소, 301, 사이트맵이 늘어남. 끼니 값이 주소에 들어가 기존 원칙(선택 값을 주소에 넣지 않음, AC-16, AC-23)을 바꿔야 함 |

추천: A(한 화면 단일 선택)로 간다. B는 검색 유입 데이터를 본 뒤 결정한다. 이는 기존 "지역 landing은 검색 유입 데이터를 본 뒤 결정" 원칙과 같다.

세부 방향
- 끼니는 한 번에 하나만 고른다(기본안). 두 끼니를 한꺼번에 섞으면 결과의 성격이 흐려진다.
- 끼니를 바꾸면 기존 결과를 지운다. 기존 조건 변경 원칙(점심 Q4)과 같다.
- 끼니 값은 화면 상태에만 둔다. 주소, 저장소, 쿠키에 넣지 않는다(기존 AC-16, AC-23과 같은 원칙).
- 기본 끼니를 무엇으로 할지는 열린 질문 M10이다. 기기 시각으로 기본값을 정하는 안도 있으나, 사용자가 정한다.
- 조건(카테고리, 국물)은 끼니마다 따로 기억하지 않는다. 끼니를 바꾸면 조건은 유지하되 결과만 지운다(기본안). 겹치는 카테고리만 남기고, 남는 것이 없으면 새 끼니의 기본 선택을 쓴다. 저녁의 기본 선택은 "야식"을 뺀 6개다. 저녁에서 야식을 켠 채 다른 끼니로 가면 야식 선택은 사라진다. 이 부분은 M2에 함께 넣는다.
  - 변경 이유: 저녁 야식 칩이 기본 꺼짐이라, 끼니를 바꿀 때 카테고리가 어떻게 넘어가는지 정해야 한다.

## 그 밖의 끼니 후보 (술안주 대체)

요구: 음주와 무관해야 하고, 사이트 성격과 AdFit 심사에 안전해야 한다. 아래 3개 후보를 비교한다.

| 후보 | 장점 | 단점 | 음주 연상 | 건강 표현 위험 | 메뉴 풀 준비 |
|---|---|---|---|---|---|
| 아침·브런치 | "끼니"라는 점에서 점심, 저녁과 맞는다. 음주와 거리가 멀다. 토스트, 죽, 샌드위치, 계란 요리처럼 메뉴가 쉽게 나온다. 기존 점심 목록과 겹침이 적다 | 검색 수요가 점심, 저녁보다 적을 수 있다(외부 확인 필요). "아침 결식"처럼 건강 쪽으로 읽히는 말을 피해야 한다. 카테고리 6개를 그대로 쓰면 한식과 분식이 얇을 수 있다 | 낮음 | 중간 (아침 식사를 건강 기준으로 설명하지 않는다는 규칙 필요) | 중간. 카테고리 구성을 점심과 다르게 할 수 있다 |
| 간식·디저트 | 검색 수요가 있을 수 있다. 음주와 무관하다 | "끼니"가 아니다. 서비스 이름 "메뉴 룰렛"과 맞지만 "오늘 뭐 먹지" 의도와 거리가 있다. 디저트 프랜차이즈 상표가 얽히기 쉽다. 음료를 넣으면 카페 광고처럼 보인다. 당류 표현이 식품 표시·광고 문제가 될 수 있다 | 낮음 | 높음 (당, 칼로리 연상) | 높음. 디저트와 음료의 경계를 정해야 한다 |
| 야식 | 검색 수요가 가장 클 가능성이 있다("야식 뭐 먹지") | 술안주와 가장 많이 겹친다. 치킨, 족발, 곱창 같은 메뉴가 음주와 붙는다. 심야 식사라는 점이 건강 쪽 문제로 읽힌다. 저녁 목록과 겹쳐 차별점이 약하다 | 높음 | 높음 | 중간 |

추천: 아침·브런치.
- 이유 1: "끼니"라는 사이트 방향과 맞고, 음주 연상이 가장 낮다. 이 기능의 목적인 "술안주 제외"와 가장 잘 맞는다.
- 이유 2: 검색 수요는 아직 확인되지 않았다. 리서치로 확인하고 난 뒤 확정한다(리서치 판단 장).
- 야식은 끼니로 추천하지 않는다. 사용자 결정(2026-11-23)에 따라 저녁 안의 "야식" 카테고리(기본 꺼짐)로만 둔다. 이 비교의 결론(끼니로는 쓰지 않는다)은 그대로다. 카테고리로 둘 때 생기는 음주 연상 위험은 "법적·정책 요구사항" 장에서 다룬다.
  - 변경 이유: 기존 문장 "사용자가 야식을 고르면 금지 문구와 판정 기준을 따로 정한다"는 사용자 결정(저녁 안 카테고리)과 맞지 않아 바꿨다.
- 간식·디저트는 "끼니"가 아니어서 이름과 맞지 않는다. 후속으로 남긴다.

## 저녁 야식 카테고리 (2026-11-23 사용자 결정)

- 변경 이유(이 장 전체): 사용자가 끼니는 점심, 저녁, 아침·브런치 셋으로 두고, 저녁에만 "야식" 카테고리를 더하기로 결정했다.
- 끼니는 셋이다. 야식은 끼니가 아니라 저녁 안의 일곱 번째 카테고리다. 점심과 아침·브런치는 카테고리 6개 그대로다.
- "야식" 칩은 기본 꺼짐이다. 저녁을 고르면 야식을 뺀 6개 카테고리가 켜져 있다. 사용자가 야식 칩을 켰을 때만 야식 메뉴가 후보에 들어간다.
- 안주 연상 메뉴는 저녁에서 빼지 않는다. 일부는 야식 카테고리로 옮기고, 나머지는 원래 카테고리에 둔다. 새 야식 메뉴를 더한다(끼니별 메뉴 데이터 장).
- "술", "안주", "해장"은 카테고리 키, 라벨, 메뉴 이름, 문구, FAQ, 메타, 약관 어디에도 쓰지 않는다.
- 카테고리 라벨 "야식"만 금지어 예외다. 칩, 결과 카드의 카테고리 표시, 결과 알림의 괄호 안에서만 쓸 수 있다(AC-11).
- 저녁 운세 라벨은 "오늘의 저녁운"을 그대로 쓴다. 야식 전용 라벨은 만들지 않는다. 야식 운세 4줄은 저녁 문구에 포함된다(운세 문구 원칙 장).

## 끼니별 운세 문구 원칙

- 라벨: 끼니 이름을 붙인다("오늘의 점심운", "오늘의 저녁운", "오늘의 아침운"). 라벨 방식은 M9에서 정한다. "끼니운"처럼 어색한 말은 쓰지 않는다. 야식 카테고리도 저녁 라벨을 쓴다.

- 합니다체, 한 문장, 가벼운 가능성 표현. 기존 점심 원칙(단정하지 않음, 메뉴 맛과 특성 언급 없음)을 그대로 따른다.

  - 건강·영양 관련(아침 문구 포함): 든든한, 건강한, 영양, 균형, 칼로리, 속 편한, 아침결식 등.

## 법적·정책 요구사항

개인정보 수집
- 끼니 선택 값은 화면 상태에만 둔다. 서버로 보내지 않고 저장하지 않는다. 주소, localStorage, sessionStorage, 쿠키에 넣지 않는다. 야식 칩을 켰는지도 기억하지 않는다.
- 위치는 묻지 않는다. 기존 방침의 수집 항목과 저장 문구를 바꿀 이유는 없다(판단 기준은 `docs/lunch/legal-draft.md` 2장).
- 분석 이벤트(끼니 선택, 뽑힘, 지도 링크 클릭)는 기본안으로 보내지 않는다(M10 연결과 기존 Q10 원칙).
- 14세 미만: 입력이 없으므로 연령 게이트는 두지 않는 것이 기본안이다. 음주 관련 단어를 없애면 이 판단의 근거가 더 강해진다. 최종 판단은 사용자다.

음주 관련 (미성년자, 음주 권유)
- 술안주 끼니를 빼고 음주 관련 단어를 화면과 문구에서 막으면 음주 권유 이슈는 줄어든다.
  - 변경 이유: 저녁에 안주 연상 메뉴와 야식 카테고리가 남으므로 "대부분 사라진다"는 표현을 바꿨다.
- 남는 위험 네 가지:
  1. 저녁 안의 안주 연상 메뉴(족발, 곱창 등)와 "야식" 카테고리가 음주 연상으로 읽힐 수 있다. 제외 기준을 두지 않기로 했으므로, 사용자가 판단하고 필요하면 법률 확인을 받는다(M19).
  2. 해장 연상 메뉴(순대국, 설렁탕)와 "해장" 문구. 문구와 FAQ에서 "해장"을 금지어로 막는다(M7).
  3. 저녁 끼니와 야식 카테고리가 음주 시간대와 겹친다는 사용자 인식. 기획자는 법률 판단을 하지 않는다. 사용자가 판단한다(M19).
  4. 카카오 AdFit의 주류 관련 정책에 해당하는지(리서치 판단 2번).
- 음주 관련 단어가 화면, 약관, 방침, 메타에 없는지 검사 항목을 둔다(AC-11). 카테고리 라벨 "야식"만 예외다.

고지 문구
- 기존 고지 5문장(오락 목적, 무작위, 보상 없음, 외부 링크, 결과 하단)은 끼니 이름만 바꿔 유지한다. 문장 자체의 "점심"은 "끼니", "메뉴" 등으로 바꾼다. 변경은 사용자 승인 대상이다.
- 외부 링크 안내 문구는 지도 제공자 수(2개 또는 3개)에 맞춘다(M11).

상업적 이용
- 수익은 AdFit 광고만 쓴다. 끼니 확장 뒤에도 배달, 예약, 가게 광고, 제휴 링크, 메뉴 판매 연결을 넣지 않는다.

## 예외·빈 상태

- 끼니를 바꾼 뒤: 결과를 지운다(기본안). 카테고리 선택은 겹치는 것만 남고, 없으면 새 끼니의 기본 선택이 된다.
- 끼니는 하나만 선택되어 있다. 끼니를 고르지 않는 상태는 없다(기본값이 있으므로).
- 선택한 끼니와 카테고리와 국물 조건을 합쳐 후보가 0개면 빈 상태 문구를 보이고 룰렛을 끈다(기존 AC-5 확장).
- 옛 주소로 들어오면 새 주소로 이동한다. 이동 중 기존 결과나 조건은 없다.
- `/lunch` 같은 그룹 주소로 들어오는 경우: 현재 404다. 리다이렉트 여부를 정한다(M15).
- 메뉴 목록에 같은 끼니 안 이름 중복이 있으면 출시 전에 제거한다.
- JavaScript가 꺼져 있을 때: 끼니 설명, FAQ, 고지는 서버 HTML로 보인다. 끼니 선택과 룰렛은 기존과 같이 안내 문구를 보인다.
- 연출 중 끼니 바꾸기: 막는다(기존 점심 AC-7과 같다).

## 완료 조건 (AC)

화면과 주소에서 확인할 수 있는 문장으로 쓴다. 문구는 의미 기준으로 확인한다. 룰렛 결과는 무작위이므로 "선택한 끼니와 조건의 메뉴 목록에 있는지"로 확인한다.

주소와 이름
- AC-1: 새 주소(`/meal`, M3 확정 뒤)에 로그인 없이 접속하면 h1 "오늘 뭐 먹지"와 끼니 선택 영역이 보인다.
- AC-2: 옛 주소 `/lunch/today`에 요청하면 새 주소로 영구 이동한다. 응답 상태는 301 의미를 가져야 한다(설계에서 상태 코드를 확인, M13).
- AC-3: 메뉴 그룹과 항목의 링크가 새 주소를 가리킨다. 옛 주소 링크가 없다.
- AC-4: `/sitemap.xml`에 새 주소가 있고 옛 주소 `/lunch/today`는 없다.
- AC-5: 새 주소 페이지의 canonical, og url, BreadcrumbList 주소는 모두 새 주소다.

끼니 선택
- AC-6: 기본 상태에서 끼니는 하나만 선택되어 있고, 기본 끼니는 M10 결정대로다.
- AC-7: 끼니는 한 번에 하나만 선택된다. 끼니를 바꾸면 이전 결과가 사라진다.
- AC-8: 끼니 선택지는 "점심", "저녁", 그 밖의 끼니 한 개(M1 결정)로 보인다.

## 열린 질문

이 기획의 확정을 막는 질문은 PM을 거쳐 사용자에게 올린다. A는 승인 전에 답이 필요하다. B는 설계나 개발 전에 답이 필요하다. C는 출시 전에 답이 필요하다.

- M1 (A, 사용자, 결정 완료 2026-11-23): 그 밖의 끼니 선택. 끼니는 점심, 저녁, 아침·브런치 셋 그대로다. 야식은 끼니가 아니라 저녁 안의 카테고리(기본 꺼짐)다. 술안주 끼니는 없다.
  - 변경 이유: 사용자가 끼니 구성을 확정했다. 이전 "야식은 비추천, 사용자가 고르면 다시 쓴다" 문구를 결정 내용으로 바꿨다.
- M2 (A, 사용자): 끼니 선택 방식. 한 화면 단일 선택(기본안)과 끼니별 페이지 중 고른다. 조건(카테고리, 국물)은 끼니를 바꿔도 유지하고 결과만 지운다는 기본안을 승인하는지. 카테고리는 겹치는 것만 남기고, 없으면 새 끼니의 기본 선택을 쓴다는 규칙도 함께 승인한다.
- M3 (A, 사용자): 새 주소. `/meal`(추천), `/menu`, `/menu-roulette` 중 고른다.
- M4 (A, 사용자): 메뉴 이름. 그룹 이름 "메뉴 룰렛"(추천)과 페이지 제목 "오늘 뭐 먹지" 유지를 승인한다. 색을 그대로 `menu-lunch`로 둘지, 새 토큰을 만들지 정한다. 새 토큰이면 `design-system.md`와 `globals.css`를 고치므로 사용자 승인이 필요하다.
- M5 (A, 사용자): "점심 메뉴 추천" 검색 키워드와 "메뉴 추천" 표현. 이전 승인(`docs/lunch/status.md` Q13)에서 이 표현을 승인했으나, 이 기획의 고지 문구("추천하지 않습니다")와 충돌한다. 키워드에서 뺄지, 유지할지 다시 정한다.
- M6 (A, 사용자): 저녁 메뉴 목록. 저녁 목록은 92개(일반 66개, 야식 26개)다. 안주 연상 메뉴는 빼지 않고 일부를 야식으로 옮기는 방향은 사용자가 정했다. 구체 목록(보충 메뉴와 야식 새 메뉴 12개)은 설계 3.7.3 기준이며 사용자 검수 대상이다.
  - 변경 이유: 저녁 목록 방향이 확정되어 검수 항목으로 바꿨다.
- M7 (A, 사용자): 안주 연상 메뉴 처리. 사용자 결정으로 안주 연상 메뉴는 저녁에서 빼지 않는다. 튀김과 치킨은 야식으로 옮기고, 탕수육, 깐풍기, 마라샹궈, 가라아게, 어묵은 원래 카테고리에 둔다. 해장 연상 메뉴(순대국, 설렁탕)는 설계 추천대로 한식에 두고 문구에서만 "해장"을 막는다. 이 부분은 사용자 확인 대상이다.
  - 변경 이유: 기존 "7개를 뺄지 확정" 질문은 사용자 결정으로 닫혔다. 해장 메뉴 처리만 확인이 남았다.
