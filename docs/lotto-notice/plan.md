# 로또 고지 문구 보강 기획서

## 목표

로또 페이지 전체에서 "당첨을 보장하지 않습니다" 고지를 화면에서 바로 확인할 수 있게 해, 이용자가 참고용 정보를 당첨 보장으로 오해하지 않도록 한다.

## 범위

- 포함:
  - `/lotto/history`, `/lotto/check`, `/lotto/my-numbers`, `/lotto/[draw]`에 고지가 화면에 보이도록 한다.
  - `e2e/lotto.spec.ts`의 고지 확인 반복문에 위 페이지를 추가한다.
  - `/lotto` 허브 포함 여부는 열린 질문 Q4에서 정한다.
- 제외:
  - 메타데이터(title, description, OG), JSON-LD, sitemap. 바꾸지 않는다.
  - 이미 고지가 있는 `/lotto/analysis`, `/lotto/simulator`, `/lotto/generator`의 문구 변경.
  - 푸터 디자인 변경, 로또 기능 로직 변경, 법률 검토 자체.

## 현재 상태 (코드 확인 결과)

| 페이지 | "당첨을 보장하지 않습니다" 화면 노출 | 확인 위치 |
|---|---|---|
| `/lotto/analysis` | 있음 | 페이지 설명(description prop) |
| `/lotto/simulator` | 있음 | 페이지 설명(description prop) |
| `/lotto/generator` | 있음 | 페이지 설명(description prop) |
| `/lotto/history` | 없음 | 페이지 파일, 기능 폴더 모두 문구 없음 |
| `/lotto/check` | 없음 | 페이지 파일, 기능 폴더 모두 문구 없음 |
| `/lotto/my-numbers` | 없음 (메타 description과 FAQ JSON-LD 답변에만 있음) | `src/app/lotto/my-numbers/page.tsx` |
| `/lotto/[draw]` | 없음 | `src/app/lotto/[draw]/page.tsx`, `src/features/lotto/draw/` 확인 |
| `/lotto` 허브 | 없음 | `src/` 전체 검색에 해당 문구 없음 |

공통 푸터는 `src/app/lotto/layout.tsx`에서 `LottoFooterNoticeComponent`(`src/features/lotto/shared/components/footer-notice.component.tsx`)를 불러오므로 모든 `/lotto/*` 페이지에 이미 나온다. 푸터에는 다음 내용이 있다: 비공식 서비스 고지, 공개 데이터 수집 방식, "정확성·적시성·완전성·지속성을 보증하지 않습니다", 만 19세 이상 안내, 투자·재정·법률 자문 아님과 책임 있는 이용 안내. "당첨을 보장하지 않습니다"라는 문장은 푸터에 없다.

## 법적 근거 (COMPLIANCE.md)

- `COMPLIANCE.md` 11번(고지)은 "Non-affiliation notice for lottery organizations"와 "Responsible use guidance and age restrictions stated on relevant pages"를 요구한다. 문구를 직접 지정하지는 않는다.
- "당첨 보장 없음" 문장을 모든 페이지에 두라는 조항은 `COMPLIANCE.md`에 없다. 이 문장의 근거는 (1) 11번의 "관련 페이지의 책임 있는 이용 안내" 요구, (2) 이용약관의 "당첨 또는 수익을 보장하지 않습니다" 문구, (3) 기존 분석·시뮬레이터·생성 페이지의 문구 관행과 `e2e/lotto.spec.ts`의 고지 확인 AC다.
- 로또 섹션에는 법률 검토 기록이 없다. 이 문장이 법적 필수인지, 내부 정책인지는 Q5에서 확인한다.

## 방식 비교

| 방식 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A. 페이지별 추가 | `history`, `check`, `my-numbers`, `[draw]`의 설명 또는 본문에 문구를 넣는다. 기존 description 패턴을 따르되 `[draw]`는 설명 자리가 없어 새 요소가 필요하다. | 페이지 상단 등 눈에 잘 띄는 위치를 정할 수 있다. | 4곳을 고친다. 페이지마다 문구가 어긋날 수 있다. 새 요소가 생기면 UI 단계가 필요할 수 있다. |
| B. 공통 푸터 1곳 추가 (추천) | `LottoFooterNoticeComponent`의 목록에 `<li>` 한 줄을 추가한다. | 한 곳만 고친다. `/lotto/*` 전체(허브, `[draw]` 포함)를 한 번에 덮는다. 회차 데이터 오류 화면에서도 나온다. AC 검증이 쉽다. | 페이지 하단에 있어 눈에 덜 띈다. 상단 설명 문구와 중복될 수 있다. |

추천은 B다. 모든 `/lotto/*` 페이지를 한 번에 덮고 문구가 어긋날 위험이 없다. 상단 노출이 필요하면 B를 기본으로 두고 history, check에 A를 더하는 방식을 Q3에서 정한다.

제안 문구(승인 필요): "로또 관련 모든 기능의 결과는 참고용이며 당첨을 보장하지 않습니다."

## 유저 스토리

- US-1: 로또 기능 이용자로서, 어느 로또 페이지에서든 결과가 당첨을 보장하지 않는다는 안내를 바로 확인하고 싶다. 왜냐하면 번호 채점·분석 결과를 당첨 예측으로 오해하지 않기 위해서다.

## 완료 조건 (AC)

- AC-1: `/lotto/history`, `/lotto/check`, `/lotto/my-numbers`에서 "당첨을 보장하지 않습니다"가 하단 고지 영역 안에 화면에 보인다.
- AC-2: 유효한 회차 주소 `/lotto/[draw]`에서 같은 문구가 화면에 보인다.
- AC-3: 데이터가 없는 `/lotto/[draw]` 상태(잘못된 회차 또는 불러오기 실패)에서도 같은 문구가 화면에 보인다.
- AC-4: `/lotto/analysis`, `/lotto/simulator`, `/lotto/generator`에서 기존처럼 문구가 보인다 (회귀).
- AC-5: `e2e/lotto.spec.ts`의 고지 반복문에 위 페이지가 추가되어 데스크톱·모바일에서 통과한다. 검사는 푸터 영역 안에서 찾도록 해, 설명 문구 같은 다른 요소가 `.first()`로 잡혀 통과하는 일이 없게 한다.
- AC-6: 모바일 화면 너비에서 문구가 잘리지 않고 줄바꿈되어 보인다.
- AC-7: 각 페이지의 `<title>`, meta description, canonical, JSON-LD 출력이 변경 전과 같다.
- AC-8: `pnpm typecheck`와 `pnpm lint`가 통과한다.

## 예외·빈 상태

- `/lotto/[draw]`의 잘못된 회차 값, 데이터 없음, 불러오기 실패 상태에서도 푸터는 나와야 한다 (레이아웃 기준).
- `/lotto/my-numbers`에 저장된 번호가 없는 상태에서도 고지가 보여야 한다.
- 푸터 문구가 늘어나 모바일에서 스크롤이 길어지는 것은 허용한다.
- 방식 A를 고르면 같은 문구가 한 페이지에 두 번 나올 수 있다. 허용하되 AC-5의 검사 범위를 맞춘다.

## 검색 노출

- 키워드: 변경 없음. 기존 페이지 키워드를 그대로 둔다.
- 페이지가 답할 질문: 변경 없음. 이 작업은 검색 노출 문구를 바꾸지 않는다.

## 법적·정책 요구사항

- 개인정보 수집: 없음. 입력을 받거나 저장하는 기능을 추가하지 않는다. `my-numbers`의 브라우저 저장은 기존 동작이고 바뀌지 않는다.
- 고지 문구: 위 제안 문구를 추가한다. 푸터에 있는 기존 고지 다섯 항목(비공식 서비스, 공개 데이터, 보증 없음, 만 19세, 책임 있는 이용)은 그대로 둔다. (2026-11-27 개정: 사용자 승인으로 공개 데이터·정확성·자문 아님·책임 항목을 한 항목으로 합쳐 푸터는 4항이 됐다. 비공식 서비스, 당첨 보장 안 함, 만 19세 항목 원문은 그대로다. docs/text-slim/plan-stage3.md 참고.)
- 상업적 이용 주의: 광고 수익 정책은 바뀌지 않는다. 문구만 추가하므로 광고 심사에 새 항목이 생기지 않는다. 로또 페이지의 광고 배치를 바꾸지 않는다.

## 작업 흐름 (소규모 변경)

- 이 작업은 문구 추가만 하므로 설계(architect)와 UI 디자인(ui-ux-designer) 단계를 생략한다. 사용자에게 알리고 승인을 받는다.
- 순서: 기획서 승인 → frontend-dev가 푸터 문구와 필요한 경우 페이지 요소를 고친다 → `e2e/lotto.spec.ts`의 고지 반복문 확장 → 영향받는 spec만 QA → `pnpm typecheck`, `pnpm lint`.
- 방식 A를 고르거나 `[draw]`에 새 화면 요소가 필요하면 소규모 조건을 벗어나므로 UI 디자인 단계를 넣을지 다시 묻는다.

## 열린 질문

- Q1: 방식 A와 B 중 무엇으로 할지. 추천은 B다.
- Q2: 고지 문구 확정. 위 제안 문구를 쓸지, 다른 표현을 쓸지.
- Q3: 하단 푸터 위치로 충분한지. 눈에 띄는 위치(페이지 상단 설명)도 함께 넣을지.
- Q4: `/lotto` 허브에도 넣을지. 허브에는 현재 문구가 없고 푸터만 있다.
- Q5: "당첨 보장 없음" 문장이 법적 필수 고지인지, 내부 정책인지. `COMPLIANCE.md`에는 문구가 직접 지정되어 있지 않다.
- Q6: `/lotto/[draw]` 검사에 쓸 회차. 테스트 환경에 회차 데이터가 있는지, 없으면 데이터 없는 상태만 검사할지 QA와 정해야 한다.
