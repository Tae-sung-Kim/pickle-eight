## 목표

로그인 없이 이용 조건을 확인하고 동의한 뒤, 생년월일(또는 띠·별자리)만으로 오늘의 운세를 부드러운 문장으로 확인할 수 있고, 모든 문구를 처음부터 새로 작성해 출처를 기록하는 무료 운세 서비스를 만든다. 오락·참고용이라는 점과 계산 기준을 화면에 밝히고, 입력한 생년월일은 서버에 보내거나 저장하지 않는다. 법적으로 문제될 부분을 줄이기 위해 이용자가 이용 조건(만 14세 이상, 오락·참고용과 본인 판단·선택, 생년월일 비전송·비저장)을 확인하고 선택해야 운세 기능을 쓸 수 있다.

## 결정 기록

사용자가 확정한 내용이다. 본문은 아래 결정을 따른다. 기획서 초안에 대한 답변은 "결정 사항" 장에 있다.

| 번호 | 주제 | 결정 |
|---|---|---|
| 1 | 범위 | 전체(띠, 별자리, 개인 일운, 사주). 1단계(개인 일운+띠+별자리)와 2단계(사주)로 나누는 제안을 승인했다. |
| 2 | 생성 방식 | A(날짜·생년월일 시드 기반 결정적 선택) + B(사주 규칙 계산) + D(문구 풀). E(외부 공급)는 쓰지 않는다. 문구 풀의 작성은 AI 초안 + 사용자 검수(타로 방식)로 한다. 이 점은 처음의 "AI 문장(C) 제외" 결정을 바꾼 것이다(결정 사항 1). 사용자가 접속한 시점에는 AI를 호출하지 않고, 개발 중 작성·검수한 정적 문구를 코드에 지정해 쓴다(결정 사항 3). "사주 분석" 표기는 B로 실제 계산한 화면에만 쓰고, A 방식 화면은 "오늘의 운세" 같은 표현을 쓴다. |
| 3 | 띠·별자리·저장 기준 | 리서치 문서의 권장안을 따른다. 내용은 아래 "리서치 권장안"에 적었고 사용자가 확인했다(결정 사항 2). |
| 4 | 로또 연결 | 행운의 숫자를 로또와 연결할 수 있다. 단 노출 문구를 이 기획서에서 미리 지정하고, "확률 100%", "보장", "당첨 예측", "당첨될 번호" 같은 표현은 절대 쓰지 않는다. 오락·참고용 고지를 반드시 넣는다. |
| 5 | 수익·안내 | 유료·크레딧은 도입하지 않는다. 면책·위기 안내는 타로와 같은 방식이다. |
| 6 | 저작권 | 타 사이트·책의 풀이 문장은 복사도 변형도 하지 않는다. 모든 문구를 처음부터 새로 작성하고(AI 초안 + 사용자 검수), 생성 지침과 문구 점검 기록(copy-log), 유사 문장 점검 절차를 남기며, 새 라이브러리를 쓰면 `THIRD_PARTY_NOTICES.md`를 갱신한다. |
| 7 | 만 14세 미만 | 만 14세 미만은 이용할 수 없고 만 14세 이상은 이용할 수 있다. 생년월일(연·월·일 전체) 입력으로 판정하는 차단과 이용 동의 게이트의 "만 14세 이상입니다" 확인을 함께 둔다(이중 안전장치). 만 14세 이상에게는 오락·참고용과 이용자 본인의 판단·선택에 대한 책임 관련 고지를 노출한다(결정 사항 6, 15). |
| 8 | 책임 고지 방향 | 서비스는 오락·참고용임을 알리고, 결과에 따른 판단과 선택의 책임은 이용자에게 있다는 일반 이용자 확인 수준으로 쓴다. 서비스가 법적 책임을 전부 면제한다는 식의 표현(전면 면책)은 쓰지 않는다. |
| 9 | 이용 동의 게이트 | 운세 기능(입력·선택·결과를 보는 화면) 진입 전에 이용 동의 화면을 보여 준다. 동의하지 않으면 운세를 이용할 수 없고 이용 불가 안내 화면을 보여 준다. 띠·별자리 직접 선택 경로도 게이트 뒤에 둔다(결정 사항 15). |
| 10 | 법률 확인 없음, 운영자 위험 수용 | 사용자가 2026-11-05에 출시 전 법률 확인을 진행하지 않기로 결정했다. 운영자가 위험을 수용한다(타로와 같은 방식). 이유: 법률 검토에 드는 시간·비용 대신 타로 선례와 같이 운영자가 책임지고 위험을 수용하기로 했기 때문이다. 대신 이용 동의 게이트를 최소한의 동의 장치로 유지하며, 이용자가 동의하지 않으면 서비스를 제공하지 않는다(동의 항목 3개). 법적 검증이 이루어지지 않았음을 이 기획서에 기록으로 남긴다(결정 사항 7, 위험과 대응 사항). |
| 11 | 방식 A 안내 문구 | 방식 A 안내를 "…사주(태어난 연·월·일·시로 세우는 네 기둥)를 계산한 결과가 아닙니다"로 바꾼다((가)안). 금지 표현 "사주 풀이"를 피하면서 일반 이용자에게 사주가 무엇인지 알려 주기 위해서다(결정 사항 17). |

### 리서치 권장안

참고: 리서치 문서는 띠·별자리·저장 세 항목에 "권장안"이라는 이름의 결론을 따로 내리지 않았고, 선택지와 "앱 시사점"을 제시했다. 아래 표는 그 시사점(3.2, 3.3, 8.4)과 개발 가이드 4.5를 기획자가 하나로 정리한 것이며, 사용자가 이 내용을 권장안으로 확인했다(결정 사항 2).

| 항목 | 리서치 근거 | 적용하는 내용 |
|---|---|---|
| 띠의 연 경계 | 3.2: 사주명리학은 입춘, 일상 매체는 설날도 무방하다는 톤이고 "어느 쪽이 맞다"는 판정은 없다. 시사점은 "기준을 하나 정해 화면에 밝히고, 경계 구간 출생자에게는 다른 기준의 결과를 알린다". 개발 가이드 4.5는 "사주는 입춘". | 입춘 시각을 기준으로 한다(띠와 사주가 같은 기준). 설날~입춘 사이(대략 1월 하순~2월 중순) 출생자에게는 "설날 기준으로는 ○○띠" 안내를 함께 보인다. 기준은 화면의 "계산 기준"에 밝힌다. |
| 별자리 경계 | 3.3: 실제 경계는 태양 위치(절기 시각)라 해마다 하루 안팎 달라진다. (a) 날짜표 고정 (b) 연도별 시각표 중 선택. "경계일 출생자는 시각을 보고 가른다. 음력 생일은 먼저 양력으로 바꾼다." | (b)를 적용한다. 서양 점성술의 12궁(춘분점 기준)을 쓰고, 해당 연도에 별자리가 바뀌는 날 출생자에게만 출생 시각을 묻거나 두 별자리를 함께 보인다. 날짜표는 화면에 보여 주는 안내용으로만 쓴다. |
| 생년월일 저장 | 8.4: 서버에 저장하지 않고 화면 계산에만 쓰면 쟁점이 가벼워진다. 브라우저 저장은 `data-storage.md`의 "민감한 개인정보를 넣지 않는다"에 해당하는지 판단이 필요하다. 열린 질문 11은 "타로처럼 최소 저장 방식"을 제시. | 서버에 저장·전송하지 않고, 브라우저(localStorage, sessionStorage, 쿠키, URL)에도 저장하지 않는다. 입력값은 화면 메모리에서만 쓴다. 방식 A는 같은 입력이면 같은 결과가 나오므로 저장 없이도 일관성이 유지된다. "이 기기에 기억하기"는 이후 후보로 둔다. (이용 동의 상태 보관은 생년월일 저장과 별개이며 "이용 동의 게이트" 장에서 다룬다.) |

## 범위

사용자가 단계 분할을 승인했다.

- 1단계(MVP, 필수)
  - 이용 동의 게이트와 이용 불가 안내 화면 (운세 기능 화면 전체에 적용. 허브는 제외)
  - 운세 허브(`/fortune`): 오늘의 운세·띠별 운세·별자리 운세로 가는 목록, 설명, FAQ, 상시 면책, 이용 안내, 상담전화. 이용 동의 게이트가 없고 운세 문구·입력칸이 없다(사용자 요청 2026-11-05, 설계 D11)
  - 오늘의 운세(개인 일운): 생년월일 입력 → 방식 A 결과 (`/fortune/today`)
  - 띠별 오늘의 운세: 12띠 공통 운세, 내 띠 찾기(입춘 시각 반영, 설날 기준 안내)
  - 별자리별 오늘의 운세: 12별자리 공통 운세, 내 별자리 찾기(경계 시각 반영)
  - 띠별·별자리 페이지에서 "생년월일로 보는 오늘의 운세"(`/fortune/today`)로 가는 링크 (사용자 요청 2026-11-05, 설계 D12)
  - 양력/음력(윤달 포함) 생년월일 입력과 양력 변환 확인 (음력 입력은 1단계에 포함, 결정 사항 14)
  - 지원 출생 연도: 1920년 1월 1일 ~ 2028년 12월 31일(결정 사항 10, 설계 D14). 범위 밖 입력에는 지원 범위 안내를 보인다.
  - 만 14세 미만 처리: 이용 동의 항목, 안내 문구(B), 생년월일 기반 연령 확인(C), 만 14세 이상에게 오락·참고용 및 책임 관련 고지 노출
  - 결과 항목: 총운, 재물, 애정, 직장·학업, 건강, 행운의 색·숫자·방향, 오늘의 조언, 주의할 점
  - 문구 풀(AI 초안 + 사용자 검수), 생성 지침, 문구 점검 기록(copy-log), 유사 문장 점검
  - 법적 고지, 위기 상담 안내(터치 기기는 눌러서 연결, PC는 글자 표시), 행운 숫자의 로또 연결(링크 방식) 고지
  - 검색 노출 준비, 메뉴 "준비 중" 해제, 개인정보처리방침·이용약관·`COMPLIANCE.md`·`THIRD_PARTY_NOTICES.md` 갱신
- 2단계(사주, 방식 B)
  - 사주 입력(양/음력, 윤달, 태어난 시간 또는 "모름"). 지원 출생 연도는 1단계와 같다(1920-01-01 ~ 2028-12-31, 절기 월주 때문). 연령 확인(만 14세), 입력값 비저장, 상담전화, 면책, 이용 동의 게이트는 1단계 방식을 그대로 재사용한다(동의 상태도 같은 sessionStorage 값을 쓰므로 사주 때문에 새로 묻지 않는다).
  - 사주 4기둥(연·월·일·시) 계산과 표시, 일간·오행 분포 표시. 천간·지지는 한글과 한자를 함께 표시한다(결정 사항 13). "4기둥"은 개발·기획 용어이며 화면 문구의 용어는 "화면 표기 규칙"의 "용어 사용 규칙"을 따른다.
  - 23시대(23:00~23:59) 출생은 야자시 구분 방식으로 처리한다: 일주는 그날, 시주 천간만 다음 날 일간 기준(결정 사항 18). 자시 통합은 쓰지 않는다.
  - 일간과 오늘 일진 천간의 십신으로 만드는 "오늘의 사주 운세". 사주 원국 성향 풀이(평생 운)는 이번 범위에 넣지 않는다(결정 사항 11).
  - "계산 기준" 화면(자시 처리, 자시 통합을 쓰지 않는다는 점, 학설이 갈린다는 점 포함), 과거 표준시·서머타임 안내
  - 십신별 문구 풀
  - 이용 동의 게이트를 사주 화면에도 적용
  - 1단계 화면 갱신: 사주 항목을 `MENU_LIST`에 추가하면서 허브 목록·허브 설명·FAQ·ItemList JSON-LD, 헤더·모바일 메뉴, sitemap에 사주를 반영한다. 오늘의 운세·띠별·별자리 페이지 본문은 바꾸지 않는다.
- 이후(이번 기획서 범위 밖, 후보)
  - 주간·월간·신년운세 (연말~설 수요 시즌을 이유로 앞당기지 않고 이후로 둔다, 결정 사항 3)
  - 오행 균형, 지지 합·충을 반영한 사주 고도화 (지지 음양 쟁점 포함, 보정 3 참고)
  - 사주 원국 성향 풀이(평생 운, 성격 해석)
  - 토정비결(원문 권리 판단과 법률 확인 필요), 궁합·가족 운세(제3자 정보 입력 이슈)
  - 시간대별 운세, 바이오리듬, 운세 캘린더(택일)
  - 생년월일 기기 저장("기억하기"), 결과 공유, 기록 보기
  - 띠·별자리 개별 URL(12개씩) 페이지 (결정 사항 12: 지금은 만들지 않음)
  - 이름·질문 같은 자유 입력란
  - 2029년 이후 출생 지원 (절기 데이터 보완 후속 작업 F-1, 기한 2028-12-01)
- 제외(확정): 유료·크레딧, 외부 공급 콘텐츠(E), 사용자 접속 시점의 AI 문장 생성, 성별·출생지 입력

## 기존 기능과의 충돌 확인

- `src/app/fortune/today/page.tsx`: "준비 중"(ComingSoon) 상태이고 `robots: { index: false }`다. 1단계에서 실제 기능으로 바꾸면서 noindex를 제거한다. 노출된 적 없는 URL이므로 redirect는 필요 없다.
- `/fortune`(허브): 새 URL이며 기존 경로와 충돌하지 않는다. 메뉴의 "운세" 그룹 링크 목적지가 `/fortune`으로 바뀌므로 출시 후 헤더·모바일 메뉴의 그룹 링크 동작을 확인한다. 허브의 목록은 메뉴의 운세 그룹 항목에서 만들어진다(설계 D11).
- `src/constants/menu.constant.ts`: 운세 그룹이 `comingSoon: true`(그룹 단위)이고 항목은 "오늘의 운세" 하나뿐이다. 설명은 "생년월일로 오늘의 총운과 행운 포인트를 확인.", 예시는 "예: 띠별, 별자리별 오늘 운세"다. `comingSoon`은 그룹 단위이고 `sitemap.ts`가 `!group.comingSoon`인 그룹만 읽는다. 따라서 1단계 출시 때 그룹의 `comingSoon`을 풀고 그룹 링크를 `/fortune`으로 바꾸며 "띠별 운세", "별자리 운세" 항목을 추가한다. 2단계 사주 항목은 페이지가 준비되기 전에 메뉴에 넣지 않는다(넣으면 허브·메뉴·sitemap에 함께 노출됨, AC-80).
- 2단계 사주 출시와 1단계 허브: 사주 항목을 `MENU_LIST`에 추가하면 허브 목록, 헤더·모바일 메뉴, sitemap, 허브 ItemList JSON-LD에 한꺼번에 나타난다. 지금 허브 설명에는 운세가 세 가지라는 전제의 문구(`fortune-guide.constant.ts`의 "세 가지 운세의 차이"와 "세 운세 모두…" 단락)가 있어 사주가 생기면 사실과 어긋난다. 또 AC-10은 허브 JSON-LD에 "사주"를 쓰지 않는다고 하는데 ItemList는 메뉴 라벨에서 자동으로 만들어져 사주 항목이 들어간다. 두 가지를 2단계 범위에서 처리한다(AC-88, 열린 질문 S2-6, S2-7).
- 타로(`/tarot/*`): 같은 사이트에서 이미 구현되어 있다. 면책 문구 위치, 위기 상담전화 다섯 곳, 금지 표현 점검, 문구 작성 이력과 샘플 웹 검색 확인, 쿠키 동의와 무관한 동작 방식을 운세도 같은 틀로 따른다. 상담전화 번호와 문구는 타로와 다르게 관리되면 안 된다(한쪽만 고쳐지는 일이 없어야 한다). 표시 방식(터치 기기는 눌러서 연결, PC는 글자 표시)도 타로·운세가 같은 공용 방식을 쓰므로 타로의 상담전화 표시도 함께 바뀐다(타로 문서·테스트 갱신은 별도 작업, 설계 D15). 타로에는 이용 동의 게이트가 없으므로, 운세의 게이트는 타로에 적용하지 않는다.
- 쿠키 동의(`ConsentProvider`): 광고·분석 스크립트 동작 여부를 정하는 사이트 전체 동의(`unknown | accepted | declined`, localStorage 보관)다. 운세의 이용 동의 게이트는 이와 별개이며 서로의 상태에 의존하지 않는다. 이름과 문구를 구분해 "이용 동의"(운세)와 "쿠키 동의"(광고·분석)로 부른다. 푸터의 쿠키 설정 버튼은 이용 동의 상태를 바꾸지 않는다.
- 로또(`/lotto/*`): AgeGate(만 19세 확인)가 `/lotto/*`에만 걸려 있고 확인 상태를 sessionStorage에 보관한다(실제 코드 기준. 환경 설정이 없으면 개발 환경은 매번 확인, 그 밖은 탭 세션 동안 유지). 이전 기획서의 "localStorage 30일 TTL" 기재는 틀려서 바로잡는다(설계 18.3). 운세의 이용 동의 보관(sessionStorage)은 로또의 실제 동작과 같은 방식이다. 운세의 생년월일 기반 연령 확인(만 14세)은 아무것도 저장하지 않는다. 운세 화면에서 로또 번호 생성기로 가는 링크만 두면 성인 확인은 도착한 로또 화면에서 일어난다. 운세 화면 안에서 로또 번호를 만들어 보여 주지 않는다.
- 광고: 루트 레이아웃의 AdFit 슬롯이 모든 페이지에 노출된다(쿠키 동의 후). 운세 기능은 광고·쿠키 동의 상태에 의존하면 안 된다.
- `docs/conventions/data-storage.md`: 생년월일 관련 값은 저장하지 않는다. 이용 동의 상태는 "동의 여부·문구 버전·동의 시각"만 sessionStorage에 둔다(작은 설정값, 개인 식별 정보 아님, 탭을 닫으면 사라짐). 문구와 대응표는 코드 안 상수이므로 Supabase를 쓰지 않는다.
- 음력 변환·24절기: 새 라이브러리를 쓰지 않고 한국천문연구원(KASI) 공공데이터로 만든 정적 표와 직접 구현한 계산을 쓴다(설계 D1). 후보 라이브러리의 라이선스를 확인하지 못해 직접 구현으로 정했다. 새 의존성이 없어 `DEPENDENCY_LICENSES.md`는 바뀌지 않고 `THIRD_PARTY_NOTICES.md`에는 외부 데이터 출처만 추가한다. 표를 만드는 데 공공데이터포털 인증키 환경변수 `DATA_GO_KR_API_KEY`를 쓴다. 이 키는 개발 중 표 생성 스크립트(사용자가 직접 실행)에서만 쓰고, 서비스 실행(런타임)과 화면에서는 읽지 않으며 저장소에 넣지 않는다. `.env.example`과 `README.md` 환경변수 표에는 키 이름과 용도만 적는다.
- 달력 데이터 제공 범위(실제 호출로 확인, `docs/fortune/kasi-api-check.md`): KASI의 24절기는 1920~2028년, 음력은 1391~2050년이다. 이용허락범위는 두 API 모두 "제한 없음"이다. 절기가 2028년까지만 제공되므로 입춘 기준 띠와 사주 월주를 쓰는 지원 출생일은 1920-01-01 ~ 2028-12-31로 제한한다. 오늘 날짜가 2029년 이후가 되어도 절기를 쓰지 않는 "오늘" 계산(개인 일운, 12띠·12별자리 목록)은 계속 동작한다. 2029년 이후 절기 보완은 후속 작업 F-1(기한 2028-12-01)로 둔다. 약관 전문은 확인하지 못했으며 법률 검증 없이 운영자가 위험을 수용한다(위험과 대응 사항).
- `src/features/fortune/fortune-dev-guide.md`와 이 문서가 다르면 이 문서와 `docs/conventions/`를 따른다. 대표적으로 가이드의 "AI 문구 생성 + 하루 캐시", 가이드 9.4·6.1·6.2의 예시 문장·점수표는 그대로 쓰지 않는다.

## 이용 동의 게이트

사용자 요구(2026-11-05): 법적으로 문제될 부분을 최소화하고, 이용자의 선택에 따라 진행되게 하며, 연령 등에 동의하지 않으면 애초에 운세를 이용할 수 없어야 한다. 법률 확인을 진행하지 않기로 한 결정(결정 사항 7)에 따라 이 게이트는 최소한의 동의 장치로 유지하며, 이용자가 동의하지 않으면 서비스를 제공하지 않는다. 게이트가 위험을 줄이지만 법적 검증을 대신하지는 않는다.

### 적용 범위

- 적용 대상: 운세 기능 화면 전부. 생년월일 입력, 띠·별자리 직접 선택, 오늘의 운세 결과, (2단계) 사주 입력과 결과.
- 적용하지 않는 것: 페이지의 h1, 상시 면책 문구, 설명 콘텐츠, 계산 기준 요약, FAQ, 이용 안내. 이 영역은 동의 여부와 관계없이 보이고 서버 렌더링 HTML에 있다(검색 노출 유지). 운세 허브(`/fortune`)는 이 영역으로만 이뤄지므로 게이트가 없고, 허브 방문은 이용 동의 상태를 만들거나 지우지 않는다. 허브의 링크로 기능 페이지에 가면 그 페이지에서 게이트가 동작한다.
- 한 번 통과하면 운세 화면 전부(오늘의 운세, 띠별, 별자리, 사주)에 적용된다. 화면마다 다시 묻지 않는다(같은 탭 동안 유지).
- 형태(페이지 안에서 기능 영역을 대체할지, 오버레이로 띄울지)는 UI/UX 설계에서 정한다. 어느 형태든 동의 전에는 운세 결과와 입력칸이 화면에 나타나지 않는다.

### 동작

1. 운세 페이지에 들어오면 동의가 없는 상태에서는 기능 영역이 이용 동의 화면으로 대체된다.
2. 이용 동의 화면에는 확인 항목 세 개가 있고, 처음에는 모두 선택되지 않은 상태다. 세 항목을 모두 선택해야 "동의하고 시작"으로 진행할 수 있다.
   - 만 14세 이상입니다.
   - 운세는 오락과 참고를 위한 것이며, 결과를 바탕으로 한 판단과 선택에 대한 책임은 이용자 본인에게 있음을 확인합니다.
   - 입력한 생년월일은 서버로 전송되거나 저장되지 않고 이 브라우저의 메모리에서만 사용됨을 확인합니다.
3. "동의하고 시작"을 누르면 기능 영역(입력·선택·결과)이 나타난다.
4. "동의하지 않음"을 누르면 이용 불가 안내 화면이 나온다. 이 화면에서 운세 결과와 입력칸은 보이지 않는다. 마음이 바뀌면 이용 동의 화면으로 돌아갈 수 있다.
5. 동의 후에도 생년월일을 입력하면 만 14세 미만 확인(생년월일 기반)이 한 번 더 동작한다. 이용 동의의 "만 14세 이상입니다"는 이용자 자기 신고이고, 생년월일 확인은 이를 보완하는 이중 안전장치다.
6. 동의 여부는 분석·알림 이벤트로 보내지 않는다.

### 사실과 일치해야 하는 항목

세 번째 항목("생년월일은 서버로 전송되거나 저장되지 않고 브라우저 메모리에서만 사용")은 실제 구현과 일치해야 한다. 구현이 달라지면(예: 서버 계산, 생년월일 저장) 이 항목과 개인정보처리방침을 먼저 고치고 사용자 승인을 받는다. 이용 동의 상태(동의 여부)를 보관하더라도 생년월일은 저장하지 않으므로 이 항목은 여전히 사실이다.

### 동의 상태 보관 방식 (확정: C안 탭 세션, 설계 D2, 사용자 승인 2026-11-05)

동의 여부는 개인을 식별하는 정보가 아니다. 타로 선례(`docs/tarot/plan.md` 결정 5)는 날짜·카드 번호·방향을 localStorage에 두는 것이 개인정보가 아니고 별도 수집 동의가 필요 없다고 판단했다(법률 확인 없이 위험을 수용한 판단이었다). 이용 동의 상태도 같은 논리를 쓰며, 법률 확인 없이 운영자가 위험을 수용한다(결정 사항 7).

| 방식 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A. 보관 안 함 (채택 안 함) | 페이지를 불러올 때마다 동의 화면을 보여 준다. | 저장 항목이 없다. 선택이 매번 확인된다. | 매 방문 재동의가 번거롭다. 같은 방문 안에서 다른 운세 화면으로 이동해도 다시 묻게 될 수 있다. |
| C. 탭 세션 동안만 보관 (확정) | sessionStorage에 동의 여부를 두고 탭을 닫으면 사라진다. | 방문 동안은 한 번만 묻는다. 저장이 오래 남지 않는다. 로또 AgeGate의 실제 동작과 같다. | 새 탭·재방문마다 다시 묻는다. |
| B. 브라우저에 동의 여부 보관 (제안이었으나 채택 안 함) | localStorage 키 하나에 동의한 문구 버전과 동의일(KST 날짜)만 저장한다. 만료 30일, 문구 버전이 바뀌면 다시 동의받는다. 사용자가 동의를 다시 설정(철회)할 수 있는 링크를 둔다. | 재방문이 편하다. | 저장 항목이 오래 남는다. 개인 식별 정보가 없다는 판단이 더 무겁게 걸린다. |

확정 내용
- 저장소는 sessionStorage이고, 값은 동의 여부(키 존재)·동의 문구 버전·동의 시각뿐이다. 생년월일·태어난 시각·연령 판정 결과·이름은 저장하지 않는다. localStorage와 쿠키에는 운세 키가 새로 생기지 않는다.
- 같은 탭에서는 새로고침이나 다른 운세 페이지 이동 뒤에도 다시 묻지 않는다. 새 탭·새 브라우저 컨텍스트에서는 묻는다. 만료 기간(30일)은 없다.
- 동의 문구 버전이 바뀌면 다시 동의받는다.
- "동의 다시 설정" 버튼을 기능 페이지에 두고(허브에는 없음), 누르면 저장값이 지워져 동의 화면이 나온다.
- 거부(동의하지 않음)는 저장하지 않는다.
- 쿠키 동의 거절과 관계없이 동작한다.
- 동의 화면의 보관 안내 문구는 사용자가 승인한 `ui-ux-design.md`의 확정 문구를 쓴다.

### 검색 노출과의 충돌 가능성 (설계 단계에서 결정 완료)

사용자는 띠·별자리 직접 선택 경로도 동의 게이트 뒤에 두라고 했다. 그러면 다음 충돌 가능성이 생긴다.

- `docs/conventions/seo.md`는 검색에 노출될 핵심 내용을 서버 렌더링 HTML에 두라고 한다. 이 기획서는 설명·면책·FAQ·계산 기준·이용 안내·이용 대상 안내를 게이트와 관계없이 서버 HTML에 둔다(유지).
- 띠별·별자리 페이지의 "오늘의 운세 문구 12개"를 서버 HTML에 둘지가 문제다. 둔다면 동의하지 않은 사용자(JS를 끈 환경 포함)와 검색 엔진에게 결과가 노출되어 게이트의 의도와 어긋나고, 사용자 화면과 크롤러가 보는 내용이 달라 보일 수 있다. 두지 않으면 검색 엔진이 날짜별 운세 본문을 보지 못한다. 기획 기본안은 운세 문구를 서버 HTML에 두지 않는 것이다. 이 경우 검색 유입은 설명 콘텐츠(내 띠·별자리 찾는 법, 계산 기준, FAQ)에 의존한다.
- 게이트를 전체 화면 오버레이로 만들면 검색 엔진의 "방해되는 전면 광고(interstitial)" 평가나 콘텐츠 가림 문제가 생길 수 있다. 형태 선택 시 확인한다.
- 결정(설계 D3, 13.2): 운세 문구는 서버 HTML에 두지 않고, 게이트는 페이지 안에서 기능 영역을 대체하는 방식이다. 설명·면책·FAQ·계산 기준·이용 안내와 허브의 목록은 서버 HTML에 유지한다. 이로써 열린 질문 2는 닫혔다.

## 화면 표기 규칙 (방식별)

방식 A 화면을 "사주 분석"처럼 보이게 하면 오인 소지가 있다(리서치 8.2). 그래서 화면 종류별 표기를 정한다.

| 화면 | 생성 방식 | 써도 되는 이름 | 쓰지 않는 표현 |
|---|---|---|---|
| 오늘의 운세(개인) | A | "오늘의 운세", "생년월일로 보는 오늘의 운세" | 사주 분석, 사주 풀이, 정통, 정확한 맞춤, 전문가 수준, AI 분석 |
| 띠별 운세 | A (띠+날짜 시드) | "띠별 운세", "오늘의 띠별 운세" | 위와 같음 |
| 별자리 운세 | A (별자리+날짜 시드) | "별자리 운세", "오늘의 별자리 운세" | 위와 같음 |
| 운세 허브 | 해당 없음(목록·설명) | "운세", "오늘의 운세·띠별 운세·별자리 운세 모음" | 위와 같음. 방식 A 화면과 같은 "사주" 규칙을 따른다. |
| 사주 | B (만세력 계산 + 십신) | "사주", "사주 분석", "만세력", "오늘의 사주 운세" | 정통, 정확한, 전문가 수준, AI 분석, 평생 운을 알려 줌 |

- A 화면에는 결과 근처에 "생년월일과 날짜를 바탕으로 서비스가 정한 규칙에 따라 문구를 고른 결과이며 사주(태어난 연·월·일·시로 세우는 네 기둥)를 계산한 결과가 아니다"라는 취지의 안내를 둔다(문구 초안은 "고지 문구" 고지 3). 이전의 "사주 풀이가 아닙니다" 표현은 금지 표현 "사주 풀이"에 걸려 이 문장으로 바꿨다((가)안, 결정 사항 17).
- 점수는 "서비스가 정한 규칙으로 만든 수치"이며 정확도나 적중과 연결해 설명하지 않는다.
- 메뉴 라벨, 페이지 title, description, OG, JSON-LD 모두 위 표를 따른다.
- 문구를 AI가 초안으로 작성했더라도 화면에서 "AI가 분석한 운세"처럼 보이게 하지 않는다. 문구의 작성 이력은 `copy-log.md`에 기록한다.

### 용어 사용 규칙: "사주"

금지 표현은 "사주 분석", "사주 풀이", "맞춤 풀이" 같은 특정 구다. "사주"라는 단어 자체가 금지는 아니다. 방식 A 화면(허브 포함)에서 "사주"가 나올 수 있는 범위를 아래로 한정한다.

| 위치 | "사주" 사용 | 근거 |
|---|---|---|
| 방식 A 안내 문장(고지 3과 띠·별자리 변형) | 허용. 정해진 문장 그대로만 쓴다: "…사주(태어난 연·월·일·시로 세우는 네 기둥)를 계산한 결과가 아닙니다." | 방식 A가 사주 계산이 아님을 알려 오인을 막는다. 금지 구("사주 분석", "사주 풀이")를 포함하지 않는다. |
| 방식 A 화면의 FAQ·설명 콘텐츠 중 방식 구분 설명 문장 | 허용. 방식 A는 사주를 계산한 결과가 아니라는 취지의 설명에 한한다. 첫 언급에 괄호 설명(태어난 연·월·일·시로 세우는 네 기둥)을 붙인다. | 같은 이유 |
| 2단계 사주 페이지로 가는 링크·메뉴 라벨(2단계 출시 후) | 허용 | 다른 화면을 안내하는 이름 |
| 방식 A의 운세 문구 풀(점수·항목별 문구, 조언, 주의), 결과 제목, 메타데이터(title, description, OG), JSON-LD | 쓰지 않는다. 단 FAQPage JSON-LD는 화면 FAQ와 같은 내용이어야 하므로 위 FAQ 허용 문장과 같을 때만 허용 | 방식 A 결과가 사주에 기반한다는 인상을 막는다. |
| 방식 B(2단계 사주 화면) | 허용. "사주 분석" 표기도 허용 | 실제로 계산하는 화면 |
| 허브의 사주 소개(2단계 출시 후) | 허용(S2-7 확정, 2026-11-09). 허브 목록의 사주 행 이름·설명과 허브 가이드의 사주 페이지 소개 한 단락, ItemList의 사주 항목 이름에 한한다. 첫 언급에 괄호 설명을 붙인다. 허브 title·description·OG·keywords·Breadcrumb에는 쓰지 않는다. | 허브가 네 번째 운세를 안내하려면 필요 |

- 사주 용어 표기: 사주(四柱)는 연주·월주·일주·시주의 네 기둥을 뜻하므로 "사주 네 기둥", "사주 4기둥"은 같은 말을 겹쳐 쓴 표현이다. 화면 문구에서는 첫 언급에 "사주(태어난 연·월·일·시로 세우는 네 기둥)"로 쓰고, 이후에는 "사주", "연·월·일·시 기둥", "연주·월주·일주·시주"를 쓴다. "사주 네 기둥", "사주 4기둥"은 화면 문구(제목, 설명, 고지, FAQ, 표 캡션)에서 쓰지 않는다. "4기둥", "3기둥"은 이 기획서와 개발 작업의 내부 용어로만 쓴다.
- 이용자에게 보이는 괄호 설명은 "태어난 연·월·일·시로 세우는 네 기둥"으로 통일한다. 괄호 설명을 쓰지 않고 "사주"만 단독으로 처음 언급하는 문장은 방식 A 화면에 두지 않는다.

## 계산 기준과 리서치 보정 4가지

리서치 0장에서 개발 가이드와 달라 보정이 필요하다고 지적한 네 가지를 아래처럼 반영한다.

| 번호 | 보정 | 반영 방식 | 적용 단계 |
|---|---|---|---|
| 1 | 입춘: 날짜가 아니라 시각까지 본다. 입춘은 양력 2월 3~5일에 들고, 2025년은 2월 3일 23시 10분이었다. | 띠(1단계)와 사주 연주·월주(2단계)는 입춘 시각을 기준으로 가른다. 해당 연도에 입춘이 드는 날 출생자에게만 출생 시각을 묻는다. 시각을 입력하면 입춘 전은 전년도 띠, 후는 해당 연도 띠로 판정한다. "시각 모름"이면 두 띠(사주는 두 경우)를 나란히 보여 주고 선택하게 한다. 입춘 시각 값은 천문 자료(한국천문연구원 등)와 대조해 확정한다. | 1, 2 |

기타 계산 정책(개발 가이드 4.5 기준, 모두 확정)
- 날짜 기준: 한국 시간(KST) 자정에 하루가 바뀐다. 사용자 기기의 시간대와 무관하다.
- 일주는 한국 시간 자정에 바뀐다. 시주는 시계 시각으로 판정하며 23:00~00:59를 자시로 본다. 23:00~23:59 출생은 일주가 그날이고 시주 천간만 다음 날 일간 기준으로 구한다(야자시 구분 방식, 결정 사항 9·18). 오늘 일진도 자정에 바뀌며, 접속 시각이 23시대여도 그날 일진을 쓴다. 이 처리 방식과 자시 통합을 쓰지 않는다는 점은 계산 기준 화면에 밝힌다.
- 시간 모름: 시주 없이 3기둥으로 계산하고 결과에 안내한다.
- 지원 출생 연도: 1920년 1월 1일부터 2028년 12월 31일까지이며 한국 시간 기준 오늘 이전이어야 한다(결정 사항 10, 설계 D14). KASI 24절기 제공 범위(1920~2028년)에 맞춘 것이다. 음력 입력은 양력으로 환산한 날짜로 판단한다. 범위를 벗어나면 지원 범위 안내를 보이고 결과를 내지 않는다. 2029년 이후 출생은 절기 데이터 보완(F-1) 뒤에 늘린다. 사주(2단계)도 같은 범위다.
- 만 나이는 한국 시간 기준 오늘 날짜와 양력으로 환산한 생년월일(연·월·일 전체)로 계산한다.
- 계산 기준 화면: 입춘 시각 기준, 절기 월 기준(2단계), 별자리 경계 시각 기준, 자시 처리(일주는 자정, 시주는 23:00부터 자시, 23시대는 시주 천간만 다음 날 일간 기준), 자시 통합을 쓰지 않는다는 점, 출생지 보정 안 함, 표준시·서머타임 보정 안 함과 안내, 지원 출생 연도(1920-01-01 ~ 2028-12-31), "학파마다 기준이 다르며 이 서비스의 기준"이라는 문장을 한곳에서 볼 수 있어야 한다.
- 검산: 2000-01-01의 일주는 무오(리서치 0장의 검산). 개발 중 알려진 날짜 여러 건으로 일주·연주·월주를 재검증한다.
- 용어 정리(R-1 반영, 후속 문서가 같은 말을 쓰도록 정한다)
  - 야자시: 자정 이전의 자시(23:00~23:59). 조자시: 자정 이후의 자시(00:00~00:59).
  - 야자시 구분 방식(채택, 설계의 `next-day`): 일주는 자정에 바뀐다. 23시대는 일주가 그날이고 시주 천간만 다음 날 일간으로 구한다. 00시대는 일주·시주 모두 그날 기준이다.
  - 자시 통합(미채택): 자시가 시작되는 23시에 일주가 다음 날로 바뀐다. "정자시"는 이 방식과 자정(子正)을 모두 가리키는 데 쓰여 혼란이 있으므로 기획·설계·화면에서 쓰지 않는다.
  - `same-day`(23시대 시주 천간도 그날 일간으로 구함): 학파로 확인되지 않아 채택하지 않는다. 내부 값 이름이며 화면에 쓰지 않는다.

| 십신 이름과 한 줄 설명 | 필수(2단계) | 사주 화면에서 오늘 일진과의 관계 표시 |
| 시간대별 운세, 바이오리듬, 캘린더 | 이후 | |

- 같은 사람이 "띠 운세"와 "개인 운세"에서 서로 다른 점수를 받을 수 있다. 두 운세가 다른 기준이라는 한 줄 안내를 둔다.
- 건강운은 병명·증상·약을 쓰지 않고 휴식·생활 리듬 같은 일반 표현만 쓴다. 재물운은 투자·주식·코인·복권·도박을 권하지 않고 지출 점검·정리 같은 표현만 쓴다.

## 콘텐츠 제작 원칙

작성 방식은 타로와 같다. AI(Claude)가 개발 중에 문구 초안을 쓰고 사용자가 검수하며, 확정된 문구는 정적 데이터로 코드에 지정해 쓴다. 사용자가 접속한 시점에 AI를 호출하지 않는다(결정 사항 3). 이 방식은 AI가 타 사이트·책의 문장을 따라 쓸 위험과 AI 생성물의 권리 귀속이 불확실하다는 위험을 안고 있으므로, 아래 생성 지침·기록·점검 절차를 완료 조건(AC-40, AC-41)으로 둔다.

- 문구 풀(방식 D): 조건별(띠 / 별자리 / 개인 일운 / 십신, 항목, 점수 구간)로 작성한 문구를 시드로 고른다. 같은 입력이면 같은 날 같은 결과가 나온다.
- 규모(변형 수 3으로 확정, 결정 사항 4)

| 문구 묶음 | 계산 | 문구 수 | 단계 |
|---|---|---|---|
| 개인 일운 | 항목 5 × 점수 구간 3 × 변형 3 + 요약·조언·주의 등 | 약 100 | 1 |
| 띠 | 12 × 항목 5 × 구간 3 × 변형 3 | 540 | 1 |
| 별자리 | 12 × 항목 5 × 구간 3 × 변형 3 | 540 | 1 |
| 십신 | 10 × 항목 5 × 구간 3 × 변형 3 | 450 | 2 |
| 행운 요소 설명, 안내, 동의 화면, FAQ, 가이드 본문 | 별도 | 수십~백여 | 1, 2 |

  1단계만 해도 1,200문장 안팎이다. 예시 계산이며 설계·작성 과정에서 조금 달라질 수 있다.

- AI 생성 지침 (작성 시 반드시 지킨다. 지침은 `docs/fortune/copy-log.md` 첫머리에도 적는다)
  1. 카드 의미·십신 관계·오행 상생상극·절기처럼 이론 수준의 아이디어만 바탕으로 처음부터 새로 쓴다.
  2. 작성 중에는 타 사이트·책·앱·언론사 운세의 풀이 문장을 보지 않고, 웹에서 풀이 문장을 찾아 참조하지 않으며, 그런 문장을 AI 입력으로 붙여 넣지 않는다.
  3. 번역, 어순 변경, 일부 단어 교체로 만든 문장을 쓰지 않는다. 개발 가이드의 예시 문장(6.1의 분위기 예시, 9.3의 요약 문장)도 그대로 쓰지 않는다.
  4. 정해진 구조(조건별 묶음, 점수 구간, 변형 수)대로 쓰고, 문장 끝이 반복되지 않게 변주한다.
  5. 합니다체와 "금지 표현 목록", "문구 안전 원칙", "용어 사용 규칙: 사주"를 따른다. 건강·재물·애정 문구의 제한(결과 항목 장)을 따른다.
  6. 묶음마다 작성 주체(AI), 작성일을 기록한다.
- 제작 순서(타로 선례): (1) 각 묶음의 샘플 작성(개인 일운 전체 항목, 띠 1개, 별자리 1개, 2단계에서는 십신 2~3개) → (2) 사용자 검수와 톤 수정 → (3) 확정된 톤으로 나머지 작성 → (4) 완성 후 유사 문장 점검 → (5) 기록 갱신.
- 문구 점검 기록(copy-log): `docs/fortune/copy-log.md`에 타로 `docs/tarot/copy-log.md`와 같은 형식으로 둔다. 묶음별 작성자·작성일·검수자·검수일·상태·웹 검색 샘플 확인 결과를 남긴다.
- 유사 문장 점검 절차
  1. 작성 중: 위 생성 지침 2번대로 외부 문장을 참조하지 않는다.
  2. 완성 후: 대표 문장을 따옴표로 묶어 웹 검색해 같은 문구가 있는지 확인한다. 전수 검사가 아니며 한계를 기록한다. 샘플 규모는 묶음(개인·띠·별자리·십신)별 20문장 이상, 행운·조언·주의 10문장 이상, 고지·FAQ·가이드 10문장 이상이다.
  3. 같거나 거의 같은 문장이 나오면 새로 쓰고 기록에 "수정함"으로 남긴다.
  4. 한 풀 안에서 서로 거의 같은 문장이 반복되지 않는지 훑어본다(QA 또는 검증 단계).
  5. 점검 결과(일치 없음 / 일치 없음(일반 어구) / 수정함)와 점검일을 기록한다.
- 권리 귀속: AI가 작성한 문구의 저작권 귀속은 한국에서 불명확하다. 위험 항목으로 남기고(위험과 대응 사항), 작성자(AI)와 검수자(사용자)를 기록한다.
- 톤: 합니다체로 통일한다("~일 수 있습니다", "~해 보는 것도 방법입니다"). 단 FAQ 질문 문장은 의문형 "~나요?" 또는 "~입니까?"를 허용하고, 답변과 그 밖의 서술 문구는 합니다체를 쓴다(AC-38). 버튼 라벨은 명사형이다. 단정·과장·공포 조장을 쓰지 않는다. 금지 표현은 "금지 표현 목록"을 따른다.
- 이미지·아이콘: 외부 일러스트, 이모지 이미지, 외부 아이콘 세트를 새로 들이지 않는다. 띠·별자리 표시는 글자 중심으로 하거나 자체 제작 SVG를 쓴다. 이미 프로젝트에 있는 아이콘 라이브러리를 쓸 때도 라이선스를 확인한다. `alt`는 새로 쓴다. 한자를 표시하는 데 새 글꼴이 필요하면 포함한다. 외부 자산을 추가하면 `THIRD_PARTY_NOTICES.md`를 갱신한다.
- 라이브러리·데이터: 음력 변환과 절기는 새 라이브러리 없이 KASI 공공데이터 기반 정적 표로 처리한다(설계 D1). 따라서 `DEPENDENCY_LICENSES.md`는 바뀌지 않고 `THIRD_PARTY_NOTICES.md`에 외부 데이터 출처(한국천문연구원)를 기록한다. 다른 새 라이브러리를 쓰게 되면 두 문서를 같은 작업에서 갱신한다. KASI 이용허락범위는 "제한 없음"으로 확인했고 약관 전문은 확인하지 못했다(위험 수용).
- 명칭: 띠는 쥐, 소, 호랑이, 토끼, 용, 뱀, 말, 양, 원숭이, 닭, 개, 돼지. 별자리는 염소자리, 물병자리, 물고기자리, 양자리, 황소자리, 쌍둥이자리, 게자리, 사자자리, 처녀자리, 천칭자리, 전갈자리, 사수자리를 대표 표기로 쓰고, 설명 콘텐츠에서 "궁수자리"로도 불린다고 언급할 수 있다(결정 사항 13). 한자는 1단계 화면에 쓰지 않고, 2단계 사주 기둥 표에서만 한글과 병기한다.
- 서비스명·설명에 "점신", "포스텔러" 등 타 서비스명을 쓰지 않는다.

## 유저 스토리

- US-1: 오늘 하루가 궁금한 방문자로서 로그인 없이 생년월일만 넣고 오늘의 운세를 보고 싶다. 왜냐하면 출근 전에 가볍게 확인하고 싶기 때문이다.
- US-2: 같은 날 다시 방문한 사용자로서 같은 생년월일이면 어느 기기에서나 같은 결과가 나오길 원한다. 왜냐하면 새로고침할 때마다 결과가 바뀌면 의미가 없기 때문이다.
- US-3: 내 띠나 별자리만 알고 싶은 사용자로서 생년월일 없이 12개 중 하나를 골라 오늘의 운세를 보고 싶다. 왜냐하면 정보를 입력하고 싶지 않을 수 있기 때문이다.
- US-4: 내 띠가 헷갈리는 1~2월생으로서 입춘과 설날 중 어느 기준인지 알고, 다른 기준의 결과도 보고 싶다. 왜냐하면 주변에서 말하는 띠와 달라 혼란스럽기 때문이다.
- US-5: 별자리 경계일에 태어난 사용자로서 시각까지 반영한 별자리를 확인하고 싶다. 왜냐하면 사이트마다 별자리가 다르게 나오기 때문이다.
- US-6: 음력 생일을 쓰는 사용자로서 음력 생년월일을 그대로 입력하고 양력으로 바뀐 결과를 확인하고 싶다. 왜냐하면 양력 생일을 잘 모르기 때문이다.
- US-7: 개인정보가 걱정되는 사용자로서 입력한 생년월일이 서버로 전송되거나 저장되지 않는다는 점을 확인하고 싶다. 왜냐하면 생년월일이 다른 정보와 결합되면 개인정보가 될 수 있기 때문이다.
- US-8: 운세를 가볍게 즐기는 사용자로서 과장되거나 겁을 주는 말 없이 부드러운 문장으로 결과를 읽고 싶다. 왜냐하면 불안해지는 표현은 하루를 망치기 때문이다.
- US-9: 마음이 힘든 사용자로서 필요할 때 상담전화 정보를 보고 싶다. 왜냐하면 운세로 해결할 수 없는 상황일 수 있기 때문이다.
- US-10: 사주에 관심 있는 사용자로서(2단계) 내 사주(태어난 연·월·일·시로 세우는 네 기둥)와 오늘 일진과의 관계로 오늘의 운세를 보고, 어떤 기준으로 계산했는지 알고 싶다. 왜냐하면 서비스마다 결과가 달라 기준을 알아야 하기 때문이다.
- US-11: 태어난 시간을 모르는 사용자로서(2단계) 시간 없이도 사주를 보고 싶다. 왜냐하면 시간을 모르는 사람이 많기 때문이다.
- US-12: 검색으로 들어온 방문자로서 "오늘의 운세", "띠별 운세", "별자리 운세"를 검색해 바로 이 페이지에서 보고 싶다. 왜냐하면 가입 없이 쓰고 싶기 때문이다.
- US-13: 행운 숫자가 궁금한 사용자로서 숫자가 로또 당첨과 관계없다는 점을 분명히 알고, 원하면 로또 번호 생성기로 이동하고 싶다. 왜냐하면 오해 없이 재미로만 즐기고 싶기 때문이다.
- US-14: 쿠키 동의를 거절한 방문자로서 광고·분석 쿠키에 동의하지 않아도 운세를 이용하고 싶다. 왜냐하면 광고와 분석에 동의하지 않을 뿐 기능은 쓰고 싶기 때문이다.
- US-15: 서비스 운영자로서 모든 문구가 처음부터 새로 쓰였고 유사 문장을 점검했다는 기록을 남기고 싶다. 왜냐하면 저작권 분쟁을 피하고 광고 정책 점검에 대응해야 하기 때문이다.
- US-16: 만 14세 미만 어린이(또는 보호자)로서 이 서비스가 만 14세 이상을 대상으로 한다는 점을 분명히 알고 싶다. 왜냐하면 이용 조건을 모르고 들어왔다가 막히면 이유를 알 수 없기 때문이다.
- US-17: 만 14세 이상 이용자로서 운세가 오락과 참고용이고 결과를 바탕으로 한 판단과 선택은 내게 있다는 점을 쉬운 문장으로 확인하고 싶다. 왜냐하면 운세를 어디까지 믿고 써야 하는지 알고 이용하고 싶기 때문이다.
- US-18: 이용자로서 이용 조건을 읽고 내가 직접 동의를 선택한 뒤에 운세를 시작하고 싶다. 왜냐하면 내 생년월일이 어떻게 쓰이는지와 결과의 성격을 알고 쓰고 싶기 때문이다.
- US-19: 동의하지 않은 이용자로서 이용할 수 없다는 사실과 이유를 분명히 알고, 마음이 바뀌면 다시 동의 화면으로 돌아가고 싶다. 왜냐하면 아무 설명 없이 빈 화면이 나오면 오류로 오해하기 때문이다.
- US-20: 서비스 운영자로서 이용자가 이용 조건에 동의하지 않으면 운세 기능이 열리지 않게 하고 싶다. 왜냐하면 법적으로 문제될 부분을 최소화하고 이용자의 선택에 따라 진행되게 하고 싶기 때문이다.
- US-21: 사주가 무엇인지 잘 모르는 일반 이용자로서 오늘의 운세가 사주를 계산한 결과가 아니라는 안내를 읽을 때 사주가 무엇인지도 한 번에 알고 싶다. 왜냐하면 모르는 용어가 들어간 안내는 오히려 혼란스럽기 때문이다.
- US-22: 운세 메뉴를 처음 누른 방문자로서 오늘의 운세, 띠별 운세, 별자리 운세 중 무엇이 있는지 한 화면에서 보고 고르고 싶다. 왜냐하면 어떤 운세가 내게 맞는지 모르기 때문이다.
- US-23: 띠·별자리 운세를 보던 사용자로서 내 생년월일 기준 오늘의 운세로 바로 이동하고 싶다. 왜냐하면 같은 띠·별자리 공통 운세보다 내 생일로 본 운세가 궁금해질 수 있기 때문이다.
- US-24: 컴퓨터와 휴대전화를 함께 쓰는 사용자로서 상담전화 번호를 휴대전화에서는 눌러서 걸고, 컴퓨터에서는 글자로 읽거나 복사하고 싶다. 왜냐하면 컴퓨터에서는 전화 앱이 갑자기 열리는 것이 불편하기 때문이다.
- US-25: 사주를 세워 본 사용자로서 밤 11시대에 태어났을 때 이 서비스가 날짜와 시주를 어떤 기준으로 정했는지 알고 싶다. 왜냐하면 만세력마다 결과가 달라 기준을 모르면 틀렸다고 오해하기 때문이다.
- US-26: 허브에서 운세 목록을 보는 방문자로서 사주가 다른 세 운세와 어떻게 다른지(계산 대 문구 선택) 알고 싶다. 왜냐하면 무엇을 고를지 판단하고 싶기 때문이다.

## 완료 조건 (AC)

QA가 이 목록으로 Playwright 테스트를 만든다. 화면에서 확인할 수 있는 문장으로 쓴다.

QA 메모
- 화면 문구를 인용한 AC는 문구 일치가 아니라 의미 기준으로 검사한다. 확정 문구는 `docs/fortune/ui-ux-design.md`를 따른다. 단 방식 A·B 안내 문구와 "사주" 사용 범위(AC-10, AC-37, AC-58)는 이 기획서의 고지 3·4와 "용어 사용 규칙: 사주"가 기준이다.
- 시간이 걸린 AC는 브라우저 시계 조작(`page.clock`)과 시간대 설정(`timezoneId`)으로 검증한다.
- 날짜·시각 사례는 리서치 문서의 단일 출처 값이거나 기획자의 직접 계산이다. 개발 단계에서 천문 자료와 만세력으로 재검증하고, 값이 다르면 기획자에게 알려 AC를 고친다.
- AC-1~AC-48 중 결과를 보는 AC는 모두 이용 동의 게이트를 통과한 상태에서 검사한다(동의 상태를 만드는 헬퍼를 쓴다). 이용 동의 게이트 AC는 AC-67~AC-78에 있다.
- 1단계 AC는 AC-1~AC-48, AC-67~AC-78(사주 화면 적용은 2단계), AC-79~AC-86이고, 2단계 AC는 AC-49~AC-60과 AC-87~AC-91, 검색 노출 AC는 AC-61~AC-66이다.
- 동의 상태 보관 방식은 탭 세션(sessionStorage)으로 확정되었다. AC-29·AC-74·AC-75·AC-78은 이 기준으로 검사한다. 동의 상태 헬퍼는 sessionStorage에 값을 넣는다.

오늘의 운세 (`/fortune/today`, 1단계)
- AC-1: 로그인 없이 접속해 이용 동의를 마치고 양력 생년월일을 입력하면 결과가 나온다. 결과에는 총운 점수와 한 줄 요약, 재물·애정·직장·학업·건강 문구와 점수, 행운의 색·숫자·방향, 오늘의 조언, 주의할 점이 있다.
- AC-2: 같은 생년월일로 새로고침하거나 새 브라우저 컨텍스트에서 다시 입력해도 같은 날이면 같은 결과가 나온다.
- AC-3: 사용자 기기 시간대가 한국이 아니어도 화면의 기준 날짜는 한국 날짜이고 "한국 시간 기준"이라는 안내가 있다. 시계를 한국 시간 자정 직전에서 직후로 넘기면 기준 날짜가 바뀐다.
- AC-4: 같은 생년월일로 연속 7일을 확인하면 총운 점수가 모두 같지는 않다.
- AC-5: 모든 점수는 30~95 범위의 정수다. 점수 구간(상·중·하)에 맞는 문구가 나온다.
- AC-6: 행운의 숫자는 1~2개이고 1~10 범위다.
- AC-7: 생년월일이 같으면 양력으로 입력하든 같은 날의 음력으로 입력하든 같은 결과가 나온다. 음력 2025-01-01을 입력하면 양력 2025-01-29로 바뀐 것을 확인용으로 보여 준다. 음력 2000-01-01은 양력 2000-02-05다.
- AC-8: 음력 입력에서 그해 그 달에 윤달이 없으면 윤달을 선택할 수 없다(선택칸이 비활성). 윤달이 있는 달에서는 윤달 선택 안내가 보인다. 음력에 없는 날(예: 29일까지인 달의 30일)을 입력하면 오류 안내가 나오고 결과가 나오지 않는다.
- AC-9: 존재하지 않는 날짜(2월 30일), 미래 날짜, 1920년 이전 날짜, 2029-01-01 이후 날짜(음력 입력이면 양력으로 환산한 날짜 기준)를 입력하면 안내가 나오고 결과가 나오지 않는다. 지원 범위를 벗어난 날짜의 안내에는 지원 범위(1920-01-01 ~ 2028-12-31)가 들어 있다. 출생 연·월·일 중 하나라도 비어 있으면 결과가 나오지 않는다.
- AC-10: 결과 근처에 고지 3의 방식 A 안내가 있다. 그 안내는 이 서비스의 결과가 사주(태어난 연·월·일·시로 세우는 네 기둥)를 계산한 결과가 아니라는 뜻이며, 괄호 설명이 함께 보인다. 이 페이지 어디에도 "사주 분석", "사주 풀이", "정통", "정확한 맞춤"이 없다. 이 페이지에서 "사주"가 들어간 문장은 고지 3 안내와 FAQ의 방식 구분 설명 문장(용어 사용 규칙 표의 허용 위치)뿐이고, 운세 문구·결과 제목·메타데이터에는 "사주"가 없다. 허브(`/fortune`)도 같은 규칙을 따른다(허브 설명·FAQ에서는 방식 구분 설명 문장에만 쓰고 허브 메타데이터·JSON-LD에는 쓰지 않는다).
- AC-11: 결과 영역에서 띠별 운세·별자리 운세 페이지로 가는 링크가 있다.

띠별 운세 (1단계)
- AC-12: 이용 동의를 마친 뒤 띠별 페이지에 12띠 모두의 오늘 운세(총운 + 항목별 문구)가 있다. 이용 동의 전에는 화면에 운세 문구가 없다.
- AC-13: 이용 동의를 마친 뒤 12띠 중 하나를 선택해 그 띠의 운세를 볼 수 있다. 생년월일 없이 쓸 수 있다.
- AC-14: 내 띠 찾기: 1990-06-15는 말띠, 1992-05-10은 원숭이띠로 나온다.
- AC-15: 입춘 전·설날 후 출생자: 2025-02-01을 입력하면 용띠로 나오고 "설날 기준으로는 뱀띠"라는 안내가 함께 보인다.
- AC-16: 입춘이 드는 날 출생자: 2025-02-03을 입력하면 태어난 시각 입력칸이 나온다. 23:09는 용띠, 23:30은 뱀띠로 나온다. "시각 모름"을 고르면 두 띠가 함께 보이고 선택할 수 있다. 2025-02-04는 시각 입력칸 없이 뱀띠로 나온다.
- AC-17: 화면에 띠 기준(입춘 시각 기준)과 "설날 기준과 다를 수 있다"는 안내가 있다.
- AC-18: 같은 날 같은 띠의 운세는 누가 어느 기기에서 열어도 같다. 날짜가 바뀌면 바뀔 수 있다.
- AC-19: 띠 운세 페이지에 "개인 운세와 다른 기준"이라는 안내가 있다. 띠 운세 페이지의 방식 A 안내는 고지 3의 띠 변형이며 AC-10과 같은 "사주" 사용 조건을 지킨다.

별자리 운세 (1단계)
- AC-20: 이용 동의를 마친 뒤 별자리 페이지에 12별자리 모두의 오늘 운세가 있다. 이용 동의 전에는 화면에 운세 문구가 없다.
- AC-21: 이용 동의를 마친 뒤 12별자리 중 하나를 선택해 볼 수 있고 생년월일 없이 쓸 수 있다.
- AC-22: 내 별자리 찾기: 1990-05-15는 황소자리, 1990-08-10은 사자자리, 2026-03-10은 물고기자리로 나오고 시각 입력칸이 없다.
- AC-23: 경계일 출생자: 2026-03-20을 입력하면 시각 입력칸이 나온다. 23:00은 물고기자리, 23:59는 양자리로 나온다. "시각 모름"이면 두 별자리가 함께 보인다. (근거: 2026년 양자리는 3월 20일 23시 46분 시작이라는 단일 출처 값)
- AC-24: 2027-03-21은 시각 입력칸이 나오고 04:00은 물고기자리, 06:00은 양자리다. 2027-03-20은 시각 입력칸 없이 물고기자리다. (근거: 2027년 양자리는 3월 21일 05시 25분 시작이라는 단일 출처 값)
- AC-25: 음력으로 입력한 경계일 출생자는 양력 변환 뒤 같은 방식으로 판정된다.
- AC-26: 화면의 별자리 기간 안내에 "해마다 하루 정도 달라질 수 있다"가 있다. 별자리 페이지의 방식 A 안내는 고지 3의 별자리 변형이며 AC-10과 같은 "사주" 사용 조건을 지킨다.

개인정보·저장
- AC-27: 생년월일과 태어난 시각 입력 및 결과 확인 중 발생하는 모든 네트워크 요청(URL, 쿼리, 본문, 헤더)에 입력한 생년월일·시각이 포함되지 않는다. 분석·알림 이벤트에도 없다.
- AC-28: 주소창 URL(쿼리, 해시 포함)에 입력값이 들어가지 않는다.
- AC-29: 결과를 본 뒤 localStorage, sessionStorage, 쿠키를 열어도 입력한 생년월일·시각이 없다. 운세 때문에 새로 생긴 키는 sessionStorage의 이용 동의 상태 키 하나 이하이고, localStorage와 쿠키에는 운세 키가 새로 생기지 않는다. 그 값에는 동의 여부(키 존재)·문구 버전·동의 시각 외의 값(생년월일, 시각, 연령 판정, 이름)이 없다. 기존 쿠키 동의 키는 제외한다.
- AC-30: 입력 후 새로고침하거나 다른 페이지로 갔다 돌아오면 입력칸이 비어 있다.
- AC-31: 입력칸 근처에 "서버로 전송되거나 저장되지 않는다"는 안내, "운세는 만 14세 이상 이용자를 대상으로 한다"는 안내, 오락·참고용이며 결과를 바탕으로 한 판단과 선택은 이용자 본인에게 있다는 책임 관련 고지가 있다. 이름·연락처 같은 입력칸이 없다.
- AC-32: 쿠키 동의(광고·분석)를 거절해도 이용 동의 게이트를 통과하면 모든 운세 기능이 정상 동작한다. 쿠키 동의 상태는 이용 동의 화면의 표시 여부에 영향을 주지 않고, 이용 동의는 쿠키 동의 상태를 바꾸지 않는다.

고지·안전·문구

- AC-62: JS를 끈 서버 HTML에 설명 콘텐츠(사용법, 계산 기준 요약, FAQ, 상시 면책, 이용 대상 안내)가 이용 동의 여부와 관계없이 있다. 허브도 포함한다(설명, FAQ, 상시 면책, 이용 안내. 허브에는 입력이 없으므로 입력 영역 안내는 요구하지 않는다). 사용자별 개인 결과와 오늘의 운세 문구(점수·항목별 문구)는 서버 HTML에 없다(설계 D3로 확정).
- AC-63: 허브를 포함해 각 페이지에 `h1`이 하나뿐이다. 이미지에는 새로 쓴 `alt`가 있다.
- AC-64: BreadcrumbList와 FAQPage JSON-LD가 있고 FAQ 내용이 화면과 같다. BreadcrumbList의 "운세" 단계 URL은 `/fortune`이다(기능 페이지는 홈 > 운세 > 페이지, 허브는 홈 > 운세 2단계). 허브에는 운세 페이지 목록을 담은 ItemList JSON-LD가 추가로 있다. 리뷰·평점 구조화 데이터가 없다.
- AC-65: `/sitemap.xml`에 `/fortune`, `/fortune/today`, `/fortune/tti`, `/fortune/star-sign`이 있고, 아직 출시하지 않은 페이지(2단계 `/fortune/saju` 등)는 없다.
- AC-66: 데스크톱과 모바일 모두 이용 동의 → 입력 → 결과 확인까지 끊김 없이 된다.

이용 동의 게이트 (1단계, 사주 화면 적용은 2단계)
- AC-67: 이용 동의 상태가 없는 브라우저에서 오늘의 운세, 띠별 운세, 별자리 운세 페이지(2단계에서는 사주 포함)를 열면 기능 영역 대신 이용 동의 화면이 나온다. 생년월일 입력칸, 12띠·12별자리 선택·결과, 총운 점수와 운세 문구가 화면에 없다. h1, 상시 면책 문구, 설명 콘텐츠는 보인다. 허브 `/fortune`에는 이용 동의 화면이 나오지 않는다(AC-79).
- AC-68: 이용 동의 화면에 확인 항목 세 개(만 14세 이상 / 오락·참고용이며 결과를 바탕으로 한 판단과 선택에 대한 책임은 본인에게 있음 / 생년월일은 서버로 전송·저장되지 않고 브라우저 메모리에서만 쓰임)가 있고, 처음에는 모두 선택되지 않은 상태다.
- AC-69: 세 항목을 모두 선택하기 전에는 진행할 수 없다(버튼이 비활성이거나, 눌러도 진행되지 않고 선택이 필요하다는 안내가 나온다). 한두 항목만 선택해도 진행되지 않는다.
- AC-70: 세 항목을 모두 선택하고 "동의하고 시작"을 누르면 기능 영역이 나타나고 입력·선택이 가능해진다.
- AC-71: "동의하지 않음"을 누르면 이용 불가 안내 화면이 나온다. 이 화면에는 운세 결과와 입력칸이 없고, 이용할 수 없는 이유와 이용 동의 화면으로 돌아가는 방법이 있다. 돌아가기를 누르면 이용 동의 화면이 다시 나온다.
- AC-72: 이용 동의 전에는 DOM에 운세 결과(점수, 운세 문구)와 생년월일 입력칸이 없다. 동의 전에 입력·결과 요청이나 계산이 일어나지 않는다. JS를 끈 서버 HTML에는 운세 결과가 없고 "운세 이용에는 JavaScript가 필요합니다" 안내가 있다.
- AC-73: 이용 동의 화면과 이용 불가 안내 화면의 문구는 합니다체이고 "금지 표현 목록"에 걸리지 않으며, 동의가 법적 책임을 모두 없애 준다는 뜻으로 읽히는 표현이 없다. 합니다체의 예외(버튼 라벨 같은 명사형, FAQ 질문 문장의 의문형)는 AC-38을 따른다. 동의 여부(동의함·동의하지 않음)가 분석·알림 이벤트로 전송되지 않는다.
- AC-74: 이용 동의 상태는 탭 세션(sessionStorage)에 보관된다. 같은 탭에서는 새로고침하거나 다른 운세 페이지로 이동해도 다시 묻지 않는다. 새 탭이나 새 브라우저 컨텍스트에서는 묻는다. 동의 문구 버전이 바뀌면 다시 묻는다. 만료(30일) 검사는 없다. "동의하지 않음"은 저장되지 않는다.
- AC-75: 한 번 이용 동의를 통과하면 같은 탭에서 오늘의 운세, 띠별, 별자리, (2단계) 사주 화면에서 다시 묻지 않는다. 기능 페이지에 "동의 다시 설정" 링크가 있고, 누르면 저장된 동의 상태(키)가 지워져 이용 동의 화면이 나온다. 허브에는 이 링크가 없다.
- AC-76: 이용 동의를 통과한 뒤에도 생년월일을 입력하면 만 14세 미만 차단(AC-42~AC-47)이 그대로 동작한다. 이용 동의의 "만 14세 이상입니다"를 선택했어도 만 14세 미만 생년월일을 입력하면 결과가 나오지 않는다.
- AC-77: 이용 동의 화면과 이용 불가 안내 화면, 이용 동의 항목 안내는 모바일과 데스크톱에서 키보드만으로 선택·진행·돌아가기를 할 수 있고, 항목의 선택 상태와 진행 불가 이유가 화면 읽기 도구로 전달된다.
- AC-78: 저장소(sessionStorage)에는 동의 여부·문구 버전·동의 시각만 있고 생년월일·시각·연령 판정이 없다(AC-29와 같은 조건). 쿠키 동의 배너와 이용 동의 화면이 동시에 떠도 서로를 가려 진행이 막히지 않는다.

운세 허브와 링크 (1단계)
- AC-79: `/fortune` 허브가 있다. h1 "운세"와 오늘의 운세(`/fortune/today`)·띠별 운세(`/fortune/tti`)·별자리 운세(`/fortune/star-sign`)로 가는 링크가 이용 동의 여부와 관계없이 보이고 JS를 끈 서버 HTML에도 있다. 허브에는 이용 동의 화면, 생년월일 입력칸, 띠·별자리 선택, 점수, 운세 문구가 서버 HTML과 DOM 어디에도 없다.
- AC-80: 1단계 출시 상태에서 허브, 헤더·모바일 메뉴, sitemap 어디에도 `/fortune/saju` 링크가 없다(2단계 출시 때 함께 나타난다).
- AC-81: `/fortune/tti`와 `/fortune/star-sign`에 "생년월일로 보는 오늘의 운세"(의미 기준) 링크가 하나 있고, 동의 전에도 보이며 JS를 끈 서버 HTML에도 있다. href는 쿼리·해시 없는 `/fortune/today`다.
- AC-82: AC-81 링크를 누르면 `/fortune/today`로 이동한다. 같은 탭에서 이미 동의했으면 동의 화면 없이 입력 폼이 나오고, 동의 전이면 동의 화면이 나온다.
- AC-83: 허브 방문은 이용 동의 상태를 만들거나 지우지 않는다(방문 전후 sessionStorage의 운세 키가 같다). 허브에는 "동의 다시 설정"이 없다.

지원 출생 연도와 윤달 (1단계)
- AC-84: 기기 시계를 2029-01-02(KST)로 맞춰도 오늘의 운세(개인 일운)·12띠 목록·12별자리 목록은 동의 후 정상 결과를 보이고, 연도 입력 상한은 2028이다. 내 띠·내 별자리 찾기는 1920~2028년 출생에 대해 정상 판정한다.
- AC-85: 음력 입력에서 윤달이 있는 달(예: 2023년 2월)은 평달과 윤달이 서로 다른 양력 날짜로 변환되고, 확인 줄에 "(윤달)"이 표시된다.

상담전화 표시 (1단계)
- AC-86: 운세 네 페이지(허브 포함)에서, JS를 켜든 끄든 같은 결과로: 터치 기기(모바일)는 상담전화 다섯 곳이 보이는 `tel:` 링크이고 각 터치 영역이 44px 이상이다. 마우스 환경(PC)은 다섯 번호가 링크가 아닌 글자로 보이고, 마우스 클릭이나 키보드(Tab·Enter)로 통화 앱이 열리지 않으며, Tab 순서에 번호가 없고, 번호를 선택해 복사할 수 있다. 두 환경 모두 각 번호가 화면 읽기 도구에 한 번만 읽힌다. 하이드레이션 오류가 없다.

사주 2단계 추가 (4차 명확화)
- AC-87: 사주 페이지에서도 1단계 장치가 같다. 같은 탭에서 이미 동의했으면 동의 화면 없이 입력 폼이 나오고(AC-75), 사주 방문으로 동의 문구 버전이 바뀌지 않는다. "동의 다시 설정"이 있다. 상담전화 다섯 곳이 AC-86과 같은 조건으로 보인다(운세 다섯 페이지: 허브, 오늘의 운세, 띠별, 별자리, 사주). 행운 숫자를 보이면 로또 고지가 AC-35와 같이 보인다.
- AC-88: 2단계 출시 상태에서 허브 목록(서버 HTML 포함), 헤더·모바일 메뉴 운세 그룹, sitemap에 `/fortune/saju`가 있다(AC-65·AC-80은 1단계 출시 상태 기준이며 이 AC가 2단계에서 대체한다). 허브 설명과 FAQ가 운세가 세 가지라고 말하지 않고, 오늘의 운세·띠별·별자리는 문구 선택 방식이고 사주는 만세력 계산 방식이라는 차이를 서버 HTML에서 읽을 수 있다. 허브 title·description·OG·keywords·BreadcrumbList에는 "사주"가 없다. 허브 ItemList에는 사주 항목이 있다(AC-10 허브 JSON-LD 줄의 예외, S2-6 확정). 오늘의 운세·띠별·별자리 페이지는 1단계와 같고 AC-10을 그대로 통과한다.
- AC-89: 사주 페이지에 noindex가 없고 title, description, canonical, OG가 있다. BreadcrumbList(홈 &gt; 운세 &gt; 사주)와 화면 FAQ와 같은 FAQPage JSON-LD가 있고 h1이 하나다. JS를 끈 서버 HTML에 설명(첫 언급에 괄호 설명), 사용법, 계산 기준(AC-56), 시간 모름 안내, 오늘의 운세와의 차이, FAQ(사주란 무엇인가요 / 태어난 시간을 모르면 / 계산 기준은 / 23시 이후 출생은 / 평생 운이나 성격도 알 수 있나요), 면책, 이용 대상 안내가 있고 약 600자 이상이다. 기둥 표·십신·점수 등 개인 결과는 서버 HTML에 없다. "사주 네 기둥", "사주 4기둥", "사주 풀이"가 메타데이터·keywords·FAQ 질문을 포함해 어디에도 없다.
- AC-90: 오늘의 사주 운세 점수는 30~95 정수이고, 같은 일간이면 같은 날 같은 결과다. 한 일간 기준으로 10일 연속 확인하면 십신 열 가지가 한 번씩 모두 나온다(일진 천간이 10일 주기). 7일 연속 총운 점수가 모두 같지는 않다. 어떤 십신 날도 문구가 비지 않고 낮은 구간 문구도 행동 조언으로 끝난다(AC-39).
- AC-91: 지원 범위 경계(사주): 1920-01-01 00:30 출생은 결과가 나온다(월주 자월). 2028-12-31 23:30 출생은 결과가 나온다(시주 천간에 2029-01-01의 일간이 쓰이지만 절기 표를 쓰지 않으므로 오류가 아니다). 2029-01-01 출생은 지원 범위 안내만 나온다(AC-9). 기기 시계를 2029-01-02(KST)로 맞춰도 오늘 일진과 십신이 정상이고 연도 상한은 2028이다(AC-84).

## 예외·빈 상태

- 입력 오류: 비어 있음(연·월·일 중 하나라도), 존재하지 않는 날짜, 미래 날짜, 범위 밖 연도(지원 범위는 1920~2028년), 음력 변환 실패(없는 윤달·없는 날)는 오류 안내만 보이고 결과는 나오지 않는다. 범위 밖 안내에는 지원 범위가 들어 있다.
- 2028-12-31 이후 출생 입력(음력 입력이면 양력 환산 기준): 지원 범위 안내만 보이고 결과는 나오지 않는다. 기기 시계가 2029년 이후여도 오늘 기준 기능(개인 일운, 12띠·12별자리 목록)은 정상 동작한다.
- 음력 입력에서 그해 그 달에 윤달이 없는 경우: 윤달을 선택할 수 없다.
- 태어난 시각 입력칸은 연령 판정을 통과한 뒤, 해당 연도에 입춘이 드는 날 또는 별자리가 바뀌는 날(2단계는 절기가 바뀌는 날 포함)에만 나타난다. 시각을 모르면 후보를 나란히 보이고 사용자가 선택한다.
- 후보 두 개를 보여 줄 때 어느 쪽도 "정답"으로 표시하지 않는다.
- 이용 동의를 하지 않은 경우: 이용 불가 안내 화면을 보이고 운세 결과와 입력칸은 나타나지 않는다. 동의 거부는 저장하지 않으므로 새로고침하면 이용 동의 화면이 다시 나온다.
- 이용 동의 화면을 못 보는 환경(JS 비활성): 설명·면책·FAQ는 보이고, 기능 영역에는 "운세 이용에는 JavaScript가 필요합니다" 안내가 나온다. 동의 없이 결과가 보이는 경로는 없다.
- 보관된 이용 동의 값이 손상되었거나 알 수 없는 문구 버전인 경우: 오류 없이 값을 지우고 이용 동의 화면을 다시 보여 준다.
- 브라우저 저장소를 쓸 수 없는 환경(시크릿 모드, 저장소 비활성): 동의 상태를 보관할 수 없으므로 방문(페이지 로드)마다 이용 동의 화면이 나온다. 오류 화면은 없다.
- 허브 `/fortune` 방문: 이용 동의 화면이 나오지 않고 동의 상태를 만들거나 지우지 않는다.
- 만 14세 미만으로 판정된 경우: 결과 대신 연령 안내 화면을 보이고 이용을 계속할 수 있는 장치(보호자 확인 버튼 등)는 두지 않는다. 아무것도 저장하지 않으므로 새로고침하면 처음부터 다시 입력해야 한다. 다른 생년월일을 다시 입력해 우회할 수 있으며, 이용 동의와 이 확인은 둘 다 자기 신고 방식이라는 한계를 받아들인다.
- 2월 29일생의 만 나이: 평년에 생일이 지난 것으로 보는 날(2월 28일 또는 3월 1일)은 법률 검증 없이 위험으로 수용하고, 보수적으로 3월 1일부터 한 살이 늘어난 것으로 본다.
- 페이지를 연 채로 자정이 지난 경우: 다시 불러오면 새 날짜 결과가 나온다.
- 사용자 시간대가 한국이 아닌 경우: 날짜 기준은 항상 KST이고 "한국 시간 기준"을 쓴다.
- 이미지·아이콘 로드 실패: 이름이 글자로 나오고 운세는 정상 표시된다.
- 쿠키 동의 전·거절, 광고 차단, 광고 불러오기 실패: 운세 기능에 영향이 없다.
- 같은 사람의 띠 운세와 개인 운세 점수가 서로 다른 경우: 다른 기준이라는 안내를 둔다.
- 같은 날 같은 입력으로 반복해서 보는 경우: 막지 않고 같은 결과를 보여 준다.
- 서버 통신 없이 계산이 불가능한 사정(예: 절기 자료를 서버에서 받아야 하는 경우)이 설계에서 생기면 생년월일·시각이 요청에 포함되지 않는 방식으로만 허용한다. 그것이 불가능하면 기획으로 되돌려 결정한다. 이는 이용 동의 세 번째 항목의 사실성과 직결된다. (설계는 절기·음력을 미리 만든 정적 표로 처리해 서버 통신이 없다.)

  - 각 페이지: noindex 제거(`/fortune/today`), 설명 콘텐츠(사용법, 계산 기준 요약, FAQ, 면책, 이용 대상 안내)를 서버 렌더링 HTML에 둔다. 이 영역은 이용 동의 게이트와 관계없이 보인다. 권장 분량은 한국어 약 600자 이상(얇은 콘텐츠 방지, 타로와 같은 기준).
  - 허브 `/fortune`: 세 운세의 차이(생년월일 기준 개인 운세 / 같은 띠·별자리 공통 운세), 결과를 고르는 방식 안내, 이용 전 확인 절차, 생년월일 비저장, 지원 출생 연도, 계산 기준을 각 페이지에서 밝힌다는 안내를 설명 콘텐츠로 둔다. 목록·설명·FAQ·상시 면책·하단 고지·이용 안내가 모두 서버 HTML에 있다.

  - 별자리 페이지: 12별자리 이름과 일반 날짜 기간 안내("해마다 하루 정도 달라질 수 있다" 병기), 내 별자리 찾는 법을 설명 콘텐츠로 서버 HTML에 둔다. 오늘의 운세 문구는 위와 같다.
  - 띠별·별자리 페이지에 "생년월일로 보는 오늘의 운세" 링크(`/fortune/today`)를 하나 둔다. 동의 전에도 보이고 서버 HTML에 있어 크롤러가 내부 링크를 따라갈 수 있다.
  - 개인 결과(생년월일 입력 결과)는 URL이 없고 검색 노출 대상이 아니다.
  - URL은 소문자와 하이픈이다. 허브는 `/fortune`, 기능 페이지는 `/fortune/today`(기존 유지), `/fortune/tti`, `/fortune/star-sign`이고 2단계 사주는 `/fortune/saju`다(설계 D11 확정).
- 메타데이터: `buildMetadata()`로 title, description, canonical, OG를 만든다. OG 이미지 `alt`를 새로 쓴다. 키워드는 `keywords`로 넘긴다. 메뉴 라벨은 `getOgTag` 규칙을 따른다. 위 "화면 표기 규칙"의 표현 제한과 "용어 사용 규칙: 사주"를 적용한다(허브와 방식 A 페이지의 title·description·OG에는 "사주"를 쓰지 않는다).
- JSON-LD: BreadcrumbList(홈 > 운세 > 페이지, 허브는 홈 > 운세), FAQPage(화면의 FAQ와 같은 내용), 허브에는 운세 페이지 목록 ItemList. 근거 없는 리뷰·평점은 넣지 않는다.
- 사이트맵: `MENU_LIST`에 항목을 추가한다. 그룹 단위 `comingSoon`이므로 1단계 출시 시점에 해제하고(그룹 링크 `/fortune`), 2단계 사주는 준비 후에 항목을 추가한다.
- 차별 포인트: 리서치 10장은 경쟁이 많고 차별이 없으면 유입이 어렵다고 본다. 이 서비스의 차별 요소는 계산 기준을 밝히는 설명(입춘·경계 시각)과 로그인·저장 없는 사용성이다. 설명 콘텐츠에서 이를 앞세운다. 오늘의 운세 문구가 검색에 잡히지 않는 점과 이용 동의 단계가 유입 후 이탈을 늘릴 수 있는 점은 유입 효과를 낮추는 요인이다.

## 법적·정책 요구사항

법률 검증 상태: 이루어지지 않았다. 사용자가 2026-11-05에 출시 전 법률 확인을 진행하지 않기로 결정했고 운영자가 위험을 수용한다(타로와 같은 방식, 결정 사항 7). 아래 내용은 기획자의 일반적인 판단이며 법률 전문가의 검토를 거치지 않았다.

### 개인정보 수집

- 서버에 수집·저장하는 개인정보는 없다. 생년월일과 태어난 시각은 서버로 전송하지도 않는다. 모든 계산은 사용자의 브라우저 안에서 한다. (계산에 서버가 불가피하면 입력값이 요청에 포함되지 않는 경우에만 허용하고, 아니면 기획으로 되돌려 결정한다.)
- 입력값은 화면 메모리에서만 쓰고 localStorage, sessionStorage, 쿠키, URL, 분석·알림 이벤트 어디에도 남기지 않는다. 페이지를 벗어나거나 새로고침하면 사라진다.
- 만 14세 미만 판정 결과도 같은 방식으로 다룬다. 메모리에서만 계산하고 어디에도 저장하거나 보내지 않는다.
- 이용 동의 상태는 "동의 여부, 동의한 문구 버전, 동의 시각"만 sessionStorage(탭 세션)에 둔다. 탭을 닫으면 사라진다. 개인을 식별하는 정보가 아니며 생년월일과 연결되지 않는다. 이 판단은 법률 검증 없이 운영자가 위험을 수용한다. 동의 여부는 분석·알림 이벤트로 보내지 않는다. 동의하지 않은 기록은 남기지 않는다.
- 이름, 연락처, 성별, 출생지, 질문 같은 자유 입력란을 두지 않는다. 그래서 건강·성 관련 민감정보가 들어올 입력 경로가 없다.
- 생년월일은 단독으로는 개인정보가 아니라는 견해가 있고 이름 등과 결합하면 개인정보가 될 수 있다(리서치 8.4, 검색 요약 기준). 이 서비스는 결합할 정보를 받지 않고 저장하지도 않는다.
- 쿠키 동의(광고·분석) 거절과 관계없이 운세는 동작한다. 동의 후 동작하는 분석·광고·알림에 입력값을 담지 않는다.
- 개인정보처리방침에 운세 항목(서버 저장·전송 없음, 생년월일 브라우저 저장 없음, 이용 동의 상태를 탭 세션 동안 sessionStorage에 보관한다는 항목과 탭을 닫으면 사라진다는 점, 만 14세 이상 대상 안내)을 추가하고 이용약관에 서비스 성격(오락·참고용), 이용 동의, 이용자 본인 책임 관련 고지를 추가한다. 두 문서의 기존 문구는 이번에 확인하지 않았다(출시 전 최종 확인). 기존 이용약관에는 "법이 허용하는 범위 내에서 책임을 부담하지 않는다"는 취지의 전면 면책 성격 문구(11. 책임 제한)가 있으며, 운세의 일반 확인 수준 책임 고지와 어긋날 수 있다. 이 부분은 법률 검증 없이 위험으로 수용한다(위험과 대응 사항).

### 만 14세 미만 (이용 동의 + 안내 문구 B + 생년월일 기반 연령 확인 C, 법률 검증 없음·위험 수용)

쟁점: 개인정보보호법 제22조의2에 따라 동의가 필요한 처리에는 법정대리인 동의를 받아야 한다. 이 서비스는 생년월일을 입력받지만 저장·전송하지 않는다. 이런 일회성 계산 구조에서 이 조항이 적용되는지는 리서치에서 확인하지 못했고 법률 확인도 하지 않는다. 운세는 청소년 이용이 있다(사주핑 회원 중 10대 18%라는 기사). 사용자는 만 14세 미만은 이용할 수 없고 만 14세 이상은 이용할 수 있게 하기로 했으며(결정 사항 6), 이를 이용 동의 게이트와 생년월일 기반 확인으로 이중으로 막는다(결정 사항 15). 법률 확인은 진행하지 않고 운영자가 위험을 수용한다(결정 사항 7).

장치별 역할

| 구분 | 내용 | 위치 |
|---|---|---|

| C. 생년월일 기반 연령 확인 | 생년월일 입력 직후 브라우저 메모리에서 만 나이를 계산한다. 만 14세 미만이면 결과를 보여 주지 않고 연령 안내 화면(게이트)을 보인다. 이용을 계속할 수 있는 장치는 두지 않는다. | 생년월일을 입력하는 모든 기능 |

동작 순서(생년월일 기반 확인)
1. 이용 동의를 마친 사용자가 출생 연·월·일 전체(음력이면 양력으로 변환한 값)를 입력하고 입력 검증을 통과한다.
2. 브라우저가 한국 시간 기준 오늘 날짜와 비교해 만 나이를 계산한다. 출생 연도만으로는 만 14세 판정이 안 되는 해(생일 전후)가 있으므로 연·월·일 전체로 판정한다.
3. 만 14세 이상이면 계속 진행한다(경계일이면 태어난 시각 입력, 이후 결과와 책임 관련 고지). 만 14세 미만이면 연령 안내 화면으로 가고 결과, 시각 입력칸, 점수는 보이지 않는다.
4. 연령 안내 화면에는 이용 대상 안내, 책임 관련 고지, 홈으로 가는 링크가 있다. 입력한 생년월일은 다시 표시하지 않는다.

"생년월일을 서버로 전송·저장하지 않는다" 원칙과의 관계
- 판정은 입력한 값을 브라우저 메모리에서 계산하는 일회성 연산이다. 서버로 보내지 않고, localStorage·sessionStorage·쿠키·URL에 남기지 않고, 분석·알림 이벤트에 "미성년으로 판정됨" 같은 값을 담지 않는다(타로의 위기 표현 감지와 같은 방식).
- 그래서 판정 상태를 기억하지 못한다. 새로고침하면 처음부터 다시 입력해야 하며, 로또 AgeGate(sessionStorage에 확인 상태 보관)와 달리 "한 번 통과/차단되면 유지"가 되지 않는다. 이 한계를 받아들인다. 이용 동의 상태 보관(sessionStorage)은 별개이며 연령 판정 결과를 담지 않는다.

적용 범위와 한계
- 이용 동의는 운세 기능 전부(띠·별자리 직접 선택 포함)에, 생년월일 기반 확인은 생년월일을 입력하는 기능(오늘의 운세, 내 띠 찾기, 내 별자리 찾기, 2단계 사주)에 적용한다.
- 두 장치 모두 자기 신고 방식이라 이용자가 거짓으로 선택하거나 다른 날짜를 입력하면 우회할 수 있다. 법정대리인 동의를 대신하는 장치가 아니며, 법적 효력은 검증하지 않았고 운영자가 위험을 수용한다.
- 2월 29일생은 평년에 3월 1일부터 한 살이 늘어난 것으로 보는 보수적 가정을 쓰고, 법률 검증 없이 위험으로 수용한다.
- 아동 대상 서비스로 오해되지 않도록 문구와 시각 요소를 정한다.
- 로또 링크 때문에 연령 문제가 생기지 않도록 로또 화면의 AgeGate(만 19세)를 그대로 거친다.

### 로또 연결 노출 문구

연결 방식은 "로또 번호 생성기로 가는 링크"만 둔다(리서치 9장 선택지 2). 운세가 번호를 정한다는 인상을 피하려는 것이다. 행운 숫자를 생성기에 넘기거나 고정 번호로 채우는 기능, 행운 숫자로 6개 조합을 만들어 보여 주는 기능은 이번 범위에서 제외한다(필요하면 별도 기획과 승인).

- 표시 이름: 행운 숫자는 "오늘의 행운 숫자"로 쓴다. "로또 번호", "당첨 번호", "행운의 번호 6개"로 쓰지 않는다.
- 표시 규칙: 숫자는 1~2개, 1~10 범위로 제한한다. 한 페이지에 로또 링크 영역은 한 번만 둔다. 행운 숫자를 보이는 화면(오늘의 운세, 띠·별자리 페이지, 사주 결과)에서 숫자 근처에 고지가 함께 보인다.
- 고지 문구(접거나 숨기지 않는다): "행운 숫자는 재미를 위한 오락용 표시이며, 로또 추첨 결과나 당첨 확률과 관계가 없습니다. 번호 생성기는 운세와 상관없이 번호를 무작위로 만듭니다. 복권은 만 19세 이상만 구매할 수 있으며, 무리하지 않는 범위에서 즐기시기 바랍니다."
- 링크 라벨(명사형): "로또 번호 생성기 (무작위 생성)"
- 이 고지 문구에만 "당첨"을 쓸 수 있다. 같은 문구를 다른 위치에서 변형해 쓰지 않는다. 문구를 바꿀 때는 사용자 승인을 받는다.
- 로또 화면 쪽에는 운세 링크를 추가하지 않는다.
- 광고·정책 영향: 로또 서비스와 같은 도메인이고 AdFit에 "사행성(복권)" 항목이 있다(리서치 8.6). 링크가 운세 페이지의 광고 심사에 영향을 줄 수 있어 출시 전 확인 항목으로 둔다. 복권법에 당첨 예상번호 제공·홍보를 금지하는 개정안이 추진된다는 보도(2025-10)가 있고 진행 상태는 확인하지 못했다. 이 서비스는 예상 번호를 제공하지 않으며 위 규칙으로 그 인상을 피한다. 로또 연결 표현의 법적 적합성은 법률 검증 없이 운영자가 위험을 수용한다.

### 문구 안전 원칙

1. 결과가 앞날을 알려 주거나 약속하지 않는다는 점을 밝힌다.
2. 전문 분야(법률·의학·재정·심리) 조언을 대신하지 않는다고 밝힌다.
3. 단정·과장·공포 조장 표현을 쓰지 않는다. 부정적인 결과도 행동 조언으로 마무리한다.
4. 효과·적중률·"과학적으로 입증" 같은 주장을 하지 않는다. 바넘 효과를 활용해 짧고 모호한 문구를 쓸 수는 있지만 "정확도"를 내세우는 근거로 쓰지 않는다.
5. 특정 운세 서비스·역술인과의 제휴·후원을 암시하지 않는다.
6. 결과는 참고용이며 판단과 선택은 이용자 본인에게 있다는 일반 수준의 책임 관련 고지만 쓰고, 서비스 책임을 전부 면제하는 표현이나 동의가 책임을 없애 준다는 암시는 쓰지 않는다.
7. 로또 고지 외의 고지 문구는 위 초안을 기준으로 하고, 바꿀 때는 사용자 승인을 받는다.

### 상업적 이용 주의

- 수익은 AdFit 광고만이다. 유료 결제, 크레딧 차감, "광고 보면 결과 공개" 구조를 쓰지 않는다. 광고는 결과를 막지 않는다. 이용 동의 화면은 광고와 무관하며 광고 시청을 동의 조건으로 삼지 않는다.
- AdFit 슬롯은 루트 레이아웃에서 자동 노출된다. 운세 페이지가 페이지당 광고 수 제한(AdFit 기준 4개 이하)을 넘지 않게 한다.
- 문구는 개발 단계에서 한 번 작성해 정적 데이터로 두고, 접속할 때마다 자동 생성하지 않는다. 날짜별 URL·아카이브를 만들지 않아 검색 엔진이 대량 자동 생성 페이지로 보지 않게 하고, 직접 검수한 문구와 설명 콘텐츠를 둔다(리서치 8.6).
- 광고 기준에서 문제될 소지가 있는 콘텐츠: 로또 연결(위 설명), 건강·투자 단정 표현, 불안 조장 표현, 정확도·적중 주장.
