# KASI API 사전 확인 (design.md 열린 질문 Q2)

확인일: 2026-11-05. 웹 검색 결과 요약 기준이며 공공데이터포털 원문(활용가이드 Word 문서, 약관 전문)은 직접 열어 보지 못했다. 실제 API를 호출해 확인한 것은 없다.

## 실제 호출 결과 (2026-11-05, 사용자 제공 키 `DATA_GO_KR_API_KEY`)

엔드포인트 `https://apis.data.go.kr/B090041/openapi/service/SpcdeInfoService`, 응답 XML. 키 값은 출력·기록하지 않았다.

**24절기(`get24DivisionsInfo`) 제공 연도: 1920년 ~ 2028년.** 설계의 1920~2050 전제는 맞지 않는다.

| solYear (2월 조회) | totalCount | 비고 |
|---|---|---|
| 1919, 1918, 1915, 1910, 1900 | 0 | 없음 |
| 1920 | 2 | 입춘 1920-02-05 11:26, 우수 02-20 07:29 |
| 1921, 1950, 1960, 2000 | 2 | 있음 |
| 1950 | 2 | 입춘 1950-02-04 18:21 |
| 2026 | 2 | 입춘 2026-02-04 05:02 (month2k 교차 확인값과 일치), 우수 02-19 00:52 |
| 2027, 2028 | 2 | 있음 |
| 2029, 2030, 2035, 2040~2049, 2050, 2051 | 0 | 없음 |

- 1920-01, 1920-12는 각각 2건이라 1920년은 1월부터 12월까지 있다. 2049-12는 0건이다.
- 응답의 `sunLongitude`는 비어 있다(undefined). 절기 이름으로 판정해야 한다. `kst`는 HHMM 문자열이다.
- 상한이 2028년인 이유는 확인하지 못했다. 향후 연도가 갱신 방식으로 추가될 가능성이 있으나 추정이다.

**음양력(`LrsrCldInfoService`): 활용신청 후 호출 성공.** 처음에는 활용신청 전이라 `SERVICE_KEY_IS_NOT_REGISTERED_ERROR`(403)였고, 사용자가 신청한 뒤 같은 키로 정상 응답한다. 신청된 상세기능은 `getLunCalInfo`(양력→음력), `getSpcifyLunCalInfo`, `getJulDayInfo`, `getSolCalInfo`(음력→양력)이다.

| 호출 | 결과 |
|---|---|
| `getLunCalInfo` 양력 1391-02-05 | 음력 1391-01-01 (하한과 일치) |
| 양력 1900-01-01, 1920-01-01, 1920-02-05 | 정상. 1920-02-05는 음력 1919-12-16 |
| 양력 2026-02-04 | 음력 2025-12-17 (설날 2026-02-17과 일치) |
| 양력 2028-12-31, 2029-01-01, 2040-06-01 | 정상 |
| 양력 2050-12-31 | 음력 2050-11-18 (상한) |
| 양력 2051-01-01 | totalCount 0 (없음) |
| `getSolCalInfo` 음력 1920-01-01, 2050-11-18 | 정상 |
| `getSolCalInfo` 음력 2023-02-01 | 2건(평달·윤달 각각). 윤달이 있는 달은 응답이 2건이므로 파싱에서 평/윤을 구분해야 한다 |

- **음력 변환은 1391~2050년 전부 가능**하다. 지원 연도 1920년 이후 전제는 음력에서는 문제없다.
- 응답에 음력 간지(`lunSecha` 세차, `lunWolgeon` 월건, `lunIljin` 일진)가 함께 온다. 2단계 사주의 일주·월주 대조 검증 자료로 쓸 수 있다(단, 월건은 음력월 기준이라 절기 월주와 다를 수 있어 그대로 쓰면 안 된다).
- 이용허락범위·약관은 호출로는 알 수 없고 포털 페이지 확인이 필요하다(사용자 확인 대기).

## 이 결과가 설계에 미치는 영향

- 입춘·별자리 경계(절기 기반) 판정: 1920~2028년만 KASI 표로 만들 수 있다. 2029년 이후 출생·운세 날짜 계산은 해당 없음(출생 연도는 보통 과거라 큰 문제는 아니나, 사주 2단계의 절기 월주와 "오늘 날짜" 기준 처리는 영향 가능).
- 결정이 필요한 안(사용자 선택): (가) 2029년 이후 절기는 천문 계산으로 보완, (나) 지원 출생 연도를 1920~2028로 제한하고 이후는 별도 처리, (다) 특일 정보의 나머지 연도를 나중에 갱신.

## 확인하지 못한 것 (위험)

1. **24절기의 제공 연도 범위.** 검색에서 1920~2050년을 보장하는 문구를 찾지 못했다. 한 GitHub 프로젝트는 2004년부터 조회하는 구현이라서, 특일 정보가 1920년까지 거슬러 올라가는지 알 수 없다. 설계(1920년 이후 지원)의 핵심 전제이므로 실제 호출로 확인해야 한다.
2. **음양력 정보의 이용허락범위.** 특일 정보는 "제한 없음"이 확인되지만 음양력 정보 페이지의 해당 문구는 검색 요약에 없었다.
3. **약관 원문.** 재배포(코드 상수로 포함해 서비스 배포)가 허용되는지 약관 전문을 읽지 못했다. "이용허락범위 제한 없음" 표기는 확인됐으나 법적 해석은 하지 않았다.

## 사용자가 해야 할 일

- 공공데이터포털 키가 있으면(없으면 발급, 특일 정보와 음양력 정보 활용신청 필요) 아래 두 호출 결과를 확인한다.
  - `get24DivisionsInfo?solYear=1920&solMonth=02` 와 `solYear=2050&solMonth=02`: 입춘의 `kst` 값이 나오는지.
  - `getLunCalInfo?solYear=1920&solMonth=01&solDay=01`: 음력 정보가 나오는지.
- 키는 `.env`에만 두고 문서나 채팅에 적지 않는다.

## 24절기가 1920년까지 안 나올 때의 대안

- 태양황경 315°(입춘 등) 도달 시각은 천문 계산(Meeus 알고리즘 등)으로 직접 구할 수 있고 분 단위 오차가 날 수 있다. 이 경우 정확도는 KASI 표보다 낮고, 입춘 당일 출생자의 경계 판정 오류 가능성이 생긴다. 이 대안을 쓰려면 설계로 되돌려 사용자가 고른다.
- 지원 연도를 API가 제공하는 범위로 줄이는 안도 있다(plan 결정 사항 변경 필요).
