### 2. KASI 데이터 저장 방식 (현재 동작)

- 런타임 코드에는 KASI 호출이 없다. `src/features/fortune/` 안에서 `fetch(`와 `DATA_GO_KR`를 찾을 수 없었다(Grep 결과, 일치 0건). 키 환경변수를 읽는 곳은 없다. `process.env`는 `fortune-consent-storage.service.ts:12`의 사이트 이름 한 곳뿐이다.
- 절기·음력 표는 코드 상수다. 음력 표 `src/features/fortune/constants/calendar/lunar-table.constant.ts`(음력 1919~2049, 131행), 절기 표 `src/features/fortune/constants/calendar/solar-term-table.constant.ts`(양력 1920~2028, 2,616개)가 저장소에 들어 있다(`docs/fortune/calendar-verification.md` 13~18행).
- 표는 개발자가 `scripts/fortune-calendar/generate.mjs`를 사용자 환경에서 실행해 만든다. 실행은 `DATA_GO_KR_API_KEY` 환경변수로 한다(`docs/fortune/design.md` 2.1 항목, 220행).
- 표를 쓰는 곳: 띠 판정(`src/features/fortune/utils/fortune-tti.util.ts:37`, 입춘 시각), 별자리 판정(`src/features/fortune/utils/fortune-star-sign.util.ts:28`, 중기 시각), 음력 변환(`fortune-lunar.util.ts`). 화면에서는 `today/components/panel.component.tsx`, `tti/components/finder.component.tsx`, `star-sign/components/finder.component.tsx`가 이 유틸을 가져온다.
- 설계상 기능 패널은 `next/dynamic`(`ssr: false`)으로 불러 동의 전에는 표를 내려받지 않는다(`docs/fortune/design.md` D5). 실제 번들 분리는 빌드 산출물로 확인하지 않았다(열린 질문 Q2 안에서 확인).
- 데이터 저장 기준(`docs/conventions/data-storage.md` 7행): "모두에게 같고 자주 안 바뀌는 데이터는 코드 안 상수". 음력·절기 표가 이에 해당한다. Supabase는 "서버에서 갱신하거나 사용자끼리 공유하는 데이터"에만 쓴다(11행).

### 3. 띠·별자리의 생년월일 입력 (현재 동작)

- 띠 목록은 생년월일 없이 12띠를 모두 보여 준다. 목록의 문구는 날짜와 띠 키로만 정해진다. 시드는 `fortune-v1|tti|${zodiac.key}|${todayKey}`(`src/features/fortune/tti/components/list.component.tsx:51`, 123~124행).
- 띠 찾기(`tti/components/finder.component.tsx`)는 생년월일을 받아 띠 키 하나를 정한다. 찾기 결과는 `onFound(key)`로 목록 패널에 전달되고(`finder.component.tsx:180-183`, `tti/components/panel.component.tsx:84-86`) 목록에서 같은 띠 카드를 펼친다. 펼친 카드의 문구는 목록 시드와 같으므로 생년월일이 문구를 바꾸지 않는다.
- 찾기 화면의 추가 정보: 설날 기준 띠가 입춘 기준 띠와 다르면 "설날 기준으로는 ○○띠" 안내를 보인다(`finder.component.tsx:272-279`). 입춘 날 출생이면 시각 입력을 묻고 두 띠 중 고르게 한다(`fortune-tti.util.ts:37-76`).
- 별자리 목록도 같은 구조다. 시드는 `fortune-v1|star-sign|${key}|${dateKey}`(`src/features/fortune/star-sign/components/list.component.tsx:35-36`, 136행). 별자리 찾기는 생년월일로 별자리 키 하나를 정하고(`star-sign/components/finder.component.tsx:266-270`에 이름만 표시), 경계 시각을 묻는다(`fortune-star-sign.util.ts:28-78`).
- 생년월일을 실제로 문구 생성에 쓰는 곳은 오늘의 운세 하나다. `src/features/fortune/today/components/panel.component.tsx:151`의 시드는 `fortune-v1|personal|${toDateKey(solar)}|${todayKey}`이다.
- 결론(사실): 띠·별자리 페이지에서 생년월일은 "내 띠 또는 별자리 이름을 찾는 데만" 쓰인다. 찾은 뒤 보이는 문구는 생년월일을 넣지 않은 경우와 같다. 효과는 (a) 해당 카드 강조, (b) 설날 기준 안내(띠, 차이가 있을 때만), (c) 경계일 시각 질문과 후보 선택이다. 이 점은 화면 안내 문구로 밝혀져 있지 않다(목록 안내 `FORTUNE_DIFFERENT_BASIS_NOTICE`는 두 운세의 기준이 다르다는 내용이다. `tti/components/list.component.tsx:207`).

### 4. 기존 승인과의 관계

- 띠·별자리 찾기는 1단계 plan의 F-3, F-5("내 띠 찾기", "내 별자리 찾기")다(`docs/fortune/plan.md` 기능 목록). 폼을 없애면 승인 기능이 빠진다.
- 검색 노출에서 "내 띠 찾기"는 설명 콘텐츠의 찾는 법으로 서버 HTML에 있다(`docs/fortune/design.md` 1장 `tti/components/guide.component.tsx`). 찾기 기능을 제거하면 이 설명도 함께 고쳐야 한다.

## 유저 스토리

- US-1: 띠 운세를 보는 사용자로서 생년월일을 넣으면 내 운세가 더 정확해지는지 알고 싶다. 왜냐하면 입력이 개인 맞춤인지 판단하고 싶기 때문이다.
- US-2: 운영자로서 KASI 표를 어디에 두어야 하는지 근거와 함께 알고 싶다. 왜냐하면 재배포와 데이터 갱신 방식을 정해야 하기 때문이다.
- US-3: 운영자로서 출시 전에 남은 확인이 무엇인지 한 곳에서 보고 싶다. 왜냐하면 배포 전 누락을 막고 싶기 때문이다.

## 완료 조건 (AC)

QA가 이 목록으로 Playwright 테스트를 만든다. 데스크톱과 모바일에서 실행한다. 기본안(Q3 A안, Q2 코드 상수 유지)을 기준으로 쓰며, 답변에 따라 바뀐다.

- AC-1: `/fortune/tti`에서 생년월일(양력 1990-05-10)을 입력해 찾기를 실행하면, 강조된 띠 카드의 한 줄 요약과 점수가 생년월일 없이 같은 띠 카드를 펼쳤을 때와 글자 단위로 같다.
- AC-2: 같은 띠가 되는 다른 생년월일(예: 1990-05-10과 1978-08-01, 둘 다 말띠)을 입력하면 펼쳐진 카드의 문구가 같다.
- AC-3: 찾기 결과 아래에 "생년월일은 내 띠를 찾는 데 쓰이며, 띠별 운세 문구는 누구에게나 같습니다"의 취지 문장이 보인다(Q3 기본안, 문구 (가)안 확정 2026-11-09). 문장은 JS를 켠 상태에서 찾기 결과 뒤에 나타난다.
- AC-4: 설날 기준 띠가 입춘 기준 띠와 다른 생년월일(예: 2월 초 출생)을 찾으면 "설날 기준으로는 ○○띠" 안내가 나타나고, 같은 띠이면 나타나지 않는다.
- AC-5: `/fortune/star-sign`에서 별자리 찾기 결과 아래에 AC-3과 같은 취지의 문장이 보이고, 펼친 별자리 문구는 생년월일 없이 펼친 것과 글자 단위로 같다.
- AC-6: 경계일(예: 3월 20일 또는 21일 근처, 해당 연도 별자리 경계일)에 찾기를 실행하면 출생 시각 입력 또는 후보 선택이 나온다(기존 동작 유지). 시각 입력 뒤 결과가 바뀌지 않는다는 사실을 깨뜨리지 않는다.
- AC-7: 띠·별자리 목록(JS 끔 제외) 페이지를 열 때 `apis.data.go.kr`, `astro.kasi.re.kr`로 가는 네트워크 요청이 0건이다(Playwright request 기록으로 확인).
- AC-8: 빌드 결과물(`.next/static`)에서 문자열 `DATA_GO_KR`과 `DATA_GO_KR_API_KEY`를 찾을 수 없다(Playwright 대신 빌드 후 검사 스크립트로 확인, QA 항목).
- AC-9: 띠·별자리·오늘의 운세 페이지의 메타데이터, JSON-LD, sitemap이 이번 변경 전과 같다. 찾기 문구 추가는 메타 설명을 바꾸지 않는다.
- AC-10: 추가된 문구에 금지 표현(`docs/fortune/plan.md` "금지 표현 목록")이 없다. "보장", "정확", "맞춤" 같은 말을 쓰지 않는다.
- AC-11: `status.md`에 1단계 출시 전 확인 항목(상담전화 재확인, AdFit, 방침·약관, 스크린리더, 운영 배포)이 "사용자 할 일"로 남아 있다.

## 법적·정책 요구사항

- 개인정보 수집: 생년월일은 서버로 보내지 않고 브라우저 메모리에서만 쓴다(기존 승인 유지). 이번 변경은 이를 바꾸지 않는다. 변경 전후 차이 없음(`docs/fortune/plan.md` 이용 동의 게이트, 세 번째 항목).
- 고지 문구: AC-3, AC-5 문장은 새 고지 문구다. 금지 목록 검사를 거치고 사용자 승인을 받는다. 기존 "오락·참고용" 고지와 책임 고지 수준(일반 확인)을 넘지 않는다.
- KASI 데이터: 이용허락범위는 "제한 없음"으로 확인했다(`docs/fortune/kasi-api-check.md`). 약관 전문은 확인하지 못했다. 기존 위험 수용 항목 그대로다(법률 검증 없음, 운영자 수용). 출처 표기는 `THIRD_PARTY_NOTICES.md`에 있어야 한다. 현재 반영 여부는 이번에 확인하지 않았다(열린 질문 Q2에서 확인).
- 상업적 이용 주의: 수익은 AdFit뿐이다(기존). 찾기 문구는 광고 수익 구조에 영향이 없다. 광고 정책 확인은 기존 출시 전 항목이다.
- 14세 미만: 띠·별자리 찾기도 기존 연령 확인(생년월일 기반)을 그대로 쓴다. 이번 변경은 연령 판정을 바꾸지 않는다.

## 열린 질문

각 질문에 추천안을 붙였다. 추천안이 기존 승인과 다르면 "기존 승인 변경"이라고 표시했다.

- Q1. 사주(2단계)를 이번 fortune-v2 범위에 넣을까요?
  - 추천: 넣지 않는다. 사주는 별도 진행 중이고, plan-saju-edits의 S2-1~S2-11 답변과 U-11 재승인이 먼저 필요하다. fortune-v2는 1단계 정리에 한정한다. 기존 승인 변경 없음.
  - 대안: 같은 fortune-v2에 넣으면 기획 범위가 커지고 설계·UI·개발 단계가 모두 다시 돈다.

- Q2. KASI 표(절기·음력)를 코드 상수로 둘까요, 아니면 DB나 API로 옮길까요?
  - 추천: 코드 상수 유지. 이유는 아래 비교 표를 본다. 기존 승인(`docs/fortune/design.md` D1, D9) 유지. 기존 승인 변경 없음.
  - 추가 확인(Q2에서 답 후 설계 단계에서 함): 설계상 panel에서만 쓰는 표가 실제 번들에서 분리되는지 빌드로 확인한다.

  | 항목 | 코드 상수(현재, 추천) | Supabase 테이블 | 서버 API(런타임 KASI 호출) |
  |---|---|---|---|
  | 저장 기준(`data-storage.md`) | 모두에게 같고 드물게 바뀜: 맞음 | 서버 갱신·공유 데이터용: 맞지 않음 | 런타임 호출: 해당 없음 |
  | 키 노출 | 런타임에 키 없음 | 서비스 키는 서버에만 둠 | 키를 서버에 둬야 함, 호출 한도 10,000건/일 공유 |
  | 네트워크·장애 | 없음 | DB 장애 영향 | KASI 장애·호출 한도 영향 |
  | 변경 방식 | 생성 스크립트 재실행 후 재배포 | 행 수정, 재배포 불필요 | 즉시 반영 |
  | 2029년 이후 확장 | 스크립트 재실행 후 배포 | 데이터 추가 | 가능하나 KASI 제공 범위(1920~2028)가 막음 |
  | 비용·복잡도 | 낮음 | 테이블, 권한(RLS), 마이그레이션 필요 | 서버 라우트, 캐시, 키 관리 필요 |
  | 번들 크기 | 표 크기만큼 증가(추정: 음력 약 5KB, 절기 약 20KB, `design.md` 2장) | 없음 | 없음 |

  - 장점 요약(코드 상수): 키가 런타임에 없고, 네트워크가 없고, 비용이 없다. 단점: 번들이 커지고, 데이터 갱신에 배포가 필요하다. 표는 1920~2028 범위라 자주 바뀌지 않는다.
  - 조건부 추천: 2028년 이후 F-1을 하기로 하면 생성 스크립트와 표를 같은 방식으로 다시 만든다. 그때도 코드 상수가 맞다.

- Q3. 띠·별자리 찾기에서 생년월일 입력을 어떻게 할까요?
  - 사실: 생년월일은 "이름 찾기"에만 쓰인다. 결과 문구는 같다(현황 분석 3번).
  - 옵션 A(추천): 유지하고 효과를 밝힌다. 찾기 결과 아래에 "생년월일은 이름을 찾는 데만 쓰며, 결과 문구는 같다"는 문장을 둔다(AC-3, AC-5). 설날 안내와 경계 시각 질문은 그대로 둔다. 목록의 "오늘의 운세로 개인 결과 보기" 링크는 기존 D12 그대로다. 기존 승인 변경 없음(문장 추가만).
  - 옵션 B: 찾기 폼을 없애고 12개 목록만 둔다. 찾기는 "띠 고르기" 버튼으로 바꾼다. 효과: 입력 부담 없음, 설날·경계 안내 제거. 단점: 1단계 F-3, F-5(내 띠 찾기, 내 별자리 찾기)와 설명 콘텐츠의 찾는 법을 고쳐야 한다. 기존 승인 변경.
  - 옵션 C: 생년월일을 실제로 개인화한다(띠·별자리 문구 시드에 생년월일을 넣음). 효과: 생년월일이 의미를 가진다. 단점: 띠·별자리 운세가 "공통 운세"라는 승인 결정과 충돌하고, 개인 일운(`/fortune/today`)과 역할이 겹친다. 문구 풀의 검수 부담이 커진다(같은 띠 내 변형이 늘어남). 기존 승인 변경이 크므로 별도 기획이 필요하다.
  - 추천 이유: 옵션 A는 승인 기능을 그대로 두고 오인만 줄인다. 생년월일이 꼭 필요한 이유(입춘 시각, 음력 변환, 경계 시각)가 실제로 있으므로 입력 자체를 없앨 이유가 약하다.

- Q4. TODO 항목 "남은 일"을 이번 범위에서 어떻게 다룰까요?
