# e2e 테스트 정리 기획서

## 목표

기능별로 겹치는 e2e spec을 합치고 핵심 흐름만 남겨 실행 시간과 유지 비용을 줄인다. 계산·문구 검증은 단위 테스트로 옮겨 문구만 바꿔도 여러 spec이 깨지는 일을 없앤다.

## 범위

- 포함: `e2e/` spec 17개 정리, 계산·문구 검증의 단위 테스트 이관, 모바일 smoke 축소, 푸시 전 수동 코드리뷰 운영 방법 기록(README.md 한 줄)
- 제외: 기능 동작·화면·문구 변경, 커밋 훅에 e2e 추가, pre-commit에 코드리뷰 추가

## 현황 (기획 시점 확인)

- spec 17개, 총 19,330줄. describe·test 항목 805건(사용자 집계 약 766개). 데스크톱·모바일 두 프로젝트로 실행한다.
- `fortune-calc.spec.ts`(2,842줄)는 `page`를 쓰지 않고 계산 유틸을 직접 import해 검증한다. 브라우저가 필요 없어 단위 테스트로 옮기기 쉽다.
- `tarot-copy.spec.ts`는 1,369줄 중 `page` 사용이 10회뿐이다. 카드 데이터, 금지 표현, 합니다체, 소스 파일 스캔이 대부분이다. `dream-copy`, `lunch-copy`, `fortune-copy`도 같은 구조다.
- `.githooks/pre-commit`은 Biome과 typecheck만 실행한다. e2e는 현재 훅에 없다.

## 유저 스토리

- US-1: 개발자로서 문구 한 줄을 바꿔도 e2e가 여러 개 깨지지 않게 하고 싶다. 왜냐하면 `-copy` spec 유지 비용이 크기 때문이다.
- US-2: 개발자로서 전체 e2e를 짧은 시간에 끝내고 싶다. 왜냐하면 실행이 1,500회 이상이기 때문이다.

## 완료 조건 (AC)

목표 수치는 현재 상태 대비 기준이다. QA가 확인한다.

- AC-1: `e2e/`의 spec 파일(`*.spec.ts`)이 기능당 1개, 총 6개다 (fortune, tarot, dream, lunch, swagger-docs, lotto). `e2e/helpers/`의 공용 헬퍼 파일은 spec이 아니므로 이 6개 수에 넣지 않는다.
- AC-2: 기능별 e2e test 수는 fortune 15개 이하, tarot·dream·lunch·swagger-docs·lotto 각 5~10개다. 전체 합은 60개 이하이고, 목표는 50개 안팎이다. test 수는 `test(` 호출 수로 센다. 반복문으로 test를 만들지 않고, `test.step`은 세지 않는다. 기준은 desktop 실행 수다. 모바일 smoke 수는 AC-8에서 따로 확인한다.
- AC-3: `e2e/` 아래 `.ts` 파일 전체(헬퍼 파일 포함)의 줄 합계가 2,500줄 이하다. 현재는 spec 17개 19,330줄이다.
- AC-4: 삭제한 test 전부가 "남김 / 단위 이관 / 삭제 사유" 중 하나로 분류되어 있고, 분류되지 않은 test가 0건이다. 분류 표는 `docs/e2e-cleanup/qa-report.md`에 있으며, 이관한 test는 옮긴 단위 테스트 파일 경로를 적는다.
- AC-5: 아래 대상이 단위 테스트로 실행되고 `pnpm test`가 통과한다. (a) 음력·절기·만 나이·날짜 검증, (b) 사주의 기둥·일진·십신·점수, (c) 로또 핫/콜드 집계와 번호 생성 조건(최대 20게임 제외 포함), (d) swagger-docs 명세 합치기 규칙, (e) 금지 표현·상표 명칭 검사, (f) 카드 78장·소재 120개·메뉴의 개수와 중복.
- AC-6: 법적 고지 원문은 글자 단위로 고정하는 단위 테스트가 있다. 대상은 면책 문구, 상담전화 번호 5개(이름·번호·링크·순서), 개인정보 입력 안내, 로또 당첨 보장 없음 문구다. 로또 생성기 화면의 문구는 e2e에서 확인한다. FAQ·가이드·SEO 문구는 글자 단위 고정 대상이 아니다.
- AC-7: `pnpm e2e`(desktop 프로젝트) 통과.
- AC-8: `pnpm e2e:mobile`이 `@smoke` 태그 test만 실행하고 통과한다. smoke는 기능당 1~2개다.
- AC-9: `pnpm typecheck`, `pnpm lint` 통과.
- AC-10: `.githooks/pre-commit`에 e2e 명령과 단위 테스트 명령이 없다.
- AC-11: 도구를 새로 추가하면 `DEPENDENCY_LICENSES.md`와 `THIRD_PARTY_NOTICES.md`가 갱신되어 있다.
- AC-12: 수동 코드리뷰 운영 한 줄이 `README.md`에 있다. 훅으로 강제하지 않는다.
- AC-13: fortune, tarot, dream, lunch, lotto 각각에 서버 HTML(JS 없이) SEO 검사 test가 1개씩 있다. swagger-docs는 개발 전용이라 제외한다.
- AC-14: 개인정보 비저장 검사(운세 생년월일, 타로 질문)가 e2e에 기능별 1개씩 있고, 광고 차단 상태에서 동작하는 검사가 dream e2e에 1개 있다.

## 예외·빈 상태

- 고지 원문을 글자 단위로 고정하는 단위 테스트는 문구 개정 때 깨지는 것이 의도된 동작이다. 법적 고지 원문을 바꾸려면 상수와 단위 테스트를 함께 고치고 사용자 승인을 받는다(확정 결정 2).
- FAQ·가이드·SEO 문구 개정은 원문 고정 테스트를 깨지 않는다. 이 문구는 금지 표현·구조 검사로만 보호한다.
- 기능 흐름이 바뀌어 남긴 e2e가 실패하면 삭제 목록을 다시 확인하지 않고 바로 고치지 않는다. 기획 기준을 먼저 확인한다.

## 검색 노출

- 키워드: 없음 (신규 노출 없음). 기존 페이지의 검색 문구는 이 작업에서 바꾸지 않는다.
- 페이지가 답할 질문: 없음 (신규 페이지 없음)
- 참고: 정리 후에도 fortune, tarot, dream, lunch, lotto 각각에 메타데이터·JSON-LD·sitemap을 확인하는 SEO 서버 HTML 검사 1개를 남긴다(AC-13, `docs/conventions/seo.md`). 검사 항목은 title, description, canonical, og:title, h1 1개, JSON-LD 파싱, sitemap 등록이다.

## 법적·정책 요구사항

- 개인정보 수집: 이 작업은 수집 기능을 바꾸지 않는다. 운세 생년월일과 타로 질문이 저장되지 않는다는 검사를 e2e에 기능별 1개씩 남긴다(`COMPLIANCE.md` 기준).
- 고지 문구: 면책(오락 목적, 결과를 보장하지 않는다는 문구), 상담전화 5개, 개인정보 입력 안내, 로또 당첨 보장 없음 문구의 원문은 단위 테스트가 글자 단위로 고정한다. 로또 생성기 화면 문구는 e2e에서 확인한다.
- 상업적 이용 주의: 광고 차단 상태에서도 기능이 동작하는지 dream e2e 1개로 유지한다. 광고 수익과 관련된 콘텐츠 변경은 이 작업 범위가 아니다.
- 새 개발 의존성(Vitest, MIT)은 개발 전용이라 배포 번들에 들어가지 않는다. 고지 문서 2개를 갱신한다(AC-11).

## 확정된 결정

사용자가 아래 답을 확정했다. 이 기획서의 기준이다.

1. 단위 테스트 도구는 Vitest다. 단위 테스트 파일은 루트의 `unit/<기능>/` 아래에 둔다.
2. 고지 원문을 글자 단위로 고정하는 검사를 유지하고, 단위 테스트로 옮긴다. 승인 원문을 보호하는 장치다.
3. 소스 파일 스캔은 제품 규칙(금지 표현, 상표 명칭)만 단위 테스트로 옮긴다. 문서 기록 검사(copy-log, status.md, HEAD diff)와 이미지 파일 위치 검사는 삭제한다.
4. SEO 서버 HTML 검사(메타, JSON-LD, sitemap)는 e2e에 기능당 1개 둔다.
5. 모바일 smoke는 기능당 1~2개이고 `@smoke` 태그로 구분한다. 모바일 프로젝트는 태그가 붙은 test만 실행한다.
6. `pnpm e2e`는 desktop 프로젝트 기준으로 통과를 확인한다. 모바일은 `pnpm e2e:mobile`로 따로 확인한다.
7. fortune은 e2e 테스트를 15개까지 허용한다. 나머지 기능은 5~10개다.
8. 전체 줄 수 목표는 2,500줄 그대로 둔다. 세는 범위는 AC-3과 같다.
9. 푸시 전 `/code-review` 수동 실행 운영은 README.md에 한 줄로 적는다. 훅은 추가하지 않는다.
