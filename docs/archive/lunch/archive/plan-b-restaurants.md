# 점심 추천 기획서 (오늘 뭐 먹지)

작성일: 2026-11-19
입력 문서: `REFACTORING.md`(점심 추천 절), `src/constants/menu.constant.ts`(lunch 그룹), `src/app/lunch/today/page.tsx`(현재 준비 중 페이지), `supabase/migrations/0003_restaurants.sql`(테이블 스키마), `docs/fortune/plan.md`, `docs/tarot/plan.md`(형식 참고), `docs/_templates/plan.md`, `docs/conventions/seo.md`, `docs/conventions/data-storage.md`, `docs/conventions/design-system.md`(메뉴 색 절), `COMPLIANCE.md`(11장 고지 형식), `README.md`(표 형식)
상태: 기획 완료, 승인 대기. 사용자 확정 방향(B안)을 따른다.

## 목표

점심 메뉴를 고르기 어려운 사용자가 룰렛으로 오늘의 점심 업태(한식, 중식 등)를 가볍게 뽑고, 현재 위치 근처에서 그 업태의 가게 목록을 무작위로 확인해 바로 지도 앱에서 찾아볼 수 있는 무료 오락형 서비스를 만든다.

## 사용자 확정 방향 (다시 묻지 않는다)

- 1차 버전은 B안이다.
  1. 업태(category)를 룰렛 등 뽑기 연출로 뽑고, "오늘의 점심운" 느낌의 문구를 붙인다. 사이트 컨셉은 운이다.
  2. 뽑힌 업태의 "내 주변 가게" 목록을 보여준다. 브라우저 위치 권한을 쓰고 lat/lng 반경 검색을 한다.
  3. 가게 상세와 리뷰는 만들지 않는다. 카카오맵·네이버지도 검색 링크로 넘긴다.
- 자체 별점, 후기, 가격대, 혼밥 필터는 하지 않는다. 공공데이터에 없는 정보다.
- 가게는 순위나 추천순이 아니라 무작위로 보여준다. 광고처럼 보이지 않게 한다.
- 위치는 서버에 저장하지 않는다.
- 음식점 동기화 cron(신규·폐업 반영)은 이 기능과 별도 후속 작업이다. 이 기획의 범위 밖이다.

## 기존 기능과의 충돌 확인

- `REFACTORING.md` 34~37행: "점심 추천 (추후 개발, 아직 정하지 않음)" 절에 "별점, 후기, 거리, 추천순 등 필터 기능을 추가한다"가 적혀 있다. 확정 방향과 충돌하므로 정정이 필요하다. 이 문서는 루트에 있고 기획자가 쓸 수 없는 위치라서, 정정은 PM 승인 후 별도로 한다.
- `src/constants/menu.constant.ts` 133~148행(lunch 그룹): `comingSoon: true`, 항목 "오늘 뭐 먹지" 하나다. 설명 "직장인 점심 메뉴를 조건에 맞게 추천하고 룰렛으로 결정."과 예시 "예: 한식/중식, 가격대, 혼밥 조건으로 고르기"는 가격대와 혼밥 조건을 말하므로 정정한다. 항목의 `colorClass`는 `text-orange-600`인데, `design-system.md`의 점심 메뉴 색 토큰은 `menu-lunch`(`#a5481f`)다. 불일치하므로 UI 단계에서 정한다(열린 질문 Q15).
- `src/app/lunch/today/page.tsx`: 준비 중(ComingSoon) 상태이고 `robots: { index: false, follow: true }`다. 메타 description에 "조건에 맞게 추천하고"라는 문구가 있어 정정한다. 제목 "오늘 뭐 먹지 - 점심 메뉴 추천"의 "메뉴 추천"도 실제로는 메뉴가 아니라 업태와 가게를 보여주므로 정정 여부를 묻는다(Q13).
- `src/app/sitemap.ts`: `MENU_LIST`에서 `comingSoon`이 없는 그룹만 읽는다. 출시 시 `comingSoon`을 풀면 `/lunch/today`가 사이트맵에 자동으로 들어간다.
- `src/app/privacy/page.tsx`: 위치 정보에 대한 문구가 없다. 위치를 쓰기 시작하면 개인정보처리방침 개정이 필요하다(아래 법적 요구사항 참고).
- `src/app/terms/page.tsx`: 외부 지도 링크, 영업 정보 보장 없음, 공공데이터 출처에 대한 문구가 없다. 추가가 필요하다.
- `src/app/layout.tsx`: AdFit 슬롯이 모든 페이지에 붙는다. 룰렛과 가게 목록은 광고 동의 여부와 관계없이 동작해야 한다(AC-26).
- 타로와 운세 기능은 쿠키 동의 여부와 관계없이 기능이 돌아간다. 점심도 같은 원칙을 따른다.
- 0003 마이그레이션: `restaurants` 테이블은 `anon`과 `authenticated`에 공개 읽기(RLS `using (true)`)가 열려 있다. 공개 데이터이므로 개인정보 문제는 없지만, 읽기 방식과 비용은 설계 단계에서 다룬다(Q14).

## 범위

- 포함
  - 점심 룰렛: 업태 한 개를 뽑는 뽑기 연출과 결과 문구 (`/lunch/today`)
  - 주변 가게 목록: 위치 권한을 허용하면 선택 업태의 가게를 반경 안에서 무작위 순서로 보여준다.
  - 위치 거부 시 대체 흐름: 시·도, 시·군·구 선택
  - 지도 검색 링크: 카카오맵, 네이버지도 검색 페이지로 이동
  - 고지 문구: 오락 목적, 영업 여부 보장 없음, 위치 사용 안내, 데이터 출처
  - 검색 노출: 메타데이터, JSON-LD(BreadcrumbList, FAQPage), 서버 렌더링 설명 콘텐츠, 출시 시 noindex 해제와 메뉴 등록 해제
  - 메뉴 설명과 메타 설명 정정
  - 법적 고지 반영: `COMPLIANCE.md` 11장, 개인정보처리방침, 이용약관, `THIRD_PARTY_NOTICES.md`(공공데이터 출처)
- 제외 (후속 작업 또는 범위 밖)
  - 음식점 동기화 cron(신규·폐업 반영). 공공 API 조사가 끝나지 않았다. 후속 작업이다.
  - 가게 상세 페이지, 가게별 리뷰, 별점, 후기, 가격대, 혼밥 필터, 영업시간 표시(공공데이터에 없거나 신뢰하기 어렵다)
  - 가게별 개별 URL 페이지(수십만 페이지가 생기고 얇은 콘텐츠가 된다. 검색 정책상 위험하다)
  - 로그인, 즐겨찾기, 방문 기록 저장, 기기 간 동기화
  - 유료 결제, 가게 광고 게재, 제휴 링크(수익 구조는 AdFit 광고만이다)
  - 메뉴 이름 추천(예: "김치찌개"). 1차는 업태 단위다.
  - 길찾기, 전화 연결, 지도 앱 API 연동(키 발급과 약관 부담)

## 화면 목록과 흐름

화면은 `/lunch/today` 한 페이지다. 별도 라우트는 만들지 않는다.

1. 진입: h1, 상시 오락 목적 고지(h1 바로 아래), 서버 렌더링 설명 문단, 룰렛 영역.
2. 룰렛: 업태 목록을 룰렛처럼 돌려 한 개를 뽑는다. 뽑힌 업태와 "오늘의 점심운" 문구 한 줄을 보여준다. 사용자는 뽑은 결과를 확인하고, 필요하면 다시 뽑을 수 있다(Q4).
3. 주변 가게 보기 버튼: 누르는 순간 위치 권한을 요청한다. 룰렛을 돌리는 것만으로는 위치를 묻지 않는다.
4. 허용 흐름: 현재 위치 기준 반경 안에서 선택 업태의 가게 목록을 무작위 순서로 보여준다. 각 가게에 지도 검색 링크 두 개를 둔다.
5. 거부·실패 흐름: 위치 권한을 거부하거나 위치 확인이 실패하면 오류 대신 시·도, 시·군·구 선택 흐름으로 바꾼다. 선택한 지역 기준으로 같은 목록을 보여준다.
6. 빈 결과 흐름: 반경 안에 가게가 없으면 빈 상태 문구와 "다른 업태 뽑기" 버튼을 보여준다.
7. 결과 하단: 짧은 고지 문구와 공공데이터 기준 안내를 다시 보여준다.

흐름 요약: 룰렛 → (결과 확인) → 주변 가게 보기 → 위치 허용: 목록 → 지도 링크 / 위치 거부: 지역 선택 → 목록 → 지도 링크.

## 업태 분류 처리 방안

현재 상태: 데이터의 `category` 실제 값 분포를 확인하지 못했다. 기획 단계에서 DB에 접근하지 않았다. 아래는 확인 전 방안이다.

- 원칙 1: 룰렛 항목은 원본 `category` 값을 그대로 쓰지 않고 고정된 업태 그룹 목록을 쓴다. 원본 값은 표기가 제각각이거나 세분화되어 있을 가능성이 높다. 그룹은 사용자 승인 후 확정한다.
- 원칙 2: 원본 값을 그룹에 옮기는 매핑표는 코드 안 상수로 둔다(`data-storage.md`의 "코드 안 상수" 기준). DB에 매핑 테이블을 새로 만들지 않는다(용량 제약).
- 원칙 3: 점심 목록에서 제외할 업종이 있다. 예: 카페·제과, 주점·유흥, 편의점성 업종. 제외 목록을 확정해야 한다(Q3).
- 원칙 4: 그룹에 가게가 너무 적으면(지역 기준) 룰렛 항목에서 빼거나, 빈 상태 처리를 한다. 기준 수치는 Q3과 함께 정한다.
- 원칙 5: 데이터 값이 음식 종류(한식, 중식)가 아니라 인허가 업종 분류(예: 일반음식점, 휴게음식점)라면 룰렛 의미가 달라진다. 이 경우 기획을 다시 맞춘다(Q2).
- 확인 요청: 사용자가 데이터에서 `category`의 값별 개수(상위 목록)를 조회해 주면 그 결과로 그룹과 제외 목록을 확정한다. 권장 조회는 읽기 전용 집계 한 번이다.

## 노출 문구 규칙

- 말투: 합니다체로 통일한다(`tarot` 기획과 같은 원칙).
- 룰렛 결과 문구는 "오늘의 점심운"을 쓰되, 운세처럼 단정하지 않는다. 예: "오늘은 국물 요리가 어울리는 날일 수 있습니다." 같은 가벼운 표현만 쓴다. "반드시", "무조건", "대박", "최고의 선택" 같은 표현은 쓰지 않는다.
- 금지 표현: 특정 가게 추천, 맛·위생·친절 평가, "맛집", "추천 가게", "인기", "베스트", "광고" 표시가 붙은 목록. 가게 목록에는 순위 번호를 붙이지 않는다.
- 가게 정보는 공공데이터 원문 그대로 보여준다(상호명, 도로명 주소, 없으면 지번). 운영자가 임의로 바꾸거나 설명을 덧붙이지 않는다.
- 지도 링크 라벨은 "카카오맵에서 찾아보기", "네이버지도에서 찾아보기"처럼 검색 행위를 나타낸다. 외부 사이트 이동임을 링크 옆에 표시한다.
- 위치 요청 전에 "위치 정보는 주변 가게를 찾는 데만 쓰고 저장하지 않습니다."라는 안내를 버튼 근처에 둔다.
- 상표 사용: 카카오, 네이버는 링크 라벨에서만 쓴다. 로고를 쓰지 않는다.

## 유저 스토리

- US-1: 점심 메뉴를 정하지 못한 직장인으로서 룰렛으로 업태를 뽑고 싶다. 왜냐하면 고르는 시간을 줄이고 싶기 때문이다.
- US-2: 뽑힌 업태를 원하는 사용자로서 지금 있는 곳 근처 가게 목록을 보고 싶다. 왜냐하면 바로 걸어갈 곳을 찾고 싶기 때문이다.
- US-3: 목록에서 마음에 드는 가게를 고른 사용자로서 지도 앱에서 길과 정보를 확인하고 싶다. 왜냐하면 이 서비스는 상세 정보를 주지 않기 때문이다.
- US-4: 위치 권한을 주고 싶지 않은 사용자로서 시·군·구를 골라 같은 목록을 보고 싶다. 왜냐하면 위치를 공유하지 않아도 쓰고 싶기 때문이다.
- US-5: 위치를 공유하는 것이 걱정되는 사용자로서 위치가 어디에도 저장되지 않는다는 말을 보고 싶다. 왜냐하면 개인 위치가 남는 것을 원하지 않기 때문이다.
- US-6: 검색으로 들어온 방문자로서 "오늘 뭐 먹지"나 "점심 룰렛"을 검색해 바로 룰렛을 돌리고 싶다. 왜냐하면 가입 없이 쓰고 싶기 때문이다.
- US-7: 목록이 폐업한 가게를 보여줄 수 있다는 점을 아는 사용자로서 확인 안내를 보고 싶다. 왜냐하면 헛걸음을 피하고 싶기 때문이다.
- US-8: 쿠키 동의를 거절한 방문자로서 광고 동의와 관계없이 룰렛과 목록을 쓰고 싶다. 왜냐하면 기능 사용과 광고는 별개이기 때문이다.
- US-9: 운영자로서 목록이 광고나 추천 순위처럼 보이지 않는다는 점을 확인하고 싶다. 왜냐하면 공정 노출 원칙과 광고 정책을 지키기 위해서다.

## 완료 조건 (AC)

QA가 이 목록으로 Playwright 테스트를 만든다. 화면에서 확인할 수 있는 문장으로 쓴다. 테스트에서 위치 권한은 mock으로 허용, 거부, 실패 상태를 만들 수 있다고 가정한다. 문구 인용은 일치가 아니라 의미 기준으로 확인한다. 열린 질문이 확정되기 전까지 괄호 표시 AC는 보류한다.

룰렛 (`/lunch/today`)
- AC-1: 로그인 없이 페이지에 접속해 룰렛을 돌릴 수 있다. 이때 위치 권한 요청이 뜨지 않는다.
- AC-2: 룰렛을 돌리면 업태 한 개가 결과로 표시되고, "오늘의 점심운" 문구 한 줄이 함께 보인다.
- AC-3: 결과 문구에 "반드시", "무조건", "보장" 같은 단정 표현이 없다.
- AC-4: 모션 줄이기 설정이 켜진 상태에서는 룰렛 회전 애니메이션이 없고, 결과만 바뀐다.
- AC-5: (Q4 확정 후) 다시 뽑기 버튼의 유무와 동작이 확정된 내용과 같다.

주변 가게
- AC-6: "주변 가게 보기" 버튼을 누르면 브라우저 위치 권한 요청이 뜬다. 룰렛을 돌리는 것만으로는 권한을 요청하지 않는다.
- AC-7: 위치를 허용하면 뽑힌 업태의 가게 목록이 보인다. 목록의 모든 항목은 선택한 업태에 속한다.
- AC-8: 목록의 각 항목에 상호명, 주소(도로명 주소, 없으면 지번)가 보인다.
- AC-9: 목록에 순위 번호, "추천", "인기", "광고", "AD" 표시가 없다.
- AC-10: 각 가게 항목에 "카카오맵에서 찾아보기"와 "네이버지도에서 찾아보기" 링크가 있고, 누르면 각 지도 검색 페이지가 새 탭에서 열린다. 링크 옆에 외부 사이트 이동 표시가 있다.
- AC-11: 같은 업태와 위치에서 "다시 섞기"(또는 Q6 확정안)를 누르면 목록 순서가 바뀔 수 있다. 목록 항목 수는 확정된 상한을 넘지 않는다.
- AC-12: 좌표는 localStorage, sessionStorage, 쿠키 어디에도 저장되지 않는다. 테스트는 페이지 종료 후 각 저장소를 검사한다.
- AC-13: (Q7 확정 후) 거리 표시 여부가 확정된 내용과 같다.

위치 거부·실패
- AC-14: 위치 권한을 거부하면 오류 화면 대신 시·도, 시·군·구 선택 흐름이 보인다.
- AC-15: 지역을 선택하면 그 지역 기준 목록이 보이고, 지역 선택 흐름에서도 지도 링크가 동작한다.
- AC-16: 위치 확인이 실패(시간 초과, 사용 불가)해도 AC-14와 같은 대체 흐름이 보인다.
- AC-17: 위치 권한이 거부된 상태에서 안내 문구가 "브라우저 설정에서 위치 권한을 허용하면 현재 위치로 찾을 수 있습니다"의 의미로 보인다.

빈 결과
- AC-18: 반경 안에 가게가 없으면 빈 상태 문구와 "다른 업태 뽑기" 버튼이 보인다. 버튼을 누르면 룰렛으로 돌아간다.
- AC-19: 가게 목록 요청이 실패하면 오류 문구와 다시 시도 버튼이 보이고, 룰렛 결과는 사라지지 않는다.

고지와 개인정보
- AC-20: h1 바로 아래에 "본 서비스는 오락 목적으로 제공되며, 실제 식당 선택이나 영업 여부를 보장하지 않습니다"의 의미를 가진 문구가 보인다.
- AC-21: 목록 근처에 "가게 정보는 공공데이터를 기준으로 하며, 폐업·이전·휴업 여부를 보장하지 않습니다"의 의미를 가진 문구가 항상 보인다.
- AC-22: 위치 요청 버튼 근처에 위치 정보 사용 목적과 저장하지 않는다는 안내가 보인다.
- AC-23: `/privacy` 페이지에 위치 정보 항목(수집 여부, 목적, 저장하지 않음, 거부 시 대체 흐름)이 추가되어 있다. `/terms`에 외부 지도 링크와 영업 정보 보장 없음 문구가 추가되어 있다.

광고와 접근성
- AC-24: 쿠키 동의를 거절한 상태에서도 룰렛과 주변 가게 목록이 동작한다.
- AC-25: 모바일 뷰포트(Playwright mobile 프로젝트)에서 AC-1부터 AC-19가 같은 방식으로 동작한다.
- AC-26: 룰렛 버튼과 가게 항목 링크는 키보드로 포커스와 실행이 가능하다.

메뉴와 검색 노출
- AC-27: 메뉴의 점심 항목 설명과 예시에 "가격대", "혼밥", "별점", "후기" 단어가 없다.
- AC-28: 서버가 보내는 `/lunch/today` HTML에 h1, 설명 문단, FAQ 텍스트가 들어 있다(클라이언트 렌더링 전 HTML 검사).
- AC-29: 출시 상태에서 `robots`에 noindex가 없고, canonical과 og 정보가 `buildMetadata()` 결과와 같다.
- AC-30: 출시 상태에서 메뉴 점심 그룹에 "준비 중" 표시가 없고, `/sitemap.xml`에 `/lunch/today`가 있다.
- AC-31: 페이지의 JSON-LD는 BreadcrumbList와 FAQPage 두 가지이며, 가게 개별 정보를 담은 구조화 데이터가 없다.

## 예외·빈 상태

- 위치 권한 거부: 지역 선택 흐름으로 전환한다(AC-14, AC-15). 같은 브라우저에서 다시 들어와도 권한 요청을 자동으로 반복하지 않는다. 버튼은 항상 보이게 둔다.
- 위치 확인 실패(시간 초과, 신호 없음): 같은 대체 흐름을 쓴다(AC-16).
- 한국 밖 좌표 또는 데이터 범위 밖: 가게가 없으므로 빈 상태(AC-18)로 처리한다.
- 반경 안 가게 없음: 빈 상태 문구와 다른 업태 뽑기 버튼(AC-18). 반경을 넓히는 버튼은 Q5 결과에 따른다.
- 좌표가 없는 데이터(lat 또는 lng가 없음): 목록에서 제외한다. 사용자에게 따로 표시하지 않는다.
- 주소가 비어 있는 데이터: 상호명만 보여주고 주소 줄은 숨긴다. 지도 링크는 상호명으로 검색한다.
- 같은 상호가 여러 번 나오는 경우: 공공데이터 원문대로 보여준다. 중복 제거는 하지 않는다(범위 밖).
- 룰렛 중 새로고침: 결과는 저장하지 않으므로 처음부터 다시 시작한다(Q4 확정 전 기본안).
- 위치 허용 후 목록을 보는 중 권한이 철회된 경우: 다음 요청에서 AC-14 흐름으로 전환한다.
- 가게 수가 아주 많은 지역(예: 대도시 중심): 목록 상한(Q6)을 넘는 항목은 무작위로 골라 보여준다. 표시 개수는 항상 같다.
- 업태 그룹에 해당 지역 가게가 0개인 경우: 룰렛 결과에서는 뽑힐 수 있으나 목록에서 빈 상태가 된다. 룰렛 항목 제외 기준은 Q3에서 정한다.

## 법적·정책 요구사항

- 개인정보 수집: 위치 정보(좌표)를 수집한다. 브라우저 위치 권한을 허용하면 좌표를 주변 가게 검색 요청에 쓴다. 서버는 검색에만 쓰고 저장하지 않는다는 것이 기획 요구다. 다음 사항은 확정이 필요하다.
  - 서버 접속 로그, Vercel 등 호스팅 로그에 정확한 좌표가 남으면 "저장하지 않는다"는 말과 충돌한다. 요구: 정확한 좌표가 로그와 분석 도구에 남지 않아야 한다. 방법(정밀도 낮춤, 요청 방식 등)은 설계 단계에서 정한다(Q9).
  - 좌표는 localStorage, sessionStorage, 쿠키에 저장하지 않는다(AC-12).
  - 개인정보처리방침 개정이 필요하다. 현재 문서에는 위치 항목이 없다. 추가할 내용: 수집 여부, 목적(주변 가게 검색), 서버 저장 여부와 로그 처리 방식, 거부 시 대체 흐름, 처리 위탁(호스팅, 지도 외부 링크로 이동 시 해당 사업자 정책 적용).
  - 개인위치정보 관련 법률 검토가 필요하다(Q8). 위치정보의 보호 및 이용 등에 관한 법률의 적용 여부(위치기반서비스 사업자 신고, 동의 방식, 보관 기준), 14세 미만 아동의 위치 정보 처리 관련 규정을 확인해야 한다. 이 기획은 법적 판단을 하지 않는다. 확인이 끝나기 전에는 출시하지 않는다(사용자 판단 필요).
  - 업태, 가게 이름, 주소는 공공데이터의 사업장 정보다. 개인정보가 아니며 개인 식별 정보(대표자명 등)는 테이블에 없다. 마이그레이션에 있는 `mgt_no`는 화면에 보여주지 않는다.
- 고지 문구:
  - 상시 오락 목적 고지(h1 아래, 항상 보임): "본 서비스는 오락 목적으로 제공되며, 실제 식당 선택이나 영업 여부를 보장하지 않습니다."
  - 영업 여부 보장 없음(목록 근처, 항상 보임): "가게 정보는 공공데이터를 기준으로 하며, 폐업·이전·휴업 여부를 보장하지 않습니다. 방문 전에 지도 앱이나 가게에 직접 확인하세요."
  - 데이터 기준일(Q11 확정 후): "데이터 기준일: YYYY-MM-DD"
  - 위치 사용 안내(위치 요청 버튼 근처): "위치 정보는 주변 가게를 찾는 데만 사용하며, 서버나 브라우저에 저장하지 않습니다." (로그 처리 방식이 정해지면 문구를 맞춘다.)
  - 외부 링크 안내: "지도 검색 페이지는 카카오와 네이버가 운영하는 외부 사이트입니다. 이동 후에는 해당 사이트의 정책이 적용됩니다."
  - 결과 하단 짧은 고지: 오락 목적 고지를 한 번 더 둔다.
  - 공공데이터 출처 표기: "출처: 공공데이터포털 음식점 정보 (이용 조건과 표기 문구는 Q12 확정 후 확정)". `THIRD_PARTY_NOTICES.md`에 기록한다.
- 상업적 이용 주의:
  - 수익은 AdFit 광고만 쓴다. 가게 광고, 제휴 링크, 유료 노출을 만들지 않는다. 가게 목록이 광고처럼 보이지 않도록 AC-9를 지킨다.
  - 공공데이터의 이용 조건(상업적 이용 허용 여부, 출처 표기 방식, 공공누리 유형)을 확인해야 한다. 확인 전에는 광고 수익이 있는 상태에서 출시하지 않는다(Q12).
  - 지도 서비스 검색 링크는 외부 사이트 이동이다. 지도 API를 쓰지 않으므로 API 키와 사용량 제한은 없다. 다만 두 서비스의 링크 이용 정책은 확인이 필요하다(Q17).
  - 가게 데이터를 대량으로 복사해 다른 사이트에 공개하지 않는다. 목록은 사용자 요청마다 반경 안 결과만 보여준다.
  - 카카오, 네이버 상표는 링크 라벨 텍스트로만 쓴다.
- 서비스 약관(이용약관): 외부 링크 이동, 영업 정보 보장 없음, 위치 정보 사용, 공공데이터 기준 안내를 추가한다(AC-23).
- COMPLIANCE.md 11장에 점심 고지 항목을 추가한다(타로, 운세 형식을 따른다). 법률 검토 여부는 "위험 수용" 또는 "검토 완료" 중 하나로 기록한다. 현재 사용자 결정은 없다(Q8).
- 연령: 연령 확인 게이트는 없다. 위치 수집과 관련해 Q8에서 확인한다.
- 위기 안내(자살, 정신건강 전화): 이 기능은 민감한 입력을 받지 않으므로 필요 없다.

## 열린 질문

이 기획의 확정을 막는 질문은 PM을 거쳐 사용자에게 올린다. 우선순위 A는 승인 전에 답이 필요하다. B는 설계 또는 개발 전에 답이 필요하다. C는 출시 전에 답이 필요하다.

- Q1 (A, 사용자): `restaurants.category`의 실제 값 분포가 궁금하다. 값 종류 수, 상위 값과 개수, 빈 값(null) 비율을 알려 주면 업태 그룹과 제외 목록을 확정한다. 권장 조회는 읽기 전용 집계 한 번이다. 기획 단계에서는 DB에 접근하지 않았다.
- Q2 (A, 사용자): `category` 값이 음식 종류(한식, 중식, 일식 등)인지, 인허가 업종 분류(일반음식점, 휴게음식점 등)인지 확인이 필요하다. 후자라면 룰렛 항목 자체를 다시 설계해야 한다.
- Q3 (A, 사용자): 룰렛 업태 그룹의 목록, 점심 목록에서 제외할 업종(예: 카페, 제과, 주점, 유흥, 편의점성 업종), 그룹을 룰렛에서 뺄 최소 가게 수 기준.
- Q4 (A, 사용자): 룰렛 다시 뽑기를 허용할지, 횟수 제한을 둘지. 결과를 같은 기기에서 유지할지(타로처럼 하루 고정)와 기본 가정 "새로고침 시 결과 초기화"가 맞는지. 결과 유지가 필요하면 날짜 키 저장이 생기므로 기획을 다시 맞춘다.
- Q5 (A, 사용자): 기본 반경과 선택 옵션. 제안은 기본 1km, 선택 500m, 1km, 2km다. 반경을 넓히는 버튼을 둘지.
- Q6 (A, 사용자): 한 번에 보여줄 목록 개수(제안: 10개), "다시 섞기"와 "더 보기" 중 방식.
- Q7 (B, 사용자): 거리 표시 여부. 제안은 거리 표시를 하되 정렬은 하지 않는다. 거리 표시가 "가까운 순"으로 오해될 수 있는지 검토가 필요하다.
- Q8 (A, 사용자, 법률): 위치정보 관련 법령 적용 여부. 개인위치정보 처리 시 신고 또는 동의 방식, 보관 기준, 14세 미만 아동 관련 규정. 법률 검토를 받을지, 위험 수용으로 갈지 결정이 필요하다. 이 결정 없이는 출시 기준을 세울 수 없다.
- Q9 (A, 사용자): 서버 접속 로그와 호스팅 분석 도구에 정확한 좌표가 남지 않아야 한다는 요구를 기획 원칙으로 확정할지 승인이 필요하다. 구현 방법(좌표 정밀도 낮춤, 요청 형식, 로그 설정)은 설계 단계에서 정한다.
- Q10 (B, 사용자): 위치 거부 시 시·도, 시·군·구 목록의 출처. 데이터 주소에서 만들지, 코드 상수로 둘지. 어느 쪽이든 목록 자체는 설계 단계에서 정한다.
- Q11 (B, 사용자): 데이터 기준일을 화면에 표시할지. 기준일은 초기 적재 시점이며 후속 cron이 나오기 전까지 고정된다.
- Q12 (A, 사용자): 공공데이터 이용 조건 확인. 상업적 이용 허용 여부, 출처 표기 문구, 공공누리 유형, 변경 사항 고지 의무. 광고 수익이 있는 서비스이므로 확인 전 출시하지 않는다.
- Q13 (A, 사용자): 페이지 title과 description 정정안 승인. "메뉴 추천" 표현을 유지할지(검색량 측면) 바꿀지(실제 기능 측면) 결정이 필요하다.
- Q14 (B, 설계 단계로 넘김): 반경 검색 방식. 단순 bbox 조건과 거리 계산으로 할지, PostGIS 같은 공간 인덱스를 쓸지. 테이블 약 67만 행(예상 용량 약 250MB), 무료 플랜 500MB 제약을 고려해야 한다. 공개 읽기(RLS `using (true)`)를 그대로 쓸지, 서버 API만 읽게 할지도 설계에서 정한다. 신규 테이블은 최소화한다.
- Q15 (B, 사용자와 UI 단계): 메뉴 점심 항목의 `colorClass`(`text-orange-600`)와 디자인 규칙 토큰(`menu-lunch`, `#a5481f`)이 다르다. 토큰으로 통일할지 승인이 필요하다. `design-system.md` 표 변경이 필요하면 사용자 승인 후 바꾼다.
- Q16 (C, 사용자): 가게별 상세 페이지와 지역별 landing 페이지는 이번 범위 밖이다. 검색 유입을 더 원하면 후속 기획으로 다룰지 결정이 필요하다.
- Q17 (C, 사용자): 카카오맵, 네이버지도 검색 링크 방식의 이용 정책 확인(검색 링크 사용 허용 범위, 라벨 표기 규칙). 확인 전 출시하지 않는다.
- Q18 (B, 사용자): "오늘의 점심운" 문구 샘플 검수. 결과 문구 목록을 몇 개 만들지, 개수와 톤 검수 방식(타로처럼 샘플 검수 후 나머지 작성)을 정한다.
- Q19 (C, 사용자): 출시 시점에 음식점 동기화 cron이 없는 상태를 허용할지. 폐업 가게가 섞이는 기간이 생기므로 고지 문구(AC-21)로만 대응한다. 기간 제한이나 허용 범위를 정해야 한다.
- Q20 (C, PM): 메뉴 설명, `REFACTORING.md` 34~37행, `README.md`의 API 표(반경 검색 API가 생기면 추가), `THIRD_PARTY_NOTICES.md`(공공데이터 출처), `DEPENDENCY_LICENSES.md`(새 라이브러리가 생기면) 갱신을 누가 언제 할지 정한다.

## 후속 작업 (이 기획 범위 밖)

- 음식점 동기화 cron: 공공 API 조사 완료 후 별도 기획. 신규 가게 추가와 폐업 가게 반영, 실패 시 재시도, 적재 기준일 갱신을 포함한다. 이번 기능은 이 cron에 의존하지 않는다.
- 가게 상세 정보나 지도 앱 API 연동이 필요해지면 별도 기획과 법적 검토를 한다.
- 지역별 landing 페이지와 가게 카드 페이지는 검색 유입 데이터를 본 뒤 결정한다.
