## 목표

점심 메뉴를 정하기 어려운 사용자가 룰렛으로 메뉴 하나를 가볍게 뽑고, 뽑힌 메뉴를 카카오맵이나 네이버지도에서 바로 검색해 볼 수 있게 하는 무료 오락 서비스를 만든다. 서버는 사용자 위치, 가게 정보, 룰렛 결과를 다루지 않는다.

## 확정 방향 (다시 묻지 않는다)

1. 뽑는 단위는 메뉴다(예: 짜장면, 김치찌개, 돈카츠). 업태를 먼저 뽑지 않는다. 업태를 뽑으면 그 안에서 또 메뉴를 골라야 하므로 처음부터 메뉴를 돌린다.
2. 결과 메뉴에서 "근처에서 찾기"는 카카오맵·네이버지도 검색 링크로 넘긴다. 검색어는 메뉴 이름이다. 자체 가게 DB, 주변 가게 목록, 위치 권한, 지오코딩, 공공데이터 적재는 하지 않는다. 우리 서버는 사용자 위치를 받지 않는다.
3. 메뉴 데이터는 정적 데이터(코드 상수)로 만든다. DB를 쓰지 않는다.
4. 사이트 컨셉은 "운"이다. 돌림판 연출과 "오늘의 점심운" 문구를 붙인다.
5. 돌림판은 이후 "운빨 뽑기 도구(사다리타기, 돌림판, 제비뽑기)"와 공유할 재사용 컴포넌트가 될 가능성이 크다. 이번 기획에서는 이 가능성만 적고, 점심 도메인과 분리하는 방식은 설계 단계에서 정한다.

- `supabase/migrations/0003_restaurants.sql`: 스테이징 상태이고 적용 여부는 확인하지 않았다. 새 방향에서는 이 테이블이 필요 없다. 파일을 어떻게 할지(삭제, 보관, 다른 용도)는 사용자가 정한다(Q9). 기획자는 건드리지 않는다.
- `docs/lunch/status.md`의 2 설계 승인 대기 상태와 설계 D1~D9는 새 방향에 맞지 않으므로 무효다. 설계는 이 기획이 승인된 뒤 새로 쓴다.
- 쿠키 동의 원칙: 타로·운세와 같다. 점심 기능은 쿠키 동의 여부와 관계없이 동작한다(AC-23). AdFit 광고는 기존처럼 모든 페이지에 붙는다.
- 브라우저 저장: 점심 기능은 저장할 데이터가 없다. 룰렛 결과와 조건 선택은 새로고침하면 사라진다. 기존 localStorage 키(동의 상태 등)와 충돌하지 않는다.

## 화면 목록과 흐름

화면은 `/lunch/today` 한 페이지다. 별도 라우트는 만들지 않는다.

1. 진입: h1 "오늘 뭐 먹지", 상시 오락 고지(h1 바로 아래), 설명 문단, 사용 순서 3단계, 룰렛 영역.
2. 조건 선택: 카테고리(한식, 중식, 일식, 양식, 분식, 세계·기타)를 칩으로 고른다. 기본은 전체 선택이다. 칩을 하나도 고르지 않으면 룰렛 버튼이 꺼지고 안내 문구가 보인다.
3. 룰렛: 선택한 카테고리의 메뉴가 돌림판 칸에 놓인다. "룰렛 돌리기" 버튼을 누르면 돈다. 결과는 돌리기 전에 정해지고, 연출은 그 메뉴에서 멈춘다.
4. 결과: 뽑힌 메뉴 이름, 카테고리 이름, "오늘의 점심운" 라벨과 문구 한 줄을 보여 준다. 결과 아래에 지도 검색 링크 두 개와 "다시 뽑기" 버튼을 둔다.
5. 지도 링크: "카카오맵에서 찾아보기", "네이버지도에서 찾아보기"를 누르면 각 지도 검색 페이지가 새 탭에서 열린다. 링크 옆에 외부 사이트 이동 표시를 둔다.
6. 다시 뽑기: 같은 조건으로 다시 돌린다. 이전 결과는 지워진다. 직전 메뉴 제외 여부는 Q3에서 정한다.
7. 조건 변경: 칩을 바꾸면 룰렛 칸이 바뀐다. 기존 결과를 지울지는 Q4에서 정한다(기본안: 지운다).
8. 결과 하단: 오락 목적 고지와 무작위 결과 고지를 짧게 다시 보여 준다.

흐름 요약: 진입 → 카테고리 선택(기본 전체) → 룰렛 돌리기 → 결과 메뉴와 점심운 문구 → 지도 링크 또는 다시 뽑기.

위치 권한은 어떤 단계에서도 요청하지 않는다. 지도 검색 페이지가 위치를 쓸지는 해당 서비스 정책에 따른다(지도 링크 장 참고).

## 메뉴 데이터 범위 (제안)

근거와 한계: 리서치를 하지 않았고 공공 데이터도 쓰지 않는다. 아래 분류와 개수는 일반적인 점심 메뉴 분류를 바탕으로 한 기획자 제안이다. 사용자 검수가 필요하다(Q1).

| 카테고리 | 1차 메뉴 수 | 예시 메뉴 (확정 아님) |
|---|---|---|
| 한식 | 10 | 김치찌개, 된장찌개, 비빔밥, 제육볶음, 불고기, 순대국, 설렁탕, 칼국수, 냉면, 백반 |
| 중식 | 8 | 짜장면, 짬뽕, 탕수육, 볶음밥, 마라탕, 마라샹궈, 누룽지탕, 깐풍기 |
| 일식 | 8 | 돈카츠, 초밥, 라멘, 우동, 규동, 소바, 카레라이스, 가라아게 |
| 양식 | 8 | 파스타, 스테이크, 리조또, 피자, 오므라이스, 샌드위치, 햄버거, 그라탕 |
| 분식 | 6 | 떡볶이, 김밥, 라볶이, 쫄면, 튀김, 어묵 |
| 세계·기타 | 8 | 쌀국수, 팟타이, 타코, 케밥, 샤브샤브, 똠얌꿍, 치킨, 쌈밥 |
| 합계 | 48 | |

제안 근거
- 총 48개: 40개 미만이면 며칠 사이 같은 메뉴가 자주 보인다고 느끼기 쉽다. 60개를 넘으면 돌림판 칸의 글자가 작아져 결과를 읽기 어렵다(칸 수 최종 판단은 ui-ux 단계).
- 카테고리 간 균형: 메뉴마다 같은 확률이면 카테고리 확률은 메뉴 수에 비례한다. 한식 10개는 약 21%, 나머지 대부분은 약 17%다. 한 카테고리가 과하게 나오지 않도록 차이를 작게 둔다. 분식은 6개로 가장 적은데, 이 값이 카테고리 하나만 골랐을 때의 최소 메뉴 수가 된다. 조건 하나만 골라도 뽑기가 성립하도록 최소 6개를 보장한다.
- 한식을 많이 둔 이유: 국내 점심 외식에서 한식 비중이 크다는 일반적 가정이다. 근거 자료는 없다(Q1).
- 메뉴 이름은 모두 일반 음식 이름이다. 특정 프랜차이즈 상표(예: 브랜드 이름이 붙은 메뉴)는 넣지 않는다.
- 1차 항목은 이름만 둔다. 메뉴 설명, 재료, 가격, 사진은 넣지 않는다. 설명을 넣으면 맛·건강 평가와 식품 광고 표현 위험이 생긴다(법적 장 참고).

## 조건 필터 후보

메뉴 자체의 속성으로만 판단할 수 있는 항목만 후보로 둔다. 필터를 많이 두면 뽑을 칸이 줄어 "운" 느낌이 약해지고, 추천처럼 보일 수 있다. 1차에는 카테고리 선택만 필수로 두고 나머지는 Q2에서 정한다.

| 후보 | 설명 | 판단 | 제안 |
|---|---|---|---|
| 카테고리 선택 | 고른 카테고리 안에서만 뽑기 | 메뉴 속성이 명확하다 | 필수 (기본 전체 선택) |
| 국물 있음·없음 | 국물 요리만, 또는 비국물만 | 국물의 경계(짜장면은 없음, 쌀국수는 있음 등) 기준이 필요하다 | 선택 후보 (Q2) |
| 주재료(면, 밥, 고기, 빵) | 면 요리만 뽑기 등 | 메뉴마다 대표 재료 기준이 필요하고 한 메뉴에 여러 재료가 있다 | 보류 |
| 매운맛 | 매운 메뉴 제외 등 | 주관적이라 같은 메뉴도 집마다 다르다 | 보류 |
| 고기 포함 여부 | 채식 고려 | 대표 재료 기준이라 오해를 부를 수 있다 | 보류, 신중 |
| 최근 뽑은 메뉴 제외 | 연속 중복 방지 | 저장 없이 화면 안에서만 가능하다. 새로고침하면 사라진다 | 선택 후보 (Q3) |
| 혼밥 가능 | 혼자 먹기 쉬운지 | 식당 속성이지 메뉴 속성이 아니다 | 제외 |
| 가격대 | 저렴, 비싼 메뉴 | 정확한 가격 정보가 없다 | 제외 |
| 조리·대기 시간 | 빨리 나오는 메뉴 | 주관적이고 식당마다 다르다 | 제외 |

## 노출 문구 규칙

- 말투: 합니다체로 통일한다.
- 점심운 문구: 운세처럼 단정하지 않는다. 메뉴 특성을 과장하지 않는다. 예: "오늘은 국물 요리가 어울리는 날일 수 있습니다." 같은 가벼운 표현만 쓴다.
- 결과 문구에 쓰지 않는 표현: 반드시, 무조건, 보장, 확실, 100%, 최고, 대박, 맛집, 인기, 베스트, 1위, 광고, 추천합니다, 추천 메뉴. 고지 문구의 "보장하지 않습니다"만 예외다.
- 맛, 건강, 영양, 효능을 설명하는 문장을 쓰지 않는다. 메뉴 이름 말고는 메뉴를 설명하지 않는다.
- 뽑힌 결과는 "뽑힌 메뉴"나 "오늘의 메뉴"로 부른다. "추천"이라는 말을 쓰지 않는다. 무작위 결과임을 상시 고지한다.
- 지도 링크 라벨: "카카오맵에서 찾아보기", "네이버지도에서 찾아보기"처럼 검색 행위를 나타낸다. 외부 사이트 이동 표시를 링크 옆에 둔다. 라벨 "근처에서 찾기"는 Q5 결과에 따라 쓴다.
- 상표: 카카오, 네이버는 링크 라벨 텍스트로만 쓴다. 로고와 아이콘을 쓰지 않는다.
- 가게 목록이 없으므로 순위 번호, 광고 표시, 가게 평가 문구는 해당하지 않는다. 그래도 노출 문구 전체에 "추천 가게", "인기", "광고" 표현을 쓰지 않는다.

## 지도 링크 방식과 한계

방식
- 결과 메뉴 이름을 검색어로 카카오맵, 네이버지도의 웹 검색 페이지를 새 탭으로 연다.
- 우리 서버는 검색어를 저장하지 않고, 두 지도 서비스에 사용자 정보를 보내지 않는다. 검색어는 메뉴 이름뿐이다.
- 지도 API, 앱 연결 주소, 로그인 연동을 쓰지 않는다. API 키와 사용량 제한이 없다.

한계
- 검색 기준 위치: 링크가 사용자의 현재 위치 기준으로 검색되는지 확인이 필요하다. 메뉴 이름만 검색하면 지도 서비스가 지역 기본값을 쓸 수 있다. 확인 전에는 "근처에서 찾기"라는 라벨을 쓰지 않는다(Q5). 검색어에 "근처"나 "점심" 같은 말을 붙이는 것이 결과를 바꾸는지도 확인한다.
- 결과 품질은 지도 서비스가 정한다. 우리는 검색 결과의 정확성, 가게의 영업 여부, 검색 결과에 붙은 광고를 통제하지 않는다. 링크 옆 안내 문구에 이 점을 밝힌다.
- 모바일: 앱이 열릴지, 웹에서 열릴지는 각 서비스 동작에 따른다. 확인이 필요하다(Q17).
- 링크 정책: 두 서비스의 검색 링크 이용 조건과 라벨 규칙을 출시 전에 확인한다(Q17).

## 예외·빈 상태

- 카테고리를 하나도 고르지 않음: 룰렛 버튼을 끄고 "카테고리를 하나 이상 고르세요"라는 뜻의 안내를 보인다.
- 카테고리 하나만 고름: 최소 6개 메뉴 안에서 뽑는다. 메뉴 수가 6개 밑으로 내려가는 조건은 없다.
- 룰렛 연출 중: 버튼과 칩을 누를 수 없게 하고, 중복 실행을 막는다.
- 조건을 바꾼 뒤: 기존 결과를 지운다(기본안, Q4).
- 직전 결과와 같은 메뉴가 연속으로 나옴: 기본안은 허용이다. 직전 메뉴 제외는 Q3에서 정한다.
- 새로고침: 결과, 조건 선택, 연출 상태 모두 처음 상태로 돌아간다. 저장하지 않는다.
- 모션 줄이기 설정: 회전 없이 결과만 바뀐다. 결과 문구와 지도 링크는 똑같이 보인다.
- 지도 링크 팝업 차단: 링크는 일반 링크로 두며 별도 처리는 하지 않는다. 브라우저 설정에 따른다.
- JavaScript 꺼짐: 설명, 사용 순서, FAQ, 고지는 서버 HTML로 보인다. 룰렛 영역에는 "자바스크립트를 켜야 이용할 수 있다"는 안내를 보인다.
- 메뉴 목록에 중복 이름이 있음: 출시 전에 제거한다. 목록 검사로 확인한다.

## 검색 노출

- 키워드: 오늘 뭐 먹지, 점심 뭐 먹지, 점심 메뉴 추천, 점심 룰렛, 점심 메뉴 룰렛, 오늘 점심 메뉴, 점심 메뉴 고르기.
  - "주변 음식점 찾기", "점심 식당 찾기"는 제외한다. 가게 목록이 없는 서비스인데 검색 의도를 받으면 기대와 어긋난다.
- 페이지가 답해야 할 질문:
  - 점심 메뉴를 빨리 고르는 방법은 무엇인가? (룰렛)
  - 메뉴는 어떻게 뽑히나? (선택한 카테고리 안에서 무작위, 같은 확률이며 추천이 아니다)
  - 뽑힌 메뉴는 어디서 찾나? (지도 검색 링크)
  - 결과가 정확하거나 보장되나? (아니다, 오락 목적이다)
  - 어떤 메뉴가 들어 있나? (카테고리와 메뉴 목록)
- 메타데이터: `src/lib/seo.ts`의 `buildMetadata()`로 title, description, canonical, OG를 만든다. 직접 객체를 만들지 않는다.
  - title 초안: "오늘 뭐 먹지 - 점심 메뉴 룰렛" (Q13)
  - description 초안: "룰렛으로 오늘의 점심 메뉴를 무작위로 골라 보는 오락 서비스입니다. 뽑힌 메뉴는 지도 앱에서 바로 검색할 수 있습니다." (Q13)
- 구조화 데이터: BreadcrumbList(홈 > 점심 > 오늘 뭐 먹지), FAQPage(서버 HTML의 FAQ와 같은 내용). 가게 정보를 담은 구조화 데이터(Restaurant, LocalBusiness, ItemList)는 쓰지 않는다.
- 서버 렌더링 콘텐츠: 설명 문단(서비스가 무엇인지), 사용 순서 3단계, 무작위 결과 설명, FAQ 4~5개. 룰렛과 결과는 클라이언트에서 그려도 되지만 설명은 HTML에 있어야 한다.
- FAQ 초안 주제: 무엇을 하는 서비스인지, 메뉴는 어떻게 뽑는지(같은 확률), 추천인지(아니다), 지도 링크는 어디로 가는지, 결과가 맞는지 보장되는지(아니다).
- 현재 상태: `robots: { index: false, follow: true }`가 있다. 출시 시 noindex를 제거하고 title, description을 정정한다.
- 출시 전: noindex를 유지한다. 출시와 함께 `comingSoon`을 풀면 사이트맵에 자동으로 들어간다.
- URL: `/lunch/today`를 유지한다. 이미 메뉴에 노출된 URL이고 "오늘"이라는 말이 뽑기 의미와 맞는다.
- 이미지: OG 이미지 하나만 쓴다. 음식 사진은 쓰지 않는다.

## 법적·정책 요구사항

개인정보 수집
- 우리 서버는 사용자 위치, 식별자, 룰렛 결과, 조건 선택 값을 받지 않고 저장하지 않는다. 이것을 기획 원칙으로 둔다.
- 위치 권한을 요청하지 않는다. 따라서 위치정보 관련 법령(이전 Q8)의 적용 대상은 우리 서비스 기준에서 크게 줄어든다. 적용 여부는 사용자가 확인한다. 기획자는 법률 판단을 하지 않는다(Q11).
- 브라우저 저장: 룰렛 결과와 조건 선택은 화면 메모리에만 둔다. localStorage, sessionStorage, 쿠키, 주소 표시줄(URL)에 넣지 않는다(AC-22).
- 접속 로그: 호스팅 접속 로그에는 페이지 주소가 남는다. 조건 선택 값을 주소에 넣으면 로그에 남으므로 넣지 않는다.
- 분석 도구: 메뉴가 뽑혔다는 이벤트, 지도 링크 클릭 이벤트를 보낼지 정해야 한다. 기본안은 보내지 않는다(Q10). 이벤트를 보내면 분석 동의 조건을 따른다.
- 14세 미만: 민감한 입력이 없으므로 연령 확인 게이트는 두지 않는다(사용자 확인 대상, Q11에 포함).

개인정보처리방침(`src/app/privacy/page.tsx`) 변경 필요성 판단
- 판단: 변경 필요성은 낮다. 위치 수집, 점심 기능의 저장, 쿠키, 광고 식별자 추가가 없으면 기존 방침의 수집 항목과 저장 문구를 바꿀 필요가 없다.
- 선택 사항: 외부 지도 링크로 이동하면 해당 사업자 정책이 적용된다는 한 줄을 외부 서비스 안내에 넣으면 투명성이 좋아진다(Q12).
- 확인 조건: 구현 중 로컬 저장, 이벤트 수집, 외부 연동을 추가하면 이 판단을 다시 한다.

고지 문구(초안, Q13 확정 필요)
- 상시 오락 목적 고지(h1 바로 아래, 항상 보임): "본 서비스는 오락 목적으로 제공되며, 메뉴 선택 결과나 식당의 영업 여부를 보장하지 않습니다."
- 무작위 고지(화면 상시): "결과는 무작위로 정해지며, 특정 메뉴나 식당을 추천하거나 평가하지 않습니다."
- 외부 링크 안내(지도 링크 근처): "지도 검색 페이지는 카카오와 네이버가 운영하는 외부 사이트입니다. 이동 후에는 해당 사이트의 정책이 적용됩니다. 검색 결과와 영업 정보는 해당 서비스 기준입니다."
- 결과 하단 짧은 고지: 오락 목적과 무작위 결과 고지를 한 번 더 둔다.
- 보상 없음 고지(Q6 결과에 따라 추가): "룰렛 결과는 금전, 상품, 포인트와 무관합니다."

상업적 이용
- 수익은 AdFit 광고만 쓴다. 가게 광고, 제휴 링크, 메뉴 판매 연결을 만들지 않는다.
- 메뉴 목록과 문구는 자체 작성한다. 공공데이터를 쓰지 않으므로 출처 표기와 공공누리 조건은 이번 기능에 해당하지 않는다. 자체 작성 기록을 남긴다(타로·운세 copy-log 방식 권장).
- 카카오, 네이버 상표는 링크 라벨 텍스트로만 쓴다.
- 지도 검색 링크 정책은 Q17에서 확인한다.

사행성 우려
- 룰렛 결과가 현금, 포인트, 쿠폰, 경품과 연결되면 안 된다. 이번 기획은 보상이 없다는 전제로 쓴다(Q6).
- 한국의 사행성 관련 규제 해당 여부는 법률 판단이므로 사용자가 확인한다. 기획자는 판단하지 않는다.

식품 표시·광고 우려
- 메뉴에 건강, 효능, 영양, 맛 평가 문장을 쓰지 않는다. 이번 1차 범위는 메뉴 이름만 쓴다.
- 식품 광고 규제 해당 여부는 사용자 확인 대상이다(Q20).

이용약관(`src/app/terms/page.tsx`)
- 점심 추천 조항을 추가한다. 포함할 내용: 오락 목적, 결과는 무작위이며 추천이나 평가가 아님, 식당 정보와 영업 여부 보장 없음, 외부 지도 링크 이동 후 해당 사이트 정책 적용, 보상과 무관함.
- 3장(데이터 출처 및 정확성)은 점심 메뉴가 자체 목록이라는 점을 확인한다. 공공데이터 출처 문구는 필요 없다.
- 11장(제3자 서비스)에 카카오맵, 네이버지도 링크를 추가한다.
- 조항 번호 배치는 설계 또는 PM 단계에서 정한다.

`COMPLIANCE.md` 11장
- 점심 항목을 타로·운세와 같은 형식으로 추가한다(오락 목적 고지, 무작위 결과, 금지 표현 목록 위치, 외부 링크, 보상 없음, 개인정보 미수집).
- 법률 검토 상태는 "위험 수용" 또는 "검토 완료" 중 하나로 기록한다. 현재 사용자 결정은 없다(Q11).

연령·위기 안내
- 민감 입력이 없으므로 위기 상담 안내는 필요 없다.

## 유저 스토리

- US-1: 점심 메뉴를 정하지 못한 직장인으로서 룰렛으로 메뉴를 뽑고 싶다. 고르는 시간을 줄이기 위해서다.
- US-2: 한식이나 분식처럼 종류를 정하고 싶은 사용자로서 카테고리를 골라 그 안에서만 뽑고 싶다. 그날 먹고 싶은 범위가 있기 때문이다.
- US-3: 뽑힌 메뉴를 먹고 싶은 사용자로서 지도 앱에서 그 메뉴를 바로 검색하고 싶다. 이 서비스는 가게 정보를 주지 않기 때문이다.
- US-4: 결과가 마음에 들지 않는 사용자로서 다시 뽑고 싶다. 여러 번 돌려 보는 재미 때문이다.
- US-5: 가입 없이 검색으로 들어온 방문자로서 "점심 룰렛"을 검색해 바로 돌리고 싶다. 가입 절차가 귀찮기 때문이다.
- US-6: 위치를 주고 싶지 않은 사용자로서 위치를 묻지 않는다는 점을 확인하고 싶다. 개인 위치가 남는 것을 원하지 않기 때문이다.
- US-7: 쿠키 동의를 거절한 방문자로서 광고 동의와 관계없이 룰렛을 쓰고 싶다. 기능 사용과 광고는 별개이기 때문이다.
- US-8: 운영자로서 결과가 추천이나 광고로 보이지 않는다는 점을 확인하고 싶다. 광고 정책과 공정 노출 원칙을 지키기 위해서다.

## 완료 조건 (AC)

QA가 이 목록으로 Playwright 테스트를 만든다. 화면에서 확인할 수 있는 문장으로 쓴다. 문구는 일치가 아니라 의미 기준으로 확인한다. 룰렛 결과는 무작위이므로, 테스트는 "결과가 선택한 카테고리 메뉴 목록에 있는지"로 검증한다. 특정 결과가 나오도록 고정해야 할 때의 방법은 설계 단계에서 정하되, 운영 화면에 테스트용 결과 지정 기능을 노출하지 않는다. 열린 질문이 확정되기 전까지 괄호 표시 AC는 보류한다.

룰렛·조건
- AC-1: 로그인 없이 `/lunch/today`에 접속해 룰렛을 돌릴 수 있다.
- AC-2: 룰렛을 돌리면 메뉴 이름 하나가 결과로 표시되고, 그 이름은 현재 선택한 카테고리의 메뉴 목록에 있다.
- AC-3: 기본 상태에서 모든 카테고리 칩이 선택되어 있다.
- AC-4: 카테고리를 하나만 고른 상태에서 10회 돌리면, 모든 결과가 그 카테고리 메뉴 안에 있다.
- AC-5: 카테고리 칩을 모두 끄면 룰렛 버튼이 비활성이고, 카테고리를 하나 이상 고르라는 안내가 보인다.
- AC-6: 모션 줄이기 설정이 켜진 상태에서는 돌림판이 회전하지 않고 결과만 바뀐다.
- AC-7: 룰렛이 도는 동안 룰렛 버튼과 카테고리 칩은 눌러도 동작하지 않는다.
- AC-8: 결과가 정해지면 결과 영역이 스크린 리더에 읽히도록 알림 영역에 결과가 들어간다.

결과·점심운
- AC-9: 결과 영역에 "오늘의 점심운" 라벨과 문구 한 줄이 함께 보인다.
- AC-10: 점심운 문구에 "반드시", "무조건", "보장", "확실", "100%", "최고", "대박", "맛집", "추천합니다"에 해당하는 단정, 추천, 평가 표현이 없다.
- AC-11: 결과 영역과 본문에 "인기", "베스트", "광고", "추천 메뉴"가 없다. 고지 문구는 예외다.
- AC-12: 결과 영역에 가격, 칼로리, 별점, 후기, 건강이나 효능 설명이 없다.

지도 링크
- AC-13: 결과가 나오면 "카카오맵에서 찾아보기"와 "네이버지도에서 찾아보기" 링크 두 개가 보인다.
- AC-14: 두 링크는 새 탭에서 열린다. 각 링크 옆에 외부 사이트 이동 표시가 있다.
- AC-15: 두 링크의 검색어에 결과 메뉴 이름이 들어 있다.
- AC-16: 두 링크 주소에 메뉴 이름 외의 사용자 관련 값(위치, 식별자, 선택 기록)이 없다.
- AC-17: 두 링크는 키보드로 포커스와 실행이 가능하다.

다시 뽑기
- AC-18: 결과가 나온 뒤 "다시 뽑기" 버튼이 보인다. 누르면 연출 후 새 결과가 나오고 이전 결과 문구가 사라진다.
- AC-19: [Q3 확정 후] 다시 뽑기에서 직전 메뉴가 연속으로 나오지 않는다.
- AC-20: [Q4 확정 후] 조건을 바꾸면 결과가 확정된 방식(지우기 또는 유지)대로 처리된다.
- AC-21: 새로고침하면 결과와 조건 선택이 처음 상태로 돌아간다.

위치·저장
- AC-22: 페이지 어디에서도 위치 권한 요청이 뜨지 않는다. 룰렛, 지도 링크 클릭 전후 모두 해당한다.
- AC-23: 룰렛 결과와 조건 선택 값은 localStorage, sessionStorage, 쿠키, 주소(URL) 어디에도 저장되지 않는다. 테스트는 룰렛을 돌린 뒤 각 저장소를 검사한다.
- AC-24: 쿠키 동의를 거절한 상태에서도 룰렛, 조건 선택, 지도 링크가 동작한다.

고지
- AC-25: h1 바로 아래에 상시 오락 목적 고지가 보인다. 의미는 "오락 목적으로 제공되며 메뉴 선택 결과나 식당의 영업 여부를 보장하지 않는다"이다.
- AC-26: 화면에 "결과는 무작위로 정해지며 추천이나 평가가 아니다"의 의미를 가진 문구가 보인다.

접근성·모바일

## 열린 질문

이 기획의 확정을 막는 질문은 PM을 거쳐 사용자에게 올린다. A는 승인 전에 답이 필요하다. B는 설계나 개발 전에 답이 필요하다. C는 출시 전에 답이 필요하다.

- Q1 (A, 사용자): 1차 메뉴 목록 검수. 카테고리 6개와 48개 제안(한식 10, 중식 8, 일식 8, 양식 8, 분식 6, 세계·기타 8)을 승인할지, 카테고리나 메뉴를 바꿀지 정한다. 개수 범위(40~60)도 확인한다.
- Q2 (A, 사용자): 1차 조건 필터 범위. 카테고리 선택만 둘지, 국물 있음·없음 필터를 추가할지 정한다. 국물 판단 기준(예: 짜장면은 없음, 쌀국수는 있음)을 사용자가 정해야 한다.
- Q3 (A, 사용자): 다시 뽑기에서 직전 메뉴를 제외할지 정한다. 기본안은 허용이다.
- Q4 (A, 사용자): 조건을 바꾸면 기존 결과를 지울지 정한다. 기본안은 지운다.
- Q5 (A, 사용자): 지도 링크 라벨. "근처에서 찾기"를 쓸지, 중립 표현인 "지도에서 찾아보기"를 쓸지 정한다. 검색이 현재 위치 기준인지 확인되기 전에는 중립 표현을 권장한다. 검색어에 "근처"를 붙이는 방식도 확인한다.
- Q6 (A, 사용자, 법률): 보상 없음 확정. 룰렛 결과가 금전, 상품, 포인트, 쿠폰과 연결되지 않는다는 조건을 확정하고, 사행성 관련 규제 해당 여부를 사용자가 확인한다. 확인 전에는 보상 기능을 넣지 않는다.
- Q7 (B, 사용자): 점심운 문구 개수와 작성 방식. 카테고리별 문구를 둘지, 공통 풀을 쓸지, 몇 개를 쓸지, 검수 방식(샘플 검수 후 나머지 작성)을 정한다.
- Q8 (B, 사용자): 메뉴 설명과 사진. 1차는 메뉴 이름만 두는 것이 기본안이다. 설명을 넣을지 정한다. 넣으면 맛, 건강, 영양 표현 금지 원칙을 지킨다(Q20과 함께 본다).
- Q9 (B, 사용자): 기존 자료 처리. 스테이징된 `supabase/migrations/0003_restaurants.sql`과 저장소 밖 `지역음식점 파일/` 폴더를 삭제할지, 보관할지 정한다. 삭제는 되돌리기 어려운 변경이므로 사용자 확인 후에만 한다. 기획자와 PM은 실행하지 않는다.
- Q10 (B, 사용자): 이벤트 수집. 룰렛 결과 뽑힘, 지도 링크 클릭을 분석 도구로 보낼지 정한다. 기본안은 보내지 않는다.
- Q11 (B, 사용자, 법률): 위치정보와 14세 미만 관련 법령 확인 결과. 우리 서비스가 위치를 받지 않으므로 대상이 줄었다. 적용 여부 판단을 사용자가 하고, `COMPLIANCE.md` 11장에 "위험 수용" 또는 "검토 완료"를 기록한다.
- Q12 (B, 사용자): 개인정보처리방침 변경 여부. 기획 판단은 변경 필요성이 낮다는 것이다. 외부 지도 링크 이동 안내 한 줄을 추가할지 승인한다.
- Q13 (A, 사용자): title, description 정정안과 "메뉴 추천" 표현. 검색 키워드 측면에서 "점심 메뉴 추천"을 유지할지, 실제 기능(무작위 뽑기)에 맞춰 바꿀지 정한다. 메뉴 설명 정정안(메뉴 탭의 description과 example)도 함께 승인한다.
- Q14 (B, 사용자): 카테고리 표시 이름. "세계·기타"라는 이름과 6개 카테고리 이름을 승인한다.
- Q15 (B, 사용자와 UI 단계): 메뉴 점심 항목의 `colorClass`(`text-orange-600`)와 디자인 토큰(`menu-lunch`, `#a5481f`)을 맞출지 정한다. `design-system.md` 표 변경이 필요하면 사용자 승인 후 바꾼다.
- Q16 (B, 설계 단계): 돌림판 재사용. 이번 기능의 돌림판을 처음부터 여러 기능이 쓸 수 있게 만들지, 점심 안에 두고 나중에 옮길지 설계 단계에서 정한다. 기획은 재사용 가능성만 기록한다.
- Q17 (C, 사용자): 카카오맵, 네이버지도 검색 링크 정책 확인. 링크 사용 허용 범위, 라벨 표기 규칙, 검색 URL 형식, 모바일에서 앱 또는 웹으로 열리는 동작을 확인한다. 확인 전에는 출시하지 않는다.
