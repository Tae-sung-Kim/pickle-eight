## 디자인 방향

한 줄 요약: **"두 시료 대조표"**. 운빨연구소가 시료 두 개를 나란히 놓고 관계를 적어 둔 대조 기록이다. 종이 위에 강황(`menu-fortune`) 잉크로 두 이름을 잇는 선 하나를 긋고, 선 아래에 관계 이름과 등급을 적는다. 하트, 반지, 커플 일러스트, 분홍 계열, 궁합 점수 게이지 같은 궁합 기본값은 쓰지 않는다.

- 이유: 사이트 컨셉("운을 차분하게 관찰하는 연구실")과 맞고, 결과를 "점수 대신 관계 유형 설명"으로 보여 주는 plan의 차별 포인트가 "두 대상의 관계를 기록한다"는 그림 하나로 전달된다.
- 개성은 **결과 맨 위의 "대조 줄"(두 이름 + 잇는 선 + 관계 이름) 한 곳**에만 준다. 허브, 입력 폼, 동의 화면, 가이드, 버튼은 운세와 같은 공용 체계를 그대로 쓴다. 이유: 같은 `/fortune` 아래 화면이라 운세와 다른 사이트처럼 보이면 안 된다(design-system).
- 동의·이용 불가·연령 안내 화면은 운세와 똑같이 담담하게 둔다. 움직임·아이콘·경고색이 없다. 이유: 법적 확인 화면에 장식이 붙으면 가볍게 읽힌다. 특히 궁합은 상대방 정보를 다루므로 더 그렇다.
- 두 사람을 부르는 말은 "첫 번째 사람 / 두 번째 사람"이다(design.md D-3). 이유: 연인·친구·가족을 전제하지 않는다(plan 열린 질문 10번).
- 등급은 색으로 구분하지 않는다. 좋고 나쁨을 초록·빨강으로 칠하지 않는다. 이유: 요구 사항(색만으로 구분 금지)이고, "조율이 필요한 편"을 경고색으로 칠하면 관계를 판정하는 인상을 준다.
- 공통 규칙(운세 문서와 같음): 본문 왼쪽 정렬(h1·면책·대조 줄만 가운데), 대문자 라벨·제목 위 머리 라벨·링크 뒤 화살표·가운뎃점 메타 문자열 없음, 번호 장식 없음, 그림자 없음, 면은 `background` → `card` → `muted`와 `border`로 나눈다.

## 간격·그리드

- 4px 눈금. 본문 폭 `mx-auto max-w-4xl px-4`(운세와 같음). 섹션 사이 40px, 섹션 안 16px, 패널 안 묶음 사이 24px.
- 기능 영역 패널: `rounded-panel`, `border`, `card`, 안쪽 여백 20px(sm 이상 32px).
- 하위 면(시각 질문, 시각 모름·1~2월 안내): `rounded-lg`, 안쪽 여백 16px. 안내 줄은 면 없이 왼쪽 선 2px + 12px 안쪽 여백.
- 반경: 등급 칸·입력·버튼·동의 행 `rounded-lg`, 패널·하단 고지 상자 `rounded-panel`.
- 결과 기록표(md 이상): 왼쪽 열 13rem + 오른쪽 열 나머지, 열 간격 32px. 행 사이 `border-t` + 위아래 20px. 모바일은 한 열. 이유: 운세 결과와 같은 구조이고, 13rem 열이 세로 3칸 등급 목록에 알맞다.
- 터치 영역 44px 이상(버튼, 동의 행, 등급 칸은 누르는 대상이 아니므로 제외, 링크). 인접 대상 사이 4px 이상.
- 쿠키 배너와 겹침 방지: 패널 안 모든 상호작용 요소에 `scroll-mb-48`(운세와 같음).
- **320px 기준**: 페이지 좌우 16px, 패널 안쪽 20px → 내용 폭 248px. 가로 스크롤이 생기면 안 된다(400% 확대 시 reflow, WCAG 1.4.10).
  - 날짜 칸(연도 96 + 월 64 + 일 64 + 칸 사이 간격 12×2 = 248px)은 한 줄에 겨우 들어가며 넘치면 줄바꿈된다. 기존 입력 폼 동작 그대로이고 어느 쪽이든 가로 스크롤이 없어야 한다.
  - 대조 줄: 두 이름 칸이 각각 남은 폭을 나눠 쓰고(`min-w-0`), 가운데 선은 최소 16px. 5글자 이름 두 개(18px × 5 × 2 = 180px) + 선 + 칸 사이 간격이 248px 안에 들어간다. 그래도 넘치는 이름은 마지막 방어로 단어 중간 줄바꿈을 허용한다.
  - 등급 목록·버튼은 한 열이라 폭 문제가 없다. 허브 목록은 공용 컴포넌트가 처리한다.

## 화면별 레이아웃

### 허브 `/fortune/compatibility` (서버 전용, 동의 전후 같은 화면)

순서(design.md 5.2): h1 + 설명 → 상시 면책 → "궁합 고르기" h2 + 목록 2행 → 허브 가이드 → 내 띠·별자리 확인 링크 → FAQ → 상세 이용 안내. 동의 게이트, 입력칸, noscript, 하단 상담전화 상자가 없다.

모바일
```
[       궁합 테스트       ]   ← h1 (가운데)
[ 설명 한 줄 ]
┌ 상시 면책 상자 ────────────────┐
└────────────────────────────────┘
궁합 고르기                          ← h2
────────────────────────────────
[발] 띠 궁합                         ← 행 전체가 링크
     두 사람의 띠가 어떤 관계인지 …
────────────────────────────────
[망] 별자리 궁합
     두 사람의 별자리를 네 원소로 …
────────────────────────────────
(허브 가이드 h2 + 단락 3개)
각자의 띠와 별자리가 궁금하면 …     ← 안내 한 줄 + 링크 2개
 띠별 운세   별자리 운세
자주 묻는 질문 (h2 + h3/p)
[ 이용 안내 상자 ]
```

데스크톱
- 같은 한 열(폭 `max-w-4xl`). 목록 행은 공용 컴포넌트가 가로를 조금 넓힌다. 2열 카드 격자를 만들지 않는다. 이유: 항목이 둘뿐이고 설명이 한 문장이라 줄 친 목록이 운세 허브·로또 허브와 같다.

세부
- 목록은 공용 `MenuListComponent`를 그대로 쓴다. 아이콘은 기존에 등록된 `PawPrint`(띠 궁합), `Telescope`(별자리 궁합)를 쓰고, 색은 `text-menu-fortune`. 이유: 띠별 운세·별자리 운세와 같은 그림이라 "띠"와 "별자리"가 한눈에 이어지고, 새 아이콘 등록이 필요 없다. 두 목록이 한 화면에 나란히 놓이지 않으므로 같은 아이콘이 혼동을 만들지 않는다.
- 메뉴 항목(운세 그룹 안 "궁합 테스트")의 아이콘은 `Users`(design.md 5.6 초안 그대로)를 권한다. 이유: 두 사람을 뜻하고 하트·연애를 떠올리지 않는다. `MENU_ICONS` 등록은 FE-6.
- 허브 가이드 단락은 plan "페이지가 답해야 할 질문" 3개(무엇을 기준으로 보는가, 띠와 별자리 중 무엇으로 봐야 하는가, 어디까지 믿어도 되는가)에 답한다. 하위 제목을 두지 않는다(운세 허브와 같음, 단락이 짧아 목차만 늘어난다).
- 내 띠·별자리 확인 링크(F-8): 종이 위 글로 둔다(상자·테두리 없음). 안내 한 줄(14px, `muted-foreground`) + 링크 2개(16px 중간 굵기, `primary`, 밑줄, 높이 44px 이상). 모바일은 세로로 쌓고, sm 이상은 한 줄. 이유: 바로 위가 가이드 글이라 상자로 감싸면 고지처럼 보인다.
- FAQ는 아코디언 없이 펼친 목록(서버 HTML과 구조화 데이터가 같아야 한다). 광고 요소를 새로 만들지 않는다.

### 띠 궁합 `/fortune/compatibility/tti`, 별자리 궁합 `/fortune/compatibility/star-sign` (공통 틀)

서버 영역과 게이트 영역을 운세와 같은 방식으로 나눈다.

```
[서버] h1 + 설명
[서버] 상시 면책 상자 (운세 문장 + 궁합 과학적 근거 없음 문장)
[서버] 입력 영역 안내 두 문단 (상대방 정보 안내 / 연령 안내)
[서버] noscript 안내 (기존)
┌ [게이트] 기능 영역 패널 (card) ────────────┐
│ checking  : 스켈레톤                        │
│ required  : 이용 전 확인 화면 (항목 4개)    │
│ declined  : 이용 불가 화면                  │
│ granted   : 두 사람 입력 흐름 → 결과        │
│ age-blocked: 연령 안내 화면                 │
└────────────────────────────────────────────┘
[서버] 결과 하단 고지 상자 (궁합 결과 고지 한 문장, 상담전화 없음)
[서버] 다른 운세·궁합 링크 (아래 "연결 링크")
[서버] 가이드
[서버] 계산 기준 (기존 컴포넌트)
[서버] 자주 묻는 질문
[서버] 이용 안내 (기존)
[게이트] 동의 다시 설정 (granted일 때만, 기존)
```

- 입력 영역 안내는 운세와 같은 모양이다: 상시 면책 아래, 패널 바로 위, 왼쪽 정렬, 문단 앞 16px 아이콘. 상대방 정보 안내 앞에는 `EyeOff`(문장 안에 "전송되거나 저장되지 않습니다"가 있다), 연령 안내 앞에는 `Info`. 이유: 운세의 아이콘 배정을 그대로 따라 사이트 일관성을 지킨다. "안전 보증" 모양(`ShieldCheck`)은 쓰지 않는다.
- 상대방 정보 안내는 동의 전에도 서버 HTML에 항상 보인다(design.md D-6). 두 번째 사람 입력 단계에서 같은 문장을 패널 안에 다시 쓰지 않는다. 이유: 같은 문장이 한 화면에 두 번 있으면 읽지 않게 된다. 상대방 정보는 이용 전 확인 4번째 항목으로 한 번 더 확인받는다.
- 패널 폭은 `max-w-4xl`. 동의·이용 불가·연령 안내 화면의 내용 폭은 `max-w-2xl`.
- `checking`·지연 로드 스켈레톤은 동의 화면과 같은 높이(제목 줄, 안내 두 줄, 항목 행 **4개**, 버튼 둘)로 그려 아래 서버 영역이 밀리지 않게 한다. 맥박은 `animate-pulse`에 `motion-reduce:animate-none`. 컨테이너 `aria-busy="true"`, 안에 `role="status"`와 화면 읽기 전용 "불러오는 중입니다".

#### 이용 전 확인 화면 (재사용: `FortuneConsentFormComponent`, 항목 4개)

운세 동의 화면과 같은 구조다. 달라지는 점만 적는다.
- 항목이 4개다(만 14세 이상 / 오락·참고와 본인 판단 / 두 사람의 생년월일 미전송·미저장 / 상대방에게 알리고 동의를 받음). 항목 행·체크박스·진행 불가 안내·버튼·보관 안내 모양과 동작(S4 A: 버튼은 누를 수 있고 안내가 바뀌며 첫 미선택 체크박스로 포커스)은 운세와 같다.
- 4번째 항목(상대방 동의)에도 별도 강조를 주지 않는다. 같은 행, 같은 크기. 이유: 4개 항목 모두 같은 무게로 확인해야 하고, 하나만 튀면 나머지를 가볍게 본다.
- legend의 읽기 전용 이름은 "이용 전 확인 항목 네 가지", 안내 문장의 개수 표현도 "네 가지"(design.md 8.1). 문구는 궁합용으로 새로 쓴다.
- 모바일에서 4개 행이 길어 버튼이 첫 화면 밖으로 밀린다. 진행 불가 안내는 버튼 바로 위에 있어 스크롤하면 보이고, 버튼을 눌렀을 때 포커스가 첫 미선택 체크박스로 가며 화면이 따라간다. 이 길이는 줄이지 않는다.
- 체크는 매번 모두 해제 상태로 시작한다(운세와 같음).

#### 이용 불가 화면 (재사용: `FortuneConsentDeclinedComponent`)
- 운세와 같은 구조: h2(포커스) + 안내 단락 + outline 버튼 "이용 전 확인 화면으로 돌아가기". 아이콘·경고색 없음. 채운 버튼을 쓰지 않는다(다시 동의하라고 재촉하는 모양을 피한다).

#### 연령 안내 화면 (재사용: `FortuneAgeBlockedComponent`)
- 운세와 같은 구조: h2(포커스) + 안내 + 책임 고지 + 입력 미저장 안내 + outline "홈으로" 링크 하나. 폼·후보·결과·"다시 입력"이 모두 사라진다.
- 두 사람 중 누가 해당하는지 알리지 않는다. 입력한 생년월일과 이름도 다시 보이지 않는다. 일러스트·경고색·큰 숫자 표식 없음. 상담전화 없음(확정 답변).
- 이 화면은 두 번째 사람 입력 중에도, 첫 번째 사람 입력 중에도 나올 수 있다. 어느 쪽이든 같은 화면이다. 이유: 어느 사람이 해당하는지 구분되면 상대방 나이를 알려 주는 셈이 된다.

#### 두 사람 입력 흐름 (granted)

단계: 첫 번째 사람 → (시각 질문 → 후보 선택) → 두 번째 사람 → (시각 질문 → 후보 선택) → 결과. 괄호는 입춘 당일(띠), 별자리 경계일일 때만이다.

한 번에 폼 하나만 보인다(design.md D-3 안 1). 단계가 바뀌면 폼이 새로 만들어져 비어 있다. 입력 폼, 음력 확인 줄, 시각 질문, 후보 선택은 모두 기존 컴포넌트를 그대로 쓰고, 단계 이름과 요약은 이 흐름 컴포넌트가 둘러싼다. 기존 입력 폼에 새 prop을 더하지 않는다. 이유: 단계 이름은 폼 바깥 h2와 `section`의 이름(`aria-labelledby`)이 전한다. 입력 폼 변경은 운세 입력 화면 전체에 영향을 준다(design.md 11장).

두 번째 사람 (모바일)

- 데스크톱(md 이상): 기존 입력 폼이 한 줄로 펼쳐진다(달력 · 연도 · 월 · 일 · 윤달 · 제출 버튼). 별도 2열 구성을 만들지 않는다. 이유: 한 번에 한 사람만 입력하므로 좌우에 둘 것이 없다.
- 확인 줄("첫 번째 사람: 용띠")은 입력이 끝난 사람의 판정된 띠·별자리 이름만 보인다. 생년월일·시각을 다시 보이지 않는다(design.md 7장). 이유: 시각 질문·후보 선택을 거친 뒤 어떤 결과로 이어졌는지 확인하게 하고, 이름만 보여 상대방 정보를 노출하지 않는다.
- "다시 입력"은 두 번째 사람 단계에서 처음 상태로 돌아가는 텍스트 버튼이다(결과 단계의 "다시 입력"과 같은 동작과 같은 이름). 폼 제출 버튼 아래에 둬서 키보드 순서가 폼을 먼저 거치게 한다. 이 버튼은 design.md 5.3에 결과 단계만 적혀 있어 확인이 필요하다(열린 질문 2).
- 제출 버튼 이름: 첫 단계 "다음 사람 입력", 둘째 단계 "궁합 보기". 이유: 버튼 이름이 다음에 일어날 일을 말한다("제출"이 아니다).
- 음력을 고르고 제출하면 기존 음력 확인 줄("음력 → 양력")이 폼 아래에 그대로 나온다.
- 한 단계가 끝나면 다음 단계의 h2로 포커스를 옮기고 패널 맨 위가 보이도록 스크롤한다(운세가 결과 h2로 옮기는 방식과 같음). 단 패널이 이미 화면에 절반 이상 보이면 스크롤하지 않는다.

시각 질문과 후보 선택(재사용: `FortuneBirthTimeFormComponent`, `FortuneCandidateChoiceComponent`)
- 그 사람의 입력 폼 아래에 이어 붙는다. 폼은 남는다. 안내 문장, 시·분 칸, "시각 반영"(주요)과 "시각 모름"(outline)은 운세와 같다. 질문 제목은 어느 사람 단계인지 h2가 이미 전하므로 그대로 쓴다.
- "시각 모름"을 누르면 두 후보 버튼(경계 전, 경계 후)이 같은 크기·모양으로 나온다. 미리 선택하지 않고 "추천", "정답" 표시가 없다. 고르면 그 사람의 판정이 끝나고 바로 다음 단계로 간다(열린 질문 3).
- 두 번째 사람이 연령 미만이면 두 번째 입력 직후 연령 안내 화면만 남고 첫 번째 사람 확인 줄도 사라진다.

**대조 줄 (이 기능의 개성 요소)**
- 가운데 정렬. 가로로 [첫 번째 사람 칸] — 선 — [두 번째 사람 칸]. 두 칸은 같은 폭이고 남는 폭을 나눠 쓴다. 이름은 칸 가운데, 위에 "첫 번째 사람"/"두 번째 사람" 보조 줄(입력 순서). 선은 이름 높이의 가운데를 지나고 양 끝에 점이 있다. 선은 이름 글자와 겹치지 않는다(이름 칸 바깥에서 시작).
- 이름 순서는 입력 순서다(조합 키가 정렬되어도 화면은 입력 순서, design.md 5.4).
- 선은 순수 장식이며 `aria-hidden`이다. 관계 정보는 그 아래의 글자(관계 이름)가 전한다.
- 별자리 궁합에서는 각 이름 아래에 원소 이름(14px, `muted-foreground`)을 둔다. 관계 이름은 원소 관계 이름이다(같은 원소, 보완, 대립, 그 밖의 관계). 띠 궁합은 이름 아래 보조 줄이 없다.
- 같은 띠·같은 별자리 조합도 같은 모양이다. 관계 이름 자리에는 "같은 띠"/"같은 별자리"가 온다. 두 이름이 같아도 형식이 같아 규칙이 단순하다.
- 점수, 퍼센트, 하트 개수, 순위, 막대 게이지를 쓰지 않는다(design.md 5.4).

**등급 3칸 (S1 A안, 권장)**
- 세 칸을 항상 모두 보인다. 순서는 "잘 맞는 편 → 무난한 편 → 조율이 필요한 편"(plan 열린 질문 5번). 해당하는 칸만 강조한다. 모바일·데스크톱 모두 세로 목록이다(왼쪽 13rem 열 안에서도 알맞다).
- 해당 칸: 체크 아이콘(16px, 장식) + 굵은 글자 + `menu-fortune/10` 면 + `menu-fortune` 테두리(안쪽 링으로 두께를 더함, 칸 크기는 안 변함) + 화면 읽기 전용 글자 "이 결과". 해당하지 않는 칸: 아이콘 없음, 보통 굵기, `border`, `muted-foreground`.
- 이유: 색을 빼도 아이콘·굵기·테두리 두께·읽기 전용 글자로 구분된다. 세 이름을 모두 보여 주면 "무엇이 있고 그중 어디인지"가 한눈에 보이고, 등급이 서비스 자체 규칙이라는 가이드 설명과 이어진다.
- 누를 수 없는 표시용이다. 버튼 모양(hover·누름)을 만들지 않는다. 목록은 `ul`에 묶음 이름을 달고(예: "궁합 등급"), 칸마다 `li`.
- 같은 등급을 색으로 쓰지 않는 이유는 위 "색상"에 적었다.

**요약·잘 맞는 점·조율하면 좋은 점**
- 요약 1~2문장, 잘 맞는 점 2개, 조율하면 좋은 점 2개(design.md 5.4 문구 묶음). 두 목록은 불릿 목록이다. 번호를 쓰지 않는다(순서가 아님).
- 조율하면 좋은 점은 왼쪽 선(`menu-fortune/40`)으로 "덧붙인 내용"을 표시한다(운세 "주의할 점"과 같은 방식). 경고 아이콘·경고색은 없다.
- 두 사람을 부르는 말은 "두 분", "서로"처럼 중립으로 쓴다(문구 담당 지침).

**시각 모름 안내 줄과 "다른 후보로 보기"(확정 답변 Q-7)**
- 후보를 골라 결과를 본 사람이 있으면 대조 줄 바로 아래(등급 위)에 안내 줄을 둔다. 왼쪽 선 + 안내 문장(기존 시각 모름 안내 + "첫 번째 사람은 …로 보고 있습니다" 형태의 새 문장, 초안) + outline 버튼 "다른 후보로 보기". 두 사람 모두 시각 모름이면 줄이 두 개다.
- 버튼의 읽기 이름은 보이는 글자 "다른 후보로 보기"를 그대로 쓰고(WCAG 2.5.3), 어느 사람인지는 안내 줄을 `aria-describedby`로 연결해 전한다. 이유: 이름이 같은 버튼 둘이 있어도 설명으로 구분된다.
- 누르면 그 사람의 후보가 다른 쪽으로 바뀌고 대조 줄, 관계, 등급, 설명이 제자리에서 바뀐다. 포커스는 버튼에 남는다. 모션 없음. 바뀐 결과는 결과 영역 안의 읽기 전용 상태 알림 영역(`aria-live="polite"`)이 "이름, 이름, 관계, 등급"을 나열해 읽어 준다(조사 없는 나열이라 문장 틀이 필요 없다). 이유: 화면이 바뀌어도 시각 장애 사용자가 바뀐 사실을 모를 수 있다.
- 두 번 눌러 원래 후보로 돌아갈 수 있다. 어느 쪽도 "추천" 표시가 없다.
- 두 결과를 나란히 보여 주는 방식은 쓰지 않는다. 이유: 두 사람이 모두 해당하면 후보 조합이 네 가지가 되어 화면이 복잡하고, 결과가 둘이면 "어느 것이 맞나"라는 불필요한 판단을 요구한다(확정 답변 Q-7).

**띠 궁합의 1~2월 출생 안내 줄**
- 두 사람 중 한 명이라도 1~2월 출생이면 기존 띠 계산 기준 안내(`FORTUNE_CALC_BASIS_TTI`) + 링크 "띠별 운세"(`primary`, 밑줄, 44px)를 안내 줄로 보인다. 어느 사람인지 밝히지 않는다. 별자리 궁합에는 없다.

**오락 고지 한 줄 / 다시 입력**
- 결과 안에 오락 고지 한 줄(14px, `muted-foreground`)을 항상 둔다(AC-1). 결과 아래 서버 영역의 하단 고지 상자에도 같은 문장이 있다(design.md 8.1). 같은 문장이 한 화면에서 두 번 보일 수 있으나 plan이 결과 안과 하단 둘 다 요구한다(열린 질문 4).
- "다시 입력"은 outline 버튼이다. 누르면 처음 상태(첫 번째 사람 입력, 빈 폼)로 돌아가고 첫 단계 h2로 포커스·스크롤한다.
- 결과에 생년월일과 입력 시각을 다시 보이지 않는다. 이름도 입력한 사람 이름이 아니라 띠·별자리 이름만 있다.

#### 결과 하단 고지 상자 [서버, 항상]
- 운세의 하단 고지 상자와 같은 면(`background` + `border`, `rounded-panel`)이고 안에는 궁합 결과 고지 한 문장만 있다. 상담전화를 넣지 않는다(확정 답변). 이유: 같은 모양을 쓰면 운세 페이지의 고지와 이어지고, 문장이 하나뿐이라 상자가 가볍다.

#### 연결 링크 [서버]
- 띠 궁합 페이지는 "별자리 궁합"과 허브로, 별자리 궁합 페이지는 "띠 궁합"과 허브로 가는 링크를 하단 고지 상자 아래, 가이드 위에 둔다(선택 추가, 열린 질문 5). 종이 위 글, 안내 한 줄 + 링크 형식은 허브의 확인 링크와 같다. 아이콘·화살표 없음. 이유: 한 가지 궁합을 보고 나서 다른 쪽을 이어 보는 경로가 없으면 허브로 되돌아가야 한다.

#### 가이드 [서버] (관계 규칙·관계 유형 설명·등급 규칙)

띠 궁합 가이드
- h2 아래에 관계 정의 단락, 이어 관계 6개(육합, 삼합, 방합, 충, 원진, 그 밖의 관계)를 h3 + 설명 단락 + 해당 조합 목록으로 나열한다. 조합 목록은 "쥐-소"처럼 `whitespace-nowrap` 묶음을 쉼표로 이은 글이다(14px, 줄 간격 28px). 표를 쓰지 않는다. 이유: 2~4쌍씩 나뉜 목록이라 표 열이 맞지 않고 320px에서 가로 스크롤이 생기기 쉽다.
- 마지막에 "등급 규칙" h2: 등급 3개와 해당하는 관계를 잇는 2열 표(등급 | 관계). 표는 `text-sm`, 행마다 `border-t`, 배경 줄무늬 없음. 서비스 자체 규칙이라는 점과 원진은 자료마다 조금 다르다는 점(design.md 8.1)을 단락으로 밝힌다.

별자리 궁합 가이드
- 원소표(4행: 원소 | 별자리 3개), 원소 관계 4개(같은 원소, 보완, 대립, 그 밖의 관계) h3 + 설명, 등급 규칙 표(등급 | 원소 관계). 같은 방식이다.

공통
- 모든 문단은 `max-w-[68ch]`. 표는 `caption`을 화면 읽기 전용으로 둔다. 제목 계층은 h1 하나, h2(가이드, 등급 규칙, 계산 기준, 자주 묻는 질문, 이용 안내), h3(항목).
- 같은 띠·같은 별자리 전용 문구와 개인 결과는 서버 HTML에 없다(design.md D-5).

#### 운세 페이지에서 궁합으로 가는 링크 (확정 답변 Q-6, 기존 페이지 변경)

- 대상: `/fortune/tti`는 "띠 궁합", `/fortune/star-sign`은 "별자리 궁합"으로 가는 링크 하나. 오늘의 운세에는 넣지 않는다. 이유: US-4가 "띠별·별자리 운세를 보던 사용자"를 대상으로 한다.
- 위치와 모양: 기존 "오늘의 운세 링크" 바로 아래에 같은 모양(안내 한 줄 + 링크 한 줄, 상자 없음)으로 둔다. 두 묶음 사이 간격 16px. 서버 HTML이라 동의 전에도 보인다. 링크는 14px 안내 + 16px 중간 굵기 `primary` 밑줄, 높이 44px.
- 운세 페이지의 문구 테스트·결과 하단 상자는 바꾸지 않는다.

- 등급 3칸의 강조 이동, 체크 아이콘: 결과와 함께 나타나는 정적 표시다.

- 허브 목록의 hover는 공용 컴포넌트의 기존 색 전환만 있다. 새 모션 없음.

  - `foreground` on 종이 약 11.8:1, `foreground` on `menu-fortune/10` 약 10.4:1.
  - `muted-foreground` on 종이 약 5.0:1, on card 약 5.4:1(등급 선택되지 않은 칸은 card 패널 안의 `background` 면이라 약 5.0:1). 모두 AA 이상.
  - `menu-fortune` 글자(관계 이름): card 위 약 5.2:1, 종이 위 약 4.8:1. 18px 중간 이상 굵기여서 일반 글자 기준 4.5:1을 적용해도 통과한다. `menu-fortune/10` 면 위에서는 쓰지 않는다(약 4.3:1).
  - `destructive` on card 약 5.5:1. 오류는 아이콘 + 글자로 전한다.
  - 대조 줄의 선·점은 장식이라 대비 기준이 없다. 의미는 글자가 전한다.
  - 등급은 색을 빼도 구분된다: 체크 아이콘, 굵기, 테두리 두께, 읽기 전용 "이 결과" 글자 네 가지.
- 키보드 이동
  - 이용 전 확인: 체크박스 4개 → "동의하고 시작" → "동의하지 않음". 안내 버튼 동작은 운세와 같다.
  - 입력 단계: 달력 라디오 → 연도 → 월 → 일 → (윤달) → 제출 버튼 → (음력 확인은 읽기만) → (시각 질문의 시·분 → "시각 반영" → "시각 모름") → (후보 버튼 둘) → (두 번째 단계) "다시 입력".
  - 결과: h2에 포커스 → (시각 모름 줄의 "다른 후보로 보기") → (띠별 운세 링크) → "다시 입력". 등급 목록은 포커스 대상이 아니다.
  - 단계가 바뀌면 포커스가 새 단계 h2로 간다(h2는 `tabIndex -1`). 포커스를 잃은 채 화면만 바뀌지 않는다.
  - 포커스 링은 2px, offset 2px, offset 색은 놓인 면 색(`card`/`background`). 쿠키 배너에 가려지지 않도록 `scroll-mb-48`(WCAG 2.4.11).
- 라벨·읽기
  - 모든 입력 칸은 보이는 라벨이 있다(기존 입력 폼). 단계 h2가 두 번째 폼과 첫 번째 폼을 구분한다. 폼 묶음에는 단계 h2를 이름으로 하는 `section aria-labelledby`를 둔다.
  - 대조 줄은 읽기 전용 순서가 "첫 번째 사람, 이름, 두 번째 사람, 이름, 관계 이름"이 되도록 DOM을 짠다. 선은 `aria-hidden`.
  - 등급 목록은 묶음 이름이 있고 해당 칸에만 "이 결과"가 읽힌다.
  - 결과 안에 `aria-live="polite"` 상태 영역이 있고 "다른 후보로 보기" 뒤에만 내용이 바뀐다. 처음 결과가 나타날 때는 h2 포커스가 읽기를 맡는다.
  - 터치 영역 44px 이상, 인접 대상 간격 4px 이상.
  - 320px 폭과 400% 확대에서 가로 스크롤이 없다(간격·그리드 절).
  - 아이콘은 모두 `aria-hidden`. 의미를 아이콘만으로 전하지 않는다.

## 기존 디자인 시스템 변경 제안

없음. 새 토큰, 새 폰트, 새 반경, 새 의존성이 없다. 새 아이콘은 `Users` 하나(lucide, 기존 의존성)이며 메뉴 항목에만 쓴다.

기존 운세 공유 컴포넌트에 대한 변경 요구(이 문서가 전제로 둔 것, 모두 기본값은 지금 동작 그대로):
- 동의 폼, 이용 불가 화면, 연령 안내 화면, 동의 게이트가 문구 묶음을 받는다(design.md D-2 안 1, 5.5).
- 동의 폼 스켈레톤 높이가 항목 개수를 따른다(운세 3, 궁합 4).
- 결과 하단 고지 상자에 궁합 문장 선택(또는 궁합 전용 상자)이 필요하다. 상담전화가 없으므로 기존 상자의 상담전화 목록이 나오면 안 된다(열린 질문 1).

## 열린 질문 / 시안 선택 요청

PM 결정 요청
- M1. 대조 줄 그어지는 모션을 넣을지 뺄지(위 표). 제 의견은 넣는 안이다.
- S1. 등급 표시 시안 2개.
  - A안(권장): 세 칸을 모두 보이고 해당 칸만 강조(체크 아이콘, 굵기, 테두리, 읽기 전용 글자). 장점: 색에 의존하지 않고, 등급 체계가 한눈에 보이며, 기록표 13rem 열에 맞는다. 단점: 결과 안에 줄이 세 개 더 생겨 길어진다.
  - B안: 해당 등급 이름 하나만 큰 글자로 보이고 나머지는 보이지 않는다(대조 줄 아래 한 줄). 장점: 결과가 짧고 단순하다. 단점: 등급이 3단계라는 것과 다른 등급의 이름이 결과에서 보이지 않아, 이 줄이 판정처럼 읽히고 "서비스 자체 규칙"이라는 설명과 멀어진다. 가이드의 표를 봐야 맥락을 안다.

닫지 못한 질문
1. (architect) design.md 5.2·5.4 본문에 상담전화 문장이 남아 있다. 확정 답변(Q-2)이 "상담전화 없음"이므로 본문을 정리해야 한다. 이 문서는 확정 답변을 따랐다. 결과 하단 상자가 상담전화 없이 쓰이는 컴포넌트 변경 방식(문장 선택 prop 또는 궁합 전용 상자)도 architect·frontend가 정한다.
2. (architect) 두 번째 사람 단계에서 "다시 입력"(처음 상태로)을 둬도 되는지 확인한다. design.md 5.3은 결과 단계에서만 다시 입력을 둔다. 동일한 reducer 동작을 쓰는 UI 추가이고, 없으면 첫 번째 사람 입력이 틀렸을 때 두 번째 사람 입력을 끝낸 뒤에야 고칠 수 있다.
3. (architect) "시각 모름"에서 후보를 고르는 순간 그 사람의 판정이 끝나고 바로 다음 단계로 넘어가는 동작을 확인한다. 이 문서는 그렇게 가정했다. 이유: 결과에서 언제든 "다른 후보로 보기"로 바꿀 수 있어 별도 확인 버튼이 필요 없다.
4. (PM) 같은 오락 고지가 결과 안과 결과 하단 상자에 모두 있다(plan AC-1과 design.md 8.1). 한 화면에 중복되어 보일 수 있다. 하나로 줄일지, 문장을 다르게 쓸지 결정이 필요하다. 이 문서는 plan·design대로 둘 다 둔다.
5. (PM) "연결 링크"(띠 궁합 ↔ 별자리 궁합 ↔ 허브)는 design.md에 없는 UI 추가다. 넣으면 서버 컴포넌트 하나가 늘고 문구 승인 대상이 하나 늘어난다. 제 의견은 넣는 쪽이다.
6. (문구 담당) 이용 전 확인 첫 항목("만 14세 이상입니다.")이 본인만 뜻하는지 두 사람을 모두 뜻하는지 문구 단계에서 정한다. 연령은 두 사람 모두 생년월일로 판정하므로 상대방 나이는 4번째 항목과 판정으로 다룬다.
7. (PM, 배포 전) 허브·결과 페이지의 광고 위치는 이 문서에서 정하지 않았다. 사이트 공통 배치를 따르고 결과를 가리거나 잠그지 않는다(design.md 9장, AdFit 위험 수용).
