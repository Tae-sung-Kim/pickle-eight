**변경 2026-11-24 (사용자 결정, 아래 본문보다 우선):** 입력 영역 위치를 "필터 묶음 맨 아래, 돌림판 위"에서 "돌림판과 룰렛 돌리기(다시 뽑기) 버튼 아래, 지도 링크 위"로 옮겼다. 결과가 나오기 전에도 항상 보인다. 이유: 동네 이름은 지도 검색에만 쓰이므로 지도 링크 가까이에 두고, 긴 고지가 필터와 돌림판을 아래로 밀지 않게 한다. 새 DOM·탭 순서: 끼니 → 카테고리 칩 → 국물 → 룰렛 돌리기 → 동네 입력란 → (값이 있을 때) 지우기 → 지도 링크 3개. 이에 맞지 않는 본문 문장(18, 66, 82, 138, 251행 부근)은 이 변경으로 대체된다. 데스크톱은 왼쪽 칸에 돌림판과 입력란, 오른쪽 칸에 결과 카드다.

이 문서는 기존 `/meal` 화면에 "입력란 하나, 미리보기 한 줄, 고지 문장"을 더하는 변경만 정한다. 돌림판, 결과 카드, 끼니 선택, 카테고리 칩, 지도 링크 버튼, 소개, FAQ의 모양은 `menu-meals` 명세를 그대로 따른다. 새 토큰, 새 폰트, 새 shadcn 컴포넌트, 새 아이콘 묶음은 없다. 아이콘은 이미 쓰는 `lucide-react`에서만 가져온다.

## 디자인 방향

한 줄 요약: 연구 노트 여백에 연필로 "채집 장소"를 적어 넣는 칸 하나. 눈에 띄는 장식 없이, 무엇을 적는 칸인지와 그 글이 어디로 가는지만 또렷하게 읽히게 한다.

- 이유: 이 기능의 핵심은 꾸밈이 아니라 신뢰다. 이용자가 쓴 글이 "저장되지 않고, 누른 때에만 지도로 간다"는 사실이 입력란 바로 아래에서 읽혀야 한다. 그래서 개성은 쓰지 않고, 입력란의 위치와 미리보기의 정직함(링크에 실제로 들어가는 문장 그대로)에만 힘을 쓴다.
- 이번 기능의 기억에 남는 한 곳: **결과 카드의 "지도 검색어" 미리보기.** 이용자가 링크를 누르기 전에 지도로 가는 문장을 그대로 볼 수 있게 한다(US-3). 나머지는 기존 화면과 같은 조용한 종이색과 먹물 글자다.
- 입력란은 "끼니 선택", "카테고리"와 같은 필터 묶음의 맨 아래에 들어가지만, 칩이 아니라 글자를 적는 칸이므로 칩과 모양이 겹치지 않는다. 색은 새로 주지 않는다.

디자인 계획 점검 (기본값으로 흐르던 부분을 바꾼 기록)

| 처음 떠올린 안 | 왜 버렸나 | 바꾼 결정 |
|---|---|---|
| 지도 핀 아이콘이 붙은 검색창 모양 | "주변 검색", "내 위치 찾기"처럼 읽힌다. 이 기능은 위치 기능이 아니다(plan 배경). 문구 금지어 취지와도 어긋난다 | 아이콘 없이 글자 라벨 "동네 이름 (선택)"과 예시만 쓴다 |
| 5줄 고지를 접는 "자세히 보기" | plan Q9와 design Q9가 "접지 않고 항상 보임"으로 확정했다 | 접지 않고 입력란 바로 아래 목록으로 둔다. 길이 부담은 글자 크기와 줄 간격으로 줄인다 |
| 입력할 때마다 미리보기가 튀어나오는 효과 | 한 글자마다 움직이면 시선만 뺏기고 정보가 늘지 않는다 | 모션을 넣지 않는 안을 추천한다(U-L4) |
| 입력란에 `menu-meal` 색 테두리·배경 | 큰 면적 색칠 금지 규칙, 포커스 링은 `primary`를 쓰는 규칙에 어긋난다 | 포커스와 오류는 기본 입력 스타일(`ring`, `destructive`)을 쓴다 |
| 결과 카드 안 큰 배지로 "동네 포함" 표시 | 미리보기 문장 자체가 같은 정보를 이미 전한다 | 별도 배지 없음 |

## 색상

| 용도 | 토큰 | 이유 |
|---|---|---|
| 입력란 라벨 | `text-foreground`, 굵기 600 | 카테고리·국물 legend와 같은 어법. 보이는 제목 |
| 입력란 배경 | `bg-card` | 종이 위에서 한 단계 밝은 면. 끼니 스위치 틀과 같은 면이라 "조작하는 칸"으로 읽힌다 |
| 입력란 테두리 (기본) | `border-input` 또는 `border-muted-foreground` | 3:1 비대비 문제가 있어 선택을 올린다(U-L3). 추천은 `border-muted-foreground` |
| 입력란 포커스 | 기본 Input의 `border-ring ring-ring/40 ring-[3px]` | 포커스 링은 메뉴와 상관없이 `primary` 계열(`ring`)을 쓴다는 규칙 |
| 입력란 오류 테두리 | 기본 Input의 `aria-invalid:border-destructive` | 이미 `src/components/ui/input.tsx`에 들어 있다 |
| 입력 예시(placeholder) | `text-muted-foreground`(기본 Input) | 라벨을 대신하지 않는 힌트. 종이 위 약 4.9:1, 카드 위 약 5.3:1 |
| 오류 안내 글자·아이콘 | `text-destructive` | 종이 위 약 5.1:1, 카드 위 약 5.5:1(`#b23a48` 기준). 아이콘과 글자를 함께 써서 색에만 의존하지 않는다 |
| 상시 고지 글자 | `text-muted-foreground` | 기존 고지·외부 링크 안내와 같은 보조 글자색. 종이 위 약 4.9:1 |
| 지우기 버튼 | `variant="ghost"`(기본), 아이콘 `text-muted-foreground` | 입력 안에 있는 보조 동작이라 눈에 덜 띄게 한다. hover는 shadcn 기본 |
| 지도 검색어 미리보기 면 | `bg-menu-meal/10 rounded-md` | "옅은 면은 `bg-menu-<key>/10`"이라는 규칙. 결과 카드 위에 한 단계만 구분되게 한다 |
| 미리보기 글자 | 라벨 `text-muted-foreground`, 값 `text-foreground` 600 | 값 위 약 10:1 (`foreground` on `menu-meal/10`), 라벨은 위 약 4.7:1 이상 |
| 결과 화면 짧은 고지 | `text-muted-foreground` | 기존 외부 링크 안내와 같은 위계 |

- 새 토큰: **없음.**
- `menu-meal`은 미리보기 면 한 곳에만 쓴다. 입력란 자체에는 쓰지 않는다. 이유: 메뉴 색은 선택 상태와 강조에만 쓰고, 입력란은 기본 컨트롤 색을 따른다.

## 타이포그래피

폰트는 Pretendard Variable 하나. 새 폰트 없음. 입력값과 미리보기는 한글이 들어가므로 `font-mono`(Fira Mono)를 쓰지 않는다.

| 요소 | 굵기 | 크기 | 줄 간격 | 비고 |
|---|---|---|---|---|
| 입력란 라벨 "동네 이름 (선택)" | 600 | `text-sm` | `leading-6` | 카테고리·국물 legend와 같다 |
| 입력값·placeholder | 400 | `text-base`(모든 폭) | 입력 기본 | 기본 Input은 768px 이상에서 `text-sm`로 줄어든다. 이 입력은 `md:text-base`로 덮어 16px을 유지한다. 모바일은 16px 미만이면 iOS가 확대한다 |
| 오류 안내 | 400 | `text-sm` | `leading-6` | `break-keep`, 줄바꿈 허용 |
| 상시 고지 목록 | 400 | `text-sm` | `leading-6` | 항목 사이 간격 4px. 한 줄 길이는 아래 폭 규칙으로 80자 미만 |
| 미리보기 라벨 "지도 검색어" | 500 | `text-sm` | `leading-6` | |
| 미리보기 값 | 600 | `text-base` | `leading-snug` | `break-words`. 긴 메뉴 이름이 붙어도 칸 밖으로 나가지 않는다 |
| 결과 짧은 고지 | 400 | `text-sm` | `leading-6` | 기존 외부 링크 안내와 같다 |

## 간격·그리드

- 4px 눈금. 입력 영역은 필터 묶음의 세 번째 항목으로 들어가며, 기존 묶음의 `space-y-4`(16px)를 그대로 쓴다. 이유: 끼니 → 카테고리·국물 → 동네 이름이 한 흐름의 "뽑기 전 조건"으로 읽히고, 간격이 같아야 다른 사이트처럼 보이지 않는다.
- 입력 영역 안: 라벨과 입력란 사이 8px(`mb-2`, legend와 같음), 입력란과 오류 안내 사이 8px, 입력란(또는 오류)과 고지 목록 사이 12px.
- 입력란: 높이 44px(`h-11`), 반경 `rounded-lg`(버튼·입력 규칙), 좌우 안쪽 여백 12px, 오른쪽은 지우기 버튼 자리 44px 확보(`pr-11`).
  - 이유: 칩·국물·링크가 모두 44px이고 터치 영역 기준을 맞춘다. 끼니 스위치(48px)보다 한 단계 작아 위계가 맞는다.
- 폭
  - 모바일(640px 미만): 폭 전체.
  - 640px 이상: 입력란은 `max-w-sm`(384px)까지, 왼쪽 정렬. 끼니 스위치와 같은 폭이라 왼쪽 축이 하나로 맞는다.
  - 상시 고지 목록은 640px 이상에서 `max-w-2xl`까지. 이유: 14px 글자 기준 한 줄 약 50~60자라 읽기 좋고, 입력란(384px)보다 넓어도 같은 왼쪽 축에서 시작해 어긋나 보이지 않는다.
- 결과 카드 안: 기존 지도 묶음의 `space-y-3`(12px)을 따른다. 미리보기 블록의 안쪽 여백은 가로 12px, 세로 8px.

## 화면별 레이아웃

### 오늘 뭐 먹지 (`/meal`)

머리 영역(h1, 오락 고지, 소개, 사용 순서), 끼니 스위치, 카테고리·국물, 돌림판, 결과 카드의 순서와 모양은 그대로다. 달라지는 곳은 두 곳이다.

1. 필터 묶음 맨 아래, 돌림판 바로 위에 "동네 이름 입력 영역"이 들어간다. 내용은 라벨, 입력란(지우기 버튼 포함), 오류 안내(있을 때), 상시 고지 목록이다.
2. 결과 카드의 지도 묶음(`h3` "지도에서 찾아보기" 아래)에 "지도 검색어 미리보기"와 "결과 짧은 고지"가 링크 3개 위에 들어간다(동네 이름이 유효할 때만).

- 순서 근거: 이용자의 흐름은 "끼니 → 조건 → 동네 → 돌리기"다. 입력은 선택이라 돌리기 버튼 뒤로 미루면 "돌린 뒤 동네를 적는" 경로를 놓친다(plan 예외: 돌린 뒤 바꿔도 반영되지만 기본 흐름은 먼저 적는 것).
- DOM 순서 = 시각 순서 = 탭 순서. 끼니(라디오 그룹 1) → 카테고리 칩 → 국물 → (후보 0개일 때) 국물 조건 없애기 → 동네 입력란 → (값이 있을 때) 지우기 버튼 → 룰렛 돌리기 → 지도 링크 3개. CSS `order`로 바꾸지 않는다(design.md 7.2와 같음).
- 입력 영역은 "그룹 이름이 있는 묶음"으로 읽히게 한다. `fieldset`은 쓰지 않는다. 이유: 입력란이 하나라서 `label`로 충분하고, fieldset/legend는 라디오·체크 묶음용이다.
- 상시 고지는 기존 "무작위·보상 없음 고지", "상시 오락 고지"와 별도 자리다. 서로 합치거나 자리를 옮기지 않는다. 이유: 이 고지는 입력에 대한 설명이라 입력란 바로 아래여야 읽힌다.
- 고지 목록의 항목은 순서가 있는 단계가 아니므로 번호를 쓰지 않고 점(`list-disc`, 안쪽 여백 20px)을 쓴다.

#### 상시 고지 문구 (design.md 7.6 초안을 그대로 확정)

`MEAL_AREA_NOTICE_LINES`의 항목 순서와 문장:

1. 동네 이름은 적지 않아도 됩니다. 적으면 뽑힌 메뉴 이름과 함께 지도 검색어로 쓰입니다.
2. 적은 내용은 이 화면에만 있고 서버로 보내거나 저장하지 않으며, 새로고침하면 사라집니다.
3. 지도 링크를 누르면 검색어(동네 이름과 메뉴 이름)가 해당 지도 사이트로 전달되고, 그 뒤에는 그 사이트의 약관과 개인정보처리방침이 적용됩니다.
4. 상세 주소, 건물 번호, 전화번호 같은 개인 정보는 적지 마세요.
5. 위치 권한은 요청하지 않습니다. 지도 결과가 적은 동네 안의 가게인지는 확인하지 않으며, 결과는 지도 사이트가 정합니다.

- 순서 이유: 1은 "무엇을 하는 칸인가", 2~3은 "이 글이 어디로 가는가", 4는 "하지 말아야 할 것", 5는 "위치 기능이 아니라는 한계"다. 선택임을 먼저 말해 부담을 줄이고, 개인정보 주의(4)는 5보다 앞에 둔다.
- 4번 문장 강조: 굵기나 색으로 따로 강조하지 않는다. 이유: 5개 중 하나만 강조하면 나머지는 덜 중요해 보인다. 이 줄이 가장 중요한 줄이므로 위치(4번째)와 짧은 문장 길이로 눈에 띄게 한다.
- 새 금지어(주변, 근처, 현재 위치, 내 위치, GPS)와 기존 금지어를 쓰지 않았다. 문구 변경은 design.md 7.6 표와 `unit/meal/meal-copy.test.ts`가 맡는다.

## 입력 영역 상태별 화면

### 1. 빈 입력 (처음 화면)

- 라벨 "동네 이름 (선택)" + 빈 입력란 + placeholder "예: 강남역, 역삼동" + 고지 5줄.
- 지우기 버튼 없음. 오류 없음. 결과 카드에 미리보기와 짧은 고지 없음. 지도 링크는 메뉴 이름만(AC-1).
- 공백만 입력한 경우도 같은 모양이다(`status: 'empty'`). 입력란에는 공백이 그대로 남지만 오류를 보이지 않는다. 이유: 공백만 있는 것은 "아무것도 적지 않음"과 같게 처리하기로 했다(AC-4).

### 2. 정상 입력

- 입력란에 값이 있고 오류 없음. 오른쪽에 지우기 버튼(X 아이콘)이 나타난다.
- 룰렛을 아직 돌리지 않았으면 결과 카드가 없으므로 미리보기도 없다. 입력값은 남는다(plan 예외).
- 룰렛을 돌려 결과가 나오면: 지도 묶음에 "지도 검색어" 미리보기(값 예: "강남역 짬뽕")와 짧은 고지가 나타나고 세 링크가 같은 문장을 쓴다(AC-2).
- 입력을 바꾸면 미리보기와 링크가 바로 바뀐다. 뽑힌 메뉴는 그대로(Q4).
- 룰렛을 다시 돌려도 입력이 남고 미리보기의 메뉴 부분만 바뀐다.

### 3. 오류 입력 (허용 문자 밖, 21자 이상)

- 입력란: `aria-invalid="true"`가 되어 테두리가 `destructive`로 바뀐다.
- 입력란 바로 아래(고지 목록 위)에 오류 안내 한 줄(두 문장): 아이콘(`CircleAlert`, 16px) + 글자.
  - 허용 문자 밖: "한글, 영문, 숫자, 띄어쓰기, 가운뎃점(·), 하이픈(-)만 쓸 수 있습니다. 이 입력은 검색어에 넣지 않습니다."
  - 21자 이상: "동네 이름은 20자까지 적을 수 있습니다. 이 입력은 검색어에 넣지 않습니다."
  - 이유: 무엇이 틀렸는지(허용 문자, 길이)와 결과(검색어에서 빠짐)를 함께 알려 이용자가 고칠지 그대로 둘지 정할 수 있다. 사과나 "오류입니다" 같은 빈 말은 쓰지 않는다.
- 오류가 있어도 룰렛 돌리기는 막지 않는다(Q3). 결과 카드에 미리보기와 짧은 고지는 나오지 않고 링크는 메뉴 이름만 쓴다(AC-5).
- 지우기 버튼은 값이 있으므로 보인다. 이용자는 지우고 다시 쓰거나 고칠 수 있다.
- 오류 안내는 입력을 고칠 때까지 남는다. 고쳐서 유효해지거나 지우면 사라진다.
- 오류 상태에서도 고지 5줄은 그대로 보인다.

### 4. 한글 조합 중 (자음만 있는 상태 등)

- 입력란에는 이용자가 치는 글자가 바로 보인다(표시값은 항상 즉시 바뀐다).
- **오류 안내, 미리보기, 링크는 바뀌지 않는다.** 글자가 완성되어 조합이 끝난 뒤에 한꺼번에 반영한다(design.md 7.4).
- 조합 중이라는 별도의 표시(깜박임, 회색 처리, 안내 문장)는 넣지 않는다. 이유: 반영이 한두 글자 늦을 뿐이라 이용자는 차이를 느끼지 못한다. 별도 표시는 오히려 입력을 방해한다.
- 이미 오류가 떠 있는 상태에서 조합 중이면 오류가 그대로 남는다. 조합이 끝나면 새 값 기준으로 갱신된다.
- 입력란 밖을 눌러 조합이 끝나면 그때 반영된다.

### 5. 검색어 미리보기 (결과 카드, 유효할 때만)

- 위치: 결과 카드 안 지도 묶음의 `h3` "지도에서 찾아보기" 바로 아래, 링크 3개 위. `map-links.component.tsx` 안(design.md 7.2).
- 모양: 옅은 면(`bg-menu-meal/10`, `rounded-md`) 한 블록. 위 줄에 "지도 검색어"(작은 보조 글자), 아래 줄에 값(굵은 본문 글자).
  - 값은 링크에 들어가는 문장과 같다(`getMealMapSearchText` 결과). 동네 이름 부분과 메뉴 이름 부분을 색이나 굵기로 나누지 않는다. 이유: 지도에 가는 것은 한 문장이므로 한 문장으로 보여 준다. 일부만 강조하면 다른 문장처럼 읽힌다.
  - "강남역 짬뽕 짬뽕"처럼 중복되어도 있는 그대로 보인다(plan 예외, 중복 제거 없음). 이유: 링크와 미리보기가 어긋나지 않는다.
- 값은 한 줄이 기본이고 길면 줄바꿈한다. 메뉴 이름이 길어도 칸 밖으로 나가지 않는다.
- 입력이 비었거나 오류면 이 블록은 아예 그리지 않는다. 자리 표시도 만들지 않는다(AC-1, AC-5). 이유: 값이 없는 칸은 오히려 "비어 있다"는 신호가 되어 이용자를 헷갈리게 한다.
- 이 블록은 읽기 전용이다. 클릭, 복사 버튼, 선택 동작을 만들지 않는다(범위 밖). 글자 선택은 브라우저 기본대로 된다.

### 6. 결과 화면 짧은 고지

- 문구(`MEAL_AREA_RESULT_NOTICE_TEXT`, design.md 7.6): "적은 동네 이름은 저장하지 않으며, 지도 링크를 누를 때만 검색어로 해당 지도 사이트에 전달됩니다."
- 위치: 미리보기 블록 바로 아래, 링크 3개 위. 이유: 링크를 누르기 전에 무엇이 어디로 가는지(US-3) 미리보기와 한 덩어리로 읽힌다.
- 기존 외부 링크 안내(`MEAL_EXTERNAL_LINK_NOTICE_TEXT`, 문장만 수정됨)는 링크 3개 아래 자리 그대로다. 두 고지가 링크를 위아래로 감싸지만 역할이 다르다. 위는 "내가 적은 것", 아래는 "외부 사이트와 정책".
- 표시 조건은 DQ4. 추천은 A(유효할 때만). 아래 결정 요청 참고.

## 인터랙션·애니메이션

**확정해서 넣는 모션은 없다.** 입력란, 오류 안내, 미리보기, 고지, 지우기 버튼 모두 즉시 나타나고 사라진다. 기존 돌림판 회전 하나만 움직인다.

- 이유: 입력은 이용자의 직접 행동이고, 값이 바뀌면 화면이 바로 바뀌는 것이 가장 정직하다. 이 화면의 연출은 돌림판 하나로 충분하고(U2에서 이미 "끼니 전환도 즉시"로 확정), 입력에 모션을 더하면 연출이 서로 경쟁한다.
- 입력란 포커스 링의 색 변화는 기본 Input의 `transition-all duration-200`을 그대로 쓴다(새로 붙이는 모션이 아니라 기존 컴포넌트 기본값).
- 동작 줄이기: 새 모션이 없으므로 대체 동작이 필요 없다.

애매한 항목은 PM이 정하도록 올린다(U-L4).

| 안 | 내용 | 장점 | 단점 | design-system.md "모션" 표 |
|---|---|---|---|---|
| 빼는 안 (추천) | 오류 안내와 미리보기가 즉시 나타나고 사라진다 | 단순하다. 조합이 끝날 때마다 나타나는 반영이 가볍다. 오류가 나타날 때 아래 내용이 밀리는 것도 즉시라 시선이 덜 흔들린다. 동작 줄이기 대응이 필요 없다 | 결과 카드 안에서 미리보기가 갑자기 생기는 것이 눈에 안 띌 수 있다(블록이 링크 위에 있어 카드 안에서 위치는 일정하다) | 해당 항목 없음. 칩·선택 변경을 "눌러서 바로 보이면 충분"하다고 본 기존 판단과 같다 |
| 넣는 안 | 오류 안내와 미리보기가 150ms 동안 옅게 나타난다(`tw-animate-css`의 `fade-in-0`) | 새로 생긴 줄이 눈에 들어온다 | 같은 위치에서 글자만 바뀔 때는 효과가 없다. 입력할 때마다 반복돼 산만하다. CSS 애니메이션이라 `motion-reduce:animate-none` 처리가 필요하다. "목록 재배치"나 "기능의 핵심 연출"에 해당하지 않아 표에 맞는 줄이 없다 | 맞는 줄 없음, 판단이 애매함 |

## 접근성

- 명도 대비 (종이 `#eef0e6`, 카드 `#f7f8f1`, `destructive` `#b23a48`, `muted-foreground` `#5a6a5f` 기준 계산값. 구현 전에 한 번 더 재검산한다)
  - 입력값 `foreground` on `card` 약 11:1. placeholder `muted-foreground` on `card` 약 5.3:1.
  - 오류 글자·아이콘 `destructive` on 종이 약 5.1:1, on 카드 약 5.5:1. 두 곳 모두 4.5:1 이상.
  - 상시 고지·결과 고지 `muted-foreground` on 종이·카드 약 4.9~5.3:1.
  - 미리보기 값 `foreground` on `menu-meal/10` 약 10:1.
  - **입력란 테두리(비텍스트 대비 3:1).** 기본 `border-input`(`#c4cbb2`)은 카드 위 약 1.5:1로 3:1에 못 미친다. 입력란은 테두리가 유일한 "여기에 적는다"는 단서라 문제다. 선택을 올린다(U-L3). 추천은 이 입력란만 `border-muted-foreground`(약 5.3:1)를 쓰는 것.
- 키보드 이동
  - 탭 순서는 위 "화면별 레이아웃"에 적은 순서다. 입력란 → (값이 있으면) 지우기 버튼 → 룰렛 돌리기 → 지도 링크 3개(AC-6).
  - Enter를 눌러도 아무 동작도 하지 않는다. `<form>`을 쓰지 않는다(design.md 7.5). 이용자에게는 "입력 후 Enter로 뽑기"가 없다는 점을 문서로 남긴다. 이유: Enter로 제출되면 입력값이 이 사이트 주소에 붙는다(AC-3).
  - 지우기 버튼을 누르면 입력이 비워지고, 포커스는 입력란으로 돌아간다. 이유: 지우기 버튼이 사라지면서 포커스가 사라지는 것을 막고, 바로 다시 쓸 수 있게 한다.
  - Esc로 지우는 단축키는 만들지 않는다(범위 밖, 일부 IME가 Esc를 조합 취소로 쓴다).
- 라벨·스크린리더
  - 입력란: 보이는 `<label>` "동네 이름 (선택)"을 `htmlFor`/`id`로 연결한다. placeholder는 라벨을 대신하지 않는다. 접근성 이름은 보이는 글자와 같다(WCAG 2.5.3).
  - 지우기 버튼: `aria-label`은 "동네 이름 지우기"(`MEAL_AREA_CLEAR_BUTTON_LABEL`). 아이콘은 `aria-hidden`.
  - 오류 연결: 입력란에 `aria-invalid`와 `aria-describedby`(오류 안내 id + 고지 id). 오류가 없으면 고지 id만 가리킨다.
  - **오류 안내의 `aria-live` (design.md 7.5가 이 문서에 맡긴 항목).** 오류 안내를 감싸는 요소를 입력란 아래에 **항상 그려 두고** `aria-live="polite"`를 준다. 오류 문장만 안에 넣고 빼며, 요소 자체는 없애지 않는다.
    - 이유 1: 알림 영역은 먼저 존재해야 안에 생긴 내용을 읽어 준다(기존 결과 알림도 "항상 마운트"하는 방식과 같다).
    - 이유 2: `polite`를 쓰고 `role="alert"`(즉시 끊고 읽음)는 쓰지 않는다. 오류가 이용자를 막지 않고, 오류 반영은 한글 조합이 끝난 뒤에만 일어나므로 글자 하나마다 읽어 주지 않는다.
    - 이유 3: 결과 알림(`MealRouletteStatusComponent`, `role="status"`)과 다른 요소라 서로의 내용을 덮어쓰지 않는다. 오류는 입력할 때, 결과 알림은 룰렛을 돌릴 때 바뀌므로 겹치는 일이 거의 없다.
    - 오류가 사라질 때는 아무 문장도 읽어 주지 않는다(비우기만). 이유: 이용자가 고쳤다는 것을 이미 알고 있다.
  - 미리보기: `aria-live`를 붙이지 않는다. 이유: 입력할 때마다 읽으면 소란스럽다. 이용자가 결과 카드로 이동하면 읽는다. 결과 알림 문장("뽑힌 메뉴는 …")에도 동네 이름을 넣지 않는다(design.md 7.2).
  - 미리보기 구조: 라벨과 값을 `<dl>`(`<dt>` "지도 검색어", `<dd>` 값)로 묶어 "지도 검색어, 강남역 짬뽕"으로 읽히게 한다.
  - 고지 목록: 실제 `<ul>`/`<li>`로 만든다. 스크린리더가 "목록 5개 항목"을 알려 준다. 별도 제목은 달지 않는다.
  - **`aria-describedby`의 길이(U-L5).** design.md 7.5대로 입력란에 고지 전체를 연결하면 포커스할 때마다 약 300자를 읽어 준다. 한 번은 도움이 되지만 반복되면 번거롭다. 결정을 올린다.
  - 조합(IME): 접근성 이름이나 알림을 따로 달지 않는다.
- 터치·확대
  - 입력란 44px, 지우기 버튼 44x44px. 입력 글자 16px 이상으로 모바일 자동 확대를 막는다.
  - 200% 확대에서 라벨, 오류, 고지, 미리보기는 모두 줄바꿈되고 높이는 최소 높이라 잘리지 않는다. 가로 스크롤은 생기지 않는다.
- 320px 확인 항목 (AC-6)
  - 본문 폭 288px에서 입력란은 폭 전체, 지우기 버튼을 빼고 글자 영역 약 244px. 16px 한글 약 15자까지 보이고 20자까지 적으면 입력란 안에서 안쪽으로 스크롤된다. 입력은 가능하고 잘리지 않는다(기본 입력 동작).
  - 라벨 "동네 이름 (선택)", placeholder "예: 강남역, 역삼동"(약 12자)은 한 줄에 들어간다.
  - 오류 안내(최대 약 55자)는 `break-keep`으로 3줄 정도로 줄바꿈된다. 아이콘은 첫 줄에 맞춘다(`mt-1`, `shrink-0`).
  - 상시 고지 5개 항목은 모두 줄바꿈된다. 가장 긴 3번 항목이 약 5줄(약 120px)이다. 5개 합계는 약 14~16줄(약 340~380px)이다.
  - 미리보기 값은 `break-words`로 줄바꿈된다. 지도 링크 버튼 3개는 기존 `whitespace-nowrap`이 그대로라 폭 안에 들어가는지만 재확인한다.
  - 확인 폭: 320, 360, 390, 768, 1280px. 상태는 빈 입력, 정상(결과 있음), 오류, 20자 입력, 긴 메뉴 이름(예: 세 줄 가까운 메뉴) 조합으로 본다.
- 법적 고지는 접거나 숨기지 않는다. 입력란 아래에 항상 보인다(Q9).

## 다크 모드·동작 줄이기

- 다크 모드: 쓰지 않는다. 모든 색이 토큰 클래스(`bg-card`, `text-foreground`, `text-muted-foreground`, `text-destructive`, `bg-menu-meal/10`)다. `dark:` 클래스를 새로 쓰지 않는다. 기본 Input 파일(`src/components/ui/input.tsx`)에 들어 있는 `dark:`는 UI 폴더라 검사 대상이 아니고 그대로 둔다.
- 동작 줄이기: 이 문서가 추가하는 모션이 없다.

## 기존 디자인 시스템 변경 제안

없음.

- 단, U-L3(입력란 테두리 대비)에서 "추천안"을 고르면 이 입력란에 한해 `border-input` 대신 기존 토큰 `border-muted-foreground`를 쓴다. 새 토큰이나 시스템 값 변경이 아니고, 다른 컨트롤의 테두리는 바꾸지 않는다. 같은 문제가 카테고리 칩·국물 칩에도 있는지는 이 문서 범위 밖이라 PM이 알고 있도록 적어 둔다.

## 열린 질문 / 시안 선택 요청

모두 추천안이 있다. 승인하면 추천안으로 확정한다.

- **U-L1 데스크톱(768px 이상) 입력 영역 배치 (선택 요청).**
  - A안 (추천): 세로로 쌓는다. 입력란(`max-w-sm`) 아래에 고지 목록(`max-w-2xl`). 장점: plan Q9의 "입력란 아래에 항상 보임"과 글자 그대로 같고, 모바일과 구조가 같아 구현과 검사가 단순하다. 왼쪽 축이 끼니 스위치와 맞는다. 단점: 데스크톱에서 고지 5줄 때문에 돌림판이 약 130px 아래로 내려간다.
  - B안: 768px 이상에서 입력란은 왼쪽, 고지 목록은 오른쪽에 나란히(2열). 장점: 세로 길이가 줄어 돌림판이 화면에 더 빨리 보인다. 단점: "아래"가 아니라 "옆"이 되어 Q9와 어긋나고, 입력란과 고지의 폭이 달라지는 규칙이 하나 더 생긴다. 고지가 오른쪽 구석으로 밀려 눈에 덜 띌 수 있다.
- **U-L2 상시 고지의 모양 (선택 요청).**
  - A안 (추천): 틀 없이 점 목록만. 장점: 이 화면은 이미 끼니 틀, 필터, 돌림판, 결과 카드, 오락 고지 상자가 있어 상자를 하나 더 만들면 복잡해진다. 입력란에 바로 붙어 읽힌다. 단점: 고지가 덜 "공식 안내"처럼 보일 수 있다.
  - B안: 기존 상시 오락 고지처럼 `card` 면과 테두리 상자(`rounded-panel`)로 감싼다. 장점: 고지임이 분명하다. 단점: 입력란과 상자가 이중 박스가 되어 무겁고, 모바일에서 세로가 더 길어진다(안쪽 여백 약 32px 추가).
- **U-L3 입력란 테두리 대비 (선택 요청).**
  - A안 (추천): 이 입력란만 `border-muted-foreground`. 장점: 비텍스트 대비 3:1을 넘는다(약 5.3:1). 새 토큰 없음. 단점: 기본 컨트롤보다 테두리가 진해 "이 입력만 다르다"고 보일 수 있다.
  - B안: 기본 `border-input` 그대로. 장점: 사이트 전체와 같은 모양이다. 단점: 입력란 경계가 흐리다. 라벨과 placeholder가 있어 쓰임새는 알 수 있지만 3:1 기준에는 못 미친다.
- **U-L4 입력·오류·미리보기 모션 (선택 요청).** 위 "인터랙션·애니메이션" 표 참고. 추천은 빼는 안(즉시 나타남).
- **U-L5 입력란 `aria-describedby`에 고지 전체를 연결할지 (design.md 7.5 확인 요청).**
  - A안 (추천): design.md대로 오류 id + 고지 id를 모두 연결한다. 장점: 스크린리더 이용자가 입력란에 닿을 때 개인정보 주의와 외부 전달 고지를 확실히 듣는다. 승인된 설계 그대로다. 단점: 포커스할 때마다 약 300자를 읽는다.
  - B안: 오류 id만 연결한다. 고지는 DOM상 입력란 바로 뒤에 있어 읽기 순서로 닿는다. 장점: 반복 낭독이 없다. 단점: 설계 변경이 필요하고(architect 확인), 입력란에서 고지 낭독이 보장되지 않는다.
- **DQ4 결과 화면 짧은 고지 표시 조건 (design.md가 이 단계에서 정해도 된다고 맡긴 항목).**
  - A안 (추천): 동네 이름이 검색어에 들어갈 때(유효)만 보인다. 이유: 입력하지 않은 이용자에게는 해당 내용이 없고 카드가 짧아진다. "외부로 전달된다"는 일반 고지는 수정된 외부 링크 안내가 항상 맡는다.
  - B안: 항상 보인다. 장점: plan "결과 화면의 짧은 고지에도 나온다"와 글자 그대로 같다. 단점: 입력하지 않은 이용자에게 입력 관련 문장이 보여 헷갈린다.

### 개발 담당 확인 사항 (선택 요청 아님)

- 입력 영역은 `MealRouletteFilterPanelComponent` 안이 아니라 root에서 필터 패널 다음 형제로 둔다(design.md 7.2). 같은 `space-y-4` 묶음 안이다.
- 새 문구는 `meal-notice.constant.ts`에 두고 위 문장을 그대로 쓴다. 이 문서의 문장과 design.md 7.6 초안은 같다.
- 입력란, 지우기 버튼 모두 shadcn `Input`, `Button`(`variant="ghost"`, `size="icon"` 계열에 `h-11 w-11`)을 쓴다. 지우기 아이콘은 `lucide-react`의 `X`, 오류 아이콘은 `CircleAlert`다. 둘 다 `aria-hidden`.
- 오류 안내 알림 영역은 항상 마운트하고 `aria-live="polite"`를 준다. 이 요소에 조작 요소를 넣지 않는다.
- 입력란 속성(`autoComplete="off"`, `spellCheck={false}` 등)은 design.md 7.5 그대로다.
