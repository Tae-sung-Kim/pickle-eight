## 목표

궁합 결과를 본 사용자가 띠 또는 별자리 궁합 카드 이미지를 저장해 친구에게 보낼 수 있게 한다. 이미 만들어 둔 카드와 문구를 화면에 붙이는 것이 전부다. 카드에는 생년월일과 입력 정보가 들어가지 않는다.

## 범위

- 포함:
  - 띠 궁합 결과 화면과 별자리 궁합 결과 화면 아래에 공통 공유 블록(2차 운세 공유와 같은 위치, 같은 버튼 동작)을 붙인다.
  - 기존 카드 조립(`buildFortuneCompatibilityShareCard`), 카드 컴포넌트(`CompatibilityShareCardComponent`), 문구 상수(`FORTUNE_COMPATIBILITY_SHARE_*`)를 그대로 쓴다.
  - 카드 내용은 1차 계획 그대로: 두 이름(띠 또는 별자리 이름), 등급 이름, 요약 한 줄, 고지 한 줄. 생년월일과 입력 정보는 제외.
  - 검증: `e2e/share.spec.ts`에 띠 궁합 저장 흐름 1개, 별자리 궁합 저장 흐름 1개 추가. 단위 테스트는 기존 `unit/share/share-card-content.test.ts`의 궁합 케이스를 그대로 쓴다.
- 제외:
  - 새 카드 레이아웃, 새 문구 상수, 새 라우트, sitemap 변경, 메타데이터 변경.
  - 궁합 공유의 모바일 공유창 흐름 자동 테스트(열린 질문 4번에서 확인).
  - 결과 전용 링크, 서버 저장, 공유 클릭 기록.
  - 사주 궁합 등 다른 궁합 종류(이름 궁합, 혈액형 궁합, MBTI 궁합은 메타 금지어로 이미 막혀 있음).
  - 1차·2차 대상 화면의 동작 변경.

|---|---|---|
| F-1 | 띠 궁합 결과 화면 아래 공유 블록 연결 (결과가 있을 때만 보임) | 필수 |
| F-2 | 별자리 궁합 결과 화면 아래 공유 블록 연결 (결과가 있을 때만 보임) | 필수 |

## 유저 스토리

- US-1: 띠 궁합 결과를 본 사용자로서 두 띠의 궁합 카드를 이미지로 저장해 친구에게 보내고 싶다. 같이 보는 재미를 나누기 위해서다.
- US-2: 별자리 궁합 결과를 본 사용자로서 같은 방식으로 카드를 저장하고 싶다.
- US-3: 운영자로서 공유 카드에 생년월일과 입력 정보가 실리지 않기를 원한다.

## 완료 조건 (AC)

- AC-1 [E2E] (띠 궁합, 저장 흐름): 띠 궁합에서 두 띠를 골라 결과가 나오기 전에는 공유 버튼이 보이지 않는다. 결과가 나오면 결과 화면 아래에 "이미지 저장" 버튼이 보인다. 누르면 궁합 카드 PNG가 내려받아지고 파일 크기가 0이 아니다.
- AC-2 [E2E] (별자리 궁합, 저장 흐름): AC-1과 같은 흐름을 별자리 궁합에서 확인한다.
- AC-3 [단위] (궁합 카드 내용): 카드 본문은 두 이름, 등급 이름, 요약 한 줄만 가진다. 숫자가 없다. 기존 `unit/share/share-card-content.test.ts`의 궁합 케이스가 그대로 통과한다.
- AC-4 [정적] (적용 범위와 재사용): 공유 블록은 두 궁합 페이지의 결과 화면에만 붙는다. 새 카드 컴포넌트, 새 문구 상수, 새 라우트, sitemap 항목이 생기지 않는다. `title`, `description`, OG 값은 바뀌지 않고 `buildMetadata()`를 그대로 쓴다.
- AC-5 [단위] (고지와 금지어): 카드 고지 문구는 `FORTUNE_COMPATIBILITY_SHARE_NOTICE`에서 가져오고, 궁합 금지 표현(`FORTUNE_COMPATIBILITY_FORBIDDEN_TERMS`, 공통 금지어 포함)에 걸리지 않는다.

## 예외·빈 상태

- 결과가 없는 상태: 공유 블록이 보이지 않는다(2차와 같다).
- 결과 화면의 "다른 후보로 보기"(시각 모름 후보 전환)를 누르면 카드도 화면에 보이는 현재 후보의 이름과 등급으로 바뀐다. 이전 후보 카드가 남으면 안 된다(권장 기준. 열린 질문 3번에서 확인).
- 이미지 만들기 실패, 공유창 취소, 인앱 브라우저 안내: 1차 규칙과 같다(재사용).
- 위기 안내와 죽음 관련 풀이: 궁합 문구 풀에는 없다(문구 상수를 확인했다. "분위기" 단어만 검색에 걸림). 그래서 공유 숨김 조건은 해당 없음.
- 요약 문장이 길면 카드에서 잘리지 않아야 한다. 기존 카드 컴포넌트의 줄임 기준(90자 초과 시 글자 크기 축소)을 따른다(열린 질문 2번).
- 카드에 버튼, 입력란, 광고가 없으므로 캡처 제외 표시는 필요 없다.
- 320px 너비: 공유 블록이 가로 스크롤을 만들지 않는다.

## 검색 노출

- 키워드: 기존 검색어를 그대로 둔다. "띠 궁합", "별자리 궁합", "궁합 테스트"(`docs/TODO.md` 7번). 공유 기능 자체를 검색어로 노리지 않는다.
- 페이지가 답할 질문: 띠나 별자리로 두 사람의 궁합을 어떻게 보는지, 결과를 어떤 참고로 읽으면 되는지. 공유 블록은 본문 설명과 제목을 바꾸지 않는다.
- 공유 링크 미리보기: 공유 주소는 각 궁합 페이지의 canonical 주소다. 기존 OG 값이 바뀌지 않는지 확인한다(AC-4).

## 법적·정책 요구사항

- 개인정보 수집: 공유는 브라우저 안에서 이미지를 만들고 서버로 결과를 보내지 않는다. 입력 정보는 저장되거나 전송되지 않는다는 기존 문구를 유지한다. 새로 수집하는 정보는 없다. 공유 기록도 만들지 않는다.
- 파생값(열린 질문 1번): 카드의 두 이름은 생년월일에서 나온 띠·별자리 이름이다. 상대방의 파생값이 제3자에게 전달된다. `docs/TODO.md`의 2026-11-24 위험 수용 기록에 "궁합 파생값"이 이미 있으나, 입력 안내 문구는 "궁합 확인에 쓴다"까지만 말한다. 외부 공유가 이 목적 범위 안인지 확인이 필요하다.
- 고지 문구:
  - 카드 하단 고지(상수 그대로): "재미로 보는 참고용 결과입니다. 실제 관계를 판단하지 않습니다."
  - 1차 계획 초안은 해요체("재미로 보는 참고용 결과예요. 실제 관계를 판단하지 않아요.")였다. 궁합 상수와 화면 문구는 합니다체로 통일돼 있어 상수 문구를 권장안으로 쓴다(열린 질문 2번).
  - 이 문구에는 "보장"이 없어 운세 금지어 규칙에 걸리지 않는다.
  - 결과 화면의 기존 고지(궁합 결과 하단 오락 고지, 면책, 연령 고지)는 그대로 둔다.
- 상업적 이용: 광고 요소, 광고 링크, 로고, 새 글꼴을 넣지 않는다. 그래서 `DEPENDENCY_LICENSES.md`와 `THIRD_PARTY_NOTICES.md`는 바뀌지 않는다.
- 문구 권리: 한 줄 요약은 궁합 문구 풀(AI 작성, PM 검수, `docs/compatibility/copy-log.md`)에서 가져온다. "AI 문구 권리"는 2026-11-24 위험 수용 기록에 있다. 별도 조치는 없다.

## 열린 질문

사용자 확인이 필요한 것은 1, 2, 3번이다. 4번은 권장안으로 진행해도 되는지 확인한다.

1. (파생값과 공유 범위) 공유 카드에 상대방의 띠·별자리 이름이 실린다. 입력 안내 문구(`fortune-compatibility-notice.constant.ts`의 입력 안내)는 "궁합 확인에 쓴다"까지만 말하고 외부 공유를 말하지 않는다. 권장: (가) 위험 수용 기록 범위로 보고 그대로 연결한다, 또는 (나) 공유 직전 한 줄 안내("카드에는 두 분의 띠 또는 별자리 이름이 담깁니다")를 추가한다. 법률 확인 결과에 따라 (가)·(나)를 정한다. 사용자 결정 필요.
2. (고지 문구) 카드 고지를 상수 문구(합니다체)로 확정하고 1차 계획의 해요체 초안을 바꿔도 되는지. 권장: 상수 문구 채택. 사용자 승인 필요.
3. (다른 후보로 보기) 시각 모름 후보를 바꾸면 카드도 현재 후보로 맞춘다. 권장: 맞춘다. 사용자 확인 필요.
4. (검증 범위) 이번 E2E는 PC 저장 흐름 2개만 둔다. 모바일 공유창 흐름과 실기기 확인(1차 AC-6 대상 기기)을 이번 범위에 넣을지. 권장: 넣지 않는다. 2차 운세와 같은 공통 컴포넌트를 쓰므로 공유창 흐름은 2차 spec이 맡는다고 본다. 확인 필요.
5. (요약 길이) 요약은 `copy.summary`의 첫 문장이다. 샘플 문장은 대략 40자 안팎으로 보이나 최대 길이는 측정하지 않았다. 카드 줄임 기준은 90자다. 권장: 길이 상한 단위 테스트를 추가한다. 다만 이번 범위는 기존 단위 테스트 그대로이므로, 추가할지 사용자가 정한다.
