# 뭐 먹지 동네 이름 입력 지도 검색 기획서

## 목표

뭐 먹지에서 뽑힌 메뉴를 지도에서 찾을 때, 이용자가 적은 동네 이름(예: 강남역, 역삼동)을 함께 검색어로 넣어 "동네 + 메뉴" 검색 결과로 갈 수 있게 한다. 위치 권한은 쓰지 않고, 입력은 저장하지 않는다.

## 배경

- 처음 요청은 "내 위치를 공유해 주변 검색"이었다. 조사 문서(`docs/research/meal-location.md`)에서 카카오, 네이버, 구글의 웹 검색 URL은 좌표 기준 주변 검색을 공식으로 지원하지 않는 것으로 확인됐다. 구글은 좌표를 넣으면 핀만 찍히고, 카카오와 네이버의 좌표 중심 검색은 앱 스킴에만 있다.
- 이용자는 위치 권한 없이 동네 이름을 직접 적는 B안을 골랐다.
- 이 기능은 "주변" 검색이 아니다. 지도 서비스가 동네 이름을 해석해 보여 주는 결과이며, 거리나 반경을 보장하지 않는다.
- 좌표 방식은 나중에 다시 검토할 수 있다. 그때는 `docs/research/meal-location.md`를 기준으로 삼는다.

## 범위

- 포함: 동네 이름 입력란(선택 입력), 입력 검증, 검색어 조합(동네 이름 + 메뉴 이름), 결과 화면의 검색어 미리보기, 고지 문구, 방침·약관·COMPLIANCE.md의 해당 문장 갱신(승인 뒤), 기존 테스트 갱신과 새 테스트.
- 제외:
  - 위치 권한 요청, Geolocation 호출, 좌표 생성·저장·전송
  - `Permissions-Policy` 변경 (사이트 전체 `geolocation=()` 유지)
  - 동네 자동완성, 동네 목록 선택, 최근 입력 기억 (저장 금지 원칙)
  - 여러 동네 동시 입력, 반경 설정
  - 지도 API, API 키, 식당 목록·평점·영업 정보 표시
  - 새 페이지, 새 검색 키워드, 메타 설명 변경
  - 분석 이벤트 추가
  - 지도 제공자 추가·삭제 (기존 M11 열린 질문에서 따로 결정)
  - 좌표 방식 (재검토 시 별도 기획)

## 기능 목록

| ID | 기능 | 우선순위 (필수/선택) |
|---|---|---|
| F-1 | 동네 이름 입력란. 입력은 선택이며 비워 두면 지금과 같다 | 필수 |
| F-2 | 검색어 조합. 입력이 있으면 "동네 이름 + 한 칸 + 메뉴 이름", 없으면 메뉴 이름만 | 필수 |
| F-3 | 입력 정리와 검증. 앞뒤 공백 제거, 연속 공백 정리, 길이 제한, 허용 문자 확인, 오류 안내 | 필수 |
| F-4 | 결과 화면의 검색어 미리보기. 지도에 무엇이 전달되는지 보여 준다 | 필수 |
| F-5 | 고지 문구. 입력 용도, 저장하지 않음, 외부 지도로 전달됨, 위치 미요청, 결과 보장 없음 | 필수 |
| F-6 | 방침·약관·COMPLIANCE.md의 "메뉴 이름만", "입력을 받지 않음" 문장 갱신 | 필수 (승인 뒤) |
| F-7 | 입력 지우기 버튼 | 선택 |
| F-8 | 입력란 예시 문구 (예: 강남역, 역삼동) | 선택 |

## 유저 스토리

- US-1: 이용자로서 내가 있는 동네 이름을 적고 룰렛을 돌려, 뽑힌 메뉴를 그 동네에서 찾고 싶다. 왜냐하면 메뉴 이름만으로는 어느 동네 가게인지 알기 어렵기 때문이다.
- US-2: 이용자로서 동네를 적지 않고 지금처럼 메뉴 이름만으로 지도를 열고 싶다. 왜냐하면 지역을 밝히고 싶지 않을 때가 있기 때문이다.
- US-3: 이용자로서 링크를 누르기 전에 지도로 무엇이 넘어가는지 보고 싶다. 왜냐하면 외부 사이트로 이동하기 때문이다.

## 완료 조건 (AC)

QA가 이 목록으로 테스트를 만든다. 화면에서 확인할 수 있는 문장으로 쓴다.

- AC-1 [E2E]: 동네 입력란을 비운 채 룰렛을 돌리면, 결과 영역에 검색어 미리보기가 나오지 않고 세 지도 링크의 검색어는 뽑힌 메뉴 이름만이다.
- AC-2 [E2E]: 동네 입력란에 "강남역"을 적고 룰렛을 돌리면, 결과 영역에 "강남역 ○○"(뽑힌 메뉴) 미리보기가 보이고 세 지도 링크의 검색어가 같은 문장이다. 입력란 근처에 고지 문구가 보인다. 룰렛을 다시 돌려도 입력이 남고, 미리보기와 링크가 새 메뉴로 바뀐다.
- AC-3 [E2E]: 입력한 상태에서 지도 링크를 누르면 새 탭이 열리고, 이 페이지 주소에는 입력값이 없다. 새로고침하면 동네 입력란이 비어 있다.
- AC-4 [단위]: 입력 규칙 함수는 다음을 지킨다. 앞뒤 공백을 지우고 연속 공백은 한 칸으로 줄인다. 공백만 있으면 "입력 없음"과 같다. 20자를 넘으면 거부한다(길이는 열린 질문 Q1). 한글(완성형), 영문, 숫자, 공백, 가운뎃점(·), 하이픈(-) 외의 문자가 있으면 거부한다.
- AC-5 [E2E]: 허용되지 않는 입력(21자 이상, `https://`나 `/`, `:`, `?`, `&`, `<`, 이모지 등)을 적으면 입력란 아래에 오류 안내가 보이고 검색어 미리보기는 나오지 않는다. 이 상태에서 룰렛을 돌리면 지도 링크 검색어는 메뉴 이름만이다.
- AC-6 [E2E]: 320px 모바일 화면에서 동네 입력란, 고지 문구, 검색어 미리보기, 지도 링크 3개가 가로 스크롤 없이 보인다. 키보드 Tab만으로 입력란, 룰렛 돌리기, 지도 링크에 차례로 닿을 수 있다. 데스크톱과 모바일 양쪽에서 실행한다.
- AC-7 [E2E]: 입력 전후 전 과정에서 위치 권한 창이 뜨지 않고 위치 API가 호출되지 않는다. 쿠키 동의를 거절한 상태에서도 입력, 룰렛, 지도 링크가 동작한다.
- AC-8 [E2E]: 입력 전후 전 과정에서 이 사이트 도메인으로 나가는 요청(주소 쿼리와 본문 포함)에 입력 문자열이 없고, 로컬 저장소와 쿠키에 입력값이 남지 않는다. 입력 문자열은 지도 사이트로 가는 링크 요청에만 나타난다.
- AC-9 [정적]: 입력값은 화면 상태에만 있다. 입력값이 URL 쿼리나 경로, 저장소 API, 분석 이벤트, 콘솔 출력, 광고 스크립트 호출 인자로 가는 코드가 없다. 새 브라우저 저장 키가 추가되지 않는다.
- AC-10 [정적]: `next.config.ts`의 `Permissions-Policy`는 `geolocation=()`이 그대로이고, 위치 API 호출 코드가 추가되지 않는다.
- AC-11 [정적]: `COMPLIANCE.md` Meal 항목, `src/app/privacy/page.tsx` 지도 문단, `src/app/terms/page.tsx` 메뉴 룰렛 장에서 "검색어는 메뉴 이름만", "입력을 받지 않는다"는 문장이 새 기준 문장으로 바뀌고, "위치 정보를 요청하지 않는다"는 문장은 남아 있다.
- AC-12 [단위]: 입력란 이름, 예시 문구, 오류 안내, 고지 문구는 상수 파일에 있고, 기존 금지 표현 검사(`unit/meal/meal-copy.test.ts`)를 통과한다. 새 금지 표현은 "주변", "근처", "현재 위치", "내 위치", "GPS"다.

## 예외·빈 상태

- 입력이 비었거나 공백만 있으면 지금과 같다. 미리보기는 없고 링크는 메뉴 이름만 쓴다.
- 허용되지 않는 문자나 21자 이상이면 오류 안내를 보이고, 그 입력은 검색어에 넣지 않는다(AC-5). 링크를 막을지 여부는 열린 질문 Q3.
- 한글 조합 중(자음만 있는 상태)에는 미리보기와 링크를 바꾸지 않는다. 글자가 완성된 뒤 반영한다.
- 룰렛을 돌리기 전에 입력하면 결과가 없으므로 미리보기는 나오지 않는다. 입력값은 남는다.
- 룰렛을 돌린 뒤 입력을 바꾸면 미리보기와 링크가 바뀐다(권장, Q4).
- 입력한 동네에 뽑힌 메뉴 이름이 이미 들어 있으면("강남역 짬뽕"을 적고 짬뽕이 뽑힘) 검색어는 "강남역 짬뽕 짬뽕"이 된다. 중복 제거는 하지 않는다.
- 지도 사이트에 없는 이름이나 여러 곳에 있는 이름을 적으면, 지도 사이트가 결과를 정한다. 엉뚱한 지역이나 결과 없음이 나올 수 있으며 이는 고지에 포함한다. 서비스는 결과를 확인하지 않는다.
- 영문 입력(예: "Gangnam")은 허용한다.
- 새로고침하거나 다른 페이지로 갔다가 돌아오면 입력은 사라진다(AC-3). 저장하지 않으므로 복원하지 않는다.
- 인앱 브라우저에서도 위치를 쓰지 않으므로 기능 차이는 없다. 지도 링크의 인앱 동작은 기존 열린 질문(`docs/menu-meals/plan.md` Q17)을 따른다.
- 쿠키 동의를 거절해도 입력과 지도 링크는 동작한다(AC-7).

## 검색 노출

- 키워드: 변화 없음. `docs/archive/menu-meals/design.md` 944행의 `/meal` 키워드(오늘 뭐 먹지, 점심 뭐 먹지, 점심 메뉴 추천, 저녁 뭐 먹지, 아침 뭐 먹지, 메뉴 룰렛 등)를 그대로 쓴다.
- 키워드 추가 금지: "주변 음식점", "근처 맛집", "동네 맛집", "식당 찾기"를 넣지 않는다. 이 기능은 주변 검색이나 식당 찾기 서비스가 아니므로, 검색 문구와 실제 기능이 어긋난다.
- 새 페이지 없음. 사이트맵, title, description, JSON-LD는 바꾸지 않는다. 기존 `/meal` 검색 노출 검사로 충분하다.
- 페이지가 답해야 할 질문: 변화 없음. 기존 `/meal` 질문("오늘 뭐 먹지?", "점심·저녁 메뉴를 무작위로 고르려면?")에 그대로 답한다. 동네 입력은 검색 질문의 답을 바꾸지 않는다.

## 법적·정책 요구사항

- 개인정보 수집:
  - 서비스는 입력값을 수집하지 않는다. 서버로 보내지 않고, 저장소에 두지 않는다. 입력은 화면 상태에만 있다.
  - 동네 이름이 개인정보인지에 대한 기획 판단(권장): 역 이름, 행정동 이름처럼 공개된 지명은 그 자체로 특정 개인을 알아볼 수 없으므로 개인정보로 보지 않는다. 다만 이용자가 상세 주소, 건물 번호, 집이나 회사 주소, 전화번호를 적으면 개인정보가 될 수 있다. 그래서 길이와 문자를 제한하고, 상세 주소와 전화번호를 적지 말라고 고지한다. 이 판단의 법률 확인 여부는 열린 질문 Q2.
  - 외부 전달: 링크를 누르면 입력한 동네 이름과 메뉴 이름이 지도 사업자 사이트의 검색어로 넘어간다. 이용자가 직접 누른 외부 연결이며, 기존 방침 6장의 "처리위탁이 아니라 외부 사이트 연결" 문단과 같은 구조로 쓴다. 이동한 뒤에는 그 사업자의 개인정보처리방침이 적용된다.
  - 위치정보: 입력값은 단말의 위치나 좌표가 아니다. 위치 권한을 요청하지 않으므로, 위치정보의 보호 및 이용 등에 관한 법률의 위치기반서비스 대상이 아니라고 기획 판단한다(권장). 조사 문서 6장의 결론과 맞다. 법률 확인 여부는 Q2에 묶는다.
  - 분석: 입력값, 동네 이름, 지도 링크 클릭을 분석 도구나 알림으로 보내지 않는다. 동네별 통계를 만들지 않는다.
  - 기존 문구와 충돌하는 곳 (수정은 승인 뒤 설계·개발 단계에서):
    - `COMPLIANCE.md` Meal 항목: "No input is collected", "with the menu name as the only query", "The query is the menu name only, no location, no user data" 문장이 바뀌어야 한다. "no location permission is requested" 문장은 유지한다.
    - `src/app/privacy/page.tsx` 200~206행: "검색어로 뽑힌 메뉴 이름만 전달됩니다"를 메뉴 이름과 이용자가 입력한 동네 이름이 전달된다는 문장으로 바꾼다. "고른 끼니와 조건, 뽑힌 결과를 서버로 전송하거나 저장하지 않습니다"에 입력한 동네 이름을 더한다. "위치 정보를 요청하지 않으며"는 유지한다. 방침 수집 항목 설명에 "입력을 받지 않는다"는 말이 있으면 함께 고친다.
    - `src/app/terms/page.tsx` 208~216행: 같은 "메뉴 이름만" 문장을 고친다. "위치 정보를 요청하지 않으며"는 유지한다.
    - `docs/menu-meals/plan.md`, `docs/archive/menu-meals/design.md`: "검색어는 메뉴 이름만"(F-6, AC-19, 1045행) 표현은 이 기능으로 대체된다. 승인 뒤 해당 문서 표현을 갱신한다.
  - 방침과 약관의 시행일: 문장을 고치면 시행일을 바꿀지 기존 M17 흐름과 맞춰 정한다.
- 고지 문구 (요소만 정한다. 문장은 설계·UI 단계에서 상수로 쓴다):
  1. 동네 이름 입력은 선택이며, 적지 않아도 된다.
  2. 적은 동네 이름은 뽑힌 메뉴 이름과 함께 지도 검색어로 쓰인다.
  3. 입력은 이 화면에만 있고, 서버로 보내지 않으며, 저장하지 않는다. 새로고침하면 사라진다.
  4. 지도 링크를 누르면 검색어(동네 이름과 메뉴 이름)가 해당 지도 사이트로 전달된다. 이후에는 그 사이트의 약관과 개인정보처리방침이 적용된다.
  5. 상세 주소, 건물 번호, 전화번호 같은 개인 정보는 적지 않는다.
  6. 위치 권한을 요청하지 않는다. 지도 결과가 정해진 거리 안의 주변인지는 보장하지 않으며, 결과는 지도 사이트가 정한다.
  7. 기존 고지 유지: 오락 목적, 무작위 결과, 추천이나 평가가 아님, 제휴 없음, 식당 정보 정확성 보장 없음.
  - 위치: 입력란 아래에 항상 보인다(접지 않음, 기존 고지 방식과 같음). 3번과 4번은 결과 화면의 짧은 고지에도 나온다.
- 상업적 이용 주의:
  - 수익은 AdFit 디스플레이 광고만이다. 광고는 입력란, 미리보기, 지도 링크 영역을 가리지 않는다. 광고 스크립트에 입력값이 넘어가지 않는지 설계에서 확인한다(AC-9).
  - 동네 입력을 바탕으로 한 지역 광고, 지역 제휴 링크, 식당 목록, 예약·배달 링크는 넣지 않는다.
  - 입력으로 만든 데이터(동네별 검색 수요 등)를 광고나 판매에 쓰지 않는다.
  - AdFit 심사에서 지역 표현이 문제되지 않는지 확인한다. AdFit 정책 원문은 아직 확인하지 않았다(기존 점검 항목과 같이).
  - 지도 사업자의 검색 링크 이용 조건은 기존 열린 질문(M11, Q17)을 그대로 따른다. 검색어에 사용자 입력이 더해져도 웹 검색 링크 방식이 바뀌지 않는지 확인이 필요하다.
  - 위치 기능이 없으므로 위치 기반 서비스 관련 점검 항목은 해당 없음으로 기록하되, 법률 확인 여부는 Q2에서 정한다.

## 영향받는 기존 AC·테스트

- `docs/menu-meals/plan.md` AC-17 (지도 링크 있음): 유지.
- AC-19 (검색어에 결과 메뉴 이름만, 위치·식별자 없음): 입력이 없을 때만 그대로이고, 입력이 있을 때는 "동네 이름 + 메뉴 이름"이 된다. 승인 뒤 이 AC를 바꾼다. 이 기능의 AC-1, AC-2가 대체한다.
- AC-21 (위치 권한 요청 없음): 유지하고, 입력 흐름까지 확인하도록 넓힌다(AC-7).
- AC-22 (쿠키 거절 시 지도 링크 동작): 유지하고, 입력 흐름까지 확인하도록 넓힌다(AC-7).
- AC-25 (키보드만으로 조작): 입력란이 늘었으므로 키보드 순서를 다시 확인한다(AC-6).
- AC-26 (320px 가로 스크롤 없음, 끼니 칸 한 줄): 입력란, 고지, 미리보기가 추가되므로 재검사한다(AC-6).
- AC-32 (`/terms` 메뉴 룰렛 장 문장), AC-33 (`/privacy` 지도 문단): 문장이 바뀌므로 갱신한다(AC-11).
- `e2e/meal.spec.ts` 199~235행 (AC-17~19 지도 링크 검사): 입력이 없는 현재 검사는 `encodeURIComponent(name)` 포함 여부만 보므로 그대로 통과한다. 입력이 있는 흐름을 새 검사로 추가한다. `e2e/helpers/meal.util.ts`의 `mapLinks`, `stubMaps`, `watchGeolocation`을 재사용한다.
- `unit/meal/meal-copy.test.ts`: 새 입력 문구와 고지 문구를 검사 대상에 넣는다.
- 새 단위 테스트: 입력 규칙 함수(AC-4).
- 문구 작성 기록(copy-log): 새 문구를 기존 관행대로 기록한다.

## 열린 질문

각 질문에 권장안을 적었다. 사용자가 정한다.

- Q1. 입력 길이와 허용 문자
  - 권장: 최대 20자, 한글(완성형), 영문, 숫자, 공백, 가운뎃점(·), 하이픈(-)만 허용. 숫자는 허용한다("2호선 강남역"). 쉼표로 여러 동네를 적는 것은 허용하지 않는다. 상세 주소를 기술적으로 막을 수는 없으므로 고지로 대응한다.
- Q2. 법적 판단
  - 동네 이름의 개인정보 해당 여부와 위치정보 관련 법 적용 여부를 법률 자문이나 위치정보지원센터, 개인정보 상담 창구로 확인할지 정한다.
  - 권장: 기획 판단("개인정보 수집 없음, 위치정보 아님")을 기록하고, 확인 전까지 위험 수용으로 둔다(COMPLIANCE.md의 기존 방식과 같음). 상세 주소 안내 문구는 출시 조건으로 둔다.
- Q3. 입력 오류 상태에서 지도 링크
  - 권장: 오류 입력은 검색어에서 빼고 메뉴 이름만으로 링크를 연다. 룰렛 돌리기는 막지 않는다. 오류 안내에 "이 입력은 검색어에 넣지 않습니다"를 함께 보인다.
  - 대안: 오류가 있으면 룰렛 돌리기를 막는다.
- Q4. 룰렛을 돌린 뒤 입력을 바꿀 때
  - 권장: 미리보기와 링크가 바로 바뀐다. 이미 뽑힌 메뉴는 그대로 두고 검색어만 바꾼다.
- Q5. 지도 제공자 수 (기존 M11)
  - 구글 지도 링크를 유지할지는 기존 M11에서 정한다. 이 기능 출시 전에 정해야 방침, 약관, COMPLIANCE 문장을 한 번에 고칠 수 있다.
  - 권장: 이 기능으로 M11 판단을 바꾸지 않는다.
- Q6. 검색 노출 확장
  - "동네 + 메뉴" 검색 수요를 노리는 별도 페이지를 만들지 정한다.
  - 권장: 이번에는 만들지 않는다. 키워드도 추가하지 않는다(검색 노출 절 참고).
- Q7. 입력 유지 범위
  - 권장: 같은 화면 안에서는 룰렛을 여러 번 돌려도 입력을 유지하고, 새로고침이나 다른 페이지 이동 때 지운다. 입력 기록(최근 동네)은 만들지 않는다.
- Q8. 욕설이나 부적절한 단어 걸러내기
  - 권장: 문자 규칙(AC-4)만 적용하고 단어 목록 필터는 두지 않는다. 입력은 저장하거나 공개하지 않으며, 이용자 자신의 지도 검색어로만 쓰인다.
- Q9. 고지 위치
  - 권장: 입력란 아래에 항상 보이게 한다. 기존 고지(룰렛 옆 상시 고지) 방식과 맞춘다.
- Q10. 좌표 방식 재검토 시점
  - 권장: 이번 범위 밖이다. 나중에 재검토할 때 `docs/research/meal-location.md`를 출발점으로 쓴다.
