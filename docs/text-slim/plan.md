# 텍스트 접기 1단계 기획서 (text-slim)

근거 문서: `docs/text-audit/audit.md` 4장(반복 문구), 5장(접어도 되는 후보와 접으면 안 되는 블록), 7장(후보 1·3·4·7). 작성일 2026-11-27.

## 목표

긴 안내 블록(FAQ, 표, 설명 문단)을 기본으로 접어서, 이용자가 입력·결과·법적 고지를 먼저 보게 하고, 본문은 서버 HTML과 구조화 데이터에 그대로 남겨 검색 노출을 지킨다.

## 범위

- 포함:
  - FAQ 접기: 운세, 궁합, 타로, 꿈(허브와 상세), 뭐 먹지, 운빨 뽑기(허브와 도구 3개)의 FAQ 블록 17화면.
  - 띠별 운세의 12띠 출생 연도 대응표 접기 (`/fortune/tti`).
  - 별자리 운세의 12별자리 기간표 접기 (`/fortune/star-sign`).
  - 띠 궁합의 관계 설명 접기 (`/fortune/compatibility/tti`).
  - 별자리 궁합의 원소 설명 접기 (`/fortune/compatibility/star-sign`).
  - 접기 방식을 공통 컴포넌트 하나로 통일하는 것. 현재 FAQ 컴포넌트 5종을 이 공통 컴포넌트로 바꾼다.
  - 접기 결정에 따라 바뀌는 설계 문서 갱신 (`docs/fortune/ui-ux-design.md`).
- 제외:
  - 문구 삭제, 문구 수정, 중복 정리. audit 7장 후보 2, 5, 6, 8, 9, 10은 2단계다.
  - 법적 필수 고지 블록을 접는 것 (아래 AC-6 목록).
  - 사주 계산 기준(661자). COMPLIANCE 11장이 서버 HTML과 입력 단계 링크를 요구한다.
  - 운세 이용 안내 9항. 접기 후보가 아니다(2단계).
  - 로또 6개 화면. 화면에 FAQ가 없고 고지 블록은 법적 필수다.
  - 손 없는 날 연도 화면의 월별 목록 접기(F-6). 열린 질문 7번 결정 전까지 보류한다.
  - 새 기능, 새 저장 항목, 새 외부 자원.

## 유저 스토리

- US-1: 모바일 이용자로서, 운세나 타로를 열면 입력칸과 결과 버튼을 바로 보고 싶다. 왜냐하면 긴 FAQ와 표가 첫 화면 스크롤을 늘리기 때문이다.
- US-2: 검색으로 들어온 이용자로서, 질문 목록을 훑고 궁금한 답만 펼쳐 보고 싶다. 왜냐하면 답 전체를 읽지 않고도 필요한 정보를 찾을 수 있어야 하기 때문이다.

## 완료 조건 (AC)

QA가 이 목록으로 테스트를 만든다. 열린 질문 1번(접기 단위)과 5번(공통 컴포넌트)의 결정을 전제로 쓴다.

- AC-1 [E2E]: `/fortune`, `/tarot/daily`, `/meal`, `/lucky-draw/lots`를 데스크톱에서 열면 FAQ 블록의 질문 목록이 기본으로 보이고 답은 닫혀 있다. 질문을 누르면 답이 보이고, 다시 누르면 닫힌다. 마우스와 키보드(Tab 이동 후 Enter 또는 Space)가 모두 된다. 키보드로 이동하면 포커스 표시가 질문에 보인다.
- AC-2 [E2E]: `/fortune/tti`의 12띠 대응표와 `/fortune/compatibility/star-sign`의 원소 설명은 기본으로 제목(또는 요약 줄)만 보인다. 누르면 본문이 보이고 다시 누르면 닫힌다. 12별자리 기간표와 띠 관계 설명은 AC-3로 확인한다.
- AC-3 [정적]: 접히는 블록 5종(FAQ, 12띠 대응표, 12별자리 기간표, 띠 관계 설명, 별자리 원소 설명)이 모두 같은 공통 접기 컴포넌트를 쓴다. 기존 FAQ 컴포넌트 5종(운세, 꿈, 타로, 뽑기, 뭐 먹지)은 공통 컴포넌트로 바뀌었다.
- AC-4 [E2E]: JS를 끈 상태에서 `/fortune`과 `/fortune/tti`를 열면, 접힌 FAQ 답과 12띠 대응표 내용이 서버 HTML에 있다. JS를 끈 상태에서도 접힌 블록을 펼칠 수 있다. 서버 HTML의 FAQPage 구조화 데이터 질문·답은 화면 FAQ와 같다. 기존 `e2e/fortune.spec.ts`의 AC-14, AC-15가 그대로 통과한다.
- AC-5 [단위]: 문구 검사 테스트(`unit/fortune`, `unit/tarot`, `unit/lucky-draw`, `unit/meal`, `unit/dream`, `unit/fortune`의 compatibility 테스트)가 변경 전과 같이 통과한다.
- AC-6 [정적]: 이번 단계에서 문구 diff가 없다. 아래 블록의 문구와 위치가 바뀌지 않는다: 상시 면책, 결과 하단 면책, 상담전화 5곳, 이용 동의 화면, 로또 경고 알림과 하단 고지, 뭐 먹지 무작위·무보상 고지, 사주 계산 기준. 광고 슬롯이 접힌 블록 안으로 들어가지 않고 위치도 바뀌지 않는다. 삭제된 문구는 2단계 승인 목록(D-1~D-5, D-7~D-13, D-15) 기준이다.
- AC-7 [정적]: 접기 컴포넌트의 누름 영역은 터치 기준 44px 이상이다. 키보드 포커스 표시가 있다. 열림·닫힘에 움직임이 있으면 `prefers-reduced-motion`에서 움직임을 끈다.
- AC-8 [정적]: `docs/fortune/ui-ux-design.md`의 254행(허브 FAQ 표현), 1139행(12띠 대응표 `<table>` 지정), 1143행(FAQ 펼친 목록, 아코디언 없음)이 이번 결정에 맞게 갱신되고, 사용자 승인 기록이 남는다.

## 예외·빈 상태

- FAQ 항목이 0개인 화면에서는 FAQ 블록 제목도 그리지 않는다.
- JS를 끈 상태에서도 접힌 블록을 펼칠 수 있어야 한다(AC-4).
- 접힌 블록 안을 가리키는 내부 링크나 앵커가 있으면 그 블록이 열려야 한다. 현재 그런 링크가 있는지는 설계 단계에서 확인한다.
- 펼침 상태는 저장하지 않는다. 새로고침하면 닫힌 상태로 돌아간다. 쿠키나 저장소에 새 항목을 쓰지 않는다.
- 긴 답이 좁은 화면(320px)에서 가로 스크롤을 만들지 않는다. 기존 화면 기준을 따른다.
- 브라우저 찾기(Ctrl+F)로 접힌 텍스트를 찾을 때 자동으로 펼칠지는 열린 질문 9번.

## 검색 노출

- 키워드: 기존 화면 키워드를 그대로 쓴다. 제목, 설명, 메타, 키워드는 바꾸지 않는다. 예: "오늘의 운세", "띠별 운세", "별자리 운세", "띠 궁합", "별자리 궁합", "오늘의 타로", "꿈 해몽", "뭐 먹지", "제비뽑기".
- 페이지가 답해야 할 질문: 기존 FAQ 질문이 그대로 답한다. 예: "12띠 출생 연도는 어떻게 되나요?", "별자리 기간은 언제인가요?", "띠 궁합은 어떻게 정해지나요?". 접은 뒤에도 질문과 답은 서버 HTML에 있다(AC-4).
- 구조화 데이터: FAQPage 질문과 답은 화면 FAQ와 같은 문구를 쓴다(AC-4). BreadcrumbList와 기존 구조화 데이터는 바꾸지 않는다. 사이트맵은 바꾸지 않는다.
- 위험: 접힌 본문이 검색 색인과 검색 결과 설명에서 얼마나 쓰이는지 이 프로젝트에서 확인한 적이 없다(열린 질문 6번).

## 법적·정책 요구사항

- 개인정보 수집: 없음. 접기는 입력을 받지 않고 서버로 보내지 않는다. 펼침 상태를 저장하지 않는다.
- 고지 문구: 문구를 바꾸지 않는다. 사용자 승인 방침에 따라 아래 법적 필수 고지는 그대로 둔다. 운세 상시 면책과 결과 하단 면책, 타로·꿈·뭐 먹지·뽑기의 상시 고지와 하단 고지, 상담전화 5곳, 이용 동의 화면, 로또의 만 19세·비제휴·당첨 보장 안 함 고지(`docs/lotto-notice/plan.md` AC-1), 뭐 먹지 무작위·무보상 고지(COMPLIANCE 11장).
- 가이드와 FAQ는 지우지 않고 접는다. 접은 본문도 서버 HTML과 구조화 데이터에 남는다.
- 상업적 이용 주의: 광고(AdFit) 슬롯 위치와 개수를 바꾸지 않는다. 접힌 블록 안에 광고를 넣지 않는다. 최근 커밋 "광고 위치 수정"과 충돌하지 않도록 한다.
- 새 문장이 없으므로 신규 저작·약관 검토는 필요 없다.

## 열린 질문

1. FAQ 접기 단위. (a) 질문마다 접기: 질문은 항상 보이고 답만 접힌다. 추천. 검색 노출과 훑어보기에 질문이 남는다. (b) 블록 전체 접기: "자주 묻는 질문" 제목만 보인다. 사용자 결정 필요.
2. 승인 범위. 사용자가 승인한 것은 FAQ 펼친 목록 결정의 변경이다. 12띠 대응표 레이아웃(`docs/fortune/ui-ux-design.md` 1139행, `<table>` 지정)과 기간표·관계 설명·원소 설명 접기도 설계 문서 변경이 필요하다. 이 항목들이 승인 범위에 들어가는지 확인한다.
3. 기존 AC 문구 해석. fortune plan AC-67, tarot plan AC-33, lucky-draw plan AC-5와 136행의 "보인다", "화면에 보이는"을 접힌 본문에도 적용할지. 추천: 문구를 "서버 HTML에 있다(접힌 상태 포함)"로 명확히 고치고 기록한다. 문구 변경이므로 사용자 승인이 필요하다.
4. 별자리 기간표의 병기 문장("해마다 하루 정도 달라질 수 있다", fortune plan AC-26). 접힌 제목 줄에 두는 안을 승인할지 확인한다.
5. 공통 FAQ 컴포넌트. 현재 FAQ 컴포넌트는 5종이다. fortune, dream, tarot은 h2+h3+p, lucky-draw는 dl, meal은 h2+h3 구조다. `src/components/common`에는 FAQ 공통 컴포넌트가 없고, 5종은 `src/features/*/shared/components`에 흩어져 있다. 5종을 공통 컴포넌트 하나로 바꾸는 것(기존 파일 교체)을 1단계 범위에 넣을지 확인한다. 위치와 구현 방식은 설계 단계에서 정한다.
6. 검색 색인. 접힌 본문이 색인과 검색 결과 설명에 반영되는지 이 프로젝트에서 검증된 적이 없다. 배포 후 확인 계획을 넣을지 정한다.
7. 손 없는 날 연도 화면(F-6, 보류). 제안안은 달력을 기본으로 두고 월별 목록을 접는 것이다. 충돌이 세 가지 있다. (a) no-son AC-3과 `e2e/no-son-days.spec.ts` 157~196행이 월별 목록을 보임으로 검사한다. (b) 2026-11-25 UI/UX 승인 "목록 → 달력"과 다르다. (c) no-son plan 110행의 검색 질문 "2027년 손 없는 날은 언제인가?"의 답이 월별 목록이라, 접으면 검색 답이 기본 화면에서 가려진다. AC-7(서버 HTML)은 접어도 충족한다. 기획자 추천: 1단계에서 제외한다. 대안으로 월별 목록을 접지 않고 월마다 한 줄 요약만 남기는 안이 있다. 사용자가 고른다.
8. 로또 FAQPage 구조화 데이터. audit 3.20 기준 로또 화면에는 보이는 FAQ가 없고, 페이지 소스에는 FAQPage JSON-LD 생성기 2개가 있다. 이 항목은 이번 단계 밖이다. 별도로 다룰지 정한다. 이 항목은 audit의 관찰이며 이번에 직접 확인하지 않았다.
9. 브라우저 찾기(Ctrl+F)로 접힌 텍스트를 찾았을 때 자동 펼침을 요구할지. 브라우저 지원을 설계 단계에서 확인한다.
