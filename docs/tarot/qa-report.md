## 타로 기능 QA (QA-1, QA-2)

앱 코드(`src/`)와 기존 `e2e/lotto.*.spec.ts`는 수정하지 않았다. `.env`는 읽지 않았다. 쿠키 동의 키(`..._cookie_consent_v1`)의 접두어로 타로 키 이름을 만들어 오늘의 카드 저장값을 직접 넣었다.

- 실행일: 2026-11-05
- 브랜치: `develop` (작업 트리 기준, FE-1~FE-8, CT-1~CT-4, DOC-1 반영 상태)
- 실행 환경: Chrome(설치본), 프로젝트 desktop(Desktop Chrome)과 mobile(Pixel 7), workers 3, 개발 서버(`pnpm dev`, 포트 3000)
- 테스트 파일
  - `e2e/tarot.spec.ts` (QA-1): 프로젝트당 84개
  - `e2e/tarot-copy.spec.ts` (QA-2): 프로젝트당 25개

### 실행 명령과 결과 요약

같은 개발 서버 포트를 쓰므로 순서대로 실행했다. `test-results/`는 실행할 때마다 비워지므로 78장 스크린샷이 필요하면 `e2e/tarot.spec.ts`를 마지막에 실행한다.

| 순서 | 명령 | 결과 |
|---|---|---|
| 1 | `pnpm exec playwright test e2e/tarot-copy.spec.ts --reporter=list` | 총 50개(desktop 25, mobile 25) 중 통과 50, 실패 0 |
| 2 | `pnpm exec playwright test e2e/tarot.spec.ts --reporter=list` | 총 168개(desktop 84, mobile 84) 중 통과 164, 실패 4 |

실패 4개는 모두 같은 항목 `AC-33(표시)`이다(2개 페이지 x desktop·mobile). 앱 문제다(아래 "실패·확인 필요 항목" 1번). 데스크톱과 모바일의 결과 차이는 없다.

작성 중 수정한 테스트 오류(앱 문제 아님): AC-5 반전 확인에서 `transform` 대신 `rotate` 속성(Tailwind `rotate-180`)을 봐야 했음, AC-11 안내 문구가 FAQ 답변에도 있어 `.first()` 필요, 오늘의 타로 페이지는 가이드에 바보 정/역방향 그림 2개가 처음부터 있어 위기 상태 검사를 "개수가 늘지 않음"으로 바꿈, JS 비활성 검사를 "HTML에 존재(DOM)"와 "화면 표시" 둘로 나눔.

참고로 같은 테스트를 `pnpm build` + `pnpm start`(운영 빌드)로도 한 번 실행했다. 이때 AC-33(표시) 4개는 개발 서버와 같이 실패했고, 모바일에서 숨김 스트리밍 영역이 남아 같은 입력칸이 DOM에 두 번 잡히는 간헐 실패 3건이 있었다. 테스트에 대기 보강(`waitForHydration`에서 남은 숨김 영역 정리)을 넣은 뒤 개발 서버에서 다시 돌렸을 때는 발생하지 않았다. 운영 빌드는 보강 후 다시 돌리지 않았다.

### 실패 항목

이번 변경으로 새로 생긴 실패는 없다. 남은 실패는 위 "실패·확인 필요 항목" 1번(AC-33 표시, 루트 `src/app/loading.tsx`의 숨김 스트리밍 영역)이고 담당은 그대로 frontend-dev(PM이 범위 결정 후)다.

테스트 쪽에서 고친 것: 새 JS 비활성 "화면에 보인다" 테스트를 처음에 `visible`로 썼다가 같은 원인으로 실패해 DOM 존재(attached) 검사로 바꿨다. 기존 위기 패널 탭 순서 검사(109 -> 계속 보기)는 5개 변경 사양에 맞게 고쳤다. 앱 결함은 아니다.

### 알려진 한계

1. JS를 끈 브라우저 화면에서 상담전화 5개가 실제로 보이는지는 확인하지 못한다. 위 AC-33(표시) 이슈 때문에 본문이 `hidden`으로 남는다. 서버 HTML과 DOM에는 5개가 모두 있다. 위기 패널은 JS가 있어야 나오므로 JS 없는 환경에서는 결과 하단의 5개만 안내 수단이다.
2. 실제 전화 걸기는 검사하지 않는다. `tel:` 이동은 막고 `href`와 클릭 이벤트만 본다. 번호가 실제 운영 중인지, 24시간 운영인지는 e2e로 알 수 없다. plan의 출시 전 확인 항목(결정 6)이며 "모두 24시간 운영합니다." 문장은 한 곳이라도 다르면 바꿔야 한다(ui-ux-design "상담전화 문구").
3. 대비는 글자색 대 겹친 배경색(투명 조상 합성) 계산이다. 배경 이미지, 요소 `opacity`, hover·focus 상태는 계산하지 않는다. 포커스 링 대비와 hover 상태는 이번에 측정하지 않았다.
4. 터치 영역은 링크·버튼의 박스 크기(높이·너비 44px 이상)만 본다. 인접 대상 간 간격은 보지 않는다.
5. 탭 순서는 Chrome 기준이다(desktop Chrome, Pixel 7 에뮬레이션). 실제 모바일 스크린 리더(VoiceOver, TalkBack)의 읽기 순서는 확인하지 못했다.
6. 새 테스트는 번호, 이름, 설명 구절을 앱 상수에서 가져오지 않고 기준 문서 값을 직접 적었다. 문구를 바꾸면 테스트 상수 `PHONES`, `RESULT_LINE`, `PANEL_BODY`도 같이 고친다.
