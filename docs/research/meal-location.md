# "뭐 먹지" 내 위치 주변 지도 검색 리서치

작성일: 2026-11-24
대상: `/meal` 뽑기 결과의 지도 링크에 사용자 위치(좌표)를 실어 주변 검색으로 여는 옵션
범위: 지도 3사 URL 좌표·반경 지원, 위치정보 법령과 개인정보 관점, Geolocation API와 브라우저 제약, 좌표 정밀도, 유사 서비스 UX. 코드는 건드리지 않았다.
근거 문서: `docs/research/menu-meals.md`(지도 링크 기본 조사, 중복 조사하지 않음), `docs/menu-meals/design.md`(위치 요청 없음), `COMPLIANCE.md` Meal 항목, `src/app/privacy/page.tsx` 205행.

이 문서는 법률 자문이 아니다. 공개 자료를 찾아 정리했다. 법률 판단이 필요한 항목은 "법률 확인 필요"로 표시했다.

표기 규칙
- [공식]: 지도 서비스 공식 문서나 법령 원문(또는 원문을 담은 페이지)에서 확인한 내용
- [2차]: 개발자 질의응답, 블로그, 검색 요약 등 공식이 아닌 자료. 변경 위험이 있다
- [추정]: 자료를 바탕으로 한 판단이며 사실로 확정되지 않은 내용
- 확인 필요: 찾지 못했거나 출처끼리 다르거나 현재 상태를 확인하지 못한 내용

## 1. 한 줄 요약

사용자가 허락하면 브라우저 위치를 한 번 받아 지도 링크에 실어 여는 기능이다. 조사 결과, 세 지도 서비스 모두 "좌표 중심의 반경 검색"을 공식 웹 URL로 지원하지 않는다. 공식으로 확인된 것은 지도 중심 좌표 지정(카카오 앱 스킴 search, 네이버 앱 스킴 map)과 좌표 핀 표시 정도다. 따라서 "주변 검색"을 공식 근거로 구현하려면 기능 범위를 줄여야 한다. 법적으로는 서버로 보내지 않고 저장하지 않으면 위치기반서비스 신고 대상이 아닐 가능성이 있으나 확정할 수 없다.

## 2. 현재 상태와 전제

- 지도 링크 3개(카카오맵, 네이버 지도, 구글 지도)는 메뉴 이름만 검색어로 쓴다. 위치 정보는 없다 (`src/features/meal/utils/meal-map-link.util.ts`, `docs/menu-meals/design.md` 1049행).
- 사이트 전체 `Permissions-Policy: geolocation=()`이 `next.config.ts` 131행에 있다.
- `COMPLIANCE.md` Meal 항목(150~151행)은 "위치 권한을 요청하지 않는다"고 적고 있다. 이 기능을 넣으면 이 문장을 바꿔야 한다.
- `src/app/privacy/page.tsx` 205행에 "뭐 먹지는 위치 정보를 요청하지 않으며"라는 문장이 있다. 기능을 넣으면 개인정보 처리방침을 함께 고쳐야 한다.
- 과거 점심 기획 보관본(`docs/lunch/archive/design-b-restaurants.md`)은 `/lunch/today`에서만 위치를 열고 좌표를 소수 셋째 자리로 반올림하는 안을 적었다. 현행 점심 설계는 위치를 쓰지 않는 쪽으로 확정됐다(`docs/lunch/design.md` 20행). 이 보관본의 반올림 방식은 4장 참고 자료로만 쓴다.
- 기존 `docs/research/menu-meals.md` 5장은 지도 링크 기본 형식(카카오 `/link/search/검색어`, 구글 `api=1&query=`, 네이버 웹 검색 경로 확인 필요)을 이미 정리했다. 이 문서는 좌표 관련 항목만 보탠다.

## 3. 지도 서비스별 좌표·반경 지원 (항목 1)

### 3-1. 요약 표

| 지도 | 웹 검색 URL에 좌표 중심 지정 | 반경(거리) 지정 | 앱 스킴에서 좌표 중심 검색 | 근거 등급 |
|---|---|---|---|---|
| 카카오맵 | 없음 (`/link/search/검색어`는 검색어만 받음) | 없음 | `kakaomap://search?q=검색어&p=위도,경도` (앱 6.0.0 이상). 모바일웹 `http://m.map.kakao.com/scheme/search?q=...&p=...`도 같은 형태 | 앱·모바일웹 스킴은 [공식]. 웹 검색 URL 좌표는 없음 [공식] |
| 네이버 지도 | 공식 웹 검색 URL 문서 없음 | 없음 | `nmap://map?lat=..&lng=..&zoom=..&appname=..` (지도 중심). `nmap://search`는 query와 appname만 명시됨 | 앱 스킴 [공식], 웹 좌표 파라미터는 [2차] 또는 확인 필요 |
| 구글 지도 | 없음 (`query`에 좌표를 넣으면 핀만 찍힘) | 없음 (`near` 같은 파라미터 없음) | 해당 없음 (웹 URL 중심) | [공식] |

### 3-2. 카카오맵 상세

- 공식 웹 가이드의 지도 URL 패턴은 `/link/map/위도,경도`, `/link/to/이름,위도,경도`, `/link/search/검색어` 등이다. 좌표 순서는 위도, 경도다. `/link/search`에는 좌표나 반경 파라미터가 없다. 출처: https://apis.map.kakao.com/web/guide/ [공식]
- 카카오 데브톡 답변(2020년 2월)에서 카카오 측은 "위경도 직접 사용은 지원하지 않는다"고 답했다. `/link/to/이름,위도,경도`는 검색이 아니라 좌표에 마커만 찍는다고 했다. `center=me`를 쓰는 `m.map.kakao.com/scheme/search?q=검색어&center=me` 형식은 "공식적으로 지원하는 방법은 아니다"라고 밝혔다. 같은 글에서 질문자는 이 방식이 동작하지 않았다고 적었다. 출처: https://devtalk.kakao.com/t/topic/96891 [2차, 2020년 자료, 현재 동작 확인 필요]
- 앱 URL 스킴 문서는 `kakaomap://search?q=맛집&p=37.3952,127.11044`를 "지정 좌표 중심으로 검색"으로 설명한다. 모바일웹 대응형(`m.map.kakao.com/scheme/...`)도 있다. 반경 파라미터는 문서에 없다. 출처: https://apis.map.kakao.com/android_v2/docs/api-guide/urlscheme/ [공식]
- 같은 문서에 따르면 `kakaomap://` 스킴을 인식하지 못하면 앱스토어 설치 페이지로 연결된다. 앱이 없는 PC에서의 `kakaomap://` 동작은 문서에 없다. 확인 필요.
- iOS에서 `/link/map/이름,좌표`를 열면 지정 위치 대신 현재 위치가 표시된다는 보고가 있다. 카카오는 `kakaomap://look?p=위도,경도`를 대안으로 안내했다. 출처: 공식 가이드 요약(검색 결과 인용), 확인 필요.
- 카카오 웹 URL 중 좌표를 쓰는 것은 "위치 표시"와 "길찾기 목적지"뿐이다. 검색 결과 목록을 좌표 주변으로 띄우는 웹 URL은 공식 문서에 없다.

### 3-3. 네이버 지도 상세

- 공식 앱 URL 스킴(NCP 문서)은 `nmap://map?lat=..&lng=..&zoom=..&appname=..`로 지도 화면을 특정 좌표에 맞춘다. `lat`, `lng`, `zoom` 모두 선택 값이다. `appname`은 모든 URL에 필요하다. 좌표 범위는 위도 31.43~44.35, 경도 122.37~132.00이다. 출처: https://guide.ncloud-docs.com/docs/maps-url-scheme [공식]
- 같은 문서의 `nmap://search`는 `query`(필수)만 명시되어 있고 좌표 파라미터는 문서에 없다. 웹(map.naver.com) URL에 대한 내용은 이 문서에 없다.
- 네이버 클라우드 포럼의 담당자 답변(검색 결과 요약)에는 `https://map.naver.com?lng=경도&lat=위도&title=이름` 형태가 나온다. 공식 웹 URL 스킴 문서는 없다고 답했다. 이 답변은 원문을 직접 열지 못했다. 출처: https://www.ncloud-forums.com/topic/242/ [2차, 원문 확인 실패]
- 구버전 `map.naver.com/v5/search?c=x,y,...` 형식은 EPSG:3857 좌표를 쓰며, 현재 `/p/` 경로에서 동작하는지 확인되지 않았다. 확인 필요.
- 네이버 지도 API는 NCP에서 신청해야 한다. 이 기능은 API를 쓰지 않는 링크이므로 해당 없다. 단, 약관 적용 범위는 `docs/research/menu-meals.md` 5-2 항목과 같이 확인 필요.

### 3-4. 구글 지도 상세

- 공식 Maps URLs 문서: `https://www.google.com/maps/search/?api=1&query=...`. `api=1`은 필수다. `query`에 `위도,경도`를 넣으면 그 지점에 핀이 찍힌다. 장소 상세로 안정적으로 연결되지 않으므로 `query_place_id`를 같이 쓰라고 권장한다. 출처: https://developers.google.com/maps/documentation/urls/get-started [공식]
- 검색 파라미터는 `query`(필수)와 `query_place_id`(선택) 둘뿐이다. 반경이나 `near` 파라미터는 없다. 위치를 지정하려면 검색어에 지역명을 넣으라고 안내한다. 지역을 빼면 현재 위치 근처에서 찾는다. 출처: 같은 문서 [공식]
- 비공식 패턴: `https://www.google.com/maps/search/음식명/@위도,경도,17z` 형식이 지도 중심을 맞춘다고 여러 2차 자료가 소개한다. 공식 문서에는 없다. 변경 위험이 크다. 출처: https://developers.google.com/maps/architecture/maps-url (공식 개요 페이지, 비공식 형식 자체는 확인되지 않음) [2차]
- 구글 지도 웹 URL 중 `dir/?api=1&destination=위도,경도`(길찾기)와 `maps/@?api=1&map_action=map&center=위도,경도&zoom=15`(지도 화면)는 공식 문서에 있다. 특히 `map_action=map`은 핀 없이 지도 중심만 맞추는 공식 형식이다.

### 3-5. 모바일 앱으로 넘어갈 때

| 지도 | 모바일 동작 (확인된 것) | 확인 필요 |
|---|---|---|
| 카카오맵 | `kakaomap://`는 앱이 있으면 앱으로, 스킴을 모르면 앱스토어로 연결된다 [공식 문서 요약] | 웹 링크(`map.kakao.com`)를 탭했을 때 앱이 열리는지, 앱 미설치 시 웹 지도가 열리는지 |
| 네이버 지도 | 앱 스킴은 앱이 설치되어 있어야 동작한다. 미설치 시 설치 안내 코드를 직접 만들어야 한다 [공식] | 웹 `map.naver.com` 링크가 앱으로 넘어가는지 |
| 구글 지도 | 웹 URL로 열면 구글 지도 앱이 연결될 수 있다 | 앱 연결 여부는 기기와 버전에 따라 다른지 확인 필요. Android `geo:` 좌표 인텐트는 카카오 문서에 언급됨 [공식] |

- 새 탭 링크는 `target="_blank"`로 열린다. 모바일 브라우저 일부는 새 탭 대신 앱으로 넘어간다. 실제 기기 테스트 필요.

## 4. 좌표 정밀도 (항목 4)

### 4-1. 소수 자리 수와 거리

| 소수 자리 | 단위 각도 | 위도 방향 거리 | 경도 방향 거리 (적도) | 경도 방향 거리 (서울 약 37.5도 N, 추정) | 흔한 해석 |
|---|---|---|---|---|---|
| 0 | 1 | 약 111 km | 약 111 km | 약 88 km | 나라·광역 |
| 1 | 0.1 | 약 11.1 km | 약 11.1 km | 약 8.8 km | 시·군 |
| 2 | 0.01 | 약 1.11 km | 약 1.11 km | 약 0.88 km | 동네·마을 |
| 3 | 0.001 | 약 111 m | 약 111 m | 약 88 m | 거리·골목 |
| 4 | 0.0001 | 약 11 m | 약 11 m | 약 9 m | 건물 |
| 5 | 0.00001 | 약 1.1 m | 약 1.1 m | 약 0.9 m | 개인 식별 가능 수준에 가깝다 |

- 자리 수별 거리 표는 공개 자료와 일치한다. 출처: https://en.wikipedia.org/wiki/Decimal_degrees, https://support.garmin.com/en-US/?faq=hRMBoCTy5a7HqVkxukhHd8 [공식 자료 아님, 일반 참고]
- 서울 위도 값의 경도 거리(약 88 m 등)는 적도 값에 cos(위도)를 곱한 계산값이다 [추정].
- 이전 점심 보관 설계는 소수 셋째 자리(위도 약 111 m, 경도 약 89 m)를 썼다. 이 값은 같은 계산과 맞는다.
- 법령이 정한 좌표 정밀도 기준은 찾지 못했다. 확인 필요. 실무 관행으로는 "동네 단위" 검색에 소수 둘째 자리(약 1 km), "길 단위"에 셋째 자리(약 100 m)가 자주 언급된다 [2차].
- 지도 검색은 지도 서비스가 주변 결과를 정하므로 정밀도를 낮출수록 결과 차이는 커지지 않는다. 다만 지도 핀(구글 `query=좌표`, 카카오 `/link/to`)은 좌표 그대로 찍힌다. 반올림한 좌표를 쓰면 핀이 실제 위치와 수백 m 떨어질 수 있다. 사용자 기대에 맞는지 기획 판단이 필요하다.

### 4-2. 일반 관행 (출처 기반 요약)

- 위치를 받은 뒤 바로 반올림해 원본 좌표를 상태에 남기지 않는 방식은 이전 점심 보관 설계에서 제안됐다. 개인정보 최소 수집 원칙과 맞는다 [추정, 설계 참고용].
- 위치정보 보호 원칙은 "목적 달성에 필요한 최소한"을 따른다. 법률 확인 필요.

## 5. Geolocation API와 브라우저 제약 (항목 3)

### 5-1. 기본 요건 [공식 MDN]

- HTTPS(보안 컨텍스트)에서만 동작한다. HTTP에서는 권한 요청이 실패한다.
- 사용자의 명시적 허용이 필요하며, 호출 시점에 권한 창이 뜬다.
- `Permissions-Policy`의 `geolocation` 허용 목록에 포함되지 않으면 차단된다. 차단되면 오류 콜백이 `PERMISSION_DENIED`로 호출된다.
- 옵션 기본값: `enableHighAccuracy: false`, `timeout: Infinity`(무한 대기), `maximumAge: 0`. `timeout`을 명시하지 않으면 응답을 영원히 기다릴 수 있다.
- 출처: https://developer.mozilla.org/en-US/docs/Web/API/Geolocation/getCurrentPosition [공식]

### 5-2. 오류 코드 (명세 기준)

| 코드 | 이름 | 의미 | 출처 |
|---|---|---|---|
| 1 | PERMISSION_DENIED | 사용자가 거부했거나 정책으로 차단됨 | Geolocation 명세. MDN 본문에는 코드 정의가 없어 `GeolocationPositionError` 문서로 확인 필요 |
| 2 | POSITION_UNAVAILABLE | 위치 정보를 얻을 수 없음 | 같음 |
| 3 | TIMEOUT | `timeout` 안에 위치를 얻지 못함 | 같음 |

- 정확도(`coords.accuracy`)는 미터 단위로 온다. 값이 크면 실내나 와이파이 기반일 수 있다. 정확도 기준값은 자료에서 찾지 못했다. 확인 필요.

### 5-3. 권한 UX 원칙 [공식 가이드]

- web.dev는 사용자 제스처(버튼 클릭) 뒤에 위치를 요청하라고 권한다. 화면 진입 즉시 요청하면 거부율이 높다. 출처: https://web.dev/articles/user-location, https://web.dev/articles/permissions-best-practices [공식 가이드]
- 같은 자료는 사전 안내(pre-prompt)를 먼저 보여 주고, 사용자가 긍정하면 브라우저 권한 창을 띄우라고 한다. 거부 시 대안(주소 입력 등)을 제공하라고 한다 [공식 가이드].
- 웹은 한 번 거부한 권한을 페이지에서 다시 물을 수 없다는 설명이 여러 2차 자료에 있다. 공식 문서 근거는 찾지 못했다. 확인 필요. 거부 뒤에는 브라우저 설정으로 안내하는 것이 현실적이다 [추정].

### 5-5. `Permissions-Policy` 헤더로 특정 경로만 허용하기

- 문법: `Permissions-Policy: geolocation=(self)`는 같은 출처만 허용한다. `geolocation=()`는 모두 막는다. `*`는 모든 출처 허용이다. 출처: https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Permissions-Policy [공식]
- 헤더 허용 목록은 iframe 권한의 상한이다. 이 사이트는 iframe을 쓰지 않으므로 `self`로 충분하다 [추정].
- 경로별 헤더를 나누는 방법: `next.config.ts`의 `headers()`는 경로 패턴(`source`)별로 헤더를 준다. 같은 키가 여러 항목에 걸릴 때 어느 값이 최종으로 가는지는 이 조사에서 Next.js 공식 근거를 찾지 못했다. 이전 점심 보관 설계는 "뒤 항목이 이긴다"고 적었으나 확인 필요. 설계 담당이 실제 응답 헤더를 검사해야 한다.
- 다른 페이지는 `geolocation=()`을 유지해야 한다. 헤더 범위를 `/meal`로 좁히는 방식은 원칙상 가능하다. 실제 적용은 설계와 QA에서 확인 필요.
- 한 번 열린 권한은 CSP에 영향이 없다. CSP는 바꾸지 않아도 된다 [추정, 지도 링크는 새 탭 이동이라 CSP 대상이 아님. `docs/menu-meals/design.md` 1049행과 같음].

## 6. 위치정보와 개인정보 관점 (항목 2)

이 장은 법률 자문이 아니다. 공개 자료에서 확인한 조문과 해석, 그리고 확인되지 않은 부분을 나눴다.

### 6-1. 법령 원문과 개정 상태

- 법령명: 위치정보의 보호 및 이용 등에 관한 법률 (이하 위치정보법).
- 제2조 정의 (원문 확인): 개인위치정보는 특정 개인의 위치정보이며, 위치정보만으로 특정 개인의 위치를 알 수 없어도 다른 정보와 쉽게 결합해 알 수 있는 경우를 포함한다. 위치기반서비스사업은 위치정보를 이용한 서비스를 제공하는 것을 사업으로 영위하는 것이다. 출처: https://elaw.klri.re.kr/kor_service/lawViewMultiContent.do?hseq=43349 [공식 원문 페이지, 개정 이력은 2016년 기준으로 보임]
- 제9조 제1항 (신고, 원문 확인): "개인위치정보를 대상으로 하지 아니하는 위치기반서비스사업은 제외한다"는 단서가 있다. 같은 페이지는 이 단서가 없는 옛 문언을 담고 있을 수 있다.
- 2025년 10월 1일 시행 개정으로 개인위치정보를 대상으로 하지 않는 위치기반서비스사업은 신고 대상에서 빠졌다는 2차 설명이 있다. 출처: https://datalaw.kr/posts/lbs-filing-gap-in-dd/ [2차, 2026년 글]. 법령 연혁 원문으로 시행일을 다시 확인해야 한다. 확인 필요.
- 제9조의2: 소상공인과 1인 창조기업은 신고 없이 시작할 수 있다는 설명이 있다. 2차 자료 기준 [2차].
- 제15조 제1항 (원문 확인): 누구든지 개인이나 물건 소유자의 동의 없이 위치정보를 수집·이용·제공할 수 없다. 출처: 위 elaw 페이지 [공식 원문 페이지]
- 제21조의2 (2차 자료 요약): 개인위치정보사업자등은 개인정보 처리방침에 위치정보법에서 정한 위치 관련 사항을 넣어야 한다. 제17조의2는 위치 처리를 고지할 때 쉬운 양식과 명확한 언어를 쓰라고 한다. 출처: 검색 결과 요약 기반. 원문 확인 필요.
- 법무 자문 블로그(2026년)는 위치기반서비스 신고 누락, 무신고 영업 처벌 조항을 설명한다. 출처: https://datalaw.kr/posts/lbs-filing-gap-in-dd/ [2차]

### 6-3. 개인정보 관점

- 좌표 값 자체는 누구의 위치인지 알 수 없다. 단말 번호나 이름과 결합하면 개인위치정보가 된다 [2차 요약, 법 정의 원문과 일치].
- 이 기능은 서버에 좌표를 보내지 않고 저장도 하지 않으므로 개인정보 "수집"이 없다는 설명이 가능하다. 다만 위 6-2의 외부 지도 링크 부분은 별도로 적어야 한다 [추정].
- 개인정보 처리방침(`src/app/privacy/page.tsx` 205행)은 "위치 정보를 요청하지 않는다"고 적고 있다. 기능을 넣으면 이 문장을 고쳐야 한다. 처리방침은 위치 기능이 외부 지도 서비스로 좌표를 전달하는 경우를 적도록 설계해야 한다 [추정].
- 광고: 좌표가 광고 스크립트(AdFit 등)에 넘어가면 안 된다. 같은 페이지에 있는 광고 코드가 위치를 읽지 않도록 설계에서 확인해야 한다 [추정]. AdFit 정책 원문은 `docs/research/menu-meals.md` 4장과 같이 확인 필요.

### 6-4. 고지 문구에 들어갈 요소 (기획 판단, 법 조항 근거는 6-1 참고)

고지 문구 초안은 기획 단계에서 새 문장으로 쓴다. 필요한 요소는 아래와 같다.

1. 요청 이유: 메뉴 이름과 함께 내 주변 위치를 지도 검색 기준점으로 쓴다는 점
2. 동의 여부 선택: 허용하지 않아도 기존 지도 검색 링크는 그대로 쓸 수 있다는 점
3. 처리 방식: 좌표는 이 화면의 메모리에만 있고 서버로 보내지 않으며 저장하지 않는다는 점
4. 외부 전달: 링크를 누르면 좌표가 해당 지도 서비스(카카오, 네이버, 구글)의 URL로 전달된다는 점. 이 서비스가 아니라 그 지도 서비스의 약관과 개인정보 처리방침이 적용된다는 점
5. 철회 방법: 브라우저 설정에서 위치 권한을 끌 수 있다는 점, 화면에서 다시 물어보지 않게 하는 방법(세션 단위 등)
6. 이용 기록: 분석 도구에 좌표나 위치 관련 이벤트를 보내지 않는다는 점 (`docs/menu-meals/design.md` 기준과 같이)

## 8. 기능 구현 시 확인이 필요한 사항 (설계 전달용)

- 지도별로 좌표 지원 범위가 달라서 같은 버튼이 세 지도에서 다르게 동작할 수 있다 (2장 3-1표).
- 카카오 앱 스킴 `search`는 좌표 중심 검색이 공식 근거가 있는 유일한 방식이다. 웹(PC)과 앱에서 각각 동작을 확인해야 한다.
- 네이버는 좌표 중심 지도 화면까지만 공식 근거가 있다. 검색 결과 목록을 좌표 주변으로 여는 공식 방식은 없다.
- 구글은 좌표를 넣으면 핀만 찍힌다. 주변 검색은 공식 근거가 없다.
- 비공식 URL 패턴을 쓰면 지도 서비스 변경 시 깨질 수 있다. 쓸 때는 사용자 승인과 주기적 점검이 필요하다.
- 좌표는 URL의 쿼리에 실려 외부 지도 서비스로 간다. 우리 사이트 주소(URL), 브라우저 기록, 로그에는 좌표를 넣지 않는다. `rel="noopener noreferrer"`를 두면 우리 사이트 주소가 외부로 전달되지 않지만, 좌표는 지도 서비스 URL 안에 있으므로 지도 서비스가 받는다.

## 10. 열린 질문과 사용자 선택지

기획자가 사용자에게 물어야 할 항목이다.

1. 기능 범위 (가장 큰 결정)
   - A. 공식 근거 범위만 쓴다. 카카오는 앱 스킴 `search`(좌표 중심 검색), 네이버는 지도 중심 좌표(`map`), 구글은 지도 중심 `map_action=map` 같은 형식으로 "내 주변 지도 열기"만 한다. 검색어는 메뉴 이름으로 두고 좌표 중심 화면을 기대하게 한다.
   - B. 검색어에 지역명 텍스트를 넣는다(예: 사용자가 동네 이름을 입력). 좌표를 쓰지 않으므로 위치 동의가 필요 없다. 다만 "내 위치"라는 목표와 다르다.
   - C. 비공식 URL 패턴을 쓴다(예: 구글 `@좌표,줌z`, 카카오 `center=me`). 주변 검색 결과가 나올 수 있으나 변경 위험이 있다. 승인 필요.
   - D. 이번에는 보류하고 위치 기능을 빼둔다.
2. 지도별 지원 차이를 어떻게 보일지
   - 세 버튼을 지도별로 다르게 두고, 주변 검색 지원 여부를 버튼 옆에 표시할지
   - 공통 버튼 하나로 묶고 지도별 차이는 문구로 숨길지 (숨기면 기대와 달라질 수 있음)
3. 좌표 정밀도
   - 원본 좌표 사용 / 소수 셋째 자리(약 100 m) / 소수 둘째 자리(약 1 km) 중 선택
   - 법령 기준이 없으므로 정책 선택으로 정한다
4. 요청 흐름
   - 버튼 클릭 → 사전 안내 → 브라우저 권한 창 순서로 할지
   - 거부했을 때 기본 지도 링크만 열지, 설정 안내를 보일지
   - "방문할 때마다" 묻는다는 요구에 맞춰 세션 안에서도 매번 묻는지, 허용을 기억하는지 (기억은 저장 없이 메모리만 가능)
5. 법적 처리
   - 위치정보 신고 여부를 위치정보지원센터(02-588-0185 확인 필요)나 법률 자문으로 확인할지
   - 확인 전까지 "위험 수용"으로 진행할지 (COMPLIANCE 기존 방식과 같음)
   - 위치 기능 추가에 따라 `COMPLIANCE.md` Meal 항목, 개인정보 처리방침 205행, 이용약관을 함께 바꿀 승인
6. 권한 헤더 범위
   - `/meal` 경로만 `geolocation=(self)`로 열고 다른 페이지는 `()` 유지 (권장 방향, 설계 담당이 검증)
   - 사이트 전체를 여는 안은 채택하지 않는 것이 좋다
7. 인앱 브라우저 처리
   - 카카오톡, 네이버, 인스타그램 인앱에서 감지되면 외부 브라우저로 열도록 안내할지
   - 그대로 시도하고 실패하면 "위치를 가져오지 못했습니다" 안내만 할지
8. 실패 시 대체 흐름
   - 위치 실패 시 메뉴 이름만 검색하는 기본 링크로 바로 연결할지
9. 광고 분리
   - 위치 기능이 있는 화면에서 광고 스크립트에 위치 값이 전달되지 않도록 설계에 명시할지
10. 테스트 환경
   - 실제 iOS 기기(Safari, 카카오톡 인앱)와 Android에서 수동 확인을 QA 범위에 넣을지. Playwright 위치 모의는 인앱 브라우저를 재현하지 못한다.
