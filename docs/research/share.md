## 1. 한 줄 요약

공유 기능은 세 가지 조각으로 나뉜다. (a) 기기의 공유창을 여는 Web Share API, (b) 결과 화면을 PNG로 만드는 이미지화, (c) 공유된 링크를 받는 쪽에 보이는 미리보기(OG 태그와 OG 이미지). 모바일은 (a)와 (b)로 대부분 해결되고, PC는 링크 복사와 이미지 저장으로 대체한다. 카카오톡 인앱 브라우저의 Android 쪽은 공유창과 클립보드가 모두 막혀 있어서 별도 대체 경로가 필요하다.

## 2. 핵심 개념과 용어

| 용어 | 뜻 (처음 보는 사람 기준) |
|---|---|
| Web Share API | 웹페이지가 기기의 기본 공유창(OS 공유 시트)을 여는 브라우저 기능. `navigator.share`로 호출한다. 공유창에서 카카오톡, 메시지, 메일 등 앱을 사용자가 고른다. |
| `navigator.canShare` | 지금 기기에서 주어진 데이터(링크, 텍스트, 파일)를 공유할 수 있는지 미리 묻는 함수. 파일 공유 가능 여부를 확인할 때 쓴다. |
| 사용자 활성화(transient user activation) | 클릭 같은 사용자 동작 직후에만 특정 기능을 허용하는 브라우저 규칙. 자동 실행 중에는 공유창을 열 수 없다. |
| 보안 컨텍스트 | HTTPS(또는 localhost)에서만 동작하는 조건. |
| Clipboard API | 텍스트나 이미지를 클립보드에 쓰는 기능. 이미지는 `ClipboardItem`으로 감싸서 쓴다. |
| `ClipboardItem` | 클립보드에 넣을 데이터 묶음. 이미지는 보통 `image/png` 형식으로 넣는다. |
| 인앱 브라우저 | 카카오톡, 인스타그램, 네이버 앱 같은 앱 안에서 링크를 여는 내장 브라우저. 기능이 일반 브라우저보다 제한되는 경우가 많다. |
| 이미지 캡처 | 화면의 DOM을 픽셀 그림(PNG)으로 바꾸는 작업. 브라우저 안에서 하거나 서버에서 한다. |
| OG 태그 | 링크를 메신저에 붙였을 때 보이는 제목·설명·썸네일을 정하는 HTML 메타 태그(`og:title`, `og:description`, `og:image`). |
| 스크랩 서버 | 카카오톡 등 메신저가 링크를 열어 OG 태그를 미리 읽어 가는 서버. 한 번 읽은 값을 오래 캐시한다. |
| Satori | `next/og`가 쓰는 엔진. HTML·CSS 일부를 SVG로 바꾸고 PNG로 만든다. 브라우저 캡처가 아니라 서버에서 그림을 새로 그린다. |
| 톱니(tofu) | 글꼴에 없는 글자를 네모 박스로 표시하는 현상. 한글에서 폰트 누락 때 가장 흔하다. |

## 3. 규칙과 관례

### 3.1 Web Share API (표준·브라우저 규격)

공식 규칙(규격)과 브라우저 동작은 다음과 같다. 출처는 MDN `navigator.share`·`navigator.canShare` 문서다.

- 보안 컨텍스트(HTTPS)에서만 동작한다.
- 클릭 같은 사용자 동작의 이벤트 핸들러 안에서 호출해야 한다. 자동으로 실행하면 `NotAllowedError`로 거절된다.
- 전달할 값은 `url`, `text`, `title`, `files` 중 하나 이상이어야 한다. 모르는 속성은 무시된다.
- `files`(파일 배열)를 쓰려면 먼저 `navigator.canShare({ files })`로 확인해야 한다. 파일 공유를 지원하지 않는 기기에서 `files`를 넘기면 `TypeError`가 난다.
- `canShare`는 `url`/`text`만 있어도 확인할 수 있다. 공유할 수 없는 URL 형식이면 `false`를 돌려준다.
- `web-share` 권한 정책이 막혀 있으면 공유가 실패한다(iframe 등에서 확인 필요).
- 공유 결과(취소 포함)는 호출 쪽에서 `AbortError` 등 예외로 구분해야 한다. 사용자가 공유창을 닫으면 보통 예외가 난다(확인 필요: 기기별 예외 이름이 다를 수 있음).

### 3.2 iOS 공유창의 동작 (2차)

- 검색 요약에 따르면 iOS Safari는 공유할 때 문서 제목과 페이지 URL을 자동으로 앞에 붙인다. 따라서 `text`에 링크를 또 넣으면 중복될 수 있다. 원문 확인 못 함.

### 3.3 클립보드와 이미지 쓰기 (관례 아닌 브라우저 규칙)

- `navigator.clipboard.write`는 보안 컨텍스트와 사용자 동작 안에서만 쓸 수 있다. 출처: WebKit Async Clipboard 글.
- 이미지는 `image/png` 형식이 가장 안전하다. Clipboard API는 PNG를 필수 형식으로 둔다(MDN, web.dev 요약 기준).
- Promise로 Blob을 넘기면 사용자 동작 문맥이 유지되기 쉽다는 설명이 WebKit과 web.dev 예제에 있다(2차 요약 기준, 원문 세부 확인 못 함).
- `ClipboardItem.supports("image/png")`로 지원 여부를 먼저 확인하는 것이 권장된다(MDN).

## 4. 조사 항목별 결과

### 4.1 Web Share API 브라우저 지원

출처: caniuse Web Share API 표 (https://caniuse.com/web-share, 확인일 2026-11-24).

| 환경 | 기본 공유(`share`) 지원 | 파일 공유(`files`) | 비고 |
|---|---|---|---|
| iOS Safari | 12.2 이상 | 확인 필요(2차: Safari 14부터) | caniuse 표 기준 12.2~27.2 지원 |
| Android Chrome | 지원(caniuse 표는 최신 버전만 표시, 이전 버전 범위 확인 못 함) | 확인 필요(2차: Chrome 76 이상) | 2차 요약: Chrome 61부터 기본 공유 |
| 삼성 인터넷 | 8.2 이상 | 확인 못 함 | 2차 요약에서 파일 지원을 언급했으나 원문 확인 못 함 |
| Chrome 데스크톱 | 128 이상 지원, 89~127은 부분 지원 | 확인 필요(2차: Windows, macOS, ChromeOS) | caniuse 표 기준 |
| Edge 데스크톱 | 95 이상 | 확인 못 함 | caniuse 표 기준 |
| Firefox 데스크톱 | 미지원 | 미지원 | caniuse 표에서 전 버전 미지원으로 표시 |
| Firefox 안드로이드 | 160 이상 (caniuse 표 기준) | 확인 못 함 | 2차 요약은 79부터라고 해서 서로 다르다. caniuse 값을 쓴다. |
| Safari macOS | 12.1 이상 | 확인 필요 | caniuse 표 기준 |

요약
- 모바일(iOS·Android)은 대부분 기본 공유가 된다. 파일 공유 여부는 기기와 버전에 따라 달라서 `canShare`로 매번 확인해야 한다.
- Firefox 데스크톱은 공유창 자체가 없다. PC 대체 경로가 필수다.
- 2차 요약은 파일 공유 전체 커버리지를 약 87%, 기본 공유를 약 92%로 추정한다(원문 확인 못 함, 참고만).

해석
- 카카오톡 Android 인앱에서는 공유창과 클립보드가 둘 다 막혀 있다. 이 경로에서는 "외부 브라우저에서 열기" 안내나, 주소를 화면에 크게 보여 주고 길게 눌러 복사하도록 안내하는 대체 화면이 필요하다. 외부 브라우저를 강제로 여는 방법(intent 등)은 이번에 확인하지 못했다. 확인 못 함.
- 카카오 직원 답변은 2023년과 2025년 글이다. 지금 버전에서 달라졌을 수 있으므로 실기기 확인이 필요하다.
- 인스타그램과 네이버 앱의 최신 동작은 이번 조사에서 근거를 찾지 못했다. QA 단계에서 실기기로 확인해야 한다.

  - iOS Safari와 WKWebView에서 큰 이미지가 빈 상태로 나오는 문제. 안정화 옵션(`stabilizationAttempts`)을 넣는 PR #591이 있으나 병합 여부 확인 못 함.
  - 1.11.13에서 `toBlob`이 `type`과 `quality` 옵션을 무시한다는 보고(이슈 #590, 확인 필요: 원인은 옵션 미전달).
  - 웹폰트 크기 반올림 문제 수정 PR(#621), 복제 문서와 iframe 폰트 소유권 수정 PR(#623)이 있다. 둘 다 2026-11-24 시점 병합 여부 확인 못 함. 실기기(iPhone Safari) 확인 보고가 PR에 있다.
- html2canvas는 이번 조사에서 품질(CSS 재현도, 폰트)에 대한 근거 자료를 찾지 못했다. 확인 못 함.
- `next/og`의 한글 처리
  - 2차 요약: 기본 Satori 글꼴은 라틴 글자만 담고 있어 한글은 네모로 나온다. 원문 확인 못 함.
  - 공식 문서 예제는 `readFile`로 글꼴을 모듈 시작 시 한 번 읽는 방식을 쓴다. 요청 데이터에 따라 글꼴이 바뀌지 않으므로 정적 캐시가 된다.
  - 기본 이모지 옵션은 `twemoji`다(공식 문서). 이모지를 쓰면 외부 CDN에서 이미지를 받는다(확인 필요: 실제 네트워크 요청 여부).
- 공식 문서 기준 `ImageResponse`는 `display: grid` 같은 고급 레이아웃을 지원하지 않는다. flexbox 위주로 짠다.

비교 요약
- 기존 `useCapture`(html-to-image)가 가장 빠른 길이다. 다만 iOS 첫 호출 문제가 있으므로 실기기 QA가 필수다.
- `next/og`는 기기 상태와 무관하게 같은 이미지를 얻는 장점이 있다. 단 결과값이 서버에 전달돼야 하고(개인정보 장에서 다룸), 한글 글꼴 용량 한도(500KB)를 맞춰야 한다.
- html2canvas는 미확인 항목이 많아 추천 근거가 부족하다.

### 4.5 공유 링크 미리보기 (OG 이미지)

- 공유된 링크를 메신저가 열어 OG 태그를 읽는다. 카카오톡은 이 정보를 자체 스크랩 서버에 저장하고 캐시한다(2차 카카오 데브톡 요약).
- 이미지 경로가 같으면 기기나 CDN에 예전 이미지가 계속 보일 수 있다. 경로에 버전 값(예: `?v=2`)을 붙이면 새로 읽는다는 카카오 개발자 커뮤니티의 답변이 있다(답변자 경험, 공식 문서 아님).
- 카카오 공유 디버거(https://developers.kakao.com/tool/debugger/sharing)와 OG 캐시 초기화 페이지로 캐시를 지울 수 있다. 두 도구 모두 카카오 계정 로그인이 필요하다(검색 요약 기준, 원문 확인 못 함). 이미지 자체의 캐시는 따로 있어 초기화되지 않을 수 있다는 답변이 있다(확인 필요).
- 카카오 스크랩 서버는 `og:image`가 없으면 페이지 안의 첫 `img`를 대신 쓸 수 있다는 사례가 있다. 숨은 이미지가 노출될 수 있으므로 `og:image`를 명시해야 한다.
- 카카오 JS SDK를 쓰지 않으므로, 메신저 미리보기는 일반 OG 태그에만 의존한다. 결과 공유 페이지에 대해 OG를 어떻게 줄지가 기획 질문이다(열린 질문 참고).

#### 기존 `/api/og-image` 재사용 가능성

| 항목 | 현황 | 재사용 시 문제 |
|---|---|---|
| 호출 방식 | `title`, `subtitle`, `tag` 쿼리 문자열을 받아 PNG를 만든다. 길이 상한만 있다(80자, 120자, 24자). | 누구나 임의 문구로 이미지를 만들 수 있다. 우리 도메인에서 임의 문구 이미지가 생성되므로 금지어 검사가 우회된다. 허용 목록이나 서명 값이 필요하다(기획 결정). |
| 기본 문구 | 기본 부제 "로또 번호 생성 · 분석 · 채점의 모든 것", 하단 행 "… · 로또 번호 생성 · 분석 · 채점" 이 코드에 고정돼 있다. | 운세, 꿈, 타로, 점심 등 다른 기능의 이미지에 로또 문구가 나온다. 꿈 해몽 기능은 로또 용어를 금지한다. 재사용하려면 이 문구를 기능별 값으로 빼야 한다. |
| 한글 글꼴 | `fonts` 옵션이 없다. 폰트 이름만 CSS에 적혀 있다. | 한글이 네모로 깨질 가능성이 높다(확인 필요: 배포 환경에서 실제 PNG를 열어 확인). |
| 런타임·캐시 | Edge 런타임, `Cache-Control: public, max-age=86400`. | 쿼리 조합마다 캐시가 생긴다. 임의 값이 많아지면 캐시 항목이 늘어난다. |
| 로그 | 요청 URL이 서버 로그에 남을 수 있다(일반 서버 동작, 확인 필요). | 쿼리에 개인정보를 넣으면 로그에도 남는다. |

결론: 기능 소개용 고정 OG는 기존 경로를 기능별 문구로 나눠 쓰는 것이 자연스럽다. 결과마다 다른 이미지를 만들려면 쿼리 방식을 그대로 쓰지 말고 허용 목록이나 별도 설계가 필요하다.

### 4.6 개인정보·법적 주의

공유 과정에서 서버로 가는 것은 무엇인가 (확인 필요: 실제 구현에 따라 달라짐)

| 방식 | 서버로 전송되는 것 | 근거 |
|---|---|---|
| Web Share API로 링크·텍스트 공유 | 없음. 공유창에서 고른 앱이 받는다. 서비스 서버는 호출되지 않는다. | MDN 동작 설명에 따름 (클라이언트 전용 API) |
| html-to-image로 PNG 만들기 | 없음. 브라우저 안에서 만든다. 단 페이지 안 웹폰트 주소를 가져오는 요청은 있다. | 프로젝트 `use-capture.hook.ts` 구조 |
| `next/og`로 서버 이미지 만들기 | 이미지 생성 요청의 쿼리 값이 서버로 간다. 결과가 URL에 들어가면 메신저, 스크랩 서버, 로그에 남을 수 있다. | 공식 문서의 Edge 실행 구조, `/api/og-image` 코드 |
| 결과를 링크로 저장해 나중에 열기 | 결과 값이 저장소(DB 등)에 들어가면 개인정보 보관 대상이 된다. | 확인 필요: 기획 결정 |

개인정보 판단 기준(요약)
- 생년월일 하나는 같은 날 태어난 사람이 많아 그 자체로 개인을 특정하기 어렵다고 본다. 다만 이름과 결합하면 개인을 알아볼 수 있으므로 개인정보가 된다(개인정보보호위원회 해설서 2020.12를 인용한 TTA 용어사전 설명, 2차). 이름과 생년월일을 같이 쓰는 사주·궁합 같은 기능에서는 개인정보로 다룬다.
- 이미지나 링크에 이름, 생년월일, 혈액형, MBTI 같은 입력값을 넣지 않는 것이 가장 안전하다. 특히 링크 쿼리와 OG 이미지 문구에는 넣지 않는다.
- 공유된 이미지는 사용자가 직접 보내는 것이다. 서비스가 보낸 것으로 보이지 않도록, 이미지 하단에 "개인 입력 정보는 포함되지 않습니다" 같은 안내를 넣을지는 기획 결정(법률 확인 필요).

운세류 오락 고지
- 결과 이미지에 개인 해석 문구가 들어가면 같은 고지(오락·참고용)가 이미지에도 있어야 한다는 것이 이 프로젝트의 기존 원칙으로 보인다(`docs/research/tarot.md`, `COMPLIANCE.md`의 고지 형식). 이미지에서 고지를 빼면 원본 화면과 다른 인상을 줄 수 있다. 확인 필요: 고지 문구를 이미지에 넣을지 기획 결정.

### 4.8 카피 규칙과 이미지 문구

- 프로젝트는 기능마다 금지어 목록(`*-copy-rule.constant.ts`)과 검사 테스트를 둔다. 공유 이미지는 화면 문구나 OG 문구를 그대로 가져오므로 같은 검사를 받아야 한다.
- 이미지 안 글자는 DOM 텍스트 검사로 잡히지 않는다. OG 이미지는 `next/og`에서 따로 만들어지므로 테스트 파일이 이미지 문구를 보지 않는다. 기획 단계에서 이미지 문구도 검사 대상으로 명시해야 한다.
- 공유 시 "보장", "확정", "추천" 같은 표현이 이미지에 들어가지 않도록 기존 허용 문장 목록을 따른다.

| A. 링크만 | 기능 소개 링크를 공유창이나 복사로 보냄. OG 이미지는 기능별 고정 이미지. | 구현이 가장 단순. 개인정보 노출 없음. 캐시 문제가 적음. | 결과 화면을 보여 주지 못함. 바이럴 효과가 약함. | 보조안 |
| B. 링크 + 이미지 (클라이언트 캡처) | 결과 화면을 PNG로 만들어 Web Share(파일)로 공유, 실패하면 저장. 링크는 기능 소개 URL. PC는 링크 복사와 저장. | 기존 `useCapture` 재사용. 서버 전송 없음. 결과가 서버를 거치지 않음. | iOS 첫 호출 문제, 인앱 Android 제약. 결과 링크는 못 줌. | **권장** |
| C. 서버 렌더 이미지 (`next/og`) | 결과 값을 쿼리로 받아 서버에서 PNG를 만들고 OG와 공유에 씀. | 링크에 결과 이미지가 붙음. 기기 차이 적음. | 결과 값이 서버 로그와 메신저 스크랩 서버에 남음. 한글 글꼴 500KB 한도. 임의 문구 생성 악용 위험. 로또 문구 분리 필요. | 보류 |

권장안 세부(요약, 설계는 architect 몫)
1. 기본 공유는 안 B로 간다. 모바일은 파일 공유 가능 여부를 `canShare`로 확인하고, 안 되면 링크 공유로 낮춘다. PC는 링크 복사와 PNG 저장을 기본으로 둔다.
2. 기존 `useCapture`의 흐름(캡처 → 파일 공유 → 저장)을 기준으로 하되, 링크 공유와 PC 복사 경로를 추가한다. iOS 첫 호출 빈 이미지 문제는 실기기 QA 항목으로 넣는다.
3. 카카오톡 Android 인앱에서는 공유창과 클립보드가 모두 안 되므로 안내 화면(외부 브라우저에서 열기 등)을 둔다.
4. 링크의 OG 이미지는 기능별 고정 이미지로 한다. `/api/og-image`를 쓰려면 문구를 기능별로 분리하고 허용 목록을 두며, 한글 글꼴을 넣어 실제 PNG를 확인한다.
5. 결과 값은 URL이나 OG에 넣지 않는다. 개인 입력값(이름, 생년월일 등)은 이미지와 링크 어디에도 넣지 않는 것을 기본으로 한다.
6. 이미지 하단에 기능별 고지 문구를 넣는 것을 기본으로 검토한다(확인 필요).

## 8. 열린 질문 (기획자에게)

1. 공유 대상을 어디까지 둘까: 결과 이미지만, 링크만, 둘 다? 권장안은 "링크 + 이미지"다. 이 방향이 맞는지 확인이 필요하다.
2. 결과 링크(상대가 같은 결과를 열어 보는 링크)를 만들 것인가? 만들면 결과 값을 URL에 넣거나 서버에 저장해야 한다. 개인정보 처리 방침과 보관 기간을 정해야 한다. 기본값은 "만들지 않음"으로 제안한다.
3. 공유 이미지에 어떤 정보를 넣을까? 기능 이름, 결과 문장, 날짜, 사이트 주소 중 무엇을 넣을지. 입력값(이름, 생년월일 등)은 넣지 않는 것으로 제안한다.
4. 공유 이미지에 오락·참고용 고지를 넣을까? 운세, 타로, 꿈, 궁합처럼 해석 문구가 있는 기능은 고지가 이미지에도 보이는 것이 안전하다. 법률 확인 필요.
5. 공유 버튼 문구와 아이콘에 "카카오톡" 이름을 쓸 것인가? 쓰면 상표 사용 확인이 필요하다. 공유창에서 앱을 고르는 방식이면 "공유하기"로 충분하다는 제안을 검토.
6. 카카오톡 Android 인앱에서 공유가 안 될 때 어떤 안내를 할 것인가? "외부 브라우저에서 열기" 안내 문구와 링크 직접 복사 안내 중 무엇을 쓸지. 외부 브라우저 강제 실행 방법은 확인 못 함.
7. 인스타그램과 네이버 앱의 실제 동작을 QA 단계에서 실기기로 확인할지, 대상 기기 목록을 어떻게 정할지.
8. `/api/og-image`를 계속 쓸 것인가, 기능별 고정 OG 이미지 파일로 바꿀 것인가? 재사용하려면 로또 문구를 분리하고 한글 글꼴을 넣고 임의 문구 생성을 막아야 한다. 고정 이미지 방식이 더 단순하다는 의견을 제안한다.
9. 한글 글꼴을 넣는다면 어떤 글꼴을 쓸지. Noto Sans KR(OFL), Pretendard(OFL) 모두 상업 이용 가능하나 글꼴 파일이 500KB 한도를 넘을 가능성이 크다. 글자 일부만 추린 파일을 쓸지, 이미지용 글꼴을 따로 둘지 결정 필요. 서브셋은 법률 확인 필요.
10. 이모지를 이미지에 넣을 것인가? 넣으면 Twemoji(CC BY 4.0) 표기가 필요하다. 넣지 않으면 표기 부담이 없다.
11. PC에서 이미지 클립보드 복사 버튼을 보여 줄 것인가? Firefox 지원 버전이 출처마다 달라 확인이 필요하다. 링크 복사와 저장만 두는 것도 가능하다.
12. 공유 이벤트를 분석 도구로 기록할지(예: 공유 버튼 클릭 수). 기록하면 개인정보 처리 방침 갱신이 필요하다. 확인 필요.
13. 광고(AdSense 등)가 공유 화면에 붙는지, 공유 이미지에 광고 요소가 들어가는지. 광고 플랫폼 정책은 이번 조사에서 확인하지 못했다. 확인 못 함.
