## 디자인 방향

한 줄 요약: "색인 카드를 넘겨 보는 연구실의 찾아보기 장부". 종이 위에 염수(`menu-dream`) 잉크 한 색으로 표시한 차분한 사전이며, 밤하늘·별·구름으로 꿈을 꾸미지 않는다.

- 이유: 사이트 컨셉(피클 병 속 연구실, 점술집 분위기 금지)을 지키고, 소재 사전이라는 기능의 성격(찾고, 읽고, 다른 소재로 옮겨 가기)을 그대로 화면 구조로 옮긴다.
- 개성은 **허브의 색인 장부 레이아웃 한 곳**에만 준다. 카테고리 이름이 왼쪽 여백에 놓이고 소재 이름이 오른쪽에 라벨처럼 이어지는 구조다. 홈 `src/app/page.tsx`와 `MenuListComponent`가 이미 쓰는 "구분선이 있는 행"(`divide-y border-y`) 관용구를 그대로 가져와 사이트와 어긋나지 않는다.
- 소재 상세는 새로운 형태를 만들지 않는다. 한 단 읽기 흐름에 한 줄 요약의 염수색 세로 선 하나만 개성으로 둔다.
- 모션은 넣지 않는다(5장).

디자인 계획 점검 (기본값으로 흐르던 부분을 바꾼 기록)

| 처음 떠올린 안 | 왜 버렸나 | 바꾼 결정 |
|---|---|---|
| 120개 소재를 같은 모양의 카드 격자로 배치 | 카드마다 같은 반경·테두리가 반복되는 SaaS 카드 틀이다. 소재 이름은 짧아 카드 면적이 낭비된다 | 이름만 있는 라벨 칩이 줄바꿈으로 이어지는 색인 행. 카드는 쓰지 않는다 |
| 보라 밤하늘, 별, 구름, 달 장식 | 꿈 사이트의 흔한 기본값이고 타로(비트색, 달 아이콘)와도 겹친다 | 장식 없음. 색은 이름 그대로 소금물 같은 청록 한 색 |
| 첫 화면 큰 히어로 문구나 대표 일러스트 | plan 1차 범위에 이미지가 없고, 검색칸이 첫 행동이다 | 제목, 면책, 검색칸 순서의 짧은 머리 영역 |
| 모든 고지를 테두리 상자로 | 상자가 줄지어 서서 읽을 글보다 상자가 눈에 띈다 | 상자는 "반드시 보여야 하는 고지"(상시 면책, 하단 면책, 상담 안내)에만 쓰고 풀이 기준·상세 안내·FAQ는 상자 없이 글로 둔다 |

### 메뉴 라벨 색 `menu-dream` (열린 질문 Q1)

| | A안: `menu-where` 이름만 바꿔 재사용 (권장) | B안: 새 색 "도라지" |
|---|---|---|
| 값 | `#2a6672` (염수) | `#3f4a8c` (새 값, 이름은 "도라지") |
| 대비(종이 `#eef0e6`) | 약 5.6:1 (카드 위 6.1:1, 옅은 면 위 4.9:1) | 약 7.1:1 (계산값. 도입 전 재검산) |
| 승인 필요 | 이름 변경과 표 갱신. 색 값은 이미 AA 확인됨 | 새 토큰이라 값 승인 필요 |
| 장점 | 현재 사용처 없는 토큰이라 팔레트가 유지된다. 5색(딜 초록, 비트 보라, 강황 노랑, 당근 주황, 염수 청록)이 색상환에 고르게 퍼진다. 물과 소금기가 꿈의 "물"을 떠올리게 하되 별·달 클리셰가 아니다 | 꿈의 밤 이미지와 직접 이어진다. 청록보다 초록(딜)과 멀다 |
| 단점 | 딜 초록(`#2d6a3e`)과 같은 짙은 중간 명도의 차가운 계열이라 멀리서 보면 가까워 보인다. 다만 링크·버튼은 `primary`, 제목·아이콘은 `menu-dream`으로 쓰는 곳이 달라 혼동은 작다 | 새 색이 `info`(`#3b73b8`)와 `ball-bonus`(`#6b4bb8`) 사이에 놓여 파랑·보라 계열이 세 개가 된다. 타로(비트)와도 인접해 구분이 줄어든다 |

- 추천: A안. 이유: 승인 비용이 가장 낮고 팔레트 균형이 좋다. B안은 새 토큰 추가로 팔레트가 한쪽으로 쏠린다.
- 이름은 "염수"를 그대로 둔다(`globals.css` 주석 `/* 염수 */`).
- 적용 변경(승인 후)
  - `src/app/globals.css`: `--menu-where` → `--menu-dream`, `--color-menu-where` → `--color-menu-dream` (값 `#2a6672` 그대로). 현재 `--menu-where`는 이 파일 안에서만 쓰인다(design.md 9장 확인).
  - `docs/conventions/design-system.md` 메뉴 라벨 색 표 갱신안(제안만, 승인 후 PM이 수정): "어디 가 | `menu-where` | `#2a6672` | 염수" 행을 "꿈 해몽 | `menu-dream` | `#2a6672` | 염수"로 바꾼다.
  - B안이면: `--menu-where`는 지우고 `--menu-dream: #3f4a8c; /* 도라지 */`를 새로 두며, 같은 표에 "꿈 해몽 | `menu-dream` | `#3f4a8c` | 도라지" 행을 추가한다. 이 경우 종이 배경 대비 4.5:1 이상 규칙은 충족한다.

새 토큰: A안 선택 시 없음(이름 변경만). B안 선택 시 `--menu-dream`.

## 간격·그리드

- 기본 단위는 Tailwind 4px 눈금. 새 간격 토큰 없음.
- 본문 폭(레이아웃 `max-w-7xl` 안에서 좁힌다)
  - 허브: `mx-auto max-w-4xl px-4 pb-16`. 이유: 색인의 왼쪽 여백(10rem) + 소재 칩 영역이 한 행으로 읽히는 폭이다.
  - 상세: `mx-auto max-w-3xl px-4 pb-16`. 이유: 글 읽기가 주인공이라 한글 약 40자 줄 길이에 맞춘다.
- 섹션 사이 `space-y-10`, 섹션 안 `space-y-4`. 허브 머리 영역(이동 경로, 면책, 검색)은 `space-y-6`.
- 반경 계층: 칩 `rounded-md`, 버튼·입력 `rounded-lg`, 면책·상담 상자 `rounded-lg`, 생각해 볼 점·완화·위기 패널 `rounded-panel`. 링크 포커스 모서리 `rounded-sm`.
- 그림자 없음. 면의 구분은 `card`와 종이의 밝기 차이와 테두리로만 한다.
- 터치 영역: 칩, 버튼, 전화 링크 모두 높이 44px 이상(`min-h-11`). 칩 사이 간격 `gap-2`(8px), 전화 링크 사이 `gap-1`(4px) 이상.

## 화면별 레이아웃

### 공통 머리 영역 (허브, 상세)

순서는 design.md 6.2 트리 그대로이며 모두 서버 HTML이다.

1. `DreamBreadcrumbComponent`: `nav aria-label="이동 경로"` > `ol`. 항목 사이는 lucide `ChevronRight` 14px(`aria-hidden`). 컨테이너 안 왼쪽 정렬, 위 여백 `pt-4`. 허브는 "홈 > 꿈 해몽", 상세는 "홈 > 꿈 해몽 > {keywordName}". 현재 위치는 링크가 아니라 `aria-current="page"` 글자(허브에서는 "꿈 해몽"이 현재 위치이므로 링크가 아니다. 허브로 가는 링크는 상세 화면의 "꿈 해몽" 항목이 맡는다(AC-15)).
2. `TitleWrapperComponent`: h1 + description.
   - 허브: h1 "꿈 해몽", description "꿈에 나온 소재를 찾아 민간에서 전해 온 풀이를 읽어 봅니다."
   - 상세: h1 "{keywordName} 해몽", description "{카테고리 이름} 소재의 민간 풀이와 요즘 생각해 볼 점입니다." (예: "동물 소재의 …", "죽음·사고 소재의 …")
3. `DreamDisclaimerNoticeComponent`(상시 면책, h1 바로 아래): `mx-auto max-w-2xl rounded-lg border border-border bg-card px-4 py-3 text-left text-sm leading-6 text-muted-foreground`. 아이콘 없음. 문구는 plan 승인 문구 그대로. 접기, 툴팁, 스크롤 후 노출 없음. 이유: 타로와 같은 위치·모양이라 사이트 안에서 "고지가 있는 자리"가 같고, 상자로 설명문과 구분해 보이게 한다.

광고: 꿈 화면에 광고 요소를 추가하지 않는다(design.md 6.2). 루트 상단 AdFit 슬롯만 있다.

- 소재 목록 컨테이너: `divide-y divide-border border-y border-border`. 홈 서비스 목록과 같은 관용구다. 이유: 새 모양을 만들지 않고 사이트의 목록 어법을 이어 간다.
- 카테고리 한 행(`<section aria-labelledby>`): `grid gap-3 py-5 md:grid-cols-[10rem_minmax(0,1fr)] md:gap-8 md:py-6`. 왼쪽 칸 h2(카테고리 이름)와 아래 소재 수, 오른쪽 칸 칩 목록(`ul`, `flex flex-wrap gap-2`).
- 소재 칩(`li` > `next/link`, `prefetch={false}`): `inline-flex min-h-11 items-center rounded-md border border-border bg-card px-3 text-base font-medium text-foreground break-keep`. 칩 안 글자는 소재 이름(`name`)이다.
- 색인 순서는 데이터 순서(카테고리 순서, 카테고리 안 순서)를 그대로 따른다. 가나다 정렬을 따로 만들지 않는다. 이유: 설계 3.2가 배열 순서를 허브 순서로 정했고, 검색이 이름을 찾는 수단이다.
- 검색 중에는 소재가 남은 카테고리 행만 보인다. 각 행의 "N개"도 남은 개수로 바뀐다.
- 모바일 길이: 소재 120개를 한 번에 펼치면 세로 약 2,500px다. 접기를 쓰지 않는 이유: 카테고리를 접으면 목록이 숨어 훑어 보기가 어렵고 서버 HTML과 화면이 달라진다. 길이는 색인 장부의 성격으로 받아들인다.
- 하단 안내 영역: 목록 아래에서 `border-t border-border pt-10 space-y-10`으로 풀이 기준, 상세 안내, FAQ를 묶고, 마지막에 상담 안내 상자를 둔다.
- 검색칸은 따라다니지(sticky) 않는다. 이유: 모바일에서 가로 공간이 좁은데 상시 고정 요소가 키보드와 함께 화면을 가리고, 120개 글자 목록은 검색 없이도 훑을 수 있다.

#### 인기·대표 소재 노출 (열린 질문 Q3)

design.md에 인기·대표 소재를 가리키는 데이터가 없다. plan 결정 7(수치·순위 금지)과 AC-26 때문에 "인기", "많이 찾는" 같은 말은 근거 없이 쓸 수 없다. 그래서 1차 디자인은 **노출하지 않는다**. 대신 (1) 동물 카테고리를 목록 맨 앞에 두고(plan 표 순서), (2) 검색칸 placeholder에 예시 소재 두 개를 보여 첫 행동을 안내한다. 대안은 Q3에 있다.

#### 검색 영역 (`DreamHubSearchInputComponent`)

- 라벨 "꿈 소재 검색"(보이는 `<label>`, `htmlFor` 연결). 입력 `type="search"`, 높이 `h-12`, `bg-card`, `px-4`, `text-base md:text-base`, `autoComplete="off"`, `enterKeyHint="search"`, `maxLength={50}`.
- placeholder: "예: 돼지, 이빨 빠지는 꿈" (예시는 plan 예시 소재 이름이다. 샘플 소재의 `name`이 확정되면 맞춰 바꾼다).
- 아래에 개인 내용 주의 안내(`id` 부여, `aria-describedby` 연결): `text-sm leading-6 text-muted-foreground`. 문구: "소재 이름만 입력해 주시기 바랍니다. 꿈 내용이나 개인적인 이야기는 적지 않으시기 바랍니다. 입력한 검색어는 서버로 보내거나 저장하지 않습니다."
- 검색칸 외 입력칸, textarea, 폼 제출 버튼, 검색 버튼을 두지 않는다(AC-20). 별도 지우기 버튼도 두지 않는다(design.md 트리에 없다). 브라우저 기본 지우기 표시(`type="search"`)는 숨기지 않는다.
- 아이콘: 입력칸 안에 아이콘을 두지 않는다. 이유: 라벨이 이미 있고, 아이콘 자리만큼 입력 폭이 줄어든다.

#### 결과 개수 (`DreamHubResultStatusComponent`)

- 검색어가 비었을 때 "전체 소재 {N}개"(N은 데이터 개수를 읽는다. 숫자를 코드에 쓰지 않는다). 검색어가 있을 때 "“{검색어}” 검색 결과 {n}개". 검색어는 앞뒤 공백을 자르고 `break-all`로 긴 값도 넘치지 않게 한다. React 텍스트로만 그린다.
- `p`에 `aria-live="polite"` `aria-atomic="true"`. `text-sm leading-6 text-muted-foreground`. 검색칸 안내와 목록 사이(위기 패널이 있으면 그 아래)에 둔다.
- 결과 0개일 때 문장은 "“{검색어}” 검색 결과 0개". 안내 글은 빈 상태 블록이 맡는다. 이유: 같은 안내를 두 곳에서 읽어 주면 스크린리더가 반복한다.

#### 빈 상태 (`DreamHubEmptyComponent`, 결과 0개일 때만)

```
┌ 빈 상태 (card, 테두리, rounded-panel) ──────────────┐
│ 일치하는 꿈 소재가 없습니다                          │ ← 제목
│ 소재 이름이나 비슷한 말로 다시 검색해 보시기 바랍니다.│
│ 긴 문장이나 꿈 내용 전체를 적는 검색은 지원하지      │
│ 않습니다.                                            │
│ [ 전체 목록 보기 ]                                   │ ← 주요 버튼
└──────────────────────────────────────────────────────┘
```

- `rounded-panel border border-border bg-card p-6`, 왼쪽 정렬(두 문장 이상이라). 제목 `text-lg font-semibold`(`p`), 본문 `text-sm leading-7 sm:text-base`, 버튼 `h-11 rounded-lg bg-menu-dream px-6 font-semibold text-primary-foreground`(모바일 `w-full`, `sm:w-auto`).
- "전체 목록 보기"는 검색어를 비우고 입력칸에 포커스를 돌린다(design.md 4.3, 16). 포커스 이동 뒤 결과 개수는 "전체 소재 {N}개"로 바뀐다.
- 로또·복권·태몽을 검색해도 같은 빈 상태만 보인다. 번호, 관련 링크, 추천 문구를 덧붙이지 않는다.
- 이유: 막다른 길 없이 원인(일치 없음)과 다음 행동(다시 검색 또는 전체 목록)만 한 번에 알린다.

#### 검색어 위기 안내 (`DreamHubCrisisNoticeComponent`)

타로 위기 패널(`docs/tarot/ui-ux-design.md` "위기 안내 패널")과 같은 면·버튼·링크 규칙을 쓰고 아래 점만 다르다.

| 항목 | 타로 | 꿈 해몽 |
|---|---|---|
| 결과 | 패널 뒤에 가려지고 "계속 보기"로 연다 | **결과를 막지 않는다.** 패널은 결과 목록 위에 놓이고 목록은 그대로 보인다. "계속 보기" 버튼이 없다 |
| 위치 | 카드 무대 자리 | 검색 안내 아래, 결과 개수 위 |
| 포커스 | 패널 제목으로 옮긴다 | **옮기지 않는다.** 입력 중이므로 포커스를 뺏지 않는다 |
| 제목 태그 | h2 | `p`(글자 모양만 제목). 이유: 입력하는 동안 나타났다 사라지므로 문서 제목 구조에 넣지 않는다 |
| 알림 | | 패널을 감싼 `div role="status"`는 항상 DOM에 있고 내용만 조건부로 나타난다. 이유: 항상 있는 영역에 내용이 들어와야 스크린리더가 안정적으로 읽는다. `alert`는 쓰지 않는다(입력을 끊지 않는다) |
| 구획선 | "전화" 갈래와 "계속 보기" 갈래를 나눈다 | 전화 묶음과 저장 안내 문장 사이 |

- 모양: `rounded-panel bg-jar p-5 sm:p-6 text-jar-foreground space-y-4`, 아이콘 없음, 위 여백 `mt-4`.
- 내용 순서(화면 순서 = DOM 순서 = 탭 순서)
  1. 제목(`p`, `text-lg font-semibold`): "전해 드릴 안내가 있습니다"
  2. 본문: "마음이 많이 힘드시다면 혼자 견디지 마시고 아래 상담 기관에 이야기해 보시기 바랍니다. 검색 결과는 아래에서 그대로 보실 수 있습니다."
  3. 전화 묶음: 109 주 버튼(`<a>` "109 전화 연결"), 묶음 이름 "다른 상담전화", 링크 둘("정신건강위기상담전화 1577-0199", "한국생명의전화 1588-9191"). 번호는 `CRISIS_PHONES` 중 `showInCrisisPanel === true`인 세 곳을 순서대로 읽고, 각 항목은 공용 `CrisisPhoneComponent`로 그린다(PC는 글자, 터치는 `tel:` 링크). 마크업과 클래스는 타로 위기 패널 절과 같다.
  4. 구획선(`border-t border-jar-muted/40 pt-4`) 아래 저장 안내 `text-sm leading-6 text-jar-muted`: "입력한 검색어는 저장되거나 전송되지 않습니다."
- 문구 확인 사항: 타로 패널의 "세 곳 모두 24시간 운영합니다."는 가져오지 않았다. 꿈 plan의 승인 문구에 없는 주장이기 때문이다. 필요하면 사용자 승인 후 추가한다. 번호와 운영 시간은 출시 전 재확인 항목이다.
- 위기 패널이 나오는 동안에도 검색칸, 결과 개수, 목록은 평소와 같다. 위기 표현이 입력에서 사라지면 패널이 함께 사라진다.
- 이유: 도움이 필요한 순간에는 결과를 막지 않으면서도 화면에서 가장 무게 있는 면(`jar`)으로 눈에 띄게 알린다. 타로와 같은 모양이라 사이트에서 "이 면은 도움 안내"라는 학습이 이어진다.

#### JS 꺼짐 (`DreamHubNoscriptNoticeComponent`)

- 검색 영역 바로 위, `<noscript>` 안 `rounded-lg border border-border bg-card p-4 text-sm leading-6 text-foreground`.
- 문구: "검색에는 JavaScript가 필요합니다. 브라우저 설정에서 JavaScript를 켜 주시기 바랍니다. 아래 카테고리 목록에서 소재를 골라 읽으실 수 있습니다."
- 검색칸은 서버 HTML이라 JS가 꺼져도 보이지만 입력해도 목록은 바뀌지 않는다. 숨기지 않고 안내 문구로 이유를 알린다(숨기려면 JS나 새 CSS가 필요하다).

#### 허브 하단 영역 (서버)

순서: 풀이 기준 → 상세 안내 → FAQ → 상담 안내. 앞의 셋은 상자 없는 글이고, 마지막만 테두리 상자다.

- 풀이 기준(`DreamBasisNoticeComponent`): h2 "풀이 기준"(`text-lg font-semibold`) + 본문 `text-sm leading-7 sm:text-base text-foreground max-w-[68ch]`. 문구는 plan 승인 문구("이 풀이는 민간에서 전해 온 해몽 관념을 바탕으로 …") 그대로.
- 상세 안내(`DreamHubDetailNoticeComponent`): h2 "상세 안내"(`text-lg font-semibold`) + `ul list-disc space-y-1 pl-5 text-sm leading-7 text-foreground`. 항목 여섯(AC-29)은 아래 문구 표를 따른다.
- FAQ(`DreamFaqComponent`): h2 "자주 묻는 질문" + 펼친 목록(아코디언 아님). 질문 h3, 답 `p`. 타로 `TarotFaqComponent`와 같은 모양이다. 이유: 모든 답이 서버 HTML과 화면에 보여야 하고(AC-14), 질문이 둘~다섯 개라 접을 이유가 없다.
- 상담 안내(`DreamCrisisPhonesComponent`): 아래 "상담 안내 상자" 참고.

데스크톱은 같은 한 단 구조이고 폭(`max-w-3xl`)만 넓다. 두 단으로 나누지 않는다. 이유: 풀이 두 블록이 한 소재를 위아래로 읽는 이야기이고, 각각 300자 안팎이라 나란히 두면 줄이 너무 짧아진다.

- 한 줄 요약(`DreamTopicReadingComponent`의 첫 요소): `border-l-4 border-menu-dream pl-4`, 글자 `text-lg sm:text-xl font-medium leading-8 sm:leading-9 text-foreground`. 이유: 첫 줄 안내가 풀이 본문과 다른 층이라는 것을 선 하나로 알린다. 선이 이 화면의 유일한 개성이다.
- 민간 풀이: h2 + `p`(풀이 문장들을 공백으로 이어 한 문단). 종이 위에 상자 없이 둔다.
- 요즘 생각해 볼 점: `section.rounded-panel.border.border-border.bg-card.p-5.sm:p-6`, h2 + `p`. 이유: "옛 풀이"와 "요즘 시선"을 면의 단계로 나눠 다른 목소리임을 보여 주되 새 색이나 아이콘을 쓰지 않는다.
- 완화 블록(`DreamTopicSoothingComponent`, `sensitivity`가 `none`이 아닐 때만): `rounded-panel border border-menu-dream/30 bg-menu-dream/10 p-5 sm:p-6 space-y-3`.
  - h2 "불안하게 느껴지신다면"(`text-xl`).
  - 문단 순서: (죽음 소재만) 죽음 보충 문구 → 소재별 완화 문장(`soothing`) → 반복 꿈 안내. 글자 `text-base leading-8 text-foreground`. 이유: 죽음 소재에서는 "실제 죽음을 뜻하지 않는다"가 가장 먼저 읽혀야 한다(AC-23).
  - 공포를 키우는 아이콘(해골, 경고 삼각형, 느낌표)과 `warning`·`destructive` 색을 쓰지 않는다.
- 띠별 운세 링크(`DreamTopicTtiLinkComponent`, `isTtiAnimal`일 때만): 상자 없이 한 단락. 링크 "띠별 운세 보기"(`text-primary underline underline-offset-4 min-h-11 inline-flex items-center`, 경로 `/fortune/tti`) 아래 `text-sm leading-6 text-muted-foreground`: "운세 화면은 이용 동의 안내가 먼저 나옵니다." 이유: 링크 뒤에 동의 화면이 나온다는 점을 미리 알린다(plan 질문 17).
- 풀이 기준(`DreamBasisNoticeComponent`): 허브와 같은 글. 상세에서는 문단 끝에 링크 "다른 소재 찾기"(`/dream`)를 `text-primary underline`로 덧붙인다(AC-12, plan S-2).
- 관련 소재(`DreamTopicRelatedComponent`): h2 "관련 소재" + 칩 2~4개(허브 칩과 같은 모양). `ul`, 데이터의 `related` 순서. 이유: 같은 모양을 쓰면 "눌러서 다른 소재로 옮겨 간다"는 어법이 허브와 같다.
- FAQ: 허브와 같은 컴포넌트. 질문 2개.
- 하단 짧은 면책(`DreamBottomNoticeComponent`): 상시 면책과 같은 상자(`rounded-lg border border-border bg-card px-4 py-3 text-sm leading-6 text-muted-foreground text-left`). 문구 "꿈 풀이는 참고용입니다. 건강, 수면, 정신건강, 법률, 재정과 관련된 고민은 전문가와 상담하시기 바랍니다." + 둘째 문단 "풀이를 따르는 판단과 선택은 이용자 본인의 몫입니다." 이유: 위의 상시 면책과 짝을 이뤄 풀이를 위아래에서 감싼다(AC-28).
- 상담 안내 상자: 아래 참고.
- 돌아가기(`DreamTopicBackLinkComponent`): `Button asChild variant="outline"`, 높이 `h-11`, 모바일 `w-full`, `sm:w-auto`, 앞에 lucide `ArrowLeft` 16px(`aria-hidden`), 글자 "꿈 해몽으로 돌아가기". 이유: 방향을 글자와 아이콘 앞에서 알리고 문장 끝에 화살표를 붙이지 않는다.

### 상담 안내 상자 (`DreamCrisisPhonesComponent`, 허브·상세 하단, 항상)

타로 `TarotResultNoticeComponent`의 상담전화 묶음(`docs/tarot/ui-ux-design.md` "결과 하단 면책 + 상담전화")과 같은 마크업·클래스를 쓰고 아래만 다르다.

- 바깥 상자: `rounded-panel border border-border bg-background p-4 sm:p-5 space-y-3`. 타로와 달리 면책 문단은 이 상자에 넣지 않는다(상세의 하단 면책이 별도 상자다).
- 제목 h2 "상담 안내"(`text-lg font-semibold`) 다음 첫 문장(plan 승인 문구, `text-sm leading-6 text-foreground`, `id`를 목록의 `aria-labelledby`로 연결): "마음이 많이 힘드시다면 혼자 견디지 마시고 아래 상담 기관에 이야기해 보시기 바랍니다." lucide `Phone` 16px 앞 아이콘은 둔다(`aria-hidden`, `text-muted-foreground`).
- 목록: `CRISIS_PHONES` 다섯 곳을 순서 그대로(109, 1577-0199, 1588-9191, 1388, 1366). 모바일 `flex flex-col gap-1`, sm 이상 `sm:grid sm:grid-cols-2 sm:gap-x-6 sm:gap-y-1`, 109 항목만 `sm:col-span-2`. 항목 안 두 줄(이름·번호 / 설명)이 한 링크이고 높이 `min-h-11`. 번호 링크 `text-primary underline underline-offset-4 group-hover:decoration-2`(109만 `font-semibold`).
- 번호를 꿈 기능 안에 다시 적지 않는다(AC-24).
- 이유: 모든 화면에서 같은 모양이라 어디서든 같은 자리에서 도움을 찾을 수 있다.

### 없는 소재 주소 (`DreamTopicNotFound`, 404)

```
홈 > 꿈 해몽                      ← 이동 경로 없이 간단히(선택 아님: 두지 않는다)

       찾으시는 꿈 소재가 없습니다      ← h1 (menu-dream)
 주소가 바뀌었거나 없는 소재입니다. …
       [ 꿈 소재 찾기 ]  [ 홈으로 ]
```

- `ContentWrapperComponent type="dream"` 안에 `TitleWrapperComponent`(h1 "찾으시는 꿈 소재가 없습니다", description "주소가 바뀌었거나 없는 소재입니다. 꿈 해몽에서 소재를 다시 찾아 보시기 바랍니다.") + 버튼 둘. 이동 경로, 상시 면책, 상담 안내는 두지 않는다. 이유: 풀이가 없는 화면이라 고지 대상이 아니다.
- "꿈 소재 찾기"(주요 버튼, `bg-menu-dream`, `/dream`), "홈으로"(`variant="outline"`, `/`). 버튼은 가운데 정렬, 모바일 세로로 쌓고 `w-full`, sm 이상 가로 나란히.

### 메뉴와 홈 (S-4)

design.md 9장대로 `MENU_LIST`에 그룹을 추가하면 헤더와 홈이 자동으로 읽는다. 코드를 읽어 확인한 노출 방식이다.

- 헤더 PC·모바일 메뉴: 하위 항목이 1개인 그룹은 드롭다운 없이 한 줄 링크로 나온다(`items.length < 2` 분기). 그래서 그룹 링크와 하위 항목 링크가 같은 `/dream`이어도 **같은 링크가 두 번 보이지 않는다.** design.md 9장의 확인 요청에 대한 답이다. 헤더에는 그룹 아이콘(16px, `text-menu-dream`)과 "꿈 해몽"이 보이고 "준비 중" 배지는 없다.
- 홈 서비스 목록: 그룹 이름 "꿈 해몽"과 아래 줄에 하위 항목 이름 "꿈 소재 찾기"가 나온다(홈은 아이콘·색을 쓰지 않는다).
- 아이콘: 그룹과 하위 항목 모두 lucide `BookOpenText`(열린 질문 Q5). 이유: 소재 사전이라는 기능과 맞고, 헤더의 로또(원), 타로(달), 운세(별) 사이에서 모양이 겹치지 않는다. `lucide-react` 0.522에 있는 것을 확인했다.
- 메뉴 항목 값(frontend-dev 전달)
  - 그룹: `group: DREAM('dream')`, `label: '꿈 해몽'`, `href: '/dream'`.
  - 하위: `href: '/dream'`, `label: '꿈 소재 찾기'`, `icon: 'BookOpenText'`, `colorClass: 'text-menu-dream'`, `description: '꿈에 나온 소재를 찾아 민간 풀이와 생각해 볼 점을 읽는 사전.'`, `example: '예: 돼지, 이빨 빠지는 꿈처럼 떠오른 소재로 찾기'`.
  - `src/constants/theme.constant.ts`: `SECTION_ICONS.dream = BookOpenText`, `SECTION_ICON_COLOR.dream = 'text-menu-dream'`, `SECTION_BADGE_COLOR.dream = 'bg-menu-dream/10 text-menu-dream border-menu-dream/20'`, `BACKGROUND_COLORS.dream = 'bg-background'`.
  - `src/constants/menu-icon.constant.ts`: `BookOpenText` import 추가와 `MENU_ICONS` 항목 추가.
  - `src/types/menu.type.ts`: `MenuSectionKeyType`에 `'dream'`(design.md 9장).
  - `src/app/globals.css`: `--menu-dream`(Q1에 따름).

- 검색 결과 목록의 재배치·등장 효과(framer-motion `layout` 등): 목록은 입력에 맞춰 즉시 바뀌어야 따라 읽을 수 있다. 120개 항목에 레이아웃 계산을 걸면 입력이 느려질 위험이 있다. 모션 표의 "목록 재배치"에 해당하지만 무엇이 바뀌었는지는 결과 개수 문장과 목록 자체가 이미 알린다.
- 칩·링크 hover 전환(`transition`): 즉시 바꾼다. 이유: 일괄 hover 효과를 줄이는 원칙.
- 페이지·섹션 등장 효과(fade-up 등): 과하다고 보는 경우에 해당.
- 상담 안내 상자의 등장 효과, 전환: 진지한 안내는 움직임 없이 바로 읽혀야 한다(타로 결정과 같음).
- 스크롤 연동, 별이 반짝이는 장식, 구름이 떠다니는 배경: 꾸밈뿐이며 계속 움직이는 장식.
- CSS 애니메이션을 쓰지 않으므로 `motion-reduce:` 처리 대상도 없다. framer-motion을 쓰는 곳이 없다.

애매한 항목은 열린 질문 Q4에 정리했다(검색 중 위기 안내 패널의 등장 효과).

## 접근성

- 명도 대비 (종이 `#eef0e6`, 카드 `#f7f8f1`, 옅은 면 `menu-dream` 10% 기준 계산값. 구현 전에 한 번 더 재검산한다)
  - `foreground` 약 11.8:1, `muted-foreground` 종이 위 약 5.0:1·카드 위 약 5.4:1, `primary` 종이 위 약 5.6:1.
  - `menu-dream` 종이 위 약 5.6:1, 카드 위 약 6.1:1, 옅은 면(10%) 위 약 4.9:1. 모두 4.5:1 이상. `primary-foreground`(종이색)을 `menu-dream` 위에 얹은 주요 버튼 약 6.1:1.
  - `foreground` on `menu-dream` 10% 면(완화 블록, 칩 hover) 약 10:1.
  - 위기 패널: `jar-foreground` on `jar` 약 10.9:1, `jar-muted` on `jar` 약 5.7:1, `jar` on `jar-foreground`(109 버튼 글자) 약 10.9:1.
  - `bg-muted`, `bg-secondary` 위에 `muted-foreground`를 두지 않는다(약 4.2:1로 미달). 상시 면책 상자 등 보조 글자는 모두 `card`나 종이 위다.
  - 구획선, 테두리, 한 줄 요약의 세로 선은 장식·구조 표시라 대비 기준 대상이 아니다. 같은 정보를 글자가 전한다.
  - 소재 칩은 색이 아니라 테두리와 칩 모양으로 링크임을 알린다.
- 키보드 이동 (탭 순서)
  - 허브: 이동 경로 링크 → 검색칸 → (위기 패널이 있으면 109 → 1577-0199 → 1588-9191) → 소재 칩(데이터 순서) → 하단 상담전화 다섯 개(109 → 1577-0199 → 1588-9191 → 1388 → 1366).
  - 상세: 이동 경로 링크 → (띠 동물이면 띠별 운세 링크) → 풀이 기준의 "다른 소재 찾기" → 관련 소재 칩 → 하단 상담전화 다섯 개 → "꿈 해몽으로 돌아가기".
  - 위기 패널이 나타나도 포커스는 검색칸에 남는다. 이유: 입력 중에 포커스를 뺏으면 계속 입력할 수 없다.
  - "전체 목록 보기"를 누르면 검색어를 비우고 포커스를 검색칸으로 옮긴다.
  - 모든 상호작용 요소에 포커스 표시가 보인다. 기본은 `ring-ring` 2px + offset 2px, `jar` 면 안은 `ring-jar-foreground` + `ring-offset-jar`.
  - 시각 순서와 DOM 순서를 같게 둔다. CSS `order`로 바꾸지 않는다(WCAG 2.4.3).
- 라벨·스크린리더
  - h1은 페이지마다 하나. 허브 h2: 카테고리 이름 7개, 풀이 기준, 상세 안내, 자주 묻는 질문, 상담 안내. 상세 h2: 민간 풀이, 요즘 생각해 볼 점, (완화 블록) 불안하게 느껴지신다면, 풀이 기준, 관련 소재, 자주 묻는 질문, 상담 안내. FAQ 질문은 h3. 위기 패널 제목은 `p`(제목 구조에 넣지 않는다).
  - 검색칸: 보이는 `<label>` 연결, 개인 내용 주의 안내를 `aria-describedby`로 연결. 이유: 칸에 닿았을 때 "소재 이름만 입력" 안내가 함께 읽힌다.
  - 결과 개수: `aria-live="polite"` 하나. 입력할 때마다 바뀌므로 스크린리더는 보통 입력이 멈춘 뒤 읽는다. 디바운스는 두지 않는다(design.md 4.2). 읽기가 지나치게 잦다는 보고가 생기면 PM에게 올린다.
  - 위기 패널: 항상 있는 `div role="status"` 안에 나타난다. `alert`, `alertdialog`, 모달을 쓰지 않는다. 이유: 입력을 끊지 않고 결과로 가는 길도 막지 않는다.
  - 카테고리 행: `<section aria-labelledby>` + h2 id. 소재 수 문장(`p`)은 제목에 넣지 않고 뒤따르는 글로 둔다.
  - 이동 경로: `nav aria-label="이동 경로"` + `ol`, 현재 위치 `aria-current="page"`. 구분 아이콘은 `aria-hidden`.
  - 전화 링크의 접근성 이름은 기관 이름을 포함하고 보이는 글자가 이름 안에 그대로 들어간다(WCAG 2.5.3). 109 주 버튼 `aria-label="자살예방 상담전화 109 전화 연결"`, 다른 링크는 `aria-label` 없이 보이는 글자가 이름. 하단 상담 목록은 링크 안 두 줄 글자가 이름이다. 타로와 같다.
  - 상담 목록은 `<ul aria-labelledby>`로 "목록, 항목 5개"가 읽힌다. 순서는 의미 있는 단계가 아니라 `<ol>`을 쓰지 않는다.
  - 아이콘은 모두 `aria-hidden`.
- 터치·확대: 칩과 버튼과 전화 링크는 높이 44px 이상. 200% 확대에서 칩은 줄바꿈으로 흘러 넘치지 않고, 색인 왼쪽 여백은 `md` 이상에서만 두 칸이라 좁은 화면과 확대 상태에서는 한 열로 접힌다. 글은 고정 높이를 쓰지 않는다. 번호는 `whitespace-nowrap`.
- 동작 줄이기: 모션이 없어 별도 처리가 필요 없다.
- 법적 고지는 접거나 숨기지 않는다. 상시 면책은 h1 바로 아래 서버 HTML에 있고(AC-7, AC-27), 하단 면책은 상세 하단에 항상 있다(AC-28).

## 기존 디자인 시스템 변경 제안

- 승인이 필요한 변경: **메뉴 라벨 색 토큰 이름 변경**(A안) 또는 **새 토큰 추가**(B안). 열린 질문 Q1에서 고른다. 이 문서는 `docs/conventions/design-system.md`를 고치지 않는다. 승인 후 PM이 6장 표 갱신안(Q1)대로 고친다.
- 그 밖의 시스템 변경(폰트, 반경, 새 공용 컴포넌트): 없음. 새 공용 컴포넌트를 만들지 않고 기존 `ContentWrapperComponent`, `TitleWrapperComponent`, `CrisisPhoneComponent`, shadcn `Input`·`Button`·`Label`만 쓴다.
- 확인 필요(변경 제안 아님): `src/constants/menu.constant.ts`의 점심 그룹이 `colorClass: 'text-orange-600'`(Tailwind 기본 팔레트)를 쓰고 있다. 꿈 해몽 작업 범위 밖이라 건드리지 않고 PM에게만 알린다.

## 열린 질문 / 시안 선택 요청

답이 필요한 순서대로 적는다. 권장안을 기본으로 두고 진행해도 되는 항목은 그렇게 표시했다.

### Q1. 메뉴 라벨 색 (필수, 승인 필요)

- A안(권장): 기존 `menu-where`(`#2a6672` 염수)를 `menu-dream`으로 이름만 바꾼다. 장점: 승인 비용 최저, 대비 검증 완료, 팔레트 균형. 단점: 딜 초록과 멀리서 비슷해 보일 수 있다.
- B안: 새 색 "도라지" `#3f4a8c`를 `menu-dream`으로 새로 둔다. 장점: 꿈(밤)과 직접 이어진다, 대비 더 높다. 단점: 새 토큰 승인 필요, 파랑·보라 계열이 `info`·`ball-bonus`·타로와 모여 구분이 줄어든다.
- 자세한 표와 변경 파일은 "색상 > 메뉴 라벨 색 `menu-dream`" 절. 답이 A면 design-system.md 메뉴 라벨 색 표의 "어디 가" 행을 "꿈 해몽 | `menu-dream` | `#2a6672` | 염수"로 바꾸는 것에 함께 승인해 달라.

### Q2. 허브 레이아웃 방향 (시안 2개)

- A안(권장, 이 문서의 명세): 색인 장부형. 카테고리 이름이 왼쪽, 소재 칩이 오른쪽에 이어지고, 모든 카테고리가 한 화면 흐름에 펼쳐진다. 장점: 모든 소재가 서버 HTML과 화면에 보이고 JS 없이도 훑을 수 있으며 홈 목록 어법과 같다. 단점: 모바일에서 약 2,500px로 길다.
- B안: 카테고리 탭형. 일곱 개 탭 중 하나를 골라 한 카테고리만 보인다. 장점: 모바일에서 짧다. 단점: 탭 전환에 JS가 필요해 JS 꺼짐에서 다른 카테고리를 볼 수 없고, 화면 전체 목록(AC-8)과 사용자가 보는 내용이 어긋나며, 검색 결과가 탭을 가로지를 때 설명이 복잡하다.

### Q3. 인기·대표 소재 노출 (선택)

- A안(권장): 1차에는 노출하지 않는다. design.md에 대표 소재 데이터가 없고, "인기"는 근거 없는 순위 주장이 될 수 있다(plan 결정 7, AC-26). 동물 카테고리가 맨 앞이고 placeholder가 예시를 보인다.
- B안: 검색칸 아래에 "대표 소재" 한 줄(칩 6~8개)을 둔다. 라벨은 "인기"가 아니라 "대표 소재"로 쓴다. 필요한 것: architect가 `DREAM_HUB_FEATURED_SLUGS` 같은 고정 목록 상수를 design.md에 추가(소재 데이터 확정 후 사용자가 선택). 장점: 첫 화면에서 한 번에 눌러 볼 수 있다. 단점: 설계 변경 필요, 소재 선정 기준이 임의라는 질문이 생길 수 있고, 검색 중에는 숨겨야 해 규칙이 늘어난다.

### Q4. 모션 (애매한 항목 1개)

검색 중 위기 안내 패널이 나타날 때 등장 효과를 줄지.

- 넣는 안: 150ms 불투명도 페이드(`tw-animate-css`의 `animate-in fade-in-0`, `motion-reduce:animate-none`). 장점: 입력하다가 갑자기 면이 끼어드는 어색함이 줄고 "무엇이 바뀌었는지" 알려 준다(모션 표 "오버레이 열기" 계열). 단점: 입력 중 표현이 들어왔다 나갔다 하면 깜빡임이 되고, 타로가 위기 안내에 등장 효과를 넣지 않은 결정과 달라진다. 스크린리더 사용자에게는 효과가 없다.
- 빼는 안(권장): 효과 없이 즉시 나타난다. 장점: 깜빡임 없이 안정적이고 타로와 같다. 단점: 면이 갑자기 나타나 결과 목록이 아래로 밀리는 느낌이 있다. 패널이 검색칸 아래에 있어 입력칸 위치는 바뀌지 않는다.
- 나머지 모션 후보(목록 재배치 애니메이션, hover 전환)는 애매하지 않아 모두 뺀 것으로 정했다(인터랙션 절).

### Q5. 메뉴 아이콘 (선택)

- A안(권장): `BookOpenText`. 소재 사전이라는 성격과 맞고, 헤더의 원(로또), 달(타로), 별(운세) 사이에서 모양이 겹치지 않는다.
- B안: `CloudMoon`. 꿈의 느낌이 바로 오지만 16px 크기에서 타로의 `Moon`과 윤곽이 비슷해 색(비트 vs 염수)에만 의존해 구분된다.

### Q6. 민감 소재의 완화 블록 위치 (선택)

- A안(권장, 이 문서와 design.md 6.2의 순서): 풀이 두 블록을 먼저 읽고 바로 아래에 완화 블록을 둔다. 장점: 풀이가 끊기지 않는다, 승인된 컴포넌트 구조(`reading`과 `soothing`이 별도)를 바꾸지 않는다. 단점: 불안한 방문자가 완화 문장을 보기까지 풀이를 먼저 읽는다.
- B안: 한 줄 요약 바로 아래, 풀이 위에 완화 블록을 둔다. 장점: 불안한 방문자에게 안심 문장이 먼저 닿는다. 단점: 소재마다 풀이 앞에 경고 같은 면이 붙어 오히려 불안을 키울 수 있고, `reading` 컴포넌트를 둘로 나눠야 하므로 architect의 design.md 수정이 필요하다.
