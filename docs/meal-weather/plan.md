# 뭐 먹지 날씨 반영 기획서

작성일: 2026-11-28. 입력: `docs/research/meal-weather.md`, `docs/meal-weather/status.md` 결정 기록, `docs/meal-location/plan.md`. 확정된 결정은 다시 묻지 않았다. 기술 구현(폴더 구조, API 계약)은 설계 담당 몫이라 쓰지 않았다.

## 목표

오늘의 날씨(눈·비·더움·추움)에 맞는 메뉴가 뽑힐 확률을 조금 높여, 이용자가 "오늘 날씨에 어울리는 메뉴가 나왔다"고 느끼게 한다. 결과는 여전히 오락용 무작위 뽑기이며, 날씨 정보가 없어도 지금과 똑같이 동작한다.

## 범위

- 포함 (1차, 뭐 먹지 `/meal`만):
  - 날씨 지역 선택 (시·도 단위, 위치 권한 없음)
  - 기상청 동네예보 자료로 지역의 오늘 날씨 조회 (서버에서만 호출, 1시간 보관)
  - 날씨 분류 (눈 → 비 → 더움 → 추움 → 보통)
  - 날씨 태그 메뉴의 뽑힐 확률 상향, 날씨 반영 스위치 (기본 켜짐)
  - 날씨 태그 메뉴가 부족한 끼니에 메뉴 보충
  - 결과 화면의 날씨 한 줄, 출처, "실제와 다를 수 있음" 문구
  - 고지·출처 문구 상수, 금지 표현 검사 추가
  - 방침·약관·COMPLIANCE.md·README 갱신 (승인 뒤)
  - 테스트 (단위, E2E, 정적 확인)
- 제외:
  - 위치 권한 요청, Geolocation 호출, 좌표 수집·저장·전송
  - 사용자 동네 입력(`docs/meal-location/plan.md`)을 날씨 지역으로 쓰는 것. 두 입력은 따로 둔다
  - 강수량·습도 등 기온 외 숫자 값 표시 (기온은 temperature-change.md로 최저·최고·현재만 보인다)
  - 특보(폭염·한파) 기준 적용, 특보 문구 사용
  - 계절·절기·복날 연동, 날짜 기반 메뉴 가중치
  - 날씨 지역 기억(저장), 여러 지역 동시 선택, 지역 자동 판별
  - 다른 메뉴(운세, 타로, 로또 등)와의 연결
  - 메뉴 순서 변경 (보충 메뉴는 목록 끝에 추가만 한다)
  - 새 페이지, 새 지도 제공자, 식당 정보, 예약·배달 링크, 지역 광고
  - 분석 이벤트 추가 (날씨 조회 성공·실패, 지역 선택 등 어떤 것도 보내지 않는다)
  - 시·도 목록 변경 (현행 행정구역 기준으로 개발 단계에서 확정, 아래 "확인 필요 사실" 참고)

## 기능 목록

| ID | 기능 | 우선순위 (필수/선택) |
|---|---|---|
| F-1 | 날씨 지역 선택. 시·도 목록에서 고른다. 기본값 없음, 고르지 않으면 날씨 없이 동작 | 필수 |
| F-2 | 날씨 조회. 고른 지역의 오늘 날씨를 기상청 동네예보 자료로 가져온다. 서버에서만 호출하고 1시간 동안 같은 지역 결과를 쓴다. 실패하면 날씨 없이 진행 | 필수 |
| F-3 | 날씨 분류. 눈 → 비 → 더움(28℃ 이상) → 추움(5℃ 이하) → 보통 순서. 임계값은 한 곳에 둔다 | 필수 |
| F-4 | 날씨 반영 뽑기. 날씨에 맞는 메뉴(태그 메뉴)의 뽑힐 확률만 높인다. 날씨 반영 스위치 기본 켜짐. 끄면 기존 뽑기와 같다 | 필수 |
| F-5 | 메뉴 보충. 눈·비·더움·추움 중 태그 메뉴가 5개 미만인 끼니에만 메뉴를 추가한다 (보충 메뉴 수는 Q6) | 필수 |
| F-6 | 결과 날씨 한 줄. 예: "오늘은 비가 와요. ○○ 어때요?" (○○는 뽑힌 메뉴). 보통 날씨는 줄을 보이지 않는다 (Q5) | 필수 |
| F-7 | 출처와 정확도 문구. 기상청 출처, "실제와 다를 수 있음" | 필수 |
| F-8 | 날씨 실패 안내 한 줄 ("날씨 정보를 가져오지 못해 날씨 없이 뽑았어요") | 선택 (Q5) |
| F-9 | 기존 문구 갱신 (COMPLIANCE, 방침, 약관, 메뉴 FAQ·고지·검색 설명문). 승인 뒤 | 필수 |
| F-10 | 메뉴 순서 일관성 점검 (메뉴 목록, 홈, sitemap, 테스트가 같은 순서·개수를 가리키는지) | 필수 |

날씨 태그 기준표(끼니별, 메뉴별로 어떤 날씨에 붙는지)는 기획 산출물로 따로 만든다. 표가 승인되기 전에는 개발하지 않는다 (Q6).

## 유저 스토리

- US-1: 이용자로서 오늘 비가 오는 지역을 골라 룰렛을 돌리면, 비 오는 날 어울리는 메뉴가 뽑힐 가능성이 높아졌다는 한 줄을 보고 싶다. 왜냐하면 날씨에 맞는 메뉴를 가볍게 떠올리고 싶기 때문이다.
- US-2: 이용자로서 날씨 기능을 끄고 지금처럼 무작위로만 뽑고 싶다. 왜냐하면 날씨와 상관없이 즐기고 싶을 때가 있기 때문이다.
- US-3: 이용자로서 날씨 정보가 안 나와도 룰렛이 그대로 돌아갔으면 한다. 왜냐하면 날씨는 덤이고 뽑기가 본 기능이기 때문이다.
- US-4: 이용자로서 날씨 지역을 골랐을 때 어떤 정보가 어디로 가는지 알고 싶다. 왜냐하면 외부 자료를 쓰는 이유를 알아야 안심할 수 있기 때문이다.

## 완료 조건 (AC)

QA가 이 목록으로 테스트를 만든다. 태그는 검증 층이다. `[E2E]`는 브라우저 흐름, `[단위]`는 계산·문구 상수·규칙 함수, `[정적]`은 코드·문서·설정 확인이다. 기상청 응답은 QA가 고정 응답으로 바꿔 테스트한다(방법은 설계 담당 결정). 날씨 한 줄은 대표 문구 한 개(비)로 E2E를 만들고, 나머지 세 문구는 `[단위]`로 확인한다.

- AC-1 [E2E]: 날씨 지역을 고르고 날씨 반영을 켠 채 룰렛을 돌리면, 결과 영역에 "오늘은 비가 와요. 비 오는 날 메뉴가 조금 더 잘 뽑히게 돌렸어요. 결과는 여전히 무작위예요."(최종 문구는 ui-ux-design.md 기준, 메뉴 이름 없음) 줄이 보이고, 그 아래에 기상청 출처와 "실제와 다를 수 있습니다" 문구가 보인다. (데스크톱)
- AC-2 [E2E]: 날씨 지역을 고르지 않았거나 날씨 반영을 끄고 룰렛을 돌리면, 날씨 줄과 출처가 없고, 기상청으로 나가는 요청이 없으며, 결과는 지금과 같이 나온다.
- AC-3 [E2E]: 날씨 지역을 고르고 기상청 응답이 실패한 상태에서 룰렛을 돌리면, 결과가 나오고 날씨 줄은 없다. 오류 화면이나 빈 화면이 나오지 않는다. (Q5에서 안내 한 줄을 택하면 그 줄이 보인다.)
- AC-4 [E2E]: 날씨 지역을 고르고 룰렛을 돌리는 전 과정에서, 이 사이트로 나가는 요청(주소 쿼리와 본문 포함)에 동네 입력 문자열과 뽑힌 메뉴 이름이 없다. 지역 값은 시·도 목록에 있는 값으로만 나간다. 위치 권한 창과 위치 API 호출이 없다. 로컬 저장소와 쿠키에 지역 값이나 날씨 값이 남지 않는다. 쿠키 동의를 거절한 상태에서도 동작한다.
- AC-5 [E2E]: 동네 입력란에 "강남역", 날씨 지역에 "서울"을 고르고 룰렛을 돌리면, 결과에 날씨 줄과 "강남역 ○○" 미리보기가 함께 보이고, 세 지도 링크의 검색어는 "강남역 ○○"이다. 날씨 요청에는 "강남역"이 없다.
- AC-6 [E2E]: 320px 모바일 화면에서 날씨 지역 선택, 날씨 반영 스위치, 날씨 줄, 출처·정확도 문구, 지도 링크가 가로 스크롤 없이 보인다. 키보드 Tab만으로 날씨 지역(시·도) → 동네 이름 → 날씨 스위치 → 안내 접기 트리거 → 룰렛 돌리기 → 지도 링크 순서로 닿을 수 있다. 데스크톱과 모바일 양쪽에서 실행한다.
- AC-T1 [E2E]: ready이면 날씨 한 줄 바로 위에 "최저 N° · 최고 N° · 현재 N°" 줄이 보인다. 눈·비·더움·추움 문장은 그 아래다.
- AC-T2 [E2E]: 값이 null인 항목은 줄에서 빠지고, 셋 다 null이면 기온 줄이 없다.
- AC-T3 [E2E]: 보통 날씨에도 기온 줄이 보이고 그 아래 출처 → 정확도 순서다.
- AC-T4 [정적]: 기온 줄은 스크린리더에 "오늘 최저 4도, 최고 9도, 현재 6도"로 읽힌다.
- AC-7 [단위]: 날씨 분류 규칙을 지킨다. 더움은 28℃에서 더움, 27℃에서 보통이다. 추움은 5℃에서 추움, 6℃에서 보통이다. 눈 조건이 있으면 비·더움·추움보다 우선한다. 비 조건이 있으면 더움·추움보다 우선한다. 기온 값이 없으면 그 조건은 건너뛴다. 임계값은 상수 한 곳에만 있다.
- AC-8 [단위]: 뽑기 규칙을 지킨다. 날씨 반영이 켜져 있으면 태그 메뉴가 기본 확률보다 높게 뽑힌다. 스위치가 꺼져 있으면 기존 균등 뽑기와 결과 분포가 같다. 직전에 뽑힌 메뉴는 후보가 둘 이상일 때 계속 제외한다. 선택한 필터 안에 태그 메뉴가 없으면 균등 뽑기로 한다. 보충은 태그 메뉴가 5개 미만인 끼니·날씨에만 붙고, 보통 날씨에는 붙지 않는다.
- AC-9 [단위]: 지역과 캐시 규칙을 지킨다. 허용 목록 밖의 지역 값은 거부하고 날씨 없이 진행한다. 같은 지역은 1시간 안에 다시 조회하지 않고, 1시간이 지나면 다시 조회한다.
- AC-10 [단위]: 문구 상수(날씨 한 줄 4종, 출처, 정확도 문구, 지역 입력 이름, 스위치 이름, 실패 안내)는 상수 파일에 있고, `unit/meal/meal-copy.test.ts`의 금지 표현 검사를 통과한다. 금지 표현에 "날씨에 딱", "보양", "몸에 좋", "건강", "폭염", "한파", "특보", "반드시"를 추가한다.
- AC-11 [정적]: `DATA_GO_KR_API_KEY`는 서버 코드에서만 읽는다. `NEXT_PUBLIC_` 이름이 없고 클라이언트 코드와 번들에 들어가지 않는다. 로그와 응답에 키나 지역 값을 남기지 않는다. `README.md` 55행의 "런타임 미사용"이 "날씨 조회에 서버 런타임 사용"으로 바뀌었다.
- AC-12 [정적]: 법적·고지 문서가 새 기준으로 바뀌었다. 대상은 `COMPLIANCE.md` 1장(What-to-eat), 9장(환경변수), 11장 Meal 항목, `src/app/privacy/page.tsx` 지도·정보 수집 문단, `src/app/terms/page.tsx` 메뉴 룰렛 장, 메뉴 FAQ·고지·검색 설명문 상수다. 기존 "같은 확률", "추천하지 않습니다", "추천이나 평가가" 문장은 Q1 결정대로 바뀌었다. "위치 정보를 요청하지 않으며" 문장은 남아 있다.
- AC-13 [정적]: 날씨 출처 문구에 공공누리 제1유형의 표시 항목(작성연도, 기관명, 홈페이지 주소, 작성자명)이 있고, 온라인 화면에서 링크가 걸려 있다. 공공데이터 제공처(공공데이터포털) 이름이 함께 있다.
- AC-14 [정적]: 끼니별 메뉴 목록의 기존 순서가 바뀌지 않았다. 보충 메뉴는 각 목록 끝에만 추가되었다. `MEAL_MENU_COUNTS`가 실제 개수와 같다. 메뉴·홈·sitemap·테스트가 같은 순서와 개수를 가리킨다. 날씨 태그 기준표가 승인본으로 있고, 끼니·날씨별 태그 메뉴 수가 기록되어 있다.
- AC-15 [정적]: 시·도 목록은 개발 시점에 확인한 현행 행정구역과 같다. 각 지역의 기상청 격자 좌표를 대조한 기록이 `docs/meal-weather/`에 있다. 이 기록에는 확인 날짜와 출처가 있다.
- AC-16 [정적]: `next.config.ts`의 `Permissions-Policy`는 `geolocation=()` 그대로다. 위치 API 호출 코드가 없다. 날씨 지역 값, 날씨 결과, 날씨 상태는 광고 스크립트 인자나 광고 요청 파라미터로 가지 않는다. 새 브라우저 저장 키가 없다. 분석 이벤트가 추가되지 않았다.

## 예외·빈 상태

- 날씨 지역을 고르지 않으면 날씨 줄이 없고 기존 뽑기와 같다. 기본 지역을 자동으로 고르지 않는다(서울 등 기본값 금지). 날씨를 추측하지 않기 위해서다.
- 날씨 반영 스위치를 끄면 날씨 조회 요청 자체를 하지 않는다.
- 룰렛 대기 시간: 기상청 응답이 늦으면 날씨 없이 바로 뽑는다. 제한 시간은 설계 담당이 정하되, 룰렛 돌리기를 날씨 응답 때문에 막지 않는다.
- 기상청 응답이 빈 값, 기온 없음, 강수 값 없음이면 그 항목은 건너뛰고 나머지 조건으로 분류한다. 아무 조건도 없으면 보통이다.
- 기상청이 허용되지 않은 지역 값이나 오류 코드를 주면 날씨 없이 진행한다.
- 한도 초과나 기상청 장애가 계속되면 날씨 기능만 멈추고 뽑기는 계속된다.
- 날씨를 바꿔 다시 뽑을 때: 같은 1시간 안에는 같은 지역 날씨를 쓴다. 날씨가 바뀌는 것은 1시간이 지난 뒤다.
- 날씨 분류가 바뀌어도 이미 뽑힌 메뉴는 그대로 둔다. 다음 뽑기부터 반영한다.
- 필터(카테고리, 국물)로 태그 메뉴가 0개가 되면 그 뽑기는 균등이다. 필터 조건은 바꾸지 않는다.
- 비와 눈이 함께 있으면 눈으로 분류한다(비/눈 혼합 값 포함, 확정 결정).
- 날씨 한 줄과 동네 미리보기가 함께 나올 때 두 문장이 서로 다른 이름을 쓰지 않는다 (AC-5).
- 보통 날씨: 한 줄을 보이지 않는다(Q5 권장). 뽑기는 기존과 같다.
- 지역 선택 후 날씨 조회 중에 지역을 바꾸면, 늦게 온 이전 지역 응답은 버린다.
- 날씨 정보가 틀릴 수 있다는 문구는 항상 보인다(결과 줄이 보일 때). 기온은 "최저 4° · 최고 9° · 현재 6°" 한 줄로 보이고(temperature-change.md), 강수량 같은 다른 숫자는 보이지 않는다.

## 검색 노출

- 키워드: 변화 없음을 기본으로 한다. 기존 `/meal` 키워드(오늘 뭐 먹지, 점심 뭐 먹지, 점심 메뉴 추천, 저녁 뭐 먹지, 아침 뭐 먹지, 메뉴 룰렛 등)를 그대로 쓴다. 날씨 키워드 후보("비 오는 날 뭐 먹지", "날씨 메뉴 추천")는 검색 수요를 조사하지 않았으므로 추가하지 않는다 (Q7).
- 키워드 추가 금지: "날씨 맛집", "날씨별 식당", "배달 추천"처럼 식당·배달 서비스로 읽히는 문구. 이 기능은 음식점 찾기가 아니다.
- 새 페이지 없음. sitemap, title, canonical, JSON-LD는 바꾸지 않는다. 설명문(`meal-seo.constant.ts`)에서 "무작위" 표현을 Q1 결정에 맞게 바꾸는 것만 허용한다.
- 페이지가 답해야 할 질문: 기존 `/meal` 질문("오늘 뭐 먹지?", "점심·저녁 메뉴를 무작위로 고르려면?")에 그대로 답한다. 날씨 반영은 "날씨에 따라 뽑힐 확률이 조금 달라진다"는 설명으로 FAQ에 한 항목을 더할 수 있다(Q7). 날씨 문장은 클라이언트에서만 그려지므로 검색에 잡히는 설명은 서버 렌더링 FAQ에 둔다.

## 법적·정책 요구사항

- 개인정보 수집:
  - 날씨 지역 값은 시·도 단위 선택값이다. 개인 식별 정보가 아니다(기획 판단). 다만 이 값이 우리 서버로 간다는 점이 기존 방침(화면 입력은 서버로 보내지 않는다)과 다르므로 방침을 고친다.
  - 서버는 지역 값을 조회에만 쓰고 저장하지 않는다. 앱 코드에서 지역 값과 날씨 결과를 로그에 남기지 않는다(플랫폼 접속 로그는 별도 확인, Q9).
  - 기상청 조회에는 이용자 입력이 아니라 지역의 대표 격자 좌표만 보낸다.
  - 날씨 결과는 서버에서 1시간 보관하지만 이용자 식별자와 묶지 않는다.
  - 위치정보: 지역 선택은 단말의 위치나 좌표가 아니다. 위치 권한을 요청하지 않으므로 위치기반서비스 대상이 아니라고 기획 판단한다(권장). 법률 확인 여부는 Q9에서 meal-location Q2와 묶어 정한다.
  - 분석: 지역 선택, 날씨 결과, 지도 링크 클릭을 분석 도구나 알림으로 보내지 않는다.
  - 방침 갱신: `src/app/privacy/page.tsx`에 "지역 선택값이 날씨 조회를 위해 서버로 전송되며 저장하지 않는다"는 문장을 넣고, "서버로 전송하거나 저장하지 않습니다"와 "입력을 받지 않는다"는 문장을 바꾼다. 시행일 변경 여부는 기존 M17 흐름과 맞춘다.
  - 공공데이터 이용: 기상청 자료를 쓰므로 공공데이터포털 이용 정책(제14조 5항, 시스템 지장 시 이용 제한 가능)을 따른다. 호출 수는 1시간 캐시로 줄인다.
- 고지 문구 (초안, 문장은 Q1 결정 뒤 확정):
  1. "내 지역" 두 입력(시·도, 동네 이름) 아래 한 줄: "시·도는 날씨 조회에만 쓰이고, 동네 이름은 서버로 보내거나 저장하지 않습니다. 위치 권한은 요청하지 않습니다. 상세 주소나 전화번호는 적지 마세요."
  2. 날씨 반영 스위치 옆: "날씨 반영을 켜면 날씨에 어울리는 메뉴가 뽑힐 확률이 조금 높아집니다. 결과는 여전히 무작위입니다." (Q1에 따라 "추천" 표현을 쓰지 않는다)
  3. 결과 날씨 줄 아래 출처: "날씨 정보: 기상청 단기예보·초단기실황 ([작성연도]), 기상청, 공공데이터포털 (공공누리 제1유형). 홈페이지: [기상청 홈페이지 주소, 개발 단계 확인]"
  4. 결과 날씨 줄 아래 정확도: "날씨는 실제와 다를 수 있습니다."
  5. 실패 안내 (Q5 채택 시): "날씨 정보를 가져오지 못해 날씨 없이 뽑았어요."
  6. 기존 고지 유지: 오락 목적, 무작위 결과, 제휴 없음, 식당 정보 정확성 보장 없음. 추천·평가 표현은 Q1 결정에 맞게 바꾼다.
  7. 상세 주소, 건물 번호, 전화번호는 적지 말라는 문구는 동네 입력 기능(`docs/meal-location/plan.md`)의 고지를 따른다.
  - 금지 표현 (AC-10에 추가): "날씨에 딱 맞는", "보양", "몸에 좋은", "건강에 좋은", "폭염", "한파", "특보", "반드시", "정확한 날씨". 음식 효능을 단정하는 문장은 쓰지 않는다. 예: "비 오는 날 전 생각"처럼 가벼운 문구만 쓴다(리서치 6장).
  - 날씨 기준을 기상청 특보 기준처럼 보이게 하지 않는다. 날씨 분류는 이 서비스의 기준이다.
- 상업적 이용 주의:
  - 수익은 AdFit 디스플레이 광고만이다. 날씨 지역, 날씨 결과, 날씨 줄로 광고를 고르거나 광고에 넘기지 않는다(AC-16).
  - 날씨 줄 바로 옆이나 안쪽에 광고를 붙이지 않는다(Q8 권장). 광고가 날씨 줄을 가리지 않는다.
  - 지역 광고, 지역 제휴 링크, 식당·배달 링크는 넣지 않는다.
  - 기상청 자료는 공공누리 제1유형으로 상업적 이용이 가능하다(리서치 8장). 조건은 출처 표시다. 출처 문구가 빠지면 출시하지 않는다(AC-13).
  - 공공데이터 개발계정 한도를 넘지 않도록 캐시를 지킨다. 운영 전환 전 활용사례 등록과 운영계정 신청이 필요할 수 있다(Q10).
  - AdFit 정책 원문은 아직 확인하지 않았다. 날씨 영역 주변 광고 규칙은 확인 뒤 정한다(Q8).
  - 날씨 기능은 수익 조건을 바꾸지 않는다. 결과를 광고로 가리거나 날씨를 보려면 광고를 봐야 하는 구조는 만들지 않는다.

## 열린 질문

각 질문에 권장안을 적었다. 확정된 결정과 겹치지 않는 것만 올렸다.

- Q1. 추천 표현 충돌 (먼저 정할 것)
  - 문제: 날씨 한 줄 "○○ 어때요?"와 가중 뽑기는 "추천"으로 읽힐 수 있다. 기존 고지와 약관은 "추천하지 않음", "같은 확률"이라고 쓴다.
  - 권장: 가중 뽑기임을 밝히고 "추천이나 평가가 아니다" 문장을 "날씨에 따라 뽑힐 확률이 조금 달라지는 오락용 무작위 뽑기다"로 바꾼다. 한 줄 문구는 "○○ 어때요?" 대신 "오늘은 비가 와요. 비 오는 날 어울리는 ○○이 뽑힐 수 있어요" 같은 무작위 표현을 쓴다. 문구 안은 PM 검토.
  - 대안: 한 줄 문구를 결정대로 "○○ 어때요?"로 두고, 고지에 "추천이 아니라 오락용 뽑기"를 함께 쓴다. 이 경우 두 문장이 충돌해 권장하지 않는다.
- Q2. 날씨를 보는 시간 범위
  - 문제: "지금 날씨"(실황)인지 "오늘 하루"(최고·최저, 강수 예보)인지 정해야 한다. 한 줄 문구가 "오늘은"이므로 기준이 같아야 한다.
  - 권장: 오늘 하루 기준. 비는 오늘 중 강수 예보가 있는 경우, 더움·추움은 오늘 최고·최저로 본다. 실황은 오늘 자료가 없을 때만 쓴다.
  - 대안: 지금 실황 기준. 문구를 "지금 비가 와요"로 바꾼다.
- Q3. 날씨 지역 선택 화면
  - 문제: 동네 입력란(지도 검색어)과 날씨 지역(시·도)이 같은 화면에 있다. 둘을 합칠지 나눌지 정해야 한다.
  - 권장: 따로 둔다. 날씨 지역은 시·도 선택 한 개, 이름은 "날씨 지역", 기본값 없음. 동네 입력은 지도 검색에만 쓰이고, 날씨 지역은 날씨 조회에만 쓰인다. 두 입력이 서로를 바꾸지 않는다.
  - 대안: 동네 입력에서 시·도를 추측해 쓴다. 추측이라 틀릴 수 있어 권장하지 않는다.
- Q4. 날씨 지역과 스위치 저장 여부
  - 권장: 저장하지 않는다. 새로고침하면 지역은 비고, 스위치는 기본(켜짐)으로 돌아간다. 동네 입력과 같은 원칙이고, 새 브라우저 저장 키를 만들지 않는다.
  - 대안: 지역만 기억한다. 저장 키와 방침 문장이 하나 늘어나고 기존 "저장하지 않음" 원칙과 달라진다.
- Q5. 날씨 줄이 없을 때의 안내와 보통 날씨
  - 권장: (a) 지역을 골랐는데 조회가 실패하면 실패 안내 한 줄을 보인다. (b) 보통 날씨이면 날씨 줄을 보이지 않는다. 날씨 정보가 없거나 끈 경우는 아무 줄도 보이지 않는다.
  - 대안: 실패에도 안내를 보이지 않는다. 이용자가 날씨가 왜 안 나왔는지 알 수 없다.
- Q6. 보충 메뉴와 날씨 태그 기준표
  - 문제: 태그 메뉴가 5개 미만인 날씨·끼니에 메뉴를 얼마나 추가할지, 누가 쓰고 검수할지, 어떤 메뉴에 어떤 날씨를 붙일지가 정해지지 않았다. 리서치 6장은 일반 상식 수준이라 메뉴별 태그 기준이 되지 않는다.
  - 권장: 기획 산출물로 태그 기준표 초안을 만들어 사용자가 승인한다. 보충은 부족분만큼만 추가하고, 기존 메뉴 작성 방식(copy-log 기록)과 PM 검수를 따른다. 보충 메뉴는 목록 끝에 붙인다.
  - 대안: 보충 없이 태그 메뉴가 적은 날씨는 확률 상향을 하지 않는다. 그러면 "날씨 반영"이 거의 안 보일 수 있다.
- Q7. 검색 노출 키워드와 FAQ 추가
  - 권장: 1차에는 키워드를 추가하지 않는다. 기존 `/meal` 키워드를 유지하고, 서버 렌더링 FAQ에 "날씨를 켜면 뽑힐 확률이 달라진다"는 항목 한 개만 추가한다.
  - 대안: "비 오는 날 뭐 먹지" 같은 키워드를 추가한다. 검색 수요 조사가 없어 근거가 없다. 조사 뒤 결정한다.
- Q8. 광고 배치
  - 권장: 날씨 영역 안에 광고를 넣지 않고, 기존 광고 위치를 유지한다. 날씨 줄 바로 옆 광고는 피한다. AdFit 정책 원문 확인 뒤 최종 확정한다.
- Q9. 법률 판단과 로그
  - 문제: 지역 선택값을 서버로 보내는 것을 개인정보 처리로 볼지, 위치정보법 대상이 아니라고 볼지, 기상청 이용 조건을 어떻게 볼지, 호스팅 접속 로그를 어떻게 다룰지.
  - 권장: 기획 판단("개인정보 아님, 위치정보 아님, 저장·로그 기록 안 함")을 기록하고 meal-location Q2와 같이 위험 수용으로 둔다. 방침과 약관 문장은 출시 전에 최종 확인한다.
  - 대안: 법률 자문을 받은 뒤 출시한다. 일정이 늦어진다.
- Q10. 공공데이터 개발·운영 한도
  - 문제: 개발계정 호출 한도(10,000건)가 일 기준인지 월 기준인지 확인되지 않았다. 운영 전환 시 활용사례 등록과 운영계정 신청을 누가 할지도 정해지지 않았다.
  - 권장: 개발 단계에서 한도 기준을 공공데이터포털 화면으로 확인하고, 1시간 캐시로 추정 호출 수를 계산한다. 운영 신청 담당은 PM으로 둔다.

## 확인 필요 사실 (질문이 아니라 개발 단계 확인 항목)

- 시·도 목록: 리서치는 2026-07-01 전남광주 통합 등 보도를 근거로 16곳 가능성을 적었다. 이는 기사 기준이고 원문을 열어 확인하지 않았다. 사용자는 "현행 행정구역 기준"으로 정했으므로 개발 시 공식 자료로 확인해 확정한다.
- 격자 좌표: 리서치 5.3의 시·도 좌표는 대부분 미확인이다. 기상청 격자 자료로 대조하고 기록을 남긴다(AC-15).
- 기상청 발표 시각: 초단기실황과 단기예보의 조회 가능 시각은 공식 확인이 안 됐다. 실패 시 직전 값을 쓸지는 설계 담당이 확인한다.
- 강수 코드: 소나기(PTY 4) 포함 여부가 자료마다 달라 기상청 항목 정의로 확인한다.
- 출처 문구: 공공누리 제1유형의 표시 원문과 기상청 홈페이지 주소를 확인한다.
- 개발계정 한도 기준: Q10.
