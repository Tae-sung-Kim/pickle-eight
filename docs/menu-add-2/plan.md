# 뭐 먹지 메뉴 추가 2차 기획서

## 목표

끼니별 메뉴 수를 한 번 더 늘려 돌림판 결과가 더 다양하게 나오게 한다. 점심 90→120, 저녁 150→180, 아침·브런치 65→80으로 늘린다(사용자 확정).

## 범위

- 포함: 끼니별 메뉴 데이터 추가(이름, id, 카테고리, 국물 값), 개수 상수와 파일 주석 갱신, 개수 검사 단위 테스트 보강, `docs/menu-meals/copy-log.md` 기록.
- 제외: 화면, 계산 로직, DB, API, 카테고리 추가·삭제, 칩 기본 상태 변경, 야식 메뉴 변경, 운세·고지·FAQ·SEO 문구 변경, 메뉴 설명 문구 추가.
- 성격: 문구·상수만 바꾸는 소규모 변경. 설계·UI/UX·dev-lead 단계는 생략하고 사용자에게 알려 승인받는다(CLAUDE.md 소규모 흐름).

## 이름 기준

- 중복: 점심·아침은 끼니 안에서 이름이 유일해야 한다. 저녁은 카테고리와 이름 조합이 유일하면 된다. 점심과 저녁에 같은 이름이 있으면 id와 국물 값이 같아야 한다(기존 규칙). 야식 전용 이름은 `-late` 접미사 id를 쓴다. 이번 추가 후보는 야식 메뉴 이름과 겹치지 않게 골랐다(예: 저녁 분식 수제비, 점심 분식 수제비는 야식 이름과 겹치므로 뺐다).
- 톤: 실제로 많이 쓰는 일반 음식 이름만 쓴다. 맛, 건강, 영양, 효능, 가격, 순위 표현을 쓰지 않는다. 설명 문구는 붙이지 않는다.
- 음주 연상: 아침·브런치 목록에는 `MEAL_ALCOHOL_ASSOCIATED_MENU_NAMES` 17개 이름과 같은 이름을 넣지 않는다. 이름이 정확히 같지 않더라도 안주 이미지가 강한 이름(예: 치킨 계열)은 넣지 않는다. 이 기준에 따라 '치킨 샌드위치'는 '쉬림프 샌드위치'로 바꿨다.
- 금지어: `MEAL_FORBIDDEN_TERMS`를 부분 일치로 검사한다(메뉴 이름 예외 '해장'만 허용). '술' 패턴(`(?<![가-힣])술`)에 걸리는 단어를 쓰지 않는다.
- 지도 검색 적합성: 카카오맵·네이버지도에서 이름을 검색어로 넣었을 때 해당 음식을 파는 가게가 일반적으로 나오는 이름이어야 한다. 상호·브랜드·특정 가게 메뉴명을 쓰지 않는다. 한 단어 또는 짧은 일반명을 우선하고, 괄호나 긴 수식어를 붙이지 않는다. `mapQuery`는 1차에 쓰지 않으므로 이름 자체로 검색한다.

## 유저 스토리

- US-1: 점심 룰렛을 자주 돌리는 사용자로서, 돌릴 때마다 점심 메뉴가 더 다양하게 나왔으면 좋겠다. 왜냐하면 목록이 적어 같은 메뉴가 자주 나온다고 느낄 수 있기 때문이다.
- US-2: 아침·브런치 룰렛을 쓰는 사용자로서, 간편식과 빵류 외에 죽·샌드위치 같은 선택지도 더 있었으면 좋겠다. 왜냐하면 아침 후보가 한쪽으로 치우쳐 보일 수 있기 때문이다.

## 완료 조건 (AC)

- AC-1 [단위]: `MEAL_MENU_COUNTS`(`meal-menu.constant.ts`)가 점심 120, 저녁 180, 아침·브런치 80이고, 각 끼니 메뉴 배열 길이와 같다.
- AC-2 [단위]: 끼니별 카테고리 개수가 "현재·목표 개수" 표의 목표 값과 같고, 카테고리마다 6개 이상이다. 현재 검사는 합계만 보므로 카테고리별 고정값 검사를 추가한다.
- AC-3 [단위]: 끼니 안에서 id가 중복되지 않고, 이름이 중복되지 않는다(저녁은 카테고리와 이름 조합 기준). id는 소문자와 하이픈 형식이다.
- AC-4 [단위]: 새 메뉴 이름에 `MEAL_FORBIDDEN_TERMS` 부분 일치가 없고(메뉴 이름 예외 '해장' 적용, '술' 패턴 포함), 아침·브런치 목록에 `MEAL_ALCOHOL_ASSOCIATED_MENU_NAMES` 17개 이름이 없다.
- AC-5 [단위]: 저녁 야식 목록(57개, `LATE_NIGHT_NAMES`)과 야식 국물 목록이 기존 테스트 그대로 통과한다. 저녁 기본 후보는 야식을 뺀 123개이고, 야식을 켜면 야식 57개만 후보다.
- AC-6 [정적]: 점심과 저녁에 같은 이름이 있으면 id와 국물 값이 같다. 야식 전용 이름만 `-late` id를 쓴다. 저녁 파일 주석의 낡은 문장("야식 전용 22개")이 지워졌다.
- AC-7 [정적]: 개수 주석(`meal-menu-lunch`, `meal-menu-dinner` 헤더, `meal-menu-breakfast` 헤더)과 `meal-menu.constant.ts` 상수가 새 값이다. `docs/menu-meals/copy-log.md`에 "메뉴 추가 2차 (2026-11-26)" 표(작성자 AI 어시스턴트, 검수 대기)가 있고, 현재 개수 표기(점심 120, 저녁 180, 아침·브런치 80)가 최신 값이다. 이전 기록의 개수는 당시 기록으로 남긴다.
- AC-8 [정적]: 고지 문구, 운세, FAQ, SEO, 메뉴 그룹 설명, 카테고리 파일(`meal-category.constant.ts`), 칩 기본 상태, 화면·계산 코드의 diff가 없다.

[E2E]: 없음. 돌림판 화면 흐름과 칩 동작은 바뀌지 않는다. 기존 `e2e/meal.spec.ts`는 메뉴를 상수에서 읽고 개수를 하드코딩하지 않으므로 QA 회귀 1회(데스크톱)에서 통과만 확인한다. 점심 120칸의 칸 라벨 가독성은 화면 확인 대상이며 AC가 아니라 열린 질문 1로 둔다.

- 상업적 이용 주의: 상호명, 브랜드명, 특정 가게 메뉴명을 넣지 않는다. 일반 음식 이름만 쓴다. 상표성 판단은 열린 질문 4번에서 확인한다.

## 열린 질문

1. 점심 120칸 가독성: 점심 90칸은 이미 공개 중이고 120칸은 처음이다. 칸 라벨이 돌림판에서 읽히는지 구현 후 화면으로 확인한다. 읽기 어려우면 목표를 줄이는 것을 사용자가 결정해야 한다. 수치 자체는 확정 값(120)을 그대로 둔다.
2. 저녁 야식 증량 여부: 권장은 야식 0개 추가다. 근거: 야식 57개가 저녁 카테고리 중 가장 커서 "적은 카테고리부터" 규칙상 후순위다. 야식도 늘리려면 기본 후보에서 몇 개를 야식으로 돌릴지 정해야 한다(예: 야식 +6이면 기본 +24).
3. 아침 간편식 적합성: 이번에 추가하는 간편식은 "샐러드 도시락" 1개다. 아침 메뉴로 적절한지 사용자 검토가 필요하다. 빼면 아침은 79개가 된다. 1차 열린 질문 5(간편식 성격)는 아직 답이 없다.
4. 상표성: "로제파스타", "로제떡볶이", "치즈버거", "치킨 샐러드", "쉬림프 샌드위치" 등을 일반 명칭으로 봐도 되는지 확인이 필요하다. 1차 열린 질문 6(로제떡볶이, 크로플, 시저 샐러드)과 같은 판단이다.
5. 후보 확정 절차: AI 작성 목록은 copy-log에 "AI 어시스턴트, 검수 대기"로 적고, 사용자가 검토한 뒤 PM이 검수 완료로 바꾼다. 1차와 같은 절차로 진행해도 되는지 확인이 필요하다.
6. 소규모 흐름 승인: 설계·UI/UX·dev-lead 단계를 생략하고 planner → 승인 → 개발 → 영향 spec QA로 진행해도 되는지 승인이 필요하다(CLAUDE.md 소규모 흐름).
