# API 문서(swagger-docs) 기획서

## 목표

로또 공개 API 3개의 요청·응답 형식을 정리한 OpenAPI 명세를 만들고, `/api-docs`에서 Swagger UI로 보여준다. 앞으로 추가되는 기능의 API도 같은 문서에 쉽게 합칠 수 있는 구조로 만든다.

## 범위

- 포함: 명세를 사람이 직접 작성하고, `/api-docs` 페이지에서 Swagger UI로 표시. 문서 대상 API 3개(아래 표).
- 포함 (확장성): 명세를 기능별 조각 파일(예: lotto 조각)로 나누고, 빌드 또는 요청 시점에 하나의 명세로 합친다. 앞으로 점심 메뉴, 장소 추천 등 새 기능의 API는 조각 파일을 하나 더하는 것으로 같은 Swagger 문서에 들어간다. 단일 거대 JSON 파일 하나로 관리하지 않는다. 설계 상세(합치는 방식, 파일 위치, 검증 도구)는 개발 단계에서 정한다.
- 제외: `/api/lotto/sync`(cron 내부용), `/api/csp-report`, `/api/og-image` 문서화. 자동 생성(zod-to-openapi 등) 사용. API 코드 삭제와 동작 변경.

## 기능 목록

| ID | 기능 | 우선순위 (필수/선택) |
|---|---|---|
| F-1 | 3개 API의 명세 작성 (파라미터, 응답 필드, 오류 코드, 호출 제한) | 필수 |
| F-2 | `/api-docs`에서 Swagger UI로 명세 표시 | 필수 |
| F-3 | 페이지 노출 범위 적용 (dev 전용 또는 운영 노출 시 검색 제외) | 필수 |
| F-4 | 브라우저에서 바로 호출하는 Try it out | 선택 (열린 질문 8) |
| F-5 | 기능별 명세 조각 구조: 조각 파일 추가만으로 문서에 새 기능이 합쳐진다 | 필수 (확장성 요구) |

API 사실 요약 (코드 기준, 명세 작성 시 이 값을 따른다):

| API | 파라미터 | 성공 응답 | 주요 오류 | 호출 제한 (IP당) |
|---|---|---|---|---|
| GET /api/lotto/draws | `latest`(값 있으면 최우선), `drwNo`, `from`+`to` (둘 다 있어야 함, `to - from` 최대 500) | JSON `{ data, meta }` | 400, 404(해당 회차 없음), 429, 500 | 분당 60회 |
| GET /api/lotto/stats/hot-cold | 없음 | JSON `{ ok, data, meta }` | 500 | 코드상 없음 |
| GET /api/lotto/export | `from`+`to` 선택 (둘 다 있을 때만 적용, 없으면 전체 회차), 최대 3000회차 | `text/csv` 첨부 파일 | 400, 404(데이터 없음), 429, 500 | 분당 20회 |

## 유저 스토리

- US-1: 외부 개발자로서 회차 번호나 기간으로 당첨번호를 받는 방법을 명세로 보고 싶다. 왜냐하면 호출 전에 파라미터와 응답 형식을 알아야 하기 때문이다.
- US-2: 외부 개발자로서 CSV 다운로드의 기간 지정 방식과 호출 제한을 알고 싶다. 왜냐하면 대량 호출 전에 제한을 알아야 하기 때문이다.
- US-3: 개발자로서 dev 환경에서 명세와 실제 API가 맞는지 한 화면에서 보고 싶다. 왜냐하면 API를 바꿀 때 문서를 같이 확인해야 하기 때문이다.
- US-4: 개발자로서 점심 메뉴, 장소 추천 같은 새 기능을 만들 때 API 명세를 조각 파일 하나로 추가하고 싶다. 왜냐하면 기존 명세 파일을 건드리지 않고 문서를 늘리고 싶기 때문이다.

## 완료 조건 (AC)

명세 파일 경로는 설계 단계에서 확정한다. 아래 AC는 `/openapi.json` 기준으로 쓰고, 경로가 바뀌면 QA가 확정 경로로 맞춘다.

- AC-1: `/api-docs`에 접속하면 h1 텍스트 "API 문서"가 보이고, Swagger UI 영역(`.swagger-ui`)이 렌더링된다. (desktop, mobile 모두)
- AC-2: 화면에 operation이 정확히 3개 표시되고, 경로는 `/api/lotto/draws`, `/api/lotto/stats/hot-cold`, `/api/lotto/export`이다. `/api/lotto/sync`, `/api/csp-report`, `/api/og-image`는 목록에 없다.
- AC-3: `/openapi.json`에 요청하면 200과 JSON이 오고, `paths` 키가 AC-2의 3개 경로와 정확히 일치한다.
- AC-4: draws 명세에 `latest`, `drwNo`, `from`, `to` 파라미터가 있고, 응답 코드 200, 400, 404, 429, 500이 정의되어 있다.
- AC-5: export 명세의 200 응답 Content-Type이 `text/csv`이고, 첨부 파일(`attachment`)로 명시되어 있다. 실제 `GET /api/lotto/export?from=1&to=2` 응답도 `text/csv`이며 첫 줄이 CSV 헤더다.
- AC-6: hot-cold 명세에 200 응답이 있고, 응답 본문 필드에 `ok`, `data`, `meta`가 있다.
- AC-7: 호출 제한 수치가 실제 동작과 맞는다. 테스트마다 다른 `x-forwarded-for` 값을 써서 새 IP로 시작하고, export는 21번째 요청이 429, draws는 61번째 요청이 429를 반환한다.
- AC-8 (F-4 채택 시): Swagger UI에서 draws `latest=1`을 실행하면 응답 200이고, 화면에 `lastDrawNumber` 값이 보인다.
- AC-9 (dev 전용 채택 시): 운영 환경에서 `/api-docs`는 404를 반환한다. 운영 판정 기준은 설계에서 정하고, QA는 그 기준의 운영 환경에서 확인한다.
- AC-9' (운영 노출 채택 시): `/api-docs` HTML에 `noindex` 메타가 있고, `/sitemap.xml`에 `/api-docs`가 없다. `/robots.txt`에는 차단 규칙이 추가된다(열린 질문 1 참고).
- AC-10: 기존 3개 API의 status, Content-Type, Cache-Control 응답이 변경되지 않는다. (회귀 1회)
- AC-11: 페이지에 고지 문구가 보인다. 문구는 열린 질문 5 확정 후 적는다.
- AC-12: 모바일 폭(375px)에서 페이지 전체에 가로 스크롤이 생기지 않는다.
- AC-13 (확장성, 구조): 명세는 기능별 조각 파일로 나뉘어 있고, 합친 결과의 `paths`에는 조각마다 등록된 경로가 모두 있다. 현재는 lotto 조각 하나이며, 조각 파일 어디에도 AC-2 밖의 경로(sync, csp-report, og-image)가 없다.
- AC-14 (확장성, 추가 절차): 테스트용 더미 조각 파일(예: 가짜 `/api/test-feature/ping`) 하나를 추가하고 합치기를 한 번 실행하면, `/openapi.json`의 `paths`와 `/api-docs` 목록에 그 경로가 나타난다. 이 절차에서 필요한 작업은 조각 파일 추가와 합치기 실행뿐이다. 그 밖에 기존 파일을 고쳐야 하면 AC 실패로 본다. 확인 후 더미 조각은 지운다.
- AC-15 (확장성, 검증): 조각 파일에 필수 항목(경로, 메서드, 응답)이 빠지면 합치기 단계 또는 테스트가 실패한다.

## 예외·빈 상태

- draws: 회차 번호가 0, 음수, 소수면 400. `from`과 `to` 중 하나만 있으면 400. `from > to`이거나 차이가 500을 넘으면 400. `to`가 최신 회차보다 크면 최신 회차까지만 응답하고 `meta.partial`이 true다. 아직 저장되지 않은 `drwNo`는 404 JSON이다.
- hot-cold: 저장된 회차가 없으면 200에 `ok: true`, `data: null`이다. 명세에 이 경우를 적는다.
- export: 최신 회차가 없으면 404("No data"). 지정 범위에 데이터가 없으면 404("No data in range"). 3000회차를 넘으면 400. `from`만 있거나 `to`만 있으면 전체 범위로 동작한다. 문서에 그대로 적는다.
- 오류 형식 불일치: draws와 hot-cold는 JSON, export는 일반 텍스트다. 명세에는 실제 형식을 그대로 적는다(열린 질문 7).
- 429 응답은 `Retry-After: 60` 헤더를 갖는다. 명세에 헤더를 적는다.
- Swagger UI 스크립트 로드에 실패하면 빈 화면 대신 안내 문구와 `/openapi.json` 링크를 보인다.
- 조각 파일 하나가 잘못되면(필수 항목 누락, 경로 중복) 전체 명세 합치기가 실패해야 하며, 일부만 조용히 빠지면 안 된다.
- JavaScript가 꺼진 환경이나 검색 크롤러는 Swagger UI 내용을 읽지 못한다. 검색 노출을 원하면 핵심 설명은 서버 렌더링 텍스트로 넣는다(`docs/conventions/seo.md` 콘텐츠 규칙).

## 검색 노출

- 키워드: 운영 노출을 선택한 경우에만 적용. 후보: "로또 API", "로또 당첨번호 API", "로또 회차 데이터 API", "로또 CSV 다운로드". dev 전용이면 "없음 (검색 노출 안 함)".
- 페이지가 답할 질문: 로또 당첨번호를 API로 받는 방법은 무엇인가? 회차 번호나 기간으로 어떻게 조회하는가? CSV는 어떻게 내려받는가? 호출 제한은 얼마인가?
- 운영 노출을 선택하면 `docs/conventions/seo.md`를 따른다. 메타데이터는 `buildMetadata()` 사용을 설계에서 확인하고, `h1`은 하나만 쓴다. `noindex`를 쓸 때는 메타데이터 방식을 설계에서 정한다.

## 법적·정책 요구사항

- 개인정보 수집: 페이지 자체는 쿠키, 폼, 로그인이 없어 수집하지 않는다. 다만 API는 요청 IP를 분당 호출 제한 계산에 메모리에서 잠깐 쓴다(`src/app/api/lotto/draws/route.ts` 등). 개인정보 처리방침에 이 내용을 적을지는 열린 질문 5에서 정한다.
- 고지 문구 (제안, 최종안은 `COMPLIANCE.md` 형식을 따라 확정): "본 API가 제공하는 데이터는 참고용이며 당첨을 보장하지 않습니다." / "오락 목적으로 제공되는 정보입니다." / 데이터 출처와 갱신 시점 표기 여부는 확인 필요.
- 상업적 이용 주의: API 문서는 외부 호출과 재사용을 부른다. 당첨번호 데이터의 재배포와 상업적 이용 허용 범위를 확인하기 전에는 공개하지 않는다. CSV 대량 다운로드 허용 여부, 이용 약관(`/terms`)에 API 이용 조건을 추가할지도 함께 확인한다. 광고 수익이 있는 사이트이므로 데이터 이용 조건 확인이 먼저다.

## 위험 항목

- 새 라이브러리 추가(swagger-ui-react 등 npm 패키지, 또는 CDN 스크립트): `DEPENDENCY_LICENSES.md`, `THIRD_PARTY_NOTICES.md`, `README.md`를 같이 갱신한다. 라이선스가 맞는지 확인한다.
- CSP 영향: `next.config.ts`의 `buildCsp()`는 `script-src`, `script-src-elem`에 외부 호스트를 허용하지 않는다. CDN으로 스크립트를 읽으면 이 목록에 호스트를 추가해야 하고, 보안 허용 범위가 넓어진다. npm 번들을 쓰면 CSP 변경은 줄지만 번들 크기가 늘어난다. 기획 관점의 승인은 열린 질문 9에서 받는다. `style-src`와 `font-src`에는 `cdn.jsdelivr.net`이 이미 있다.
- CSP report-only: `next.config.ts`는 `report-uri /api/csp-report`를 붙인다. 새 호스트 추가 후 위반 보고가 늘어날 수 있으니 배포 후 확인한다.
- 명세 드리프트: 명세를 손으로 쓰므로 API가 바뀌어도 명세가 안 바뀔 수 있다. 완화책은 AC-3, AC-7이 값을 검증하는 것이다. 그래도 API 변경 시 명세 갱신을 작업 체크리스트에 넣는다.
- 조각 구조 리스크: 기능이 늘수록 조각 간 경로·스키마 이름이 겹칠 수 있다. 공통 스키마(예: 오류 응답) 위치와 이름 규칙을 설계 단계에서 정한다. 이 규칙이 없으면 AC-15가 실패한다.
- 호출 제한 수치: 제한은 메모리 기반이라 서버 인스턴스마다 따로 적용될 수 있다. 명세 수치와 실제 체감 값이 다를 수 있다(열린 질문 6).
- 테스트 간섭: QA가 제한을 테스트하면 같은 IP의 다른 테스트가 429를 받을 수 있다. 완화책은 AC-7처럼 테스트마다 IP 헤더를 분리하는 것이다.
- robots 정책: `src/app/robots.ts`는 `/api/lotto/export`를 이미 차단한다. 문서에 export가 나와도 크롤링 차단은 유지된다. 명세에 export를 넣는 것은 이 정책과 충돌하지 않는다.
- sitemap: `src/app/sitemap.ts`는 메뉴 기반 경로만 넣는다. 운영 노출을 골라도 `/api-docs`는 메뉴에 넣지 않으면 자동으로 빠진다.

## 열린 질문

1. 노출 범위: 운영에서도 보일지, dev 전용일지 정해 주세요. 추천: dev 전용 (운영에서는 404). 이유는 데이터 재배포와 상업적 이용 문제가 해결되기 전에 외부 공개를 피하기 위해서다. 운영 노출을 고르면 추천 안은 noindex 메타, sitemap 제외, robots.txt 차단 추가다. noindex와 robots 차단을 같이 쓰면 크롤러가 noindex를 못 읽으니, 새 페이지라 색인 전이면 차단만으로 충분하다. 설계에서 최종 선택한다.
2. 운영 노출을 고르면 검색 유입을 목표로 하는지 정해 주세요. 목표라면 검색 키워드와 메뉴 링크(`src/constants/menu.constant.ts`) 추가 여부도 정합니다.
3. 대상 독자: 외부 개발자 공개인지, 내부 점검용인지 정해 주세요.
4. 데이터 재배포와 상업적 이용 허용 범위가 `COMPLIANCE.md`에서 확인되는지 확인해 주세요. 확인되지 않으면 공개 범위를 다시 정합니다.
5. 고지 문구 최종안 (참고용, 당첨 보장 없음, 오락 목적, 데이터 출처 표기)과 개인정보 처리방침에 IP 처리 내용을 추가할지 정해 주세요.
6. 호출 제한 표기: 코드 수치(draws 분당 60, export 분당 20, hot-cold 없음)를 그대로 쓸지, "서버 상황에 따라 달라질 수 있음" 문구를 같이 쓸지 정해 주세요. 추천: 수치와 문구를 같이 쓴다.
7. 오류 응답 형식(draws와 hot-cold는 JSON, export는 텍스트)을 이번에는 그대로 문서화하고, API 형식 통일은 별도 작업으로 할지 정해 주세요. 추천: 그대로 문서화한다. API 동작 변경은 이번 범위 밖이다.
